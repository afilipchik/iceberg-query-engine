# Task: Per-column failure isolation + observability

## Description

Two related pieces on top of task 001's cache-state structures.

**Failure isolation**: today, `GpuEngine::mark_unhealthy()` sets a
single process-wide `healthy: AtomicBool` to false, called whenever any
upload fails for any reason — this permanently disables GPU offload for
the REST of the process's lifetime, for every table, every query, from
then on. That's the opposite of graceful degradation: one transient or
column-specific failure (a malformed value, a momentary VRAM pressure
spike, a driver hiccup) shouldn't take down GPU acceleration for
everything else. Replace this with per-column/per-upload failure
handling: a failed upload should fail (fall back to CPU) for that one
query/column, not poison the whole process.

**Observability**: expose the cache state task 001 built (resident
columns, VRAM used vs. budget, eviction count, now also failure/
isolation events) via this codebase's existing diagnostic convention —
so an operator can actually see what the GPU cache is doing, matching
the transparency this program applies elsewhere (`QE_SPILL_DEBUG`'s
per-call tracing, the rollup epic's `QueryMetrics::rollup_answered`
provenance field).

## Acceptance Criteria

- [ ] Read task 001's Outcome section in full — the exact byte-
      accounting/eviction structures it built — before designing
      failure isolation on top of them.
- [ ] `mark_unhealthy()`'s current process-wide, permanent,
      never-reset behavior replaced with per-column failure handling:
      a failed upload for column X does not prevent column Y (same or
      different table) from being uploaded and used successfully in a
      later query.
- [ ] Decide and document: does a failed column get retried on a later
      query, or permanently blacklisted for that specific
      (table-version, column) key only (not the whole process)? Either
      is acceptable — document which and why, matching this program's
      "explicit, documented, not silently assumed" bar.
- [ ] A genuinely failing upload (construct a real failure condition —
      e.g. a value outside `load_column_f64`'s accepted range, or an
      induced VRAM-exhaustion condition) is tested to confirm: that one
      query correctly falls back to CPU with a correct answer, AND a
      subsequent, unrelated GPU-eligible query still successfully uses
      the GPU path (proving the process isn't poisoned).
- [ ] Cache-state observability: resident columns, current VRAM used vs.
      budget, eviction count (this run), failure/fallback count — exposed
      via an env-gated trace (e.g. `QE_GPU_DEBUG`, matching
      `QE_SPILL_DEBUG`'s established convention) at minimum; a
      queryable/programmatic form (a debug API on `GpuEngine`, or
      similar) if practical within this task's budget.
- [ ] No regression to task 001's own eviction/budget correctness or to
      `gpu-acceleration`'s measured wins.
- [ ] Full suite green (all feature combinations including `gpu`);
      `cargo fmt --all -- --check` clean.
