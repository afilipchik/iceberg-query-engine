# Task: VRAM budget + LRU eviction + confirm/fix the mutation leak

## Description

The epic's core piece. `GpuEngine` (`src/physical/gpu.rs`) already
persists uploaded columns across queries in a process-wide,
`(table, column)`-keyed cache — but every underlying structure
(`resident: Mutex<HashSet<(usize,String)>>`, `codes: Mutex<HashMap<...>>`,
the worker thread's `columns`/`code_bufs` HashMaps) is insert-only, with
zero VRAM byte accounting anywhere. `QE_GPU_CACHE_MB` exists only as a
name in prose (the `gpu-acceleration` epic's own design doc, this PRD,
zero occurrences in actual code) — implement it for real.

Separately, and this is the task's other real deliverable: a native
table's `TableProvider::identity()` is `table_id ++ version`
(`native_table.rs:426-437`), and `GpuAggPlan::pid()` keys the cache by a
hash of that identity — so every INSERT/DELETE/UPDATE against a native
table (mutation epic, shipped) produces a NEW identity hash, and the
OLD version's already-uploaded columns become permanently unreachable
dead weight in VRAM with no way to reclaim them short of a process
restart. This task confirms this empirically (measure real VRAM before/
after N mutations against a GPU-queried native table) before treating
it as fact, then fixes it as part of the same eviction mechanism.

Read `.claude/epics/native-tables-tiering/epic.md` in full (Overview,
Architecture Decisions, Technical Approach) before starting — it has the
full research trail for every claim in this task, with exact file:line
references. Do not re-derive what's already found there.

## Acceptance Criteria

- [ ] **Confirm the leak empirically first.** A real, measured
      reproduction: register a native table, run a GPU-eligible query
      against it (populates the cache), mutate the table (INSERT/
      DELETE/UPDATE) N times (each time re-running the same query so
      each new version also gets GPU-uploaded), and measure actual VRAM
      usage (via `nvidia-smi` or `cudarc`'s own device-memory query API
      — your call which, document it) growing roughly linearly with N
      despite the table's own logical size staying roughly constant.
      This is the task's own "instrument, don't just re-read" step —
      do not skip straight to fixing on the theory alone.
- [ ] Real byte-size accounting added for every resident column (actual
      VRAM bytes, not row/group counts) in `GpuEngine`'s worker-thread
      state.
- [ ] `QE_GPU_CACHE_MB` actually implemented (read at startup or first
      use, sensible default — the design doc's own proposed 24576 MB is
      a reasonable starting point but your call, document the actual
      default chosen and why).
- [ ] LRU (or LRU-adjacent, your call — document the exact policy)
      eviction: when a new upload would exceed the budget, evict
      least-recently-used resident columns until there's room, running
      inside the worker thread's existing single-consumer loop (no new
      concurrency surface — the epic's own Architecture Decision).
- [ ] The mutation-driven leak is fixed: a superseded native-table
      version's columns become evictable, and the stress test from the
      first criterion, re-run after the fix, shows VRAM usage staying
      BOUNDED (not growing unboundedly) across many mutations — report
      the real before/after numbers.
- [ ] Correctness preserved across eviction: a query whose needed column
      was evicted transparently re-uploads and produces a cell-exact
      answer, indistinguishable from a column that was never evicted.
      Real test, not just "should work."
- [ ] No regression to `gpu-acceleration`'s own measured Q6-shape win
      (~18-20x over native tables, warm) for the common case (one
      table's columns comfortably fitting inside budget) — measure
      before/after, report the numbers.
- [ ] No regression to the existing distributed-disable gate
      (`ExecutionConfig::gpu_offload` stays `false` by default, `serve`
      never enables it, scatter/gather fragments still force it off) —
      this task must not touch that mechanism, confirm it's untouched.
- [ ] Full suite green (`scripts/claude-safe-build.sh cargo test`, all
      feature combinations including `gpu`); `cargo fmt --all -- --check`
      clean.

## Technical Details

Sole file for the core logic: `src/physical/gpu.rs` — read `GpuEngine`
(struct + all its methods), `GpuAggPlan::pid()`/`request()`, and the
worker thread's job loop in full before designing the fix. Reference
`src/storage/native_table.rs:426-437` for exactly how `identity()`
changes on mutation. This program's existing env-gated diagnostic
convention (`QE_SPILL_DEBUG`, `HJ_TIMING`, `AGG_TIMING`) is the style to
match if you add any tracing as part of this task (though full
observability is task 002's job — this task only needs enough tracing
to validate its own acceptance criteria).
