# Task: Blast-radius characterization of the wrong-answer bug

## Re-scope note (2026-08-24)

Originally scoped as a "sweep for sibling instances of a FIXED bug" —
but task 002 fixes a separate slowness issue, not the wrong-answer bug,
so there is no fix to sweep survivors of. This task is now
CHARACTERIZATION, not verification-of-a-fix: figure out how exposed
this engine actually is to the still-unconfirmed wrong-answer mechanism
task 001 found (~4.8% observed rate against native-table Q12), without
attempting to fix it. The epic's "no guess-fixes" gate still applies —
if this sweep finds a fix is now obvious, STOP and report that as a
finding for a future task rather than implementing it here; that would
violate the same gate task 001's own result was respecting.

Sequenced after 002 (not logically dependent on its result) purely
because 002's slowness fix should make each large spilling-join trial
in this sweep much cheaper in wall-clock time — check whether 002
landed and use it if so; if 002 is still in flight or didn't land,
proceed anyway using task 001's own timing (140-291s/trial) as the
budget baseline, don't block indefinitely.

## Description

Determine the actual scope of exposure to task 001's wrong-answer bug:
is it native-table-specific, or reachable via plain Parquet sources
too? Which other TPC-H queries that spill (beyond Q12) are exposed?
Does key cardinality/skew change the observed rate? This is
intelligence-gathering to inform prioritization and future
investigation — not a fix, and not expected to reduce the ~4.8% rate.

## Acceptance Criteria

- [ ] Identify which TPC-H queries actually engage
      `SpillableHashJoinExec`'s spill path at SF=10 (and SF=100 if
      time allows) — use this program's existing `HJ_TIMING`/
      `PLAN_DEBUG`-style diagnostics to CONFIRM spill engagement, don't
      infer it from wall-clock slowness alone (task 001's repro shows
      slowness happens on every run, correct or not — slow is not a
      reliable proxy for "spilled").
- [ ] For each query confirmed to spill, run enough trials to get a
      real (if imprecise) sense of its own wrong-answer rate — reuse
      task 001's repro methodology (cold + warm, DuckDB oracle,
      explicit trial count reported). Budget trials realistically; a
      handful of trials per query with an honestly-stated low
      confidence is more useful than skipping queries to hit a trial
      count.
- [ ] Repeat the same check against an equivalent plain-Parquet source
      (not just native tables) for at least Q12, to directly test
      task 001's own open hypothesis #2 (is this native-table-specific
      or general to any large spilling INNER join?). This is the
      single most important result this task can produce.
- [ ] Vary join key cardinality/skew if time allows, to see whether the
      rate changes — report what was and wasn't tried either way.
- [ ] M1/M2 distributed gates: confirm whether spilling joins occur in
      distributed query execution too, and if so whether the same
      exposure applies there. If distributed execution doesn't
      currently engage this path at all, say so explicitly rather than
      leaving it unaddressed.
- [ ] Cell-exact against a DuckDB oracle for every wrong result found —
      this sweep's whole purpose is finding silent wrong answers, so
      row-count-only checks are insufficient.
- [ ] Explicit, final written verdict: which sources/queries/conditions
      are confirmed exposed, which are confirmed clean (with trial
      counts — "clean" from 3 trials is a much weaker claim than from
      20), and which remain unknown due to time/budget. Do not round
      "didn't find it in N trials" up to "safe."
- [ ] Full suite green; `cargo fmt --all -- --check` clean. No source
      changes expected unless the sweep surfaces something that must be
      reported as code — if so, report it, don't silently fix it (per
      the gate).
