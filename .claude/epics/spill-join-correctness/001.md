# Task: Reliable reproduction + instrumented root-cause investigation

## Description

The entry point and hardest part of this epic. TPC-H Q12's spilling
INNER join, against a native table that went through a full `CREATE→
INSERT→DELETE→UPDATE` sequence at SF=10, was found to return an answer
exactly 2x too high (`high_line_count` 707644 vs DuckDB's 353822) and
take ~320 seconds. The orchestrating session independently re-verified
afterward: the extreme slowness reproduced identically on a fresh table
AND on the same table after one plain `DELETE` (both ~150s), but the
wrong answer did NOT reproduce in either of those two simpler attempts —
only the full original mutation sequence triggered it. A prior
investigation (native-tables-mutation task 006) already read
`execute_spill_path`/`build_with_partitioning`/`probe_with_spilling`/
`process_spilled_partition` end to end looking for a duplicate-counting
mechanism and did NOT find one by inspection — the partition/spill
bookkeeping "reads as mutually-exclusive-by-construction." This task's
job is to catch the bug in the act with real instrumentation, not read
the same code a third time hoping to spot it.

## Acceptance Criteria

- [ ] **Read first**: CLAUDE.md's "Mutation: QA close-out" section in
      full (search for "2x-inflated" — it has both the original finding
      AND the orchestrating session's re-verification notes) and
      `.claude/epics/archived/native-tables-mutation/006.md`'s Outcome
      section, for the exact original reproduction steps, numbers, and
      what's already been read/ruled out.
- [ ] **Reliable repro, established methodically**: reproduce the EXACT
      original sequence first (`CREATE TABLE ... AS SELECT` at SF=10 for
      orders+lineitem, then INSERT/DELETE/UPDATE matching the numbers in
      CLAUDE.md's mutation cell-exact section — 12M→15M→14,507,798→
      2,071,620 recomputed — or as close as practical), confirm the wrong
      answer reproduces. THEN, methodically vary ONE thing at a time
      (skip INSERT, skip UPDATE, smaller SF, different delete predicate,
      etc.) to isolate which step(s) are actually necessary — this
      directly answers whether it's data-shape-dependent,
      mutation-history-dependent, or something else (e.g. non-
      deterministic partition-count selection, in which case running the
      SAME sequence multiple times should sometimes reproduce and
      sometimes not — test this explicitly, don't assume determinism
      either way).
- [ ] **Find the smallest/fastest reliable repro you can**, without
      substituting a DIFFERENT bug for the real one — verify a smaller
      repro hits the SAME mechanism (e.g. same clean-ratio signature, same
      code path taken) before relying on it for iteration speed. A
      150-320s reproduction loop makes this investigation extremely slow
      otherwise.
- [ ] **Instrument, don't just re-read**: add real runtime tracking
      (counters, tracing, a debugger — your call on the tool, but it must
      directly OBSERVE behavior, not infer it) to
      `build_with_partitioning`/`probe_with_spilling`/
      `process_spilled_partition` sufficient to answer: is any partition,
      run, or batch processed/emitted more than once? Is any row visited
      by more than one code path that both contribute to the output? Get
      a direct, evidenced answer — "this partition's row count is N but Y
      rows were emitted for it, here's the trace showing why" — not a
      plausible-sounding theory.
- [ ] **Test the slowness/duplication shared-cause hypothesis directly**:
      does your instrumentation show double-processing that would
      mechanically explain BOTH the 2x count and a large fraction of the
      excess runtime? State a real verdict either way.
- [ ] **Confidence gate**: only report a "root cause found" if you have
      direct runtime evidence pinpointing the exact mechanism, not a
      plausible hypothesis. If you reach the end of a serious, genuine
      effort without that confidence, that is a complete, valid, honestly-
      reported outcome for this task — report exactly what you tried,
      what you ruled out, and your best remaining hypotheses for whoever
      continues.
- [ ] Do NOT attempt a fix in this task, even if you think you see one —
      that's task 002's job, gated on this task's confirmed root cause.
      A fix attempted here without the discipline of a dedicated,
      focused validation pass is exactly the "guess-fix on a silent-
      wrong-answer bug" this epic's PRD explicitly rules out.
- [ ] Any instrumentation left in the codebase (vs. a throwaway
      `.scratch/` version) must be clean, gated (env var or `#[cfg(test)]`,
      not always-on overhead), and `cargo fmt --all -- --check` clean.
