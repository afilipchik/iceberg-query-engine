# Task: High-cardinality int-key aggregation (Q18 subquery) + SF=100 gates

## Description

RE-SCOPED after attribution: Q18's dominant residue is its IN-subquery
aggregate — `GROUP BY l_orderkey` over 604M rows → 150M groups —
**4.0s engine vs 2.0s DuckDB**. The key is a single int with range
~600M: outside the disjoint-mode gate (2M..64M) and too sparse/wide for
the perfect-hash array, so it lands in the hash-map slow path (morsel
path, since it aggregates straight over parquet).

Investigate and fix the 150M-group regime: radix/range partitioning by
key so each worker owns a disjoint dense-ish range (the existing
disjoint finalize machinery then applies), or widen the disjoint gate
with a partitioned direct-address scheme. Then run the full SF=100
measurement gates for tasks 002+004+this against the 001 baseline.

## Technical Details

- Q18's subquery agg runs through MorselAggregateExec (parquet-direct);
  the disjoint-channel machinery lives in the fused streaming path
  (spillable.rs) — check which path actually serves it and where the 4.0s
  goes first (AGG_TIMING coverage for the morsel path may need adding).
- `partition_batch_by_hash` + `finalize_disjoint_states` exist and are
  correctness-pinned by `disjoint_aggregation_matches_plain_aggregation_
  exactly`. Reuse rather than re-implement.
- The disjoint gate's range test (2M..64M) uses footer min/max; 600M
  needs EITHER per-worker sub-ranges (range partitioning: worker i owns
  [min + i*W/N, ...)) which keeps direct addressing dense per worker, OR
  hash partitioning with per-worker hash maps.
