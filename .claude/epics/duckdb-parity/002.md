# Task: 2a core — fused probe→aggregate (JoinAggregate fusion)

## Description

When a HashJoin's ONLY consumer is an aggregation and the aggregate's
column footprint (group-by + agg inputs) is small, the probe path feeds
(group-key columns, agg-input columns) directly into aggregation state
per probe batch instead of constructing full joined RecordBatches.
PARITY-PLAN 2a; round 35 proved this must fuse INTO the probe (the
output-repartitioning variant is a net loss).

## Acceptance Criteria

- [ ] Planner detects `Aggregate(Join)` shapes and fuses when group_by + agg args reference ≤4 columns total (tunable)
- [ ] Probe path gathers ONLY the build-side columns the aggregate uses; no full joined-schema batch is built
- [ ] Falls back to today's path for outer joins the fusion can't handle, spill-triggering builds, and any unsupported expression
- [ ] Unit tests: fused vs unfused answers identical on join+group-by shapes incl. NULL keys, duplicate build matches, empty probe partitions
- [ ] SF=10: 22/22 cell-exact; full suite green both modes
- [ ] Memory safety: fused path respects the same memory budget as SpillableHashAggregateExec (fall back or spill, never OOM)

## Technical Details

- `src/physical/planner.rs`: fusion detection (mirror how Sort+Limit
  top-k fusion is detected).
- `src/physical/operators/hash_join.rs`: probe loop gains a fused sink.
- Reuse `AggregationState` (morsel_agg.rs) — it already takes batches;
  the fused sink builds a minimal batch of only needed columns.
- Diagnostics: extend HJ_TIMING/AGG_TIMING to show fusion firing.
- Beware: Semi/Anti output_partitions=1 quirks; swapped builds; the
  disjoint-mode hint must still work when the aggregate is fused.
