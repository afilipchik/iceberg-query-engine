# Task: Dense-direct-address fast-path compatibility

## Description

`src/physical/operators/morsel_agg.rs::try_execute_dense_direct` — the
engine's fastest aggregation path (the one that gets Q18-class queries to
their documented ~187ms/15M-groups floor) — currently reads key-range
bounds from parquet file footers specifically (opens a
`SerializedFileReader` per file to get them). A native table has no
parquet footer once standalone. Without this task, native tables would
silently never take this fast path even when their data shape qualifies
— a real performance regression relative to querying the same data as
parquet, not just a missed opportunity, and directly counter to this
epic's G4 success criterion.

## Acceptance Criteria

- [ ] `try_execute_dense_direct`'s footer-stats dependency is generalized
      to accept zone-map/statistics data from ANY source that can supply
      it in the right shape — parquet footers (existing, unchanged) and
      task 002's native-table manifest statistics (new) both feed the
      same decision logic.
- [ ] Verify with a real measurement, not assumption: load a Q18-shaped
      dataset (single int/date group key, large group count) into a
      native table via task 003's write path, run the aggregate query,
      and confirm via `QE_AGG_PATH`/`AGG_TIMING` (or whatever diagnostic
      this engine exposes — check current names, may have changed since
      the `duckdb-parity-2` epic) that it takes the dense-direct-address
      path, not a fallback tier.
- [ ] No regression to the existing parquet-sourced fast path — its own
      existing tests and benchmarks stay green/unchanged.
- [ ] If task 002's statistics don't cover everything
      `try_execute_dense_direct` needs (e.g. it needs more than min/max —
      check the actual gate logic in `planner.rs`'s `disjoint_group_hint`

      either extend task 002's manifest format (coordinate the change
      back into that task's file/tests if it's already closed) or
      document precisely what's missing and why it's out of scope.
- [ ] `cargo fmt --all -- --check` clean; every build through
      `scripts/claude-safe-build.sh`.

## Technical Details

- **Confirmed by task 001 (both functions read in full):**
  `disjoint_group_hint` (`src/physical/planner.rs`, currently lines
  384-412) is ALREADY provider-agnostic — it reads bounds via
  `provider.statistics()?.column_stats.get(&name)?.{min_i64,max_i64}`,
  the same generic `TableProvider::statistics()` API every provider
  (including Lance, which has no parquet footer either) already
  implements. It needs ZERO changes once task 002's manifest populates
  `TableStatistics` correctly (task 004's job) — this task's entire real
  scope is inside `try_execute_dense_direct`.
- `try_execute_dense_direct` (`src/physical/operators/morsel_agg.rs`,
  currently lines ~392-493) is the ONLY piece with the footer dependency.
  It holds `files: Vec<PathBuf>` (populated by `try_extract_parquet_
  source` and passed into `MorselAggregateExec::new(...)` at
  `src/physical/planner.rs` around line 1084) and, for the key bounds
  specifically (lines ~451-485), opens each file directly via
  `parquet::file::reader::SerializedFileReader` and reads
  `parquet::file::statistics::Statistics::Int64/Int32` per row group.
  **The fix**: thread the already-resolved `TableProvider` (or its
  pre-fetched `TableStatistics`) into `MorselAggregateExec` alongside or
  instead of `files`, and replace that block with the SAME
  `column_stats[key_name].{min_i64,max_i64}` lookup
  `disjoint_group_hint` already uses — bringing this function in line
  with a pattern that already exists in this codebase rather than
  inventing a new statistics-consumption shape. Needs the TABLE-LEVEL
  rollup (one min/max pair for the whole table), not per-segment stats —
  task 002's manifest provides both (see `002.md`), but this task only
  consumes the rollup.
- `src/physical/planner.rs` — `disjoint_group_hint` (see above, no
  changes needed) and `lower_aggregate_cpu`/`try_extract_parquet_source`
  (the call site that constructs `MorselAggregateExec` and will need to
  also supply a native-table provider's stats) — recently modified by
  the `duckdb-parity-2` epic; read that epic's archived task 002 for
  additional context on recent changes in this area.
