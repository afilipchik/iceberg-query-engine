# Task: Memory safety — cap or spill integration

## Description

CLAUDE.md's memory-safety rule is unconditional: "THE ENGINE MUST BE
MEMORY-SAFE BY DEFAULT. OOM IS NEVER ACCEPTABLE... Never add a parameter
that lets users opt out of memory safety." Native tables, once loadable
and queryable (tasks 003/004), need a real answer to "what stops someone
from loading an unbounded dataset into RAM and OOMing the process" before
this epic ships — `MemoryTable`'s existing lack of spill-awareness is a
named gap in this codebase this feature must not inherit uncritically.
Since the sidecar's read path is mmap-based (OS-evictable, safe by
construction against RAM pressure the way anonymous memory isn't), the
real question is bounded to: load-time admission control, and whether
mmap alone is sufficient or genuine `MemoryConsumer`-style spill
integration is needed for the write/build path specifically.

## Acceptance Criteria

- [ ] A concrete decision, evidenced not assumed: is mmap's OS-level
      evictability sufficient for READS (plausible, since it's the same
      mechanism the existing IPC sidecar already relies on safely), and is
      the WRITE path (task 003, which streams batches while computing
      statistics) the actual place unbounded memory growth could happen?
      Trace task 003's actual implementation for any place it could
      buffer more than one batch's worth of data at a time before
      concluding either way.
- [ ] Whichever mechanism is chosen (hard size cap enforced at load time,
      or real spill/budget integration) is implemented and tested: a
      deliberately oversized load either fails cleanly with a clear error
      (cap approach) or completes correctly within bounded memory (spill
      approach) — pick one, don't ship neither.
- [ ] Test with `scripts/claude-safe-build.sh`'s own memory-capped
      execution model as the validation environment (this repo's own
      pattern for safely testing memory-pressure scenarios without
      risking the terminal/session).
- [ ] No new opt-out flag added — memory safety is the only mode, per
      CLAUDE.md's explicit rule.
- [ ] Full suite stays green; `cargo fmt --all -- --check` clean; every
      build through `scripts/claude-safe-build.sh`.

## Technical Details

- `src/physical/operators/spillable.rs` — the existing
  `SpillableHashJoinExec`/`SpillableHashAggregateExec` budget/spill
  machinery, the closest existing precedent if genuine spill integration
  is the right call.
- `.claude/plans/larger-than-memory-support.md` — records several
  spillable operators as `PARTIAL ⚠️ / HAS BUGS / disabled by default`;
  read this before assuming the existing spill machinery is a fully solid
  foundation to build on without its own caveats.
