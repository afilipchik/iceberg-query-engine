# Task: Attribution spike — SQL DDL lift size + statistics/manifest format decision

## Description

This epic's Architecture Decisions are explicit that two things must be
decided by measurement/investigation, not assumption, before any other
task starts: (1) whether `CREATE TABLE ... AS SELECT` SQL DDL is a small
enough lift to build now, or whether a CLI-only bulk-load surface
(mirroring `write-lance`/`load-lance` in `src/main.rs`) should ship first
as the safe minimum with SQL DDL as a fast-follow; (2) the exact shape of
the table-owned manifest (schema + segment layout + per-segment min/max
statistics) that every downstream task depends on. This mirrors every
completed epic in this program's "microbenchmark or attribution spike
first" discipline — the whole epic's shape depends on this task's answers.

## Acceptance Criteria

- [ ] **SQL DDL sizing**: read `src/planner/binder.rs` in full to confirm
      the current statement-handling surface (`Statement::Query` only —
      already confirmed once this session, re-verify since code may have
      moved) and estimate concretely what `CREATE TABLE <name> AS <query>`
      parsing+binding+execution would take: does `sqlparser` (already a
      dependency) parse `Statement::CreateTable`/`Statement::Insert`
      already (it's a general SQL parser, likely yes — confirm), so the
      remaining work is binder+planner+executor wiring, not grammar. Give
      a concrete S/M/L/XL estimate with evidence (not a guess), and a
      clear recommendation: build DDL now, or ship CLI-only first.
- [ ] **Manifest/statistics format decision**: read `src/storage/
      iceberg.rs`'s metadata/manifest/snapshot structures (the epic's
      named precedent) and `src/storage/ipc_cache.rs`'s existing
      staleness-check/identity fields, then design the concrete manifest
      schema this feature needs: table schema, segment/row-group
      boundaries, per-segment min/max per sortable/filterable column
      (the zone-map data task 005 needs), a version/snapshot marker. Decide
      format (JSON sidecar file? A small Arrow IPC/Parquet manifest table?
      Reuse Iceberg's own Avro manifest format directly?) with a stated
      reason, not just a preference.
- [ ] **Module layout decision**: new module (e.g. `src/storage/
      native_table.rs`) vs. evolving `ipc_cache.rs` in place — state which,
      since this determines whether tasks 003/004 can genuinely run in
      parallel without touching the same file (per the epic's own
      preview note: "conflicts with 003 only if they touch the same new
      module — decide file layout in 001/002 to keep them separable").
- [ ] Write findings as a short design note appended to this task's
      outcome section AND propagate the decisions into tasks 002-008's own
      files (edit their Technical Details sections if a decision changes
      what they said) so nobody re-derives this.
- [ ] No source code changes required for this task unless a tiny
      throwaway spike (e.g. confirming `sqlparser` parses `CREATE TABLE`)
      is the fastest way to get evidence — if so, keep it in `.scratch/`,
      don't leave it in `src/`.
