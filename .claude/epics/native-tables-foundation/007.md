# Task: GPU-offload identity/eligibility generalization

## Description

`GpuAggPlan::pid()` (`src/physical/gpu.rs`) hashes `provider.
parquet_files()` as the cache-identity key for the GPU aggregate offload
mechanism, and `plan_gpu_agg` refuses to offload any provider where that
returns `None` — meaning GPU offload is structurally impossible for
native tables today, by construction, not by measurement. This task does
NOT build GPU-tier residency (that's phase 3, a separate future epic) —
it only generalizes the identity/eligibility hook so that work isn't
blocked from the start, and so this epic's own QA close-out (task 008)
can honestly report whether GPU offload engages for native tables at all.

## Acceptance Criteria

- [ ] `GpuAggPlan::pid()`'s identity mechanism generalized to accept any
      provider with a stable, hashable identity — not just
      `parquet_files()`. A native table's own manifest version/snapshot
      marker (from task 002) is a natural fit: stable across repeated
      queries against the same loaded data, changes when the table is
      reloaded, which is exactly the cache-invalidation behavior this
      mechanism needs.
- [ ] `plan_gpu_agg`'s eligibility check updated to accept native table
      providers under the same narrow conditions it already accepts
      parquet providers (numeric columns, simple conjunctive predicates,
      the existing `MAX_BINS=96` cap, etc.) — do not widen the mechanism's
      actual scope, only which provider types can reach it.
- [ ] Verify with a real `--features gpu` build and a real query: a
      simple aggregate (e.g. `SELECT SUM(x) FROM native_table WHERE y >
      const`) against a native table engages GPU offload the same way an
      equivalent parquet query does — confirm via the existing VRAM/log
      evidence pattern this session's `duckdb-parity-2/007` task used
      (nvidia-smi VRAM growth, or whatever diagnostic exists).
- [ ] No change to GPU offload's behavior for existing parquet providers
      — this must be purely additive to the eligibility surface.
- [ ] Distributed/`serve` contexts still refuse GPU offload for native
      tables too, for the same byte-exactness reasons the existing GPU
      cache is already disabled there — don't accidentally widen this.
- [ ] Full suite (including `--features gpu`) stays green; `cargo fmt
      --all -- --check` clean; every build through
      `scripts/claude-safe-build.sh`.

## Technical Details

- **Confirmed by task 001 (read in full)**: `GpuAggPlan::pid()`
  (`src/physical/gpu.rs`, currently lines 145-154) hashes exactly
  `provider.parquet_files()` and nothing else; `plan_gpu_agg` (currently
  line 209) gates on `provider.parquet_files()?;` as a hard early
  return. Both match this task's description precisely — no surprises
  found. The new stable identity source to accept alongside
  `parquet_files()`: task 002's manifest `table_id` + `snapshot.version`
  fields (`src/storage/native_manifest.rs`) — stable across repeated
  queries against the same loaded table, changes on every full-table
  replace (task 003's write path, `src/storage/native_write.rs`, bumps
  `snapshot.version`), exactly the cache-invalidation behavior `pid()`
  needs. Suggested shape: add a `fn identity(&self) -> Option<Vec<u8>>`
  -style method to `TableProvider` (default `None`, the parquet impl
  returns a hash of its file list, the native-table impl returns
  `table_id`+`version` bytes) rather than widening `pid()` to
  special-case two unrelated provider types by name — this follows the
  trait's existing default-method convention (`scan_knn`,
  `distributed_splits` both default to `None`/absent already).
- `src/physical/gpu.rs` — `GpuAggPlan::pid()` (identity/cache-key logic),
  `plan_gpu_agg` (eligibility gate).
- Precedent for the honest "engages but no measurable win at this scale"
  finding from `duckdb-parity-2/007` — don't assume this task alone makes
  native tables meaningfully faster under GPU offload; that mechanism's
  own limits (scan/decode dominance at SF=10) apply here too. This task's
  job is making the PATH available and correctly gated, not proving a
  speedup.
