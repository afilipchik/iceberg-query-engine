# Task: Q13 — disjoint-aggregation threshold investigation + fix

## Description

Q13 (`customer LEFT OUTER JOIN orders ... GROUP BY c_custkey`, then a
second `GROUP BY c_count`) splits its cost almost exactly down the middle:
44.7% join-side, 55.3% aggregation-side (measured this session,
`HJ_TIMING`/`AGG_TIMING`, 3-iteration average, unmodified binary — see
task 003 for the join-side fix). This task is the aggregation-side half,
which is the *larger* of the two.

The inner `GROUP BY c_custkey`'s cost is dominated by a **shared-channel
merge** (223.0ms of Q13's ~411.5ms total, confirmed via `[raw-merge]`
profiling output) because `disjoint_group_hint`
(`src/physical/planner.rs:362-390`) requires a single-int-column group
key's footer-stat range to fall in `2_000_000..=64_000_000`
(`planner.rs:384`). Direct measurement this session: `SELECT
MIN/MAX(c_custkey) FROM customer` at SF=10 → **range = 1,500,000**, just
under the floor.

The mechanism's own doc comment (`planner.rs:354-361`) names *this exact
query* as its motivating case: "Q13's c_custkey, NDV=range=15M: merge 4.3s
shared vs 0.1ms disjoint at SF=100" — a ~43,000x improvement on that
phase, at SF=100 scale. The floor exists because the code uses a
RANGE-only proxy for "dense direct-address domain" (NDV estimation was
tried and found circular — see the comment) — it is not obviously a
statement about a *minimum problem size* below which disjoint mode stops
paying off, but it might be; that distinction is exactly what this task
must establish before touching the constant.

## Acceptance Criteria

- [ ] Determine, with a small measurement (not guesswork), whether
      lowering the floor (e.g. to 1,000,000 or making it a fraction of
      row/thread count rather than an absolute constant) genuinely wins
      at SF=10's problem size, or whether the 32-way scatter overhead
      isn't amortized well enough at 1.5M groups to pay off the way it
      does at 15M. A synthetic microbenchmark (same idiom as
      `examples/radix_bench.rs`) isolating just this merge step at a few
      range/row-count combinations bracketing 1.5M is the right tool —
      don't guess from the SF=100 number alone.
- [ ] If the measurement supports it: extend `disjoint_group_hint`'s
      range floor (or replace the absolute floor with a criterion that
      generalizes correctly across scales) and re-measure Q13 end-to-end.
- [ ] If the measurement does NOT support it: document the negative
      result with the evidence (matching this project's own "measured and
      rejected" convention — see `bespoke-decoders`/`radix-execution`
      epic close-outs for the house style) and report the aggregation-side
      cost as an architecture-floor residue for this epic, informing task
      006's scope decision.
- [ ] `disjoint_aggregation_matches_plain_aggregation_exactly` and the
      full `cargo test` suite stay green regardless of outcome.
- [ ] Cell-exact validation (`tests/duckdb_validated.rs`) unchanged.
- [ ] Q13 re-measured at SF=10 (and ideally a confirmatory spot-check at
      SF=100, where sidecars/data already exist) with before/after numbers
      reported.
