# Task: Q13 — disjoint-aggregation threshold investigation + fix

## Description

Q13 (`customer LEFT OUTER JOIN orders ... GROUP BY c_custkey`, then a
second `GROUP BY c_count`) splits its cost almost exactly down the middle:
44.7% join-side, 55.3% aggregation-side (measured this session,
`HJ_TIMING`/`AGG_TIMING`, 3-iteration average, unmodified binary — see
task 003 for the join-side fix). This task is the aggregation-side half,
which is the *larger* of the two.

The inner `GROUP BY c_custkey`'s cost is dominated by a **shared-channel
merge** (223.0ms of Q13's ~411.5ms total, confirmed via `[raw-merge]`
profiling output) because `disjoint_group_hint`
(`src/physical/planner.rs:362-390`) requires a single-int-column group
key's footer-stat range to fall in `2_000_000..=64_000_000`
(`planner.rs:384`). Direct measurement this session: `SELECT
MIN/MAX(c_custkey) FROM customer` at SF=10 → **range = 1,500,000**, just
under the floor.

The mechanism's own doc comment (`planner.rs:354-361`) names *this exact
query* as its motivating case: "Q13's c_custkey, NDV=range=15M: merge 4.3s
shared vs 0.1ms disjoint at SF=100" — a ~43,000x improvement on that
phase, at SF=100 scale. The floor exists because the code uses a
RANGE-only proxy for "dense direct-address domain" (NDV estimation was
tried and found circular — see the comment) — it is not obviously a
statement about a *minimum problem size* below which disjoint mode stops
paying off, but it might be; that distinction is exactly what this task
must establish before touching the constant.

## Outcome (2026-08-23)

**Threshold moved: `disjoint_group_hint`'s range floor 2,000,000 ->
1,000,000** (`src/physical/planner.rs:384`), backed by
`examples/disjoint_merge_bench.rs`. Q13 SF=10 end-to-end: **413.1ms ->
246.9ms average (-40.2%, 1.67x faster)**; the inner `GROUP BY c_custkey`
merge phase specifically: **223ms -> 30.9ms typical (~7.1x faster)**, and
disjoint mode's `[raw-merge]` shared-merge print no longer appears at all
for this query at SF=10 (confirms the shared path is no longer reached).
No test regressions (988/988, 175/175 duckdb-validated, cell-exact
unchanged); `cargo fmt --all -- --check` clean.

SF=100 was unaffected by this specific change (range=15M already
qualified under both the old and new floor) — the spot-check there
surfaced a SEPARATE, out-of-scope finding: `finalize_disjoint_states`
(`morsel_agg.rs:166`) still routes each disjoint worker's SF=100-sized
state (~469K groups/worker, above `PARALLEL_MERGE_MIN_GROUPS`=65,536)
through the multi-state shard-merge machinery even though there is only
one state and nothing to merge, costing ~205ms/iteration instead of the
near-zero the mechanism's original design intends (and the doc comment's
cited "0.1ms disjoint" appears stale, likely predating this or another
now-superseded code path). This does not fire at SF=10 (46,875 groups/
worker < 65,536), so it did not affect this task's result, and it was left
unfixed here — `morsel_agg.rs` is outside this task's file scope. **For
task 006: the aggregation-side cost this task targeted is resolved at
SF=10 (no architecture-floor residue at this scale); at SF=100 a residue
remains, but it is a single-state finalize inefficiency, not evidence that
a new data structure (dense group-id) is needed — likely a small, targeted
fix in `finalize_disjoint_states` rather than a Stage 1 rewrite. Worth a
cheap look before committing to the larger design.**
