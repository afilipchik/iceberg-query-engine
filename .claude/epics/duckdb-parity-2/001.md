# Task: IPC-cache defaults/documentation fix + CLAUDE.md re-baseline

## Description

`src/storage/ipc_cache.rs`'s module doc comment (line 13) says IPC caching is
"default off until the gauntlet passes." The actual `Mode` enum defined
immediately below it (lines ~21-30) shows the true default (`QE_IPC_CACHE`
unset) is `Auto`: silently use a sidecar that already exists on disk, never
build one. Confirmed empirically this session: `data/tpch-10gb` and
`data/tpch-100gb` both already have `.qeipc` sidecars (built 2026-08-18);
running Q9 with `QE_IPC_CACHE` fully unset (avg 1113.9ms) matches the
explicit `=1` behavior (1036.0ms), not the explicit `=0` behavior
(1247.4ms). A "plain" benchmark run in this repo right now silently gets
the IPC-cache premise, contradicting the module's own documentation.

Separately, a genuinely-forced `QE_IPC_CACHE=0` SF=10 sweep this session
measured **8.86s total (2.03x DuckDB-over-parquet, 2.88x DuckDB-native)** —
this is the true cache-off number and is meaningfully worse than the
partially-cached 7.01s number an earlier unset-env-var run produced. The
gap between "cache off" and "cache on" (5.99s, 1.37x/1.80x) is large and
the whole suite moves through it — this single mismatch is plausibly
responsible for most of the "drastically behind" perception that started
this investigation.

Also: CLAUDE.md's SF=10 benchmark section (last updated 2026-08-17,
predates the 2026-08-22 dependency-modernization upgrade) reports ratios
only against DuckDB-native, never states the like-for-like
(DuckDB-over-the-same-parquet) ratio the SF=100 four-way matrix already
reports — the one section most people will read first is also the one
skipping the project's own "Honesty note" convention (PARITY-PLAN.md).
And the ipc-default epic's 2026-08-19 Q9 caveat ("IPC mode loses to
parquet mode by ~2s at SF=100, accepted trade-off") was superseded by
perf-marathon's very next epic (2026-08-20, commit b3c2868, "Q9 IPC now
9.7s — BEATS parquet mode") and never removed from the record.
