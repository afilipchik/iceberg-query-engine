# Task: Dense group-id remapping, Stage 0 + Stage 1

## Description

Since 2026-08-20 the performance program has repeatedly named "dense
group-id remapping" as its one unexecuted future item — the last
HashMap-fallback aggregation residue (`perf-marathon` epic close-out).
This epic's investigation produced a full staged design (Stages 0-4,
reconciled against a 67-finding competitive research sweep,
`.claude/plans/research/wave2-olap-engines.json`) and — critically —
found the codebase has **four** aggregation code paths, not the one or
two the prior research assumed: a shared core
(`morsel_agg.rs::AggregationState`, three tiers: perfect-hash, raw
single-column, true HashMap fallback) plus a **separate, more-boxed**
implementation in `hash_agg.rs` that anything with `DISTINCT` or a
handful of other functions routes to entirely, bypassing the shared
core's optimizations. This task is Stages 0 and 1 only — the kill-switch
microbenchmark and the single-int/date-column general-function flat
accumulator. Stages 2-4 are explicitly out of scope for this epic (see
the PRD's Out of Scope section and the design's own Stage 4
recommendation to spin it out as a follow-up epic).

**Scope depends on task 002's outcome.** Task 002 measures whether
extending the disjoint-aggregation threshold closes most of Q13's
aggregation-side cost. If it does, Q13 should NOT be this task's target
(redundant investment) — Stage 1 should instead target Q20 (already named
via `perf-marathon` IDEAS.md idea #6 as a "44.6M-group SPARSE aggregate,"
though its exact cost split is INCONCLUSIVE per this epic's own
floor-cluster re-check: ~55-60% of Q20's wall time evaded the available
profiling instrumentation, most likely the aggregation phase itself not
routing through an `AGG_TIMING`-instrumented path for Q20's specific
Semi/Left-join-dominated plan). Q10 is a candidate only if `PLAN_DEBUG=1`
confirms its 7-column GROUP BY still reaches the aggregate operator
un-collapsed — plausible it already reduces to a single `c_custkey`
column via the existing `GroupKeyReduction` optimizer rule before this
task would even apply, in which case Q10 needs no new work either.

## Technical Details

Full staged design (all 4 stages, correctness constraints, file/function
anchors, and the explicit ruling that this is NOT radix partitioning) is
recorded in this epic's investigation output — consult it before
starting; do not re-derive from the wave2 research file alone, which the
investigation already found needed several corrections against the
actual code (e.g. Q10 likely already reduces to a single column; Q16's
real bottleneck is DISTINCT-routing and anti-join parallelism, not group-
key shape, so Q16 is NOT a target for this task despite appearing in the
research file's findings).

Key anchors: `src/physical/morsel_agg.rs` — `AggregationState`
(~1457-1521), `PERFECT_HASH_MAX_GROUPS` (~1448), raw single-column tier
(`raw_groups`/`raw_sums`, ~1483-1490), `process_rows_hashmap` (~1988,
raw branch ~1997-2114), combined-dictionary fast path (~1766-1911,
already shipped, do not duplicate), `into_shards` fixed-seed hasher
(~2360-2367). `src/physical/operators/hash_agg.rs` — `VectorizedGroupTable`
(~448-543, the closest existing template for the finalize-into-array
step). `src/optimizer/rules/group_key_reduction.rs` — physical
`group_by` shrink (~396, ~760), relevant to the Q10 confirmation step.
