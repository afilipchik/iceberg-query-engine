# Task: Q13 — join-output-pruning + runtime-filter extension to filtered outer joins

## Description

The join side of Q13's cost (184.0ms, 44.7% of its ~411.5ms total,
measured this session) is structurally excluded from every join-side
optimization the project shipped over the past week, because its join
(`LEFT OUTER JOIN ... ON c_custkey=o_custkey AND o_comment NOT LIKE
'%special%requests%'`) is `Left` with a non-`None` filter, and three
separate gates all key on `JoinType::Inner`:

- `src/physical/planner.rs:945` — join-output-pruning eligibility
  (`analyze_join_output_usage`).
- `src/physical/operators/hash_join.rs:808-818` — physical pruning
  application (`HashJoinExec::set_retained`).
- `src/physical/operators/spillable.rs:216-233` —
  `SpillableHashJoinExec::set_retained`, which **has no type/filter guard
  of its own today** and only "works" because the upstream gate never
  hands it an ineligible mask.
- `src/physical/planner.rs:1380` — runtime-filter eligibility
  (`rt_eligible`), also `Inner`-only (with narrow Semi/Anti exceptions).

Confirmed this session: Q13 does already flow through `execute_
fused_streaming`'s channel-based join→aggregate fusion (no materialized
15M-row join output) — what it's missing is specifically pruning and
runtime-filter, not fusion. `QE_JOIN_PRUNE=0` vs default A/B (8 iterations
each) showed statistically identical timing, independently confirming
pruning never engages on this query today.

A full implementation design was produced during this epic's
investigation — this task is that design, not a fresh derivation.

## Acceptance Criteria

- [ ] New gate condition — `join_type ∈ {Inner, Left, Right, Full} AND
      (filter.is_none() OR filter contains no subquery)` — applied
      **identically** at all three gates (`planner.rs:945`,
      `hash_join.rs:808`, `spillable.rs:216`). Semi/Anti and Cross stay
      excluded (out of scope; Semi/Anti's schema is left-only width and
      needs separate handling not required by Q13).
- [ ] Force-keep rule: any column the ON-clause filter itself references
      stays in the join's output regardless of downstream need (needed to
      evaluate the filter before deciding NULL-extension). Implement via
      `filter_cols ∪ needed` at the `analyze_join_output_usage` insertion
      site (`planner.rs:945`), reusing the existing `collect_columns`
      helper. Subquery-bearing filters bail to "keep everything" (the
      existing safe default for `refs_of`, `planner.rs:900-911`).
- [ ] Fix `create_combined_batch`'s stale-schema bug
      (`hash_join.rs:1698-1737`): it reads `self.combined_schema`, a
      field built once at construction and never updated by
      `set_retained`. Once build-side pruning is live for a filtered
      join, this WILL hard-fail on the first pruned+filtered query
      (column-count mismatch) if not fixed first. Build the schema from
      the actual batches being gathered (`build_batches[0].schema()` ++
      `probe_batch.schema()`) instead of the stale field.
- [ ] Port `probe_keep` pruning (the parameter already exists; the Inner
      branch already uses it) into the outer-join gather branches that
      currently ignore it: Left parallel-batch (`hash_join.rs:2759-2768`,
      **Q13's actual hot path**), Left sequential fallback
      (`~2913-2924`), Right sequential fallback (`~2962-2973`), Full
      sequential fallback (`~3018-3023`); read through the generic
      non-VHT `probe_hash_table` path (`~3180-3329+`) for the same gap
      and fix if present, lower priority (off Q13's hot path).
- [ ] Do NOT attempt join→aggregate fusion for this shape — evaluated and
      declined during design (streaming-fusion's own "Lever B" was
      already investigated and declined for the strictly simpler
      Inner-only case). Pruning-only for this task.
- [ ] New correctness tests, following the existing
      `tests/expected_results/join/*.csv` + `manifest.json` +
      `tests/duckdb_validated.rs` convention:
      - "All candidate matches filtered out → c_count=0" case (not
        dropped, not miscounted) — see suggested SQL in the design notes
        below.
      - A "some but not all filtered" case via the DuckDB-oracle
        generation script.
      - Existing fixtures `left_on_both_sides`, `full_on_filter`,
        `right_on_filter` (`manifest.json:436-483`) stay green — these
        are the sharpest existing regression guards for the force-keep
        rule (they force-keep filter-only columns neither side selects).
      - White-box `HashJoinExec` unit test (new, in the existing
        `#[cfg(test)]` module, `hash_join.rs:4071+`) exercising a pruned
        build side flowing into `filter_candidate_pairs` directly — no
        existing test does this today.
      - Dedicated `SpillableHashJoinExec`-level test confirming Gate C
        never diverges from Gate B (catches a schema/column-count
        mismatch a unit test on the inner `HashJoinExec` alone would
        miss).
- [ ] Full suite green; cell-exact vs DuckDB on SF=10 and SF=100 sweeps;
      re-measure Q13 and report the before/after split (join-side share
      specifically, cross-referenced against task 002's aggregation-side
      number).
- [ ] Note in the close-out report (don't over-promise): Q13 permanently
      cannot take the "direct u32 match emission" fast path
      (`hash_join.rs:2570`, gated `filter.is_none()`) even after this fix
      — it will always pay a double gather (once to evaluate the filter,
      once for the real output). This task closes part of the gap, not
      necessarily all of it.

## Technical Details

Suggested SQL for the "all filtered → zero" test case:
```sql
SELECT c_custkey, COUNT(o_orderkey) AS c_count
FROM customer LEFT JOIN orders
    ON c_custkey = o_custkey AND o_orderkey < 0
WHERE c_custkey IN (1,2,3,4,5)
GROUP BY c_custkey
ORDER BY c_custkey
```
Expect exactly 5 rows, `c_count = 0` for each — exercises `o_orderkey`
being force-kept for two independent reasons at once (filter AND
downstream `COUNT` arg) and the non-shortcut branch of
`filter_candidate_pairs` (mask all-false).

Effort estimate from design: ~20 lines in `planner.rs`, ~120-150 lines in
`hash_join.rs`, ~10 lines in `spillable.rs`, ~40-60 lines of new tests
plus 1-2 new fixture pairs.

Named risks (in severity order, from the design): (1) gates shipped out
of sync — mitigate with a single commit touching all three identically
plus the dedicated `SpillableHashJoinExec` test; (2) forgetting the
`create_combined_batch` fix — fails loudly on the very first test run,
won't ship silently; (3) missing one of the ~5 probe-branch call sites —
correct but unoptimized, not a correctness bug, mitigated by the explicit
checklist above.
