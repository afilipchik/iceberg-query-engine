# Task: Q16 — anti-join parallel-probe investigation + fix

## Description

Q16 (`SELECT p_brand,p_type,p_size,COUNT(DISTINCT ps_suppkey) FROM
partsupp,part WHERE ... AND ps_suppkey NOT IN (SELECT s_suppkey FROM
supplier WHERE s_comment LIKE '%Customer%Complaints%') GROUP BY ...`) has
two joins: an anti-join (the `NOT IN` subquery) and an inner join
(`p_partkey = ps_partkey`). Measured this session (clean run,
`HJ_PROF=1`): the anti-join probes all **8,000,000 partsupp rows as a
single `partition 0` unit (49.2ms)**, plus its build phase (42.1ms) —
**91.3ms combined, ~52% of Q16's ~175.5ms total** — while the second join
in the *same query* probes in parallel across 32 partitions in 6.2ms.
`JoinType::Anti` does not match whatever gate restricts batch-parallel
probing to `Inner`/`Left` (`src/physical/operators/hash_join.rs`, near
lines 2540-2545), so it and its build run effectively single-threaded on
a 32-logical-CPU box.

This is a parallelism gap, not an algorithmic one — the existing
sequential per-partition probe logic doesn't need to change, only whether
it runs on 1 partition or N.

      exclusion from the parallel-probe gate is a deliberate correctness
      choice or an oversight. Read the surrounding code and any comments
      near `hash_join.rs:2540-2545` and the `JoinType::Anti`/`Semi`
      execution branches for why match-tracking or unmatched-row
      bookkeeping might not already be partition-safe for these join
      types the way it is for Inner/Left.
- [ ] If safe: extend the parallel-probe gate to include `Anti` (and
      `Semi` if the same investigation clears it), reusing the existing
      per-partition probe logic unchanged — this should be a gate
      extension, not new probe logic.

      blocks it (e.g. a shared mutable match-count that isn't
      partition-independent) and scope the minimal safe fix (e.g.
      per-partition local state + a cheap final merge) rather than
      abandoning the investigation with an undocumented "no."
- [ ] Cell-exact validation: Q16's `NOT IN` semantics (including NULL
      handling in the subquery side, a classic `NOT IN` correctness trap
      independent of this change but worth confirming stays correct)
      must be unaffected — same rows, same counts, just computed with
      more threads.
- [ ] Full suite green; re-measure Q16 at SF=10, report before/after and
      the specific ms recovered from the anti-join phase.
- [ ] Check for other queries in the TPC-H suite with `Anti`/`Semi` joins

      if not separately gated in this epic's success criteria.
