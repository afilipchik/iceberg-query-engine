# Task: QA close-out — full suites, cell-exact SF=10+SF=100, docs, epic close

## Description

Final task, matching every one of the six prior epics' own close-out
discipline: full suites in all feature combinations, cell-exact
validation at both scales, benchmark re-measurement, CLAUDE.md update,
and an honest before/after write-up in this epic's file — including
which gates were met, which weren't, and why (this program's own house
style never overclaims; "gate not met, residue is named and
program-level" is a normal, acceptable outcome when the evidence
supports it).

      (or the SF=10/SF=100 cell-exact sweep pattern this program has used

- [ ] **Iceberg-table benchmark (new requirement, 2026-08-23)**: benchmark
      the engine against DuckDB reading the SAME data through Iceberg,
      not just plain parquet — `data/tpch-10gb-iceberg/` (generated this
      session via `scripts/iceberg_gen.py data/tpch-10gb
      data/tpch-10gb-iceberg`, verify it exists and validated cleanly
      before using it; regenerate if missing). Engine side: point
      `benchmark-parquet`/`load-parquet`-equivalent at the iceberg
      directory (the engine auto-detects Iceberg tables via
      `is_iceberg_dir`/`register_iceberg`, `src/main.rs:1238-1243`).
      DuckDB side: `INSTALL/LOAD iceberg;` then read each table via
      `iceberg_scan('data/tpch-10gb-iceberg/<table>/metadata/<highest-
      numbered>.metadata.json')` (confirmed working, DuckDB 1.4.4; the
      generator's own `read_back_duckdb()` in `scripts/iceberg_gen.py` is
      the reference implementation — pointing at the bare directory
      instead of the metadata.json file fails with a version-guessing
      error since this is a SqlCatalog-layout warehouse with no
      version-hint.text). Engine side: `benchmark-parquet --path` does
      NOT auto-detect Iceberg (confirmed by trying it — it expects flat
      `<table>.parquet` files and errors); use `query_engine serve
      --tables data/tpch-10gb-iceberg` instead (confirmed via `--help`:
      registers Iceberg/Lance/parquet per-subdirectory via
      `is_iceberg_dir`, `src/main.rs:1238-1243`) and query its `/sql`
      endpoint, or extend `benchmark-parquet` to support Iceberg
      directories if that's a smaller, more reusable change — your call.
      Report this alongside, not instead of, the existing
      plain-parquet comparison — they may differ (Iceberg's manifest/
      snapshot indirection is real overhead on both sides) and both are
      legitimate premises worth stating separately, matching this
      program's own "report multiple premises" convention (cache-on vs
      cache-off, native vs like-for-like).
- [ ] **CPU vs GPU benchmark split (new requirement, 2026-08-23)**: run
      the SF=10 sweep both with and without `--features gpu` (`QE_GPU=0`
      to force CPU-only within a gpu build, or the default `default`-
      feature build for a true CPU-only binary) and report them as
      separate rows, not conflated. Set realistic expectations before
      running: GPU offload (`.claude/epics/gpu-acceleration/`, CLAUDE.md's
      "GPU Aggregate Offload" section) currently covers ONLY simple
      fused aggregates (SUM/MIN/MAX/COUNT/AVG, single-column conjunctive
      predicates) over DEVICE-RESIDENT columns from PARQUET providers on
      a WARM (already-uploaded) cache — it does not cover joins, does not
      cover Iceberg or Lance providers, and the first touch of any column
      is always CPU (background upload triggers async). Most of this
      epic's own target queries (Q13, Q16, Q20 — all join-heavy or
      distinct-count-heavy) will plausibly show LITTLE OR NO GPU delta
      for exactly that reason — report this as an honest finding, don't
      force a comparison where the mechanism structurally can't engage.
      Queries most likely to show a real GPU delta: Q1, Q6, Q14 (simple
      scan+filter+aggregate shapes) — call these out specifically if the
      split is measured.
