# Task: Memory safety — cap or spill integration

## Description

CLAUDE.md's memory-safety rule is unconditional: "THE ENGINE MUST BE
MEMORY-SAFE BY DEFAULT. OOM IS NEVER ACCEPTABLE... Never add a parameter
that lets users opt out of memory safety." Native tables, once loadable
and queryable (tasks 003/004), need a real answer to "what stops someone
from loading an unbounded dataset into RAM and OOMing the process" before
this epic ships — `MemoryTable`'s existing lack of spill-awareness is a
named gap in this codebase this feature must not inherit uncritically.
Since the sidecar's read path is mmap-based (OS-evictable, safe by
construction against RAM pressure the way anonymous memory isn't), the
real question is bounded to: load-time admission control, and whether
mmap alone is sufficient or genuine `MemoryConsumer`-style spill
integration is needed for the write/build path specifically.

## Outcome (closed 2026-08-23)

Independent verification of task 003/004's claims (re-derived, not
trusted) confirmed both hold — but going one step further than "trust the
mmap argument for reads" found a REAL, measured, native-table-specific
memory-safety gap the epic's own framing didn't anticipate, and fixed it.
This task ended up being both verification (write path, read mmap
mechanism) AND one real, scoped code change (read-side admission
control) — not purely the "verification only" outcome its own framing
flagged as a live possibility.

### Write path: independently re-confirmed safe, no gap

Read task 003's Outcome first per instructions, then independently
re-derived its claim by reading `src/storage/native_write.rs` directly
rather than trusting the self-report: `write_batches_with_options` drives
`stream.try_next()` in a loop (`write_staged`), `SegmentWriter::accept`
buffers into `pending: Vec<RecordBatch>` and flushes at
`target_rows_per_segment` (default 1,000,000 rows) — a real, hard,
non-configurable-by-default cap, not merely "designed to be" one. Went
further than reading code: **re-ran task 003's own experiment myself**
(converting `data/tpch-10gb/lineitem.parquet`, 60,000,000 rows, 2.8GB
compressed, to a native table) under a 900MB hard `claude-safe-build.sh`
cgroup cap (swap disabled) — succeeded, **404,044 KB peak RSS**
(`/usr/bin/time -v`), matching task 003's own reported 415,428 KB within
normal run-to-run noise. `create_table_as_select` (task 004,
`src/execution/context.rs`) independently re-read and confirmed to drive
`physical.execute(partition)` per partition through streaming
combinators (`.and_then`, `futures::stream::select_all`) directly into
`write_batches` — never through `ExecutionContext::sql()`'s
`try_collect()`-based materializing path, which itself now explicitly
refuses a `CREATE TABLE` statement (confirmed by reading `sql()`,
`context.rs` ~line 382). **No gap; no code change needed on the write
side.**

### Read path: mmap mechanism confirmed real, but a real gap exists above it

Traced `NativeTable::scan()` (`src/storage/native_table.rs`) to
`ipc_cache::read_row_group` (`src/storage/ipc_cache.rs`) directly:
confirmed genuine `memmap2::Mmap::map` + `Buffer::from_custom_allocation`
zero-copy reads — the IDENTICAL mechanism the existing parquet IPC
sidecar cache already relies on for its own no-OOM argument, independently
verified by reading the source rather than trusting the doc comment.

Went further than concluding "mmap is sufficient" from the mechanism
alone. Registered a real 60M-row native `lineitem` table (converted via
the write path above) through the REAL `TableProvider` path (`serve
--tables`, not a synthetic microbenchmark) and ran a full-table,
ungrouped `SELECT COUNT(*), SUM(l_quantity), SUM(l_extendedprice)`
under real memory pressure. Found a genuine gap:

- **`NativeTable::scan()` is NOT spill-aware.** It reads every active
  segment and returns ONE fully materialized `Vec<RecordBatch>` — the
  same "generic, non-parquet" provider contract `LanceTable::scan()`
  already has, and the exact `MemoryTable`-shaped gap this task's own
  Description warned not to inherit "uncritically."
- **Measured, not estimated**: this query needed **~1.6GB peak RSS**
  (kernel `VmHWM`, read directly from `/proc/<pid>/status` via the
  cgroup's own `cgroup.procs`, not `ps`/`pgrep` which initially
  misattributed a wrapper shell) and was **OOM-killed (SIGKILL, exit
  137)** under a bare 1GiB `claude-safe-build.sh` cgroup cap (swap
  disabled) — with NO `--memory-limit` configured (i.e. hitting the
  engine's own `ExecutionConfig::default()` 1GiB `memory_limit`, already
  in effect and already silently not enforced for this code path).
- **Controlled, decisive comparison**: the IDENTICAL query over the
  IDENTICAL data registered as plain Parquet instead (same 1GiB cgroup
  cap) finished in **109ms** and never came close to the cap —
  `ParallelParquetSource`'s genuine row-group streaming vs.
  `NativeTable::scan()`'s whole-table materialization. This confirms the
  gap is native-table-specific (and shared with Lance, which has the
  identical `scan()` contract), NOT a general characteristic every
  provider in this engine already has — ruling out "this is normal, no
  action needed" as the honest conclusion.
- Confirmed via reading `src/physical/operators/morsel_agg.rs` /
  `src/physical/planner.rs` (task 005's concurrently-in-flight territory,
  read-only, not touched) that task 005's dense-direct-address fast path
  is narrowly gated to `group_by.len() == 1` and falls through with a
  named `Err` (not a crash) when ineligible — the ungrouped query above
  genuinely takes the generic path this task fixes, not a coincidence of
  routing.

### Fix: hard, explicit admission-control cap (native_table.rs only)

Per this task's own charter ("a hard, explicit size/row cap... or point
integration with spillable.rs, whichever fits") — spillable.rs's
budget/spill machinery is shaped for join/aggregate/sort operators
consuming an already-streaming input, not a table provider's own `scan()`
method, so a cap is the correctly-fitting mechanism, not a mismatch.
A true fix (an incremental/streaming native-table scan comparable to
`ParallelParquetSource`) would need a per-provider morsel driver spanning
`src/physical/planner.rs`/`src/physical/operators/morsel_agg.rs` — outside
this task's file territory this session and a materially larger lift than
this task's M sizing; documented as follow-up, not attempted.

```rust
// src/storage/native_table.rs
pub struct NativeTable {
    // ...
    memory_budget_bytes: Option<u64>,   // NEW
}
impl NativeTable {
    pub fn with_memory_budget(mut self, budget_bytes: Option<u64>) -> Self;
    fn check_scan_budget(&self) -> Result<()>;   // called first thing in scan()
}
```

- `ExecutionContext::register_native_table` (`src/execution/context.rs`)
  computes `memory_limit * spill_threshold` — REUSING the exact formula
  `src/physical/operators/spillable.rs` already applies at 7 call sites
  for the identical "how much may one thing in this query legitimately
  hold" question — and calls `.with_memory_budget(Some(budget))`. Not a
  new concept, not a new user-facing flag: the ONLY way to affect this is
  the ALREADY-EXISTING `--memory-limit`/`ExecutionConfig::memory_limit`,
  exactly the escape hatch `spillable.rs`'s own budget-exceeded errors
  already point users to ("Raise the memory limit for this query").
- `scan()` calls `check_scan_budget()` first: if
  `self.statistics().total_byte_size > budget`, refuses with
  `QueryError::Execution` naming the exact byte counts, BEFORE touching a
  single segment — never a silent proceed-and-hope.
- The estimate is deliberately the WHOLE active segment set's on-disk
  size, ignoring any requested projection (task 002's manifest has no
  per-column byte breakdown to compute a narrower number from — adding
  one is task 002's closed territory, not this task's). Conservative in
  the safe direction only: may refuse a narrow projection of a huge table
  that would actually have fit; never proceeds when the whole table
  plainly would not.
- `shard_by_splits` propagates `memory_budget_bytes` to the shard
  unchanged (a shard is smaller than the whole table, so the same
  absolute budget is never tighter than the whole-table check).
- A `NativeTable` built directly via `try_new` (bypassing
  `ExecutionContext`: tests, `native_write.rs`'s own round-trip reader)
  gets `memory_budget_bytes: None` and is completely unaffected — the
  exact pre-task-006 behavior, zero risk to any existing caller.
- `QE_DEBUG_SCAN_BUDGET=1` traces every `check_scan_budget` call to
  stderr — a small, permanent, env-gated diagnostic matching this
  codebase's own established "cheap, zero-cost-when-unset" switch
  convention (`PLAN_DEBUG`, `AGG_TIMING`, etc.), kept because it is what
  let this task distinguish "the check fires but something else is still
  wrong" from "the check isn't being reached at all" while chasing down a
  same-session build-staleness red herring (see below).

### Fix verified end to end, not just unit-tested

Same adversarial scenario that produced the SIGKILL, re-run against the
fixed binary:

| scenario | memory_limit | cgroup cap | result |
|---|---|---|---|
| before fix | default (1GiB) | 1GiB | **SIGKILL (137)**, several seconds, no response |
| after fix | default (1GiB) | 1GiB | **clean HTTP 400 in ~20ms**: `"...needs an estimated 5641105508 bytes to scan..., which exceeds the configured memory safety budget of 858993459 bytes (memory_limit * spill_threshold)..."` (858,993,459 = 1GiB × 0.8 exactly); server stays alive |
| after fix | 8GB (`--memory-limit`) | 9GB | HTTP 200, 588ms, `cnt=60000000` — matches every earlier run's values |

Control (plain Parquet, identical data, identical 1GiB cap): 109ms, no
pressure at all — confirms the fix targets a real, native-table-specific
gap rather than "papering over" an unrelated general characteristic.

**A methodological trap worth recording**: an early re-test of the fix
still showed a SIGKILL. Root-caused (not assumed) by grepping the actual
tested binary for the new error-message text — the "rebuilt" binary's
mtime hadn't actually advanced; the earlier `cargo build --release`
invocation's background output had gone missing without a clear
`Finished` line. Rebuilding again and confirming via `grep -a "memory
safety budget" <binary>` before re-testing resolved it. Lesson for any
future task in this shared, non-worktree-isolated checkout: verify a
rebuilt artifact's content directly (grep for new strings, not just mtime
or a "completed" notification) before trusting a re-test, especially with
sibling agents concurrently building into other paths on the same box.

### For task 008

- Native-table reads now enforce `memory_limit * spill_threshold` as a
  hard admission cap (whole active-segment on-disk size vs. budget,
  ignoring projection). **Any SF=10/SF=100 native-table benchmark run
  MUST size `--memory-limit`/`ExecutionConfig::with_memory_limit` for the
  data**, exactly like `benchmark-parquet` already does
  (`(sf * 4.0).max(1.0)` GB capped at 64GB, `src/main.rs`) — this is a
  NEW, real constraint relative to querying the same data as Parquet
  (which has no such cap because its streaming path doesn't need one),
  not a pre-existing convention task 008 can assume carries over
  unchanged. Without an adequate `--memory-limit`, an SF=10 `lineitem`-
  scale (or larger) native-table query will now refuse cleanly rather
  than run — this is the intended, correct behavior (a clean refusal
  beats a silent OOM), but it DOES mean task 008's benchmark harness must
  configure memory explicitly, the same way `benchmark-parquet` already
  does for parquet.
- The underlying gap (generic `TableProvider::scan()` not being
  incremental/streaming for non-parquet providers) is real, measured, and
  now documented in `native_table.rs`'s own module doc plus this Outcome
  — but the actual fix (a native-table-aware morsel/streaming scan
  comparable to `ParallelParquetSource`) remains open, unclaimed follow-up
  work outside this epic's/task's scope (would need
  `src/physical/planner.rs`/`morsel_agg.rs`, a materially larger lift than
  this task's M sizing). `LanceTable` shares the identical underlying
  characteristic and was not touched either.
- G3 ("no uncontrolled-OOM path exists; memory safety validated the same
  way every other operator in this codebase is") is satisfied for the
  code paths this epic actually ships: the write path was already safe
  (task 003, re-confirmed here) and the read path's real gap is now
  closed with the same class of mechanism (`memory_limit * spill_threshold`
  admission control) `spillable.rs`'s own operators already use.
