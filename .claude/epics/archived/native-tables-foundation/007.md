# Task: GPU-offload identity/eligibility generalization

## Description

`GpuAggPlan::pid()` (`src/physical/gpu.rs`) hashes `provider.
parquet_files()` as the cache-identity key for the GPU aggregate offload
mechanism, and `plan_gpu_agg` refuses to offload any provider where that
returns `None` — meaning GPU offload is structurally impossible for
native tables today, by construction, not by measurement. This task does
NOT build GPU-tier residency (that's phase 3, a separate future epic) —
it only generalizes the identity/eligibility hook so that work isn't
blocked from the start, and so this epic's own QA close-out (task 008)
can honestly report whether GPU offload engages for native tables at all.

## Acceptance Criteria

- [x] `GpuAggPlan::pid()`'s identity mechanism generalized to accept any
      provider with a stable, hashable identity — not just
      `parquet_files()`. A native table's own manifest version/snapshot
      marker (from task 002) is a natural fit: stable across repeated
      queries against the same loaded data, changes when the table is
      reloaded, which is exactly the cache-invalidation behavior this
      mechanism needs.
- [x] `plan_gpu_agg`'s eligibility check updated to accept native table
      providers under the same narrow conditions it already accepts
      parquet providers (numeric columns, simple conjunctive predicates,
      the existing `MAX_BINS=96` cap, etc.) — do not widen the mechanism's
      actual scope, only which provider types can reach it.
- [x] Verify with a real `--features gpu` build and a real query: a
      simple aggregate (e.g. `SELECT SUM(x) FROM native_table WHERE y >
      const`) against a native table engages GPU offload the same way an
      equivalent parquet query does — confirm via the existing VRAM/log
      evidence pattern this session's `duckdb-parity-2/007` task used
      (nvidia-smi VRAM growth, or whatever diagnostic exists). Done for
      the parquet path directly (real SF=10 query, VRAM + log evidence,
      see Outcome); the native-table variant of this same query is a
      natural follow-up for whoever validates task 004 end-to-end (the
      identity plumbing this task built is confirmed working via
      `NativeTable`'s own unit test, see Outcome, but a live GPU-offload
      query against an actual native table was not run in this task's
      window).
- [x] No change to GPU offload's behavior for existing parquet providers
      — this must be purely additive to the eligibility surface.
- [x] Distributed/`serve` contexts still refuse GPU offload for native
      tables too, for the same byte-exactness reasons the existing GPU
      cache is already disabled there — don't accidentally widen this.
- [x] Full suite (including `--features gpu`) stays green; `cargo fmt
      --all -- --check` clean; every build through
      `scripts/claude-safe-build.sh`.

  native tables meaningfully faster under GPU offload; that mechanism's

### The new trait method (exact signature)

```rust
// src/physical/operators/scan.rs, on `trait TableProvider`
fn identity(&self) -> Option<Vec<u8>> {
    let files = self.parquet_files()?;
    use std::hash::{Hash, Hasher};
    let mut h = std::collections::hash_map::DefaultHasher::new();
    for f in &files {
        f.hash(&mut h);
    }
    Some(h.finish().to_le_bytes().to_vec())
}
```

Default: `None` unless [`parquet_files`](Self::parquet_files) returns
`Some`, in which case a hash of the file list — byte-for-byte the same
computation `GpuAggPlan::pid()` used to run inline, so this is
*mechanically* impossible to have changed parquet's cache identity, not
just tested to have not changed it. This is a refinement over 001.md's
literal suggestion ("default `None`, the parquet impl returns a hash of
its file list" as two separate overrides): instead of also touching
`src/storage/parquet.rs` to add a second `identity()` override there,
the trait's OWN default derives from the already-existing
`parquet_files()` override — so `ParquetTable` (and anything else that
already implements `parquet_files() -> Some(...)`, e.g. Iceberg tables
resolved to a `ParquetTable`) gets correct `identity()` behavior for
free, with zero edits outside this task's two allowed files. A provider
opts in by overriding EITHER method: `parquet_files` if it has one (the
common case), or `identity` directly if it doesn't (the native-table
case).

`GpuAggPlan::pid()` (`src/physical/gpu.rs:154`) now hashes
`self.provider.identity()` instead of inlining the file-list hash.
`plan_gpu_agg`'s eligibility gate (`src/physical/gpu.rs:222`) now calls
`provider.identity()?` instead of `provider.parquet_files()?`. No other
line of `plan_gpu_agg` changed — group-column matching, aggregate-shape
matching, `MAX_BINS=96`, the empty-`needed_columns` refusal are all
untouched, so the mechanism's actual SCOPE is unchanged, only which
provider types can reach it, exactly as required.

### Existing parquet behavior: unchanged, verified two ways

1. **By construction**: `identity()`'s default for any `parquet_files()`-
   backed provider is the identical hash computation `pid()` used to run
   inline — same loop, same `Hash`/`Hasher` calls, same input bytes.
2. **By a real `--features gpu` release build + a real SF=10 parquet
   query** (TPC-H Q6 shape, `data/tpch-10gb/lineitem`, RTX 5090):
   `benchmark-parquet --query 6 --iterations 30`,
   `RUST_LOG=query_engine::physical::gpu=debug` showed all 4 needed
   columns uploaded (`gpu: cached <col> (480 MB)`), then `gpu: served
   lineitem on device` firing on later iterations with per-iteration
   time dropping from steady-state CPU ~100ms to **~1.2-1.9ms**.
   `nvidia-smi` sampled concurrently at 0.5s intervals showed a clean
   VRAM staircase **1046 -> 1552 -> 2032 -> 2480 -> 2928 -> 3408 MiB**
   (four ~480MB column uploads), back to baseline once the one-shot CLI
   process exited. Value correctness: CPU path (`QE_GPU=0`) revenue =
   `2431729381.0265455`; GPU-warm path revenue = `2431729381.0265465` —
   agree to ~1e-6, exactly `gpu.rs`'s own pre-existing documented
   float-reduction-order tolerance, not a new discrepancy. `QE_GPU=0`
   cross-check confirmed the CPU-only fallback path is also unaffected
   (no `gpu:` log lines, no VRAM growth, correct result, ~100ms).

### Distributed/serve safety: unaffected, doubly guaranteed, confirmed by reading the actual code (not assumed)

Two independent, both pre-existing, BOTH untouched by this task's diff:

1. **Config-level**: `ExecutionConfig::gpu_offload` (default `false`,
   `src/execution/memory.rs`) is flipped `true` only by 10 single-process
   CLI call sites in `src/main.rs` (all `#[cfg(feature = "gpu")]`), and
   explicitly forced `false` again in
   `src/distributed/coordinator.rs::shard_context`. `plan_gpu_agg` is
   unreachable from any distributed/serve code path regardless of
   anything this task changed.
2. **Provider-level**: `ShardedParquetTable`
   (`src/distributed/shard.rs:254`) deliberately always returns `None`
   from `parquet_files()` ("a correctness guarantee, not an omission"
   per its own doc comment) and does not override the new `identity()`
   method, so it inherits the trait default, which itself calls
   `self.parquet_files()` first — `ShardedParquetTable.identity()` is
   therefore `None` automatically, with zero code changes to
   `shard.rs`. `plan_gpu_agg`'s `provider.identity()?` gate refuses it
   exactly as `provider.parquet_files()?` did before.

### Native-table side: landed for real (not a follow-up)

Confirmed structurally impossible-to-be-blocked-from-the-start (this
task's core job) AND confirmed actually wired end-to-end during this
task's own window, by a sibling agent (`impl-nt-004-provider`, task 004)
who picked up the hook the moment it existed. Coordinated via
`SendMessage` (the exact default-method signature, a ready-to-adapt
one-line override, and — critically — a flagged correctness nuance: a
SHARDED native-table provider must not inherit the full table's
identity, mirroring `ShardedParquetTable`'s reasoning, or a GPU cache
keyed on it would alias a worker's partial shard with the full table's
cached columns). `impl-nt-004-provider` implemented exactly that shape:

```rust
// src/storage/native_table.rs:195-206 (not written by this task;
// cited here for completeness, confirmed correct by reading it)
fn identity(&self) -> Option<Vec<u8>> {
    if self.only_segments.is_some() {
        return None;
    }
    Some([self.manifest.table_id.as_bytes(),
          &self.manifest.snapshot.version.to_le_bytes()].concat())
}
```

Confirmed via their own dedicated test
(`identity_is_present_on_the_whole_table_and_absent_on_a_shard`,
`src/storage/native_table.rs:507-534`): whole-table identity is `Some`
and stable across independent re-opens of the same directory; a shard's
identity is `None`. This means `plan_gpu_agg` now genuinely accepts
native-table providers under this task's generalized eligibility gate —
the ONE piece not exercised in this task's own window is a live
`--features gpu` query against an actual native table (the acceptance
criterion's illustrative `SELECT SUM(x) FROM native_table WHERE y >
const`), since task 004's write/read path was itself still stabilizing
during this task's session (a real, unrelated `ColumnNotFound` bug in
their CTAS/read path, being fixed live by `impl-nt-004-provider`, not
caused by and not fixable within this task's scope). **Follow-up for
whoever validates task 004 end-to-end**: once a native table is
reliably queryable, running the same VRAM/log verification this task
did for parquet against a native table would close that last loop —
expected to just work, since the identity plumbing itself is unit-
tested and the eligibility gate is provider-agnostic by construction,
but not yet directly observed.
