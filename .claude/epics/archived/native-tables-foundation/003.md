# Task: Write path — bulk-load from parquet/Iceberg/Lance/query results

## Description

The entrypoint that actually moves data into a native table: accept a
stream of `RecordBatch`es (from a query result, a parquet directory, an
Iceberg table, or a Lance dataset the engine can already read) and write
them out as a new native table using task 002's manifest format. Model
this directly on `src/storage/lance_write.rs`'s `write_batches`/
`write_from_parquet` — streaming, no double-materialization of either
side. Full-table replace semantics only (a "load" always produces one
complete new snapshot); no partial append/update in this epic.

## Technical Details

- **Task 001's decisions (full reasoning in `001.md`'s Outcome section):**
  - Module: `src/storage/native_write.rs` (sibling to `src/storage/
    lance_write.rs`, NOT merged into `native_manifest.rs` [002] or
    `native_table.rs` [004] — keeps this task's file disjoint from task
    004's, satisfying the parallel-safety note below).
  - **SQL DDL IS in scope for this epic.** Task 001's sizing spike
    (a `.scratch/` throwaway confirming `sqlparser` 0.62 already parses
    `CREATE TABLE t AS SELECT ...` into `Statement::CreateTable{ query:
    Some(Box<Query>), .. }`, the identical `Query` type `Binder::
    bind_query()` already fully handles) found the incremental lift
    small — S, ~8-16h — once THIS task's write path exists. Concretely,
    add to this task's own scope: a CLI command mirroring `write-lance`/
    `load-lance` (e.g. `write-native --from-parquet|--sql ... --out
    <dir>` and `load-native --path <dir> --name <t> --query <sql>`, in
    `src/main.rs`). This is both the natural test harness for this
    task's own acceptance criteria (mirrors how `write-lance` already
    doubles as `lance_write.rs`'s own integration-test surface) and the
    safe-minimum fallback the epic's Architecture Decisions call for if
    the SQL-surface task (004) slips. The actual `CREATE TABLE ... AS
    SELECT` SQL-syntax wiring (parser/binder/registration) is task 004's
    job — this task only needs a Rust entrypoint task 004 can call, plus
    ideally a CLI command that proves it end-to-end without waiting on
    004.
  - **Do NOT model the CTAS-shaped streaming path on
    `ExecutionContext::sql()` as it exists today.** Confirmed by reading
    it in full (`src/execution/context.rs`, ~lines 301-420): it collects
    every partition's `RecordBatchStream` via `try_collect()` into
    `Vec<RecordBatch>` BEFORE returning — i.e. it fully materializes the
    query result in memory. The existing `write-lance --sql` CLI command
    (`src/main.rs`, `Commands::WriteLance`) inherits this: it calls
    `ctx.sql(&query).await` and only THEN calls `lance_write::
    write_batches(r.batches, ...)` — not the "streaming, no
    double-materialization" property this epic's Architecture Decisions
    require. For a genuinely streaming native-table write (this task's
    own acceptance criterion: "computing per-segment statistics as data
    streams through, not a second pass"), the entrypoint must drive a
    `RecordBatchStream` directly (e.g. consume
    `PhysicalOperator::execute()` partition-by-partition and write each
    batch as it arrives), not go through `ExecutionContext::sql()`'s
    current fully-collecting return type. This is a real, pre-existing
    gap in the `write-lance --sql` precedent (out of scope to fix for
    Lance here) — named so this task doesn't unknowingly inherit it.
  - Dictionary encoding at write time needs an Arrow-side equivalent of
    `ipc_cache.rs::build_sidecar`'s parquet-metadata-based detection —
    see `002.md`'s Technical Details for why the parquet-specific
    technique doesn't transfer directly; flagged here since it's this
    task's own acceptance criterion.
- Direct template: `src/storage/lance_write.rs` — its own doc comment
  says outright this is "the path a `CREATE TABLE ... AS SELECT` takes:
  hand it a query result's batches and its schema," and
  `LanceWriteMode::{Create,Append,Overwrite}` is the closest existing
  enum for a mode parameter (this task only needs `Create`/`Overwrite`
  equivalents — no `Append`, that's mutation, out of scope).
- Test data available: `data/tpch-10gb-iceberg` (Iceberg, generated this
  session), `data/tpch-10gb` (parquet), existing Lance datasets under
  `data/`.

### Public API (`src/storage/native_write.rs`) — precise enough that
tasks 004/006/008 should not need to read the source

```rust
pub enum NativeWriteMode { Create, Overwrite }   // impl FromStr: "create"|"overwrite"

pub struct NativeWriteOptions {
    pub target_rows_per_segment: usize,  // default 1_000_000
    pub dict_max_cardinality: usize,     // default 4096 (mirrors ipc_cache.rs)
    pub slice_rows: usize,               // default 65_536 (mirrors ipc_cache.rs)
}                                         // impl Default

pub struct NativeWriteResult {
    pub table_id: String,   // preserved across an Overwrite; fresh UUID v4 on Create
    pub version: u64,       // the snapshot version this write committed (1 if fresh)
    pub rows: u64,          // == manifest.snapshot.row_count
    pub segments: usize,
}

// THE entrypoint a future CREATE TABLE ... AS SELECT calls. Drives
// `stream` batch-by-batch -- never materializes it. Merge multiple
// PhysicalOperator partitions with futures::stream::select_all first if
// there is more than one; this takes exactly one stream.
pub async fn write_batches(
    stream: crate::physical::RecordBatchStream,  // BoxStream<'static, Result<RecordBatch>>
    schema: arrow::datatypes::SchemaRef,
    out_dir: impl AsRef<std::path::Path>,
    mode: NativeWriteMode,
) -> crate::error::Result<NativeWriteResult>;

pub async fn write_batches_with_options(stream, schema, out_dir, mode, options: NativeWriteOptions) -> Result<NativeWriteResult>;

// Convenience wrappers -- each streams its source, never materializes it
// (StreamingParquetReader for parquet; Iceberg resolves to a ParquetTable
// so it reuses the identical streaming reader; Lance streams ONE FRAGMENT
// AT A TIME via LanceTable::fragment_infos/shard_with_fragments, bounding
// memory to one fragment rather than the whole dataset).
pub async fn write_from_parquet(parquet: impl AsRef<Path>, out_dir: impl AsRef<Path>, mode: NativeWriteMode) -> Result<NativeWriteResult>;
pub async fn write_from_parquet_with_options(.., options: NativeWriteOptions) -> Result<NativeWriteResult>;
pub async fn write_from_iceberg(iceberg_dir: impl AsRef<Path>, out_dir: impl AsRef<Path>, mode: NativeWriteMode, snapshot_id: Option<i64>) -> Result<NativeWriteResult>;
pub async fn write_from_iceberg_with_options(.., options: NativeWriteOptions) -> Result<NativeWriteResult>;
#[cfg(feature = "lance")]
pub async fn write_from_lance(lance_path: impl AsRef<Path>, out_dir: impl AsRef<Path>, mode: NativeWriteMode) -> Result<NativeWriteResult>;
#[cfg(feature = "lance")]
pub async fn write_from_lance_with_options(.., options: NativeWriteOptions) -> Result<NativeWriteResult>;

// Minimal, deliberately non-production round-trip reader (ipc_cache::
// read_row_group over every manifest segment) for THIS module's own
// tests and the `load-native --query` CLI validation path only -- NOT a
// TableProvider (that's native_table.rs, task 004, not touched here).
pub fn read_back(dir: &Path) -> Result<(SchemaRef, Vec<RecordBatch>)>;
```

### Behavioral contract (what 004/006/008 can rely on without reading source)

- **Streaming, bounded memory**: peak memory is bounded by ONE segment's
  worth of buffered rows (default 1,000,000), never by the size of the
  source or the whole stream. Measured, not just designed-for: converting
  `data/tpch-10gb/lineitem.parquet` (60,000,000 rows, 2.8GB compressed)
  peaked at **415,428 KB (~406 MB) RSS** (`/usr/bin/time -v`), in 12.28s,
  producing 58 segments / 5.3GB on disk.
- **Per-segment statistics computed once, from the in-memory batch, right
  before writing it** — never a second pass over the written file
  (`native_manifest::compute_batch_stats` called on the same
  already-buffered/coerced batch that gets written).
- **Dictionary encoding is decided ONCE, from the first segment actually
  flushed, and applied UNIFORMLY to every later segment** — not
  re-decided per segment (a deliberate difference from `ipc_cache.rs`,
  forced by the manifest declaring one Arrow type per column for the
  whole table). Candidates are plain `Utf8` columns only (not
  `LargeUtf8`/`Binary`, mirroring `ipc_cache.rs`); a column is kept
  dictionary-encoded if its first segment's dictionary has
  `<= NativeWriteOptions::dict_max_cardinality` (4096 default) distinct
  values.
- **Segment file naming**: every segment is written via
  `native_manifest::segment_full_path(staging_dir, id)` /
  `Segment::expected_file_name(id)` — task 002's contract, never an
  invented name. `NativeManifest::build`'s own internal `validate()` call
  would refuse a mismatch, so this cannot silently drift.
- **Mode safety**: `Create` refuses an existing destination outright.
  `Overwrite` refuses (rather than silently deleting, which
  `native_manifest::publish_table_dir` would otherwise do unconditionally)
  a destination that exists, is non-empty, and is NOT already a native
  table — an intentional hardening beyond the literal spec, to protect
  against a wrong `--out` path. Every error path leaves the destination
  directory completely untouched (writes go to a staging directory first,
  published atomically only on full success).
- **Zero rows is a refusal, not an empty table**: if the total row count
  across the whole stream is zero (empty stream, or a stream of only
  zero-row batches), `write_batches` returns
  `Err(QueryError::Storage(..))` naming it, and leaves no directory
  behind — mirrors `lance_write::write_batches`'s own "the source
  produced no rows" guard.
- **CLI**: `write-native --from-parquet|--from-iceberg|--from-lance|--sql
  <query> --tables <dir> --out <dir> --mode create|overwrite`;
  `load-native --path <dir> [--query <sql>]`. The `--sql` arm proves the
  CTAS-shaped streaming path end-to-end today (physical plan -> merged
  partition streams -> `write_batches`, never through `ctx.sql()`) and
  additionally strips qualified column names from a bare `SELECT *`'s
  physical schema (a pre-existing binder property, not this task's bug —
  see below) before they reach the writer.

### No gap found in task 002's manifest schema

Everything task 002 documented in its Outcome section (`Segment`/
`ColumnStats` shape, `segment_full_path`/`expected_file_name` naming
contract, `compute_batch_stats`/`merge_stats_into` as the streaming
accumulation building blocks, `staging_dir_for`/`publish_table_dir` for

task with no workarounds and no changes to `native_manifest.rs`. The one

dictionary-candidate detection without parquet column-chunk metadata —
is resolved by this task's "decide once from the first segment, lock it
in" design (see above), which is a genuine, documented, and tested
difference in approach from `ipc_cache.rs::build_sidecar`, not a gap.

### A real, pre-existing engine property found during cross-task
### validation (not a bug in this task, flagged for anyone touching
### `--sql`-shaped write paths later)

A bare `SELECT *`'s physical-plan schema carries QUALIFIED field names
("orders.o_orderkey", not "o_orderkey") — `SelectItem::Wildcard`
preserves `field.relation` in the binder, unlike an explicit column list.
Found by impl-nt-004-provider validating their own `CREATE TABLE ... AS
SELECT` path against this task's `write_batches`; also latent in
`write-lance --sql` (out of scope to fix there). Fixed narrowly in THIS
task's own `write-native --sql` CLI arm only (`unqualified_schema()` in
`main.rs`, applied to both the declared schema and every streamed
batch's schema before they reach `write_batches`) — `native_write.rs`
itself is and should stay agnostic to this; it writes whatever
schema/stream it is handed, faithfully.
