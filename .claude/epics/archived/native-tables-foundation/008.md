## Outcome (2026-08-23)

Full validation/docs close-out of the `native-tables-foundation` epic.
**One real regression found and fixed** (not assumed away): a
concurrency bug in the shared `HashJoinExec` "emit unmatched build rows"
mechanism — `SpillableHashAggregateExec::execute_fused_streaming` can
drive its child through its full partition range, abandon the attempt
after a group-count budget trips, and fall through to a SECOND full
execution of the same child; the shared completion counter only ever
fires the unmatched-row emission on the first such round. Reproduced
concretely as TPC-H Q13 against native tables at SF=10 losing its
"customers with zero orders" bucket (23 rows instead of 24) — the exact
symptom a DIFFERENT, earlier fix (`tests/spill_tests.rs::
left_join_unmatched_build_rows_preserved`) already fixed once for a
different trigger (multi-PARTITION drops, not multi-ROUND). Root-caused
with a live `gdb` thread dump and `[unmatched-debug]` instrumentation,
fixed with a one-line change (`done == target` → `done % target == 0`,
`src/physical/operators/hash_join.rs`), and pinned with a new
deterministic unit test that fails without the fix and passes with it.
Not native-table-specific — a latent bug in shared, general-purpose join
code that native tables happened to be the first to expose (their lack
of scan-level pruning makes them more likely to trip the aggregate's
spill-then-fallback path at realistic scale).

Full suite green in **all four feature combinations**: default 1061/0/1,
lance 1126/0/2, gpu 1061/0/1, pulsar 1064/0/1 (passed/failed/ignored —
zero failures; lance and pulsar's FULL suites ran for real here, not just
`cargo check`, closing task 005's explicitly deferred verification).
`cargo fmt --all -- --check` clean. M1 + M2 distributed gates PASS via
real 3-separate-process clusters (`scripts/cluster_local.sh verify` /
`verify-m2`), confirming this epic broke nothing for parquet/Iceberg/
Lance distributed behavior.

**SF=10**: 22/22 cell-exact (post-fix) vs the DuckDB-parquet oracle.
Engine 5.324s vs DuckDB-parquet 4.321s (1.23x) vs DuckDB-iceberg 6.888s
(**0.77x — engine faster**). **SF=100**: 19/22 cell-exact + successful;
3 queries (Q4, Q12, Q13) hit the SAME documented root cause (native
tables have no scan-level row-group/zone-map pruning yet, so their
post-filter join inputs are larger, which at large-enough scale crosses
`SpillableHashJoinExec`'s spill threshold — a pre-existing, separately-
scoped operator limitation, not something this epic introduced) — always
a safe refusal or a slow-but-correct completion, never a wrong answer.
Engine 75.17s vs DuckDB-parquet 50.02s (1.50x) on the 19 completing
queries. Disk footprint smaller than the parquet source at both scales
(SF=10 6.5GB vs 9.6GB; SF=100 65GB vs 97GB).

**CPU/GPU split found something genuinely new**: unlike every prior
GPU-offload measurement in this program (all parquet-sourced, all
showing NO full-query win because scan/decode dominates), native tables'
simplest GPU-eligible shape (Q6: one ungrouped SUM) shows a real,
reproducible **~18-20x end-to-end win** (CPU ~140ms vs GPU warm ~7-8ms),
because a native table has no decode step to dominate wall time —
confirmed via VRAM growth (1048→3858 MiB, RTX 5090), not assumed. Q1
(multi-aggregate + GROUP BY) stays flat, matching the parquet-sourced
finding for that same shape. Found and worked around (not fixed, out of
scope) two real CLI gaps along the way: `load-native --query` neither
enables GPU offload nor registers a real `NativeTable` (it materializes
through `native_write::read_back` into a plain `MemoryTable`); a new
permanent diagnostic (`examples/native_gpu_check.rs`) exercises the real
path directly instead.

All five epic success criteria (G1-G5): **G1, G3, G4, G5 MET**; **G2
partially met** (SF=10 1.23x is at/better than the ~1.3x IPC-sidecar
baseline; SF=100 1.50x is worse than the 1.21x historical baseline,
directly attributable to the same documented scan-pruning gap) — full
accounting, evidence, and the complete residues/deferred-work list are
in `epic.md`'s close-out section. CLAUDE.md gained a full "Native Tables"
section (format, write path, SQL DDL boundary, registration, dense-
direct fast path, memory safety, GPU eligibility, limitations,
benchmarks) plus a CPU/GPU-split addendum to the existing GPU Aggregate
Offload section. Epic moved to
`.claude/epics/archived/native-tables-foundation/` as this task's last
step, mirroring `duckdb-parity-2`/`dependency-modernization`'s archival
pattern. Full process detail, including every intermediate measurement,

documented spill-path residue, and the build-sequencing discipline used
