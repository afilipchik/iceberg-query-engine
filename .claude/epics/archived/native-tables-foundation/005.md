# Task: Dense-direct-address fast-path compatibility

## Description

`src/physical/operators/morsel_agg.rs::try_execute_dense_direct` — the
engine's fastest aggregation path (the one that gets Q18-class queries to
their documented ~187ms/15M-groups floor) — currently reads key-range
bounds from parquet file footers specifically (opens a
`SerializedFileReader` per file to get them). A native table has no
parquet footer once standalone. Without this task, native tables would
silently never take this fast path even when their data shape qualifies
— a real performance regression relative to querying the same data as
parquet, not just a missed opportunity, and directly counter to this
epic's G4 success criterion.

## Technical Details

- **Confirmed by task 001 (both functions read in full):**
  `disjoint_group_hint` (`src/physical/planner.rs`, currently lines
  384-412) is ALREADY provider-agnostic — it reads bounds via
  `provider.statistics()?.column_stats.get(&name)?.{min_i64,max_i64}`,
  the same generic `TableProvider::statistics()` API every provider
  (including Lance, which has no parquet footer either) already
  implements. It needs ZERO changes once task 002's manifest populates
  `TableStatistics` correctly (task 004's job) — this task's entire real
  scope is inside `try_execute_dense_direct`.
- `try_execute_dense_direct` (`src/physical/operators/morsel_agg.rs`,
  currently lines ~392-493) is the ONLY piece with the footer dependency.
  It holds `files: Vec<PathBuf>` (populated by `try_extract_parquet_
  source` and passed into `MorselAggregateExec::new(...)` at
  `src/physical/planner.rs` around line 1084) and, for the key bounds
  specifically (lines ~451-485), opens each file directly via
  `parquet::file::reader::SerializedFileReader` and reads
  `parquet::file::statistics::Statistics::Int64/Int32` per row group.
  **The fix**: thread the already-resolved `TableProvider` (or its
  pre-fetched `TableStatistics`) into `MorselAggregateExec` alongside or
  instead of `files`, and replace that block with the SAME
  `column_stats[key_name].{min_i64,max_i64}` lookup
  `disjoint_group_hint` already uses — bringing this function in line
  with a pattern that already exists in this codebase rather than
  inventing a new statistics-consumption shape. Needs the TABLE-LEVEL
  rollup (one min/max pair for the whole table), not per-segment stats —
  task 002's manifest provides both (see `002.md`), but this task only
  consumes the rollup.
- `src/physical/planner.rs` — `disjoint_group_hint` (see above, no
  changes needed) and `lower_aggregate_cpu`/`try_extract_parquet_source`
  (the call site that constructs `MorselAggregateExec` and will need to
  also supply a native-table provider's stats) — recently modified by
  the `duckdb-parity-2` epic; read that epic's archived task 002 for
  additional context on recent changes in this area.

## Outcome (closed 2026-08-23)

Implemented in full, committed `baf9e15` ("Task 005: generalize dense-
direct-address fast path for native tables"). Everything below is precise
enough that task 008 should not need to read this task's source.

### The real scope was bigger than the task file's own framing

Task 004's Outcome (written before this task started) said "your entire
real scope is inside `try_execute_dense_direct`... for the key bounds
specifically." Reading the function in full (not just the cited lines)
found a SECOND, equally load-bearing dependency the task file didn't name:
the scan+accumulate loop itself drives a `ParallelParquetSource` over
`self.files: Vec<PathBuf>` — a native table has no parquet files backing
its segments (they're Arrow IPC, read via `ipc_cache::read_row_group`), so
fixing only the bounds computation would have left the function permanently
unreachable for native tables (`MorselAggregateExec` is only ever
CONSTRUCTED when `try_extract_parquet_source` matches, which requires
`provider.parquet_files().is_some()` — always `None` for `NativeTable` by
design). Both dependencies needed fixing for G4 to actually hold.

### `TableProvider::as_any()` (new required trait method)

`src/physical/operators/scan.rs` — a type-erased downcast escape hatch, one
line added to all 6 implementors (`MemoryTable`, `ParquetTable`,
`LanceTable`, `PulsarTable`, `ShardedParquetTable`, `NativeTable`). Exists
so the planner can recognize a `NativeTable` specifically for dense-direct
routing WITHOUT widening the fast path to every non-Parquet provider —
Lance was investigated and explicitly rejected for this exact fast path
(see CLAUDE.md's "Tried, measured, REJECTED" table on morsel-driven
aggregation), so a shared capability method on the trait itself would have
been the wrong shape. `cargo check` confirmed clean on default +
`--features lance` + `--features pulsar` + `--features gpu` — the two
feature-gated implementors needed the same one-liner and got it.

### `MorselAggregateExec` (`src/physical/operators/morsel_agg.rs`)

- New `native_provider: Option<Arc<dyn TableProvider>>` field ALONGSIDE the
  existing `files: Vec<PathBuf>` (stays empty in native mode) — the task
  file's own suggested "alongside or instead of files" wording, chosen
  specifically to keep the parquet code path's own lines completely
  untouched (verified by diffing before/after: byte-for-byte identical,
  just moved into an `else` branch) — the strongest available guarantee
  against regressing it.
- Extracted three source-agnostic free functions from what was previously
  one large inline block: `dense_direct_shape` (group-by/aggregate-kind
  eligibility — was ALREADY source-agnostic logic, just inline),
  `dense_direct_key_bounds` (the `column_stats[key].{min_i64,max_i64}`
  lookup `disjoint_group_hint` already uses, width-capped at 64,000,000
  the same way the parquet footer loop always was), and
  `accumulate_dense_batch` (the per-batch accumulation body, now called
  identically by both branches instead of duplicated).
- Native branch: `dense_direct_key_bounds` for bounds,
  `provider.scan_with_filter(...)` for data (one call — `NativeTable::
  scan()` already reads every segment via the same mmap-backed
  `ipc_cache::read_row_group` the parquet IPC sidecar cache uses),
  `rayon::par_iter()` over the returned batches for parallel accumulation
  (simpler than the parquet branch's row-group work-stealing queue since
  there's no lazy per-row-group I/O scheduling to gain from — the batches
  are already all in hand).
- `execute()`: if a native-mode instance ever reaches past
  `try_execute_dense_direct` returning `None` (should be structurally
  unreachable — see below), it returns a clear `QueryError::Execution`
  rather than falling through to the parquet-only generic tier over an
  empty file list, which would have silently produced zero rows. Never
  observed to actually fire; it's a safety net, not a real code path.

### Planner routing (`src/physical/planner.rs`)

New `try_extract_native_dense_source` (mirrors `try_extract_parquet_
source`): matches `Scan`/`Project(Scan)` only (no `Filter` arm — a
scan-level filter is refused by name, since `NativeTable::scan_with_
filter` has no pushdown at all and `try_execute_dense_direct` never
re-evaluates one; accepting a filtered native scan here would have
silently aggregated unfiltered rows), and only matches a provider that
downcasts to `NativeTable` via the new `as_any()`.

`lower_aggregate_cpu` tries it as an `else if` after the existing parquet
extractor, then — critically — RE-VALIDATES full eligibility via
`dense_direct_shape` + `dense_direct_key_bounds` (the exact same functions
`try_execute_dense_direct` itself calls) BEFORE constructing a native-mode
`MorselAggregateExec`. This two-gate design (planner pre-check + executor
re-check, sharing code rather than duplicating logic) is why the
`execute()` safety net above is unreachable in practice: a native-mode
instance is only ever created when the planner has already proven the
executor will accept it.

### Statistics: task 002/004's manifest needed ZERO extension

`dense_direct_key_bounds` only ever needs `min_i64`/`max_i64` for the
single group-by column. `NativeTable::statistics()` (task 004) already
populates `ColumnStatistics.min_i64`/`max_i64` directly from task 002's
manifest rollup, field-for-field identical to `ParquetTable`/`LanceTable`'s
shape — confirmed by task 004's own Outcome and re-confirmed here by using
it directly with no format change. `disjoint_group_hint` needed literally
zero code changes, exactly as task 001 predicted.

### Real measurement (not assumption) — `examples/native_dense_direct_check.rs`

SF=1 `data/tpch-1gb/lineitem.parquet` (6,000,000 rows) written to a native
table projected to `(l_orderkey, l_quantity)` (6 segments), then `GROUP BY
l_orderkey` (TPC-H Q18's own group key) with `COUNT(*)`/`SUM(l_quantity)`
run against both the native copy and the parquet source in the SAME
process, `AGG_TIMING=1`:

```
[AGG_TIMING] dense-direct scan+accumulate: 33.5ms (key=l_orderkey, width=1498929, aggs=2, files=1, threads=6, projection=Some([0, 4]), filter_pushed=false)
parquet source (lineitem_src   ):  1498929 groups in 41.7ms

[AGG_TIMING] dense-direct scan+accumulate (native): 6.1ms (key=l_orderkey, width=1498929, aggs=2, batches=95, projection=None)
native table   (lineitem_native):  1498929 groups in 12.9ms
```

The `(native)` tag is the direct evidence the native leg took the new
dense-direct branch, not a fallback. The untagged parquet line is the
SAME, unmodified message format the fast path has always printed — proof
of no regression in the same run. Both legs agree on group count exactly
(1,498,929) — a correctness cross-check beyond the dedicated cell-exact
tests. **G4 (this epic's own success criterion — "`try_execute_dense_
direct` fires for native tables exactly as it does for parquet tables of
equivalent shape") is met, with evidence, not assumed.**

### Cell-exact tests added (`tests/native_table_validation.rs`)

Two new tests, both passing (file total 10 -> 12, all green):
- `native_table_matches_source_on_a_dense_direct_group_by_cell_exact` —
  `GROUP BY o_orderkey` (the orders PK — dense-direct-eligible shape:
  single Int64 column, plain COUNT/SUM/AVG) — cell-exact vs the parquet
  source. Also indirectly proves routing didn't silently fall through to
  the native-mode error path: either wrong routing OR wrong numbers would
  fail this test, one as a mismatch, the other as a panic from `.expect()`
  on the propagated `Err`.
- `native_table_matches_source_on_a_filtered_group_by_cell_exact` —
  otherwise-identical shape but with a `WHERE` clause, pinning that a
  filtered GROUP BY correctly stays OFF the no-fallback native dense-direct
  path (via `try_extract_native_dense_source`'s filter refusal) and keeps
  using the ordinary generic aggregate tier unchanged.
