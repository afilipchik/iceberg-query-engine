# Task: Attribution spike — SQL DDL lift size + statistics/manifest format decision

## Description

This epic's Architecture Decisions are explicit that two things must be
decided by measurement/investigation, not assumption, before any other
task starts: (1) whether `CREATE TABLE ... AS SELECT` SQL DDL is a small
enough lift to build now, or whether a CLI-only bulk-load surface
(mirroring `write-lance`/`load-lance` in `src/main.rs`) should ship first
as the safe minimum with SQL DDL as a fast-follow; (2) the exact shape of
the table-owned manifest (schema + segment layout + per-segment min/max
statistics) that every downstream task depends on. This mirrors every
completed epic in this program's "microbenchmark or attribution spike
first" discipline — the whole epic's shape depends on this task's answers.

### Decision 1 — SQL DDL scope: BUILD `CREATE TABLE ... AS SELECT` in this epic (S, ~8-16h), attached to tasks 003+004; not deferred to CLI-only-first

**Evidence:**

- Re-read `src/planner/binder.rs::Binder::bind()` (lines 172-180) in
  full. Confirmed unchanged from the prior session's finding: it matches
  only `Statement::Query`; every other AST variant falls through to
  `Err(QueryError::NotImplemented(format!("Statement type not
  supported: {:?}", stmt)))`. Zero DDL/DML handling exists anywhere in
  this ~4480-line file today.
- Ran a throwaway spike (`.scratch/sqlparser_spike/`, its own tiny
  `Cargo.toml` pinning `sqlparser = "0.62"` — the exact version this
  repo pins, confirmed via `Cargo.toml:19` and the
  `dependency-modernization` epic; gitignored, never touched `src/`,
  removed before commit) that parses SQL through the SAME
  `sqlparser::dialect::GenericDialect` this engine's own
  `src/parser/mod.rs::parse_sql` uses. Actual output:
  - `CREATE TABLE t AS SELECT a, b FROM src WHERE a > 10` parses to
    `Statement::CreateTable { name: "t", query: Some(Box<Query>), .. }`.
  - `CREATE TABLE t AS SELECT a, COUNT(*) FROM src JOIN other ON
    src.id = other.id GROUP BY a` (join + aggregate) parses cleanly to
    the same shape — the `query` field carries the FULL `Query` AST,
    not a restricted subset.
  - `INSERT INTO t SELECT a, b FROM src WHERE a > 10` parses to
    `Statement::Insert { table: ..., source: Some(Box<Query>), .. }`.
  - `CREATE TABLE t (a INT, b VARCHAR(50))` (columns-only, no `AS
    SELECT`) parses too, with `query: None` — the "define an empty
    table's schema, populate later via INSERT" shape.
  - `CREATE TABLE t (a, b) AS SELECT ...` (explicit column list
    combined with `AS`) does NOT parse under `GenericDialect`
    ("Expected: a data type name, found: ,") — irrelevant, since the
    no-column-list CTAS form is both what parses and the form every
    reference engine (DuckDB, Postgres) treats as canonical.
  - `DROP TABLE t` parses too, as its own `Drop` variant (not needed by
    this epic's full-replace-only semantics, noted for completeness).
  - **The load-bearing fact**: `CreateTable.query` and `Insert.source`
    are both literally `Box<Query>` — the IDENTICAL AST type
    `Binder::bind_query()` already fully handles (CTEs, joins,
    subqueries, window functions, set operations, GROUPING SETS, all
    proven by the join+aggregate CTAS parsing cleanly above). sqlparser
    does 100% of the grammar work already; nothing new is needed at the
    parser layer, and the "does sqlparser already parse this" half of
    the task's central question is answered definitively: yes.
  - Verified struct definitions directly in the pinned crate source
    (`~/.cargo/registry/.../sqlparser-0.62.0/src/ast/ddl.rs` for
    `CreateTable`, `src/ast/dml.rs` for `Insert`) to confirm the field
    types before writing the spike, then confirmed with real parse
    output rather than relying on the struct definitions alone.
- Traced the engine's own existing "run a SELECT, get batches, write
  them out as a new table" precedent, since it is the closest thing to
  CTAS that already ships: `write-lance --sql <query> --tables <dir>
  --out <path>` (`src/main.rs`, `Commands::WriteLance`, the `(None,
  Some(query))` arm, ~lines 781-820) calls `ctx.sql(&query).await` and
  then `lance_write::write_batches(r.batches, r.schema, &out, mode)`.
  This is CLI-level orchestration entirely OUTSIDE the
  binder/LogicalPlan/PhysicalOperator layers — direct proof that "parse
  a plain SELECT through the existing pipeline, then hand its result to
  an existing writer" needs no new plan-node machinery to work at all.
- **A real gap found while tracing that precedent, flagged for tasks
  003/006 (propagated into their files), not a reason to avoid the SQL
  surface**: `ExecutionContext::sql()` (`src/execution/context.rs`,
  read in full ~lines 301-420) FULLY MATERIALIZES the query result —
  every partition's `RecordBatchStream` is `try_collect()`-ed into
  `Vec<RecordBatch>` before `QueryResult` is returned. So `write-lance
  --sql` is CTAS-SHAPED but NOT actually streaming, despite
  `lance_write.rs`'s own doc comment claiming this exact pattern is
  "the path a `CREATE TABLE ... AS SELECT` takes" — an unbounded CTAS
  source would be held entirely in RAM before a single byte is written.
  This directly conflicts with this epic's own Architecture Decision
  ("Write path modeled on `lance_write.rs`... streaming-without-
  double-materializing") and CLAUDE.md's unconditional memory-safety
  rule. The fix is straightforward (drive `PhysicalOperator::
  execute()`'s stream directly into the writer instead of routing
  through `sql()`'s collecting wrapper) but must be a deliberate choice
  in task 003, not an accidental inheritance from copying the CLI
  precedent verbatim.

**Sizing** (S, ~8-16h, contingent on task 003's write-path entrypoint
already existing — this is why it attaches to tasks 003/004, not to
this task):
- Binder: one new `Statement::CreateTable` match arm, binding `ct.query`
  via the already-existing `bind_query()` and refusing (by name) the
  ~25 other `CreateTable` struct fields this epic doesn't support —
  mirrors dozens of existing "match the supported shape, `NotImplemented`
  the rest" blocks already in this binder (window functions, GROUPING
  SETS, join types, etc.). ~2-4h.
- A new `ExecutionContext` DDL entrypoint: needs `&mut self` (unlike
  `sql()`'s current `&self`, since registering the new table mutates
  `self.tables`) and must drive the SELECT's stream directly into task
  003's writer rather than materializing first (see the gap above).
  ~3-6h.
- Wiring into REPL/CLI/`/sql` HTTP: falls out mostly free since all
  three already funnel through `ExecutionContext`. ~2-4h.

**Recommendation**: build the SQL DDL surface within this epic. The
lift is small relative to the storage-format work (002 alone is M-L,
16-32h), grammar/parsing is a fully solved non-issue (proven above),
and a CLI-only path is not meaningfully cheaper or lower-risk than the
SQL surface once task 003's writer exists — both ultimately call the
same entrypoint. Both still ship, though: a `write-native`/`load-native`
CLI command (mirroring `write-lance`/`load-lance`) is attached to task
003 itself as its own natural integration-test harness AND as the
epic's safe-minimum fallback if the SQL-surface work (attached to task
004, since registration is what CTAS needs beyond a raw writer) slips.
Explicitly OUT of scope, confirmed parseable but deliberately not
wired: `Statement::Insert` handling (mutation, phase 2 per the PRD) and
the columns-only `CREATE TABLE` form (would need a later `INSERT` to
populate — also phase 2).

**Propagated to**: `003.md` (module name, CLI command as a new
Acceptance Criteria bullet, the streaming-vs-materializing warning),
`004.md` (binder wiring detail, new `ExecutionContext` entrypoint, a new
Acceptance Criteria bullet for the end-to-end `CREATE TABLE AS SELECT`
path), `006.md` (the materialize-then-write gap as a concrete thing to
verify task 003 avoided), `008.md` (a reminder to validate whichever
surface actually shipped).

### Decision 2 — Manifest/statistics format: a JSON sidecar (`_manifest.json`), NOT an Arrow IPC/Parquet manifest table, NOT Iceberg's own Avro format

**Segments themselves are not in question** — the epic's own Architecture
Decisions already fix that: Arrow IPC, mmap zero-copy, dictionary-coerced,
unchanged from today's sidecar. This decision is about the METADATA
layer only (schema, segment list, per-segment stats, version marker).

**Evidence considered, weighing the real tradeoffs (not just a
preference):**

- **Option A — JSON sidecar (chosen).** `serde`/`serde_json` are already
  dependencies, and already used for exactly this "table-level metadata
  describing a versioned snapshot" job in this exact codebase:
  `src/storage/iceberg.rs`'s `TableMetadata`/`Snapshot` structs
  deserialize Iceberg's `*.metadata.json` via `#[derive(Deserialize)]`
  with `#[serde(default)]` for optional/evolvable fields. Pros: near-
  zero new-dependency risk (reuses a pattern already proven in this
  repo); human-readable/greppable, matching this project's demonstrated
  preference for hand-inspectable metadata (CLAUDE.md documents `cat`/
  `jq`-style inspection idioms repeatedly); trivial schema evolution
  (`#[serde(default)]`, same as `iceberg.rs` already does); corruption
  is a clean, loud JSON-parse error, trivially satisfying task 002's "a
  corrupted/partial manifest is a clear error not a panic" criterion;
  the atomic staging-dir-then-rename publication pattern already proven
  by `ipc_cache.rs::build_sidecar` generalizes to "manifest + segments
  together," so no new concurrency-safety mechanism is needed either.
  Con (the one the task explicitly named): not zero-copy/mmap-friendly
  for reading the manifest itself — real in principle, but the manifest
  is metadata (KBs to low MBs even for a table with thousands of
  segments), read ONCE at table-open time, never on the per-row hot
  path — a JSON parse of a small file costs microseconds against a
  table whose segment DATA can be gigabytes, so this con doesn't
  materialize at any size this manifest will actually reach.
- **Option B — small Arrow IPC/Parquet manifest table.** Pro: reuses the
  existing fast-read machinery. Con, and why it's the wrong tool for
  THIS job specifically: that machinery's value is amortizing decode
  cost over LARGE data, and a manifest is inherently small, so the win
  doesn't materialize while the costs are immediate and real — flattening
  a nested "per-segment, per-column min/max" structure into columnar
  rows is genuinely more code than `serde_json::from_str`, schema
  evolution is much harder than an optional JSON field, and
  debuggability regresses (no longer human-inspectable without the
  engine's own tooling or pyarrow) exactly where this codebase's
  existing Iceberg/JSON metadata handling optimizes for hand-inspection.
  This would be the right call for the segment DATA itself, which is
  exactly why segments already stay Arrow IPC — it is not the right
  call for small structured metadata.
- **Option C — reuse Iceberg's own Avro manifest format directly.** Pro:
  reuses `iceberg.rs`'s existing Avro parsing code
  (`avro_records`/`field_str`/`field_i32`/`resolve_uri`). Con, and why
  it's rejected: it couples this feature to Iceberg's FULL semantic
  model — partition specs, sort orders, snapshot parent/child lineage,
  sequence numbers, field-id-based (not name-based) schema evolution, a
  manifest-LIST pointing at multiple manifest FILES with
  status/content-based row-level-delete tracking — almost none of which
  this epic needs (no mutation, no partitioning, no row-level deletes,
  full-replace-only semantics; the epic's own text says the table "has
  no parquet footer once standalone" and wants a DECOUPLED identity
  model, which sits awkwardly inside Iceberg's snapshot-lineage
  machinery). Iceberg's actual per-file statistics
  (`data_file.lower_bounds`/`upper_bounds`, maps keyed by field-id to
  serialized bytes) aren't a simple min/max pair either — genuinely
  reusing the FORMAT (not just "a file shaped like a manifest") would
  mean re-implementing a large fraction of the Iceberg spec, which is
  MORE work than the JSON option, not less; a "shaped like Avro but not
  spec-compliant" middle ground gets none of the real reuse benefit
  while keeping Avro's binary-format debuggability cost. The epic's own
  Architecture Decision text says the Iceberg metadata/manifest/
  snapshot STRUCTURE is "the closest existing precedent," not that its
  wire format must be adopted — Option A mirrors that STRUCTURE
  (version/snapshot marker + segment list + per-segment stats) exactly,
  without the semantic baggage or serialization cost.

**Concrete schema** (starting point for task 002's implementation, not
gospel — see `002.md`'s Technical Details for the full version):
`_manifest.json` per table directory holding `format_version`,
`table_id` (stable identity generated at creation — NOT derived from
any source file's path/mtime/size), `schema` (Arrow field
names/types/nullability), `snapshot: { version, row_count,
created_at_ms }` (the marker task 003 bumps on replace and task 007
hashes for GPU-cache identity), and `segments: [{ id, path, row_count,
byte_size, column_stats }]` where `column_stats` reuses
`src/physical/operators/scan.rs`'s existing `ColumnStatistics` shape
(`min_i64`/`max_i64`/`null_count`/etc.) field-for-field, plus a
table-level rollup of the same shape computed once at write time so
`TableProvider::statistics()` is an O(1) lookup.

**Read-mechanism reuse, confirmed concretely, not just asserted**:
`src/storage/ipc_cache.rs::read_row_group(dir: &Path, rg_idx: usize,
projection, slice)` and `sidecar_dict_cols(dir: &Path)` are ALREADY
`pub fn` and ALREADY parameterized purely by directory + segment
index — verified by reading the full function bodies — with zero
dependency on parquet-shadowing anywhere inside them. Task 004's
provider can call these UNCHANGED. What is genuinely NOT reusable:
`sidecar_dir()`/`is_fresh()`/`stamp_value()` (parquet-mtime-shadowing-
specific — exactly what this epic replaces) and `build_sidecar`'s
dictionary-coercion detection (reads PARQUET column-chunk metadata,
which a native table's arbitrary `RecordBatch` sources don't carry —
task 003 needs an Arrow-side equivalent, detailed in `002.md`/`003.md`).

**Propagated to**: `002.md` (full schema, module name, exact reusable/

### Decision 3 — Module layout: a NEW module, split into three sibling files under `src/storage/`, not a single flat file, not evolving `ipc_cache.rs` in place

**Evidence:**

- The epic's own Architecture Decisions are explicit that `ipc_cache.rs`
  is reused WHOLESALE, not touched: "Reuse the sidecar's proven read
  mechanism wholesale; don't reinvent it... This epic's job is
  identity/lifecycle and the write path, not the read path." Confirmed
  by reading `ipc_cache.rs` in full (549 lines): its own module doc
  frames it explicitly as a "read-through CACHE... tied to shadowing a
  specific parquet file's path/mtime/size" — a genuinely different
  lifecycle from a first-class, independently-persistent table. Merging
  the two into one file would blur two different concepts in code that
  has three completed epics of hardening behind it, for no benefit —
  and task 002's own acceptance criteria already require the existing
  sidecar's tests to stay green throughout, which is easiest to
  guarantee by leaving the file untouched and only ADDING new sibling
  modules that call its already-`pub` functions.
- Precedent already in this exact codebase for exactly this kind of
  reader/writer file split: `src/storage/lance.rs` (reader/
  `TableProvider`) and `src/storage/lance_write.rs` (writer) are two
  separate flat sibling files under `src/storage/`, not one file and
  not a submodule directory. `src/storage/mod.rs` (read in full)
  confirms the whole module's existing convention is flat sibling
  files (`iceberg.rs`, `parquet.rs`, `lance.rs`, `lance_write.rs`,
  `ipc_cache.rs`, `metadata_cache.rs`, `pulsar.rs`) rather than
  directory-style submodules — matching that convention rather than
  introducing a new directory-module keeps this decision consistent
  with the rest of the codebase.
- Parallelism requirement, stated explicitly in the epic's own preview
  note and in tasks 003/004's own `depends_on`/`parallel: true`
  markers: "conflicts with 003 only if they touch the same new module
  — decide file layout in 001/002 to keep them separable." A single
  flat `native_table.rs` (the epic's own example name) holding
  manifest + write + provider code would force tasks 003 and 004 to
  edit the same file simultaneously, defeating their declared
  `parallel: true`. Splitting into three files, each owned by one task,
  resolves this directly.

**Decision**: three new sibling files under `src/storage/` (not a
`src/storage/native/` directory module — flat, matching the
`lance.rs`/`lance_write.rs` precedent):
- `src/storage/native_manifest.rs` — task 002. The manifest
  struct/serde/identity/versioning/atomic-publish logic. Everything
  else depends on this file; it is the one all three later tasks import.
- `src/storage/native_write.rs` — task 003. The write path
  (`write_batches`/`write_from_parquet`/`write_from_iceberg`/
  `write_from_lance`, mirroring `lance_write.rs`'s own naming exactly),
  calling into `native_manifest.rs` for the format.
- `src/storage/native_table.rs` — task 004. The `TableProvider`
  implementation (e.g. `NativeTable`) plus registration/auto-detection
  glue, calling into `native_manifest.rs` for the format and
  `ipc_cache.rs`'s existing `read_row_group`/`sidecar_dict_cols` for
  reads.

Tasks 003 and 004 therefore share zero files with each other and both
depend only on 002's `native_manifest.rs` — exactly the separability
the epic's preview note asked for, verified structurally rather than
assumed.
