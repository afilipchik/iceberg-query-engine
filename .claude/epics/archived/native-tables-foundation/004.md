# Task: TableProvider integration — splits, statistics, registration

## Description

Make a native table a real, first-class `TableProvider` the engine can
plan and execute queries against — today's IPC sidecar is a helper called
*from* `ParquetTable`, not a provider in its own right. This task gives
native tables their own provider implementation: `distributed_splits`/
`shard_by_splits` implemented for real (both default `None` today on any
provider that doesn't specifically implement them — meaning a native
table would silently be unshardable without this), `statistics()`
returning task 002's real zone-map data (not `None`), and registration
alongside parquet/Iceberg/Lance wherever tables get registered today
(`ExecutionContext`, `--tables` directory auto-detection, metastore
fileset `format` property).

## Acceptance Criteria

- [x] `TableProvider` trait implemented for the native table type:
      `scan`, `statistics()` (real min/max/row-count from task 002's
      manifest, not `None`), `distributed_splits`/`shard_by_splits` (real
      implementations — even a simple one, e.g. one split per segment, is
      fine for this epic; sophisticated split-sizing is not required, just
      "not silently absent").
- [x] Registration: a native table directory is auto-detected the same
      way Iceberg/Lance directories are today (`is_iceberg_dir`-style
      detection in `src/main.rs`'s `--tables` handling), and can be

- [x] Queries against a registered native table plan and execute

      filter it — exercising the normal physical planner, not a

- [x] Cell-exact validation: load a native table from an existing source

- [x] Full suite stays green; distributed M1/M2 gates unaffected (native

### CREATE TABLE syntax supported

`CREATE TABLE <name> AS SELECT <query>` — where `<query>` is ANY `Query`
this binder's existing `bind_query()` already handles (joins, aggregates,
subqueries, CTEs, window functions, set operations — the full surface,
confirmed by task 001's spike and unchanged since). No explicit column
list (`CREATE TABLE t (a, b) AS SELECT ...` does not parse under this
engine's `GenericDialect` anyway — confirmed by task 001, re-confirmed
here). `IF NOT EXISTS` is refused (not silently honored/ignored): this
epic's write semantics are always-replace, and IF NOT EXISTS's real
meaning — skip creation if the table exists — is not implemented.

**Refused by name, never silently ignored or downgraded** — mirrors this
binder's "match the supported shape, `NotImplemented` the rest"
convention: a columns-only `CREATE TABLE t (a INT, b VARCHAR)` (`query:
None` — no later `INSERT` in this epic to populate it), and all 57
non-`name`/`query` fields of sqlparser 0.62's `CreateTable` struct —
`or_replace`, `temporary`, `external`, `dynamic`, `global`,
`if_not_exists`, `transient`, `volatile`, `iceberg`, `snapshot`, an
explicit `columns` list, `constraints`, `hive_distribution`,
`hive_formats`, `table_options`, `file_format`, `location`,
`without_rowid`, `like`, `clone`, `version`, `comment`, `on_commit`,
`on_cluster`, `primary_key`, `order_by`, `partition_by`, `cluster_by`,
`clustered_by`, `inherits`, `partition_of`, `for_values`, `strict`,
`copy_grants`, `enable_schema_evolution`, `change_tracking`,
`data_retention_time_in_days`, `max_data_extension_time_in_days`,
`default_ddl_collation`, `with_aggregation_policy`,
`with_row_access_policy`, `with_storage_lifecycle_policy`, `with_tags`,
`external_volume`, `base_location`, `catalog`, `catalog_sync`,
`storage_serialization_policy`, `target_lag`, `warehouse`,
`refresh_mode`, `initialize`, `require_user`, `diststyle`, `distkey`,
`sortkey`, `backup`. This list was mechanically verified exhaustive
against the actual `sqlparser::ast::CreateTable` struct definition (57
fields extracted from the crate source, 57 checked in

### Where it's wired

- **Binder** (`src/planner/binder.rs`): `Statement::CreateTable` arm in
  `Binder::bind()`, `require_supported_create_table_shape()`,
  `create_table_target_name()` (public, name-extraction only — validation
  stays solely inside `bind()`).
- **ExecutionContext** (`src/execution/context.rs`): `pub async fn
  create_table_as_select(&mut self, sql: &str) ->
  Result<CreateTableAsSelectResult>` — a NEW method, deliberately NOT a
  change to `sql()` (which takes `&self` and cannot register a table, and
  fully materializes results — see task 001/003's Technical Details for
  why that gap is real). `sql()` itself now explicitly refuses a `CREATE
  TABLE` statement with a message pointing at `create_table_as_select`,
  closing a silent-wrong-behavior trap the new binder arm would otherwise
  open (bind+run just the inner SELECT, return its rows, write and
  register nothing, no error). `CreateTableAsSelectResult { table_name,
  table_id, version, rows, segments, schema, elapsed }`.
- **Write destination**: `ExecutionContext.native_table_root: PathBuf`
  (new field, default `./native_tables`, override via
  `with_native_table_root`) — CTAS has no SQL-level LOCATION clause (it's
  in the refused-fields list above), so the destination is
  `native_table_root.join(<name>)`, decided by context state, not by
  parsing. Tests/CLI point this wherever they like; the REPL's zero-config
  default just uses it as-is.
- **REPL** (`src/main.rs`): `run_repl`'s SQL dispatch parses once, routes
  a `CREATE TABLE` to `create_table_as_select` (prints table_name/rows/
  segments/version), everything else to `sql()` unchanged.
- **`--tables` auto-detection** (`src/main.rs::build_serve_context`): a
  native table directory (`_manifest.json` present) is detected and
  registered alongside Iceberg/Lance, structurally disjoint from both so
  detection order among the three doesn't matter (unlike Iceberg-vs-
  parquet-dir, which IS order-sensitive for a pre-existing reason
  unrelated to this task).
- **NOT wired**: the distributed HTTP `/sql` endpoint
  (`src/distributed/server.rs`) — out of this task's file scope by
  explicit instruction, and untouched. A `CREATE TABLE` sent there today
  reaches the SAME `sql()` guard described above and gets a clear, named
  refusal (safe: no silent partial-execution), not new DDL support. Wiring
  that endpoint (and the Arrow Flight equivalent) is unclaimed follow-up
  work for whoever next touches `distributed/server.rs`.

### `TableProvider` implementation (`src/storage/native_table.rs`, new file)

`NativeTable { dir, manifest, only_segments: Option<HashSet<u32>> }` —
the same struct represents both a whole-table provider (`only_segments:
None`) and a distributed shard (`Some(ids)`), differing only in which
methods filter by it.

- `schema()`: `manifest.arrow_schema()` with every `Dictionary(_, value)`
  field's DECLARED type replaced by `value` (see "Two real bugs" below for
  why this is not optional).
- `scan()`/`scan_with_filter` (default, delegates to `scan`): one
  `ipc_cache::read_row_group(dir, segment.id, projection, None)` call per
  active segment, in id-ascending order, concatenated. No predicate
  pushdown into the IPC reader (relies on the physical planner's own
  `FilterExec` above the scan for correctness, same as every other
  non-pushdown provider) — a real, intentionally out-of-scope gap for a
  later task to close without touching any caller.
- `statistics()`: NEVER `None`. Whole table: direct copy of
  `manifest.table_stats` (task 002's precomputed rollup, O(1)). Shard:
  refolds only the assigned segments' `column_stats`
  (`NativeManifest::rollup`) — NOT the whole table's numbers. `ndv_est` is
  derived the same way `ParquetTable`/`LanceTable` already do
  (`min(non_null_rows, max - min + 1)` for dense integer ranges).
- `distributed_splits(table, nodes)`: NEVER `None`. One real `Split` per
  segment (`row_offset: 0`, `num_rows`/`bytes` from the segment's own
  stats) — segments are this format's natural atomic unit (write-time
  sized, unlike a Parquet row group), so no further byte-target
  subdivision is added on top; feeds `assign_lpt`'s existing LPT balancer
  unchanged. Deterministic: segments sorted by id before enumeration, so
  two nodes reading the same table compute the identical `SplitSet`
  (required for the digest interlock).
- `shard_by_splits(splits)`: returns a `NativeTable` with `only_segments =
  Some(ids-from-splits)`. Every other method (`scan`, `statistics`,
  `identity`) correctly restricts to just those segments — proven by
  dedicated tests, not just implemented.
- `identity()` (added mid-task, coordinated live with impl-nt-007-gpu's
  task 007): `Some(table_id_bytes ++ version_le_bytes)` for a whole-table
  provider, `None` for a shard (GPU resident-cache aliasing guard —
  mirrors `ShardedParquetTable::parquet_files()`'s own reasoning).
- No special-cased scan path: `parquet_files()` stays at its default
  `None`, so `PhysicalPlanner::create_physical_plan_inner`'s
  `LogicalPlan::Scan` arm routes every native-table query through the
  SAME generic `scan_with_filter`-then-`MemoryTableExec` path
  `LanceTable` already uses — confirmed by reading that function, not
  assumed. Joins/aggregates/filters/projections all apply unchanged, and
  `PhysicalPlanner::prescan_shared_tables`'s 400MB shared-table cap
  applies automatically too (it falls back to `statistics().
  total_byte_size` for any non-Parquet provider, and `NativeTable` always
  populates that field).

### Two real bugs found during cell-exact validation and fixed (not assumed away)

1. **Bare `SELECT *` produces table-qualified column names.**
   `Binder::bind_select_items`'s `SelectItem::Wildcard` arm reuses the
   scan's own `SchemaField`s verbatim (including `relation`, kept for
   self-join disambiguation like `n1.n_name`/`n2.n_name`), while an
   explicit column list rebuilds fields unqualified — a genuine,
   pre-existing asymmetry, confirmed empirically (`SELECT * FROM orders`
   vs `SELECT o_orderkey FROM orders` produce differently-shaped output
   schemas from the identical table). Harmless for a transient
   `QueryResult` (what `sql()` returns); wrong to bake permanently into a
   persisted table's column names (`CREATE TABLE t AS SELECT * FROM
   orders` must let `SELECT o_orderkey FROM t` work). Fixed LOCALLY inside
   `create_table_as_select` (`output_schema_for_native_write` strips
   qualification and errors on a resulting name collision instead of
   silently producing ambiguous duplicate columns) — the general wildcard-
   binding behavior other callers depend on was NOT touched.
   impl-nt-003-write independently hit and fixed the same latent gap in
   `write-native --sql`.
2. **A `Dictionary`-typed LOGICAL schema breaks GROUP BY.** Task 003's
   writer correctly declares a dictionary-coerced column's manifest type
   as `Dictionary(Int32, Utf8)` — correct for describing what the segment
   file physically contains. Surfacing that as `NativeTable::schema()`'s
   type broke `AggregationState::build_group_array`
   (`src/physical/morsel_agg.rs`) — shared by BOTH `HashAggregateExec` and
   `MorselAggregateExec` (verified by reading both call sites) — which has
   no `Dictionary` match arm, because no existing provider ever exposed
   one at the logical level (`ParquetTable::schema()` always reports the
   plain value type; its IPC-sidecar dictionary encoding is an invisible
   physical optimization). Fixed by having `schema()` report the decoded
   value type while `scan()` still returns the real, physically
   Dictionary-encoded array unchanged (zero-copy — `MemoryTableExec`'s
   existing "rewrap" logic already retags a batch's schema to its actual
   array type when the two differ, an already-load-bearing mechanism this
   change simply exercises rather than a new one). Pinned by a dedicated
   unit test asserting both halves (`schema()` says `Utf8`, the scanned
   batch is still really `Dictionary`).
