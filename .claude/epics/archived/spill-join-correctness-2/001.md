# Task: Hash/derived-state-consistency investigation

## Description

The epic's real risk and entry point. A real, merged Trino bug fix
(PR #25892, cited in `.claude/plans/research/2026-08-27-modern-olap-
research-synthesis.md` §2.6) was caused by spilling using one
hash-generator implementation and unspilling using a DIFFERENT one,
silently grouping values incorrectly — same operator class (spilling
hash aggregation/join), same symptom shape (silently wrong, not
crashed) as this engine's own still-open bug. The prior
`spill-join-correctness` epic's own "best remaining hypotheses" list did
NOT include this specific mechanism (it focused on non-idempotent
re-execution, disproven, and a vaguer "mid-computation failure" theory).
This task checks it directly, with instrumentation, not inference.

Read `.claude/epics/archived/spill-join-correctness/` in FULL before
starting — especially `001.md`'s Outcome (the disproven leading
hypothesis, the existing `QE_SPILL_DEBUG` instrumentation, the exact
repro steps and 4.8%/0.34% rate figures) and `003.md`'s Outcome (blast-
radius characterization: not native-table-specific, distributed-
reachable, three sibling bugs). Do not re-derive what's already
established there.

## Outcome (closed 2026-08-27)

### Headline

**Confidence gate MET with direct evidence.** The hash/derived-state
instrumentation this task built caught a REAL write-vs-read mismatch in
the act — not the literal Trino PR #25892 shape ("two different hash
GENERATOR implementations disagreeing"), but the same root shape one
level up: a value written by one execution and silently overwritten or
deleted by a wholly UNRELATED, concurrent execution sharing the same
on-disk path before this execution ever reads it back. Root-caused to
`ExecutionConfig::default()`'s `spill_path`
(`$TMPDIR/query_engine_spill`) having no per-process disambiguation,
combined with `SPILL_COUNTER` always starting at 0 in a fresh process —
any two `query_engine` processes on the same host compute the IDENTICAL
default spill directory (`join_0_0`) for their first spilling join.
This is the exact same bug `spill-join-correctness` task 003 already
found and characterized as "fails loudly, HTTP 400, never silently
wrong." **That conclusion was incomplete.** Under a collision between
two DIFFERENTLY-SIZED concurrent queries, this task caught the SAME
mechanism producing a silently WRONG final answer, not just a crash —
directly, via the new checksum instrumentation, correlated with a wrong
HTTP 200 response in the same trial. Fixed with a one-line, minimal
change (PID-disambiguated default spill path), validated from multiple
independent angles (deterministic unit test, a deliberate 3-vs-0
collision reproduction, 500 single-process trials, native AND parquet).

**This task does NOT confirm or refute the archived epic's own headline
~0.34%-rate wrong-answer bug was CAUSED by this exact mechanism** —
that bug was never observed with an identifiable concurrent process at
the time (the prior epic's own trials did not check for one), so this
is circumstantial, not proven, for that specific historical bug. What
IS proven, directly: this mechanism is real, reachable at a realistic
memory-limit with ordinary concurrent usage (this repo's own CI/dev
workflow routinely runs more than one `query_engine` process on one
host), and it silently produces wrong answers, not just crashes — a
materially more severe finding than task 003's own "never silently
wrong" conclusion, which this task's own evidence corrects.

### Enumeration (every derived/cached value checked)

Read `build_with_partitioning`/`probe_with_spilling`/
`process_spilled_partition`/`probe_partition`/`build_hash_table`/
`extract_join_key`/`partition_batch_by_hash`/`create_joined_batch` in
full (all in `spillable.rs`) before instrumenting anything:

1. **Partition-routing hash** (`partition_batch_by_hash`, via
   `extract_join_key` + a fixed-seed xxHash64) — computed once per row,
   BEFORE any spill, to decide which of the 64 partitions a row goes to.
   Never recomputed after a round trip (routing happens once, pre-spill).
   Not implicated — already fixed-seed per a documented prior incident.
2. **Join-key equality/hash for the in-partition hash table**
   (`extract_join_key` -> `JoinKey`'s `Hash`/`Eq`, consumed by
   `build_hash_table`'s `HashMap`) — computed exactly once per logical
   set of rows per partition: either from ORIGINAL in-memory batches
   (never spilled) or from Parquet-read-back batches (spilled) — never
   both for the same partition. **This is the direct analog of the
   Trino mechanism and the one this task instrumented**
   (`KeyChecksum`/`batch_key_checksum`, compares a write-time checksum
   recorded when a partition's rows are spilled against a read-time
   checksum recomputed in `process_spilled_partition` after
   `read_parquet`). Caught a real mismatch — see below.
3. **Output-column type reconciliation** (`create_joined_batch` ->
   `batch_with_actual_types`) — DECLARED schema vs. ACTUAL gathered
   Arrow type. Already fixed by `native-tables-mutation` task 006;
   verified still present and unchanged. Not implicated.
4. **`extract_join_key`'s own downcast-chain gap**: it does not handle
   `DictionaryArray` (or any type beyond Int64/Int32/UInt64/Float64/
   plain `StringArray`) — an unhandled type silently becomes
   `JoinValue::Null`, and `build_hash_table`/`probe_partition` both SKIP
   null keys, so an unhandled-type join key would be silently DROPPED,
   not duplicated. A real, separate, structural gap (would apply
   identically whether spilled or not — not a spill/unspill
   inconsistency), but NOT implicated in Q12's own join key
   (`o_orderkey`/`l_orderkey`, confirmed `Int64` in
   `src/tpch/schema.rs`, a handled type). `KeyChecksum` tracks this
   directly too (`unhandled_type_rows`); 0 across every trial this task
   ran. Reported here as a finding, not fixed (out of this task's
   confirmed-mismatch scope — no evidence it's reachable via any query
   this task actually ran).
5. **Memory-pool spill accounting** (`memory_pool.record_spill`) — a
   derived byte count, but never relied on again for match correctness,
   only diagnostics/threshold decisions. Not implicated.
6. **`estimate_batch_size`** — decides WHEN to spill, not WHETHER a
   match is found. Not implicated.
7. **Retained/output column mask** (`self.retained`) — one plan-time
   value applied identically for in-memory and spilled partitions. Not
   implicated.
8. **`HashEntry{batch_idx,row_idx}` indices** — always relative to the
   SAME `build_batches` Vec within one `process_spilled_partition` call;
   verified `build_hash_table` and `probe_partition` always operate over
   the identical reference. Not implicated.
9. **The spill FILE PATH itself** (`spill_dir`/`SpilledPartition::
   build_file`/`probe_file`) — not named as a "derived value" in the
   task's own framing, but IS exactly that: a value (a path) computed
   once (`spill_id = SPILL_COUNTER.fetch_add(...)`) and relied on again
   later (`process_spilled_partition`'s `read_parquet` call). **This is
   where the real mismatch was found** — see below.

### The mismatch, caught in the act

Running the prior epic's own repro (`repro.sh`) in a tight loop with
`QE_SPILL_DEBUG=1` (which now also emits the new `KeyChecksum`
comparison), a real concurrent process on the same host (a peer agent's
own, unrelated SF=100 native-table benchmark, sharing the same default
`$TMPDIR`) produced:

```
[sj-trace] HASH-MISMATCH build partition idx=0 write_rows=27614 write_xor=f0fd58242f942b68 read_rows=275091 read_xor=f4e860d3fe699f69 write_unhandled=0 read_unhandled=0
... (all 64 build partitions, same ~9.9-10x read/write row ratio)
```

`read_rows` was consistently ~9.9-10x `write_rows` for every one of the
64 build partitions in the affected trial — matching, almost exactly,
the SF=100/SF=10 scale ratio of the concurrent peer process that was
running at the same time. The trial's final HTTP 200 answer was WRONG
(inflated, same symptom shape as the archived epic's own headline bug).
A second trial in the same sweep showed the identical 64-partition
HASH-MISMATCH pattern but happened to still return the correct final
answer (the extra rows apparently didn't affect this query's specific
aggregate). A third trial's collision manifested as a loud crash instead
(`Failed to open parquet file ".../join_0_1/build_47.parquet": No such
file or directory`) after an `execute_fused_streaming` abort+retry — the
SAME underlying collision, different symptom, depending on exact timing.

Root cause, confirmed by reading `src/execution/memory.rs`:
```rust
spill_path: std::env::temp_dir().join("query_engine_spill"),
```
No PID, no per-process disambiguation, no CLI override exists at all
(`grep`-confirmed: zero `--spill-path`-shaped flag anywhere in
`main.rs`). Combined with `SPILL_COUNTER` (a per-process `AtomicU64`
that always starts at 0 in a fresh process), the FIRST spilling
join/aggregate/sort in ANY `query_engine` process on a host lands on
the literal, identical path
`$TMPDIR/query_engine_spill/join_0_0/build_<idx>.parquet` as the FIRST
spilling operator in ANY OTHER concurrent process on that same host —
regardless of query, scale, or table. This is the SAME bug
`spill-join-correctness` task 003 already found (see CLAUDE.md's
"Concurrent same-host `serve` processes collide on the default spill
directory") — this task's contribution is DIRECT evidence that it can
be silently wrong, not just loud, correcting that task's own recorded
"confirmed never silently wrong" conclusion.

### Fix

`src/execution/memory.rs`, `ExecutionConfig::default()`:
```rust
spill_path: std::env::temp_dir()
    .join(format!("query_engine_spill_{}", std::process::id())),
```
Minimal, one field, no other behavior change. Only the DEFAULT changed
— `with_spill_path` (explicit overrides) is untouched, so any caller
that already sets its own spill path (e.g. a distributed-cluster
launcher wanting a known shared location) keeps full control.

### Process note: mid-investigation worktree isolation

Partway through this task's own trial sweep, a peer agent (working the
unrelated `native-table-pruning` epic) was found to be operating in the
SAME shared, non-worktree checkout this task started in — both agents'
uncommitted edits were mixed in one working directory. The orchestrating
session paused this task, moved its in-progress `spillable.rs` diff into
a fresh, isolated git worktree (`/tmp/qe-wt-spill2`, branch
`epic/spill-join-correctness-2`), and this task resumed there for
everything from that point on (rebuilds, the fix, all validation,
the commit). This explains the "165 trials, shared checkout" +
"200 trials, isolated worktree" split above, and is also, pointedly, the
SAME class of bug this task ended up finding IN THE PRODUCT ITSELF
(unrelated concurrent processes silently colliding on a shared default
path) — noted here because it is a genuinely fitting coincidence, not
because it affected this task's own findings (the shared-checkout period
predates the collision discovery; the actual collision was caught after
the move, against an already-built, unaffected release binary).
