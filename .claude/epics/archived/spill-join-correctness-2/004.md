### Bug 2: LIMIT not enforced under spill — root cause and fix

Root cause, confirmed by reading `planner.rs` directly:
```rust
LogicalPlan::Limit(node) => {
    // Top-K optimization: fuse Sort+Limit into a single SortExec with fetch
    if node.skip == 0 {
        if let Some(fetch) = node.fetch {
            if let LogicalPlan::Sort(sort_node) = node.input.as_ref() {
                ...
                let sort = ExternalSortExec::with_fetch(..., fetch);
                return Ok(Arc::new(sort));
```
A `skip == 0` LIMIT directly over a `Sort` never constructs a `LimitExec`
at all — it folds straight into `ExternalSortExec::with_fetch`. In
`ExternalSortExec::execute()`, the in-memory branch (`!exceeded`) correctly
threads `self.fetch` into `SortExec::with_fetch`; the SPILL branch
(`exceeded`) computed `result` (via `generate_runs`+`merge_runs`, a
correct, fully-globally-sorted output) and returned it directly —
`self.fetch` was stored at construction and never read again anywhere in
that branch. Exactly the prior epic's own "correct top-K prefix, LIMIT
never applied to truncate it" characterization.

**Fix**: a new `truncate_batches_to_limit(batches, limit)` helper (slices
the last needed batch, drops the rest) applied to the spill branch's final
`result` whenever `self.fetch` is `Some`.

**Regression test**
(`external_sort_spill_path_enforces_limit_under_forced_spill`, unit-level,
`spillable.rs`'s own test module): 20 single-row batches (descending
values 19..0) fed through `ExternalSortExec::with_fetch(..., fetch: 5)`
under a tiny `memory_limit`/`spill_threshold` that forces the spill
branch (`exceeded = true`) with several separate runs, staying under
`MAX_MERGE_FANIN` = 8 to keep this test isolated from bug 3's own fix.
**Fail-before**: reverted the truncation call, ran the test — returned
all 20 rows instead of 5 (`assertion left == right failed: ... got 20:
[0, 1, ..., 19]`), exactly the archived bug's own "correct values, wrong
row count" shape. **Pass-after**: restored the fix — exactly 5 rows,
values `[0, 1, 2, 3, 4]` (cell-exact top-K, not just the right count).

### Bug 3: sort-spill run-file-not-found crash — root cause and fix

Root cause, confirmed by reading `multi_pass_merge` directly:
```rust
for chunk in current_runs.chunks(fanin) {
    if chunk.len() == 1 {
        next_runs.push(chunk[0].clone());  // passthrough: SAME path, not a new file
    } else {
        // real merge: writes a NEW merged_pass{N}_{M}.parquet
    }
}
if pass > 0 {
    for run in &current_runs {
        let _ = std::fs::remove_file(run);   // deletes EVERYTHING, including passthroughs
    }
}
current_runs = next_runs;
```
Whenever a pass's run count is not an exact multiple of
`MAX_MERGE_FANIN` = 8, `chunks(8)` leaves a trailing chunk of exactly one
run, carried into `next_runs` UNCHANGED (same path — a passthrough is not
rewritten to a new file). The unconditional cleanup then deletes that
same path a moment later (any pass after the first), because it blindly
deletes every path in `current_runs` with no check against what
`next_runs` — this iteration's own output, about to become `current_runs`
for the next pass or the final merge — still needs. A later pass (or the
final `streaming_k_way_merge` call right after the loop) then tries to
open a file this very function just deleted:
`Failed to open run file "..." : No such file or directory`.

**Fix**: only delete a path in `current_runs` that is NOT also present in
`next_runs`:
```rust
if pass > 0 {
    let still_needed: std::collections::HashSet<&PathBuf> = next_runs.iter().collect();
    for run in &current_runs {
        if !still_needed.contains(run) {
            let _ = std::fs::remove_file(run);
        }
    }
}
```

**Regression test**
(`external_sort_multi_pass_merge_survives_a_leftover_singleton_chunk`,
unit-level, calls the private `merge_runs` directly like the file's own
pre-existing `k_way_merge_survives_a_run_needing_more_than_one_buffer_load`
test does): 129 synthetic single-row sorted run files
(`run_0.parquet`..`run_128.parquet`). Chosen deterministically, not by
chance: pass 0's chunking (129 = 16×8 + 1) leaves a 1-run trailing chunk,
producing 17 runs into pass 1; pass 1's own chunking (17 = 2×8 + 1) again
leaves a 1-run trailing chunk — exactly the shape this bug needs.
**Fail-before**: reverted the cleanup fix, ran the test — crashed exactly
as the archived epic recorded:
```
Failed to open run file "/tmp/qe_multi_pass_merge_test_920167/run_128.parquet": \
No such file or directory (os error 2)
```
(a passthrough ORIGINAL run file in this synthetic repro, rather than the
archived epic's own `merged_pass0_48.parquet` — same mechanism, same bug,
a different specific file depending on the exact run-count arithmetic of
each repro, as expected). **Pass-after**: restored the fix — all 129
distinct values `0..129`, in order, exactly once, no crash.
