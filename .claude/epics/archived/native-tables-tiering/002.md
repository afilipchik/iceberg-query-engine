# Task: Per-column failure isolation + observability

## Description

Two related pieces on top of task 001's cache-state structures.

**Failure isolation**: today, `GpuEngine::mark_unhealthy()` sets a
single process-wide `healthy: AtomicBool` to false, called whenever any
upload fails for any reason — this permanently disables GPU offload for
the REST of the process's lifetime, for every table, every query, from
then on. That's the opposite of graceful degradation: one transient or
column-specific failure (a malformed value, a momentary VRAM pressure
spike, a driver hiccup) shouldn't take down GPU acceleration for
everything else. Replace this with per-column/per-upload failure
handling: a failed upload should fail (fall back to CPU) for that one
query/column, not poison the whole process.

**Observability**: expose the cache state task 001 built (resident
columns, VRAM used vs. budget, eviction count, now also failure/
isolation events) via this codebase's existing diagnostic convention —
so an operator can actually see what the GPU cache is doing, matching
the transparency this program applies elsewhere (`QE_SPILL_DEBUG`'s
per-call tracing, the rollup epic's `QueryMetrics::rollup_answered`
provenance field).

## Outcome (closed 2026-08-26)

### Summary

`mark_unhealthy()`'s single process-wide `healthy: AtomicBool` poison
flag is GONE — the field, its two gate checks in `request()`/`ready()`,
the function itself, and its one call site are all deleted, not
replaced with a new global mechanism. Per-column failure isolation was
already structurally present in task 001's `resident`/`codes`/`queued`
maps (all keyed per `(pid, column)` or `codes_key`); the `healthy` flag
was the only thing overriding that correct per-key isolation with a
coarse, unconditional, never-reset gate. Design decision: a failed
upload is **retried** on a later query, never permanently blacklisted —
documented in full below, with three concrete reasons. Two new
`AtomicU64` counters (`upload_failures`, `run_fallbacks`) plus a
`GpuEngine::snapshot() -> GpuCacheSnapshot` API and a new `QE_GPU_DEBUG`
env-gated trace (confirmed not already present anywhere in the codebase
before adding it) give full observability. Validated on REAL hardware
with two independent failure constructions — a deterministic
"not-cacheable" Int64-range violation, and a genuinely induced real
CUDA VRAM-exhaustion failure (the actual failure class
`mark_unhealthy()`'s sole pre-fix call site handled) — both confirming
the process is never poisoned. Task 001's own hardware-backed eviction
test re-confirmed passing, unmodified. Full suite green across all four
feature combinations; `cargo fmt --all -- --check` clean.

### 1. Root-cause confirmation: only ONE call site, ever

Checked against the PRE-task-001 commit (`161b2fb`, the epic's own
starting point), not assumed: `mark_unhealthy()` had exactly ONE call
site then, and still exactly one immediately before this task's own
diff — the `Err` branch of `Job::Upload`'s `stream.memcpy_stod(&values)`
call (a genuine CUDA/driver allocation failure). Task 001's own rewrite
of the worker loop did not silently drop or add any call sites; the
epic's own research doc's "three locations" (gpu.rs 606-610, 527-529,
556-558) refers to the field declaration + the function definition +
the two `request()`/`ready()` gate checks, not three separate
invocations. This matters for scoping the fix correctly: exactly one
code path needed to stop calling `mark_unhealthy()`, and exactly two
gate checks needed to stop reading `healthy`.

### 2. Fix: delete the global gate, don't replace it with a new one

Task 001 already gives every upload attempt a `(pid, column)`- or
`codes_key`-scoped identity in `resident: Mutex<HashSet<(usize,String)>>`,
`codes: Mutex<HashMap<String,usize>>`, and `queued: Mutex<HashSet<String>>`
— a failed upload for column X was ALREADY incapable of touching column
Y's own entries in those maps. The only thing standing in the way of
correct per-column isolation was the single global `healthy` flag
layered on top, gating BOTH `request()` (so a poisoned engine stopped
even TRYING new uploads, for anything) and `ready()` (so a poisoned
engine stopped serving ALREADY-uploaded, perfectly resident columns
from the GPU, too — worse than the task description alone implies).
Removing `healthy` entirely — the field, its two gate checks,
`mark_unhealthy()`, and its one call site — is therefore the COMPLETE
fix: per-column isolation was already structurally present, just
overridden by a coarser, unconditional gate. No new lock, no new
concurrency surface, no new per-key state at all — the fix is
subtractive, not additive.

### 3. Design decision: RETRY, not a permanent blacklist — three reasons

Documented in full in `src/physical/gpu.rs`'s own module doc (new "##
Failure isolation + observability" section) and restated here:

1. **Symmetry with existing behavior.** `load_column_f64` returning
   `Ok(None)` (nulls, an unsupported type, an Int64 value outside 2^52)
   was ALREADY handled this way before this task — no blacklist;
   `unmark_queued` (task 001) clears the dedup key unconditionally after
   every job, success or failure, so the exact same doomed upload is
   retried on the very next query that needs it, and that has never
   been a problem. Treating a hard upload ERROR (a CUDA/driver failure)
   any differently would mean maintaining two different
   failure-handling mechanisms for what is, from a caller's
   perspective, the identical outcome: "this column isn't resident
   yet."
2. **A blacklist would fight task 001's own eviction mechanism.** The
   task's own named example failure modes ("a momentary VRAM pressure
   spike, a driver hiccup") are transient by construction — task 001
   built LRU eviction specifically so VRAM pressure resolves itself
   over time. A permanent per-key blacklist would keep a column stuck
   on the CPU path forever even after eviction frees the exact room its
   upload needed, actively working against the mechanism task 001 just
   built. Retry lets a later, successful attempt (once room exists
   again) simply happen, with zero new code.
3. **Minimal, surgical diff.** No new state is needed at all — the fix
   is subtractive, not additive (a new `HashSet` of blacklisted keys
   would need its own insert/check/never-cleared-on-mutation lifecycle
   to get right, and its own interaction with eviction to reason
   about). Smaller surface, less to get wrong, zero risk of regressing
   task 001's own eviction/budget logic — confirmed untouched (see
   section 6 below).

**Accepted cost, named plainly**: a column whose upload fails for a
genuinely PERMANENT reason (e.g. a value outside `load_column_f64`'s
accepted range, which cannot change without a new table version/pid) is
retried on every single future query that needs it, forever costing one
column scan + one failed device call per query — never incorrect
(always falls back to a correct CPU answer), just not free. Matches
this program's own "always correct, even if that means not fast"
standing culture. Not fixed with a backoff/cooldown here — out of this
task's own scope, which names only "retry" or "permanent blacklist" as
the two options.

### 4. Observability: counters, a snapshot API, and `QE_GPU_DEBUG`

Confirmed via `grep -rn "QE_GPU_DEBUG"` across the whole repo BEFORE
implementing: it did not exist anywhere except as a name in this epic's
own planning prose — genuinely new, not a rename.

- **`GpuEngine::upload_failures: AtomicU64`** — increments on every
  upload/build-codes attempt that did NOT result in a resident entry,
  for ANY reason: a hard CUDA/driver error, a provider scan error,
  "not cacheable" (nulls/type/Int64-range), or a row-count mismatch.
  Deliberately does NOT count the ordinary cold-start "not yet
  uploaded" path — that's expected warm-up, not a failure, and counting
  it would drown the signal. Public accessor: `upload_failures()`.
- **`GpuEngine::run_fallbacks: AtomicU64`** — increments when
  `GpuAggExec::execute` finds its plan fully `ready()` (every column/
  codes buffer already resident) but the actual device `run()` call
  itself still fails, forcing a CPU fallback for that one query.
  Distinct bucket from `upload_failures`: the data WAS resident, only
  execution failed. Public accessor: `run_fallbacks()`.
- **`GpuEngine::snapshot() -> GpuCacheSnapshot`** (new public struct,
  `Display`-implemented) — bundles `resident_columns`, `resident_bytes`,
  `budget_bytes`, `eviction_count` (task 001), `upload_failures`,
  `run_fallbacks` into one point-in-time read. The single source both
  `QE_GPU_DEBUG` tracing and any external caller (tests, a future admin
  surface) use, so the two can never silently disagree — this is the
  "queryable/programmatic form" the acceptance criteria asked for.
- **`QE_GPU_DEBUG`** — checked fresh via `std::env::var("QE_GPU_DEBUG")
  .is_ok()` on every relevant call (never cached in a `OnceLock`),
  matching `QE_SPILL_DEBUG`'s exact established convention (verified by
  reading `spillable.rs`'s own usage before writing this). Traces, to
  stderr with a `[gpu-trace]` prefix: every `Job::Upload`/`Job::
  BuildCodes` outcome (OK/SKIP-not-cacheable/SKIP-row-mismatch/FAILED,
  each with a snapshot), the "not ready, requesting upload(s)" cold
  path, and every `Job::Run` OK/FAILED outcome in `GpuAggExec::execute`.
  Confirmed working on real hardware (section 7).

### 5. Validated on real hardware — two independent failure constructions

New file `tests/gpu_failure_isolation_tests.rs` (one `#[tokio::test]`,
deliberately — mirrors `tests/gpu_cache_tests.rs`'s own established
reasoning: everything in the file shares the SAME process-wide
`GpuEngine` singleton and, in phase 2, the SAME physical GPU's real
VRAM, so splitting into concurrently-run test functions would risk one
phase's real VRAM pressure spuriously failing an unrelated upload in
another). Skips cleanly if no CUDA device is found.

**Phase 1 (deterministic, zero risk to the shared GPU)**: a table whose
only column is Int64 with every value `> 2^52` — `load_column_f64`'s own
Int64 match arm refuses the WHOLE column (`Ok(None)`, "not cacheable").
This does NOT exercise `mark_unhealthy()`'s old call site (that path
never called it, before or after this task's fix — confirmed by
reading the code, not assumed), so it does not by itself prove the
poisoning bug is fixed, but it IS a genuine, real, fully-reproducible
upload-attempt failure and independently confirms per-column isolation:
`SELECT COUNT(bigval) FROM oversized` correctly falls back to CPU with
the exact count, `upload_failures` increments, and a DIFFERENT,
unrelated table's column (`p1_ok`) immediately uploads and becomes
GPU-resident right after.

**Phase 2 (the construction that actually exercises the bug this task
fixes)**: `mark_unhealthy()`'s sole pre-fix call site was a genuine
`stream.memcpy_stod` CUDA allocation failure — so this phase induces a
REAL one. `cudarc::driver::CudaContext::new(0)` retains the device's
PRIMARY context (confirmed by reading cudarc 0.19.9's own source before
relying on it), so a second handle opened directly from the test shares
the SAME physical VRAM pool the `GpuEngine` worker thread's own context
uses. The test queries real free VRAM via `mem_get_info()` (31,644,450,816
bytes free of 33,598,078,976 total — an idle RTX 5090), allocates almost
all of it directly (down to 271,056,896 bytes free, confirmed via a
second `mem_get_info()` call — not assumed), then drives a 60,000,000-row
(~480MB) "victim" column's upload through the real `GpuEngine`/worker-
thread path. The upload genuinely fails inside `stream.memcpy_stod` —
the exact call site that used to invoke `mark_unhealthy()` — and:

- The query (`SELECT SUM(val) FROM victim`) correctly falls back to CPU
  with a numerically correct answer (relative-tolerance comparison,
  1e-6 — matching `gpu.rs`'s own documented "same 1e-6 tolerance class
  as the distributed two-phase path"; an earlier draft of this test used
  a fixed absolute delta and failed spuriously on a ~1.8e15-magnitude
  60M-row sum for a floating-point-reordering reason unrelated to
  correctness, caught and fixed before this task closed).
- `upload_failures` increments.
- After releasing the eater buffer, a THIRD, unrelated table (`p2_ok`)
  immediately uploads successfully and becomes GPU-resident — **the key
  assertion this task exists to prove**: pre-fix, `mark_unhealthy()`
  would have poisoned the engine on the victim's own failure and BOTH
  `p2_ok` and every future table would have been permanently stuck on
  CPU for the rest of the process. Post-fix, it isn't.
- A bonus phase 3 then re-queries the ORIGINAL `victim` table again
  (VRAM pressure now gone) and confirms it ALSO eventually becomes
  resident — real-hardware evidence for the RETRY design decision
  specifically, not just the isolation property.

**A genuine, honestly-reported finding from this exact run**:
`mem_get_info()` read IDENTICALLY (271,056,896 bytes free) both
immediately after eating VRAM and immediately after `drop`-ing the ~31GB
eater buffer. This is consistent with cudarc/CUDA's stream-ordered
memory-pool allocator (`CudaContext::has_async_alloc`) retaining freed
physical pages in its own pool rather than returning them to the
driver-global free count right away — NOT a bug in this task's fix or
its test. Critically, the pool still served subsequent REAL allocation
requests through `GpuEngine` correctly (`p2_ok`'s upload and `victim`'s
retried upload both succeeded) despite the flat `mem_get_info()` reading
— confirming the test's pass/fail signal correctly rests on real
allocation attempts through the actual engine, not on a raw byte-count
reading that this particular allocator's own pooling makes an
unreliable post-release indicator.

Final measured state after the whole test (`engine.snapshot()`):
```
resident_columns=3 resident_bytes=480800000 budget_bytes=25769803776 eviction_count=0 upload_failures=16 run_fallbacks=0
```
Fully explained, not just observed: `upload_failures=16` = up to 6
failed retries for the permanently-not-cacheable `oversized` column
across phase 1's 6 warm-up iterations, plus up to 10 failed retries for
`victim` across phase 2's 10 warm-up iterations before VRAM was
released — exactly the two failure-generating windows this test
deliberately opens. `resident_columns=3` = `p1_ok` + `p2_ok` + `victim`
(the oversized column never becomes resident, by design — its failure
is permanent, matching the "accepted cost" named in section 3).
`eviction_count=0` is correct too: the default 24576 MiB software
budget was never close to exceeded by ~481MB of real resident data, so
LRU eviction correctly never triggered — this test is about REAL VRAM
exhaustion outside the cache's own software accounting, not about the
budget mechanism task 001 already validated.

`QE_GPU_DEBUG` was independently smoke-tested against
`examples/gpu_cache_tiering_check.rs` (`QE_GPU_DEBUG=1 QE_TIERING_ROWS=
50000 QE_TIERING_MUTATIONS=1`) and confirmed to print real `[gpu-trace]`
lines for the cold "not ready" path, "upload OK", and "run OK", each
with a full snapshot — e.g. `[gpu-trace] upload OK pid=66149adad7103b4c
col=val bytes=400000 snapshot=[resident_columns=1 resident_bytes=400000
budget_bytes=25769803776 eviction_count=0 upload_failures=0
run_fallbacks=0]`.
