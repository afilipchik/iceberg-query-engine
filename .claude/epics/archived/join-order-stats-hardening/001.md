# Task: Missing/degenerate join-key statistics visibility

## Description

`JoinReorder`'s DPsize cost model (`src/optimizer/rules/
join_reorder.rs`) computes join selectivity from per-column NDV
estimates. When a relation's join-key column has no recorded
statistics (confirmed real, shipped path: `ExecutionContext::
register_table`/`MemoryTable` carries a real row count but an empty
`column_stats` map), the cost model falls back to a near-arbitrary
default (`base_rows[rel].max(10.0)`-style, per the go/no-go
investigation's own finding) with zero signal to anyone. The
investigation's repro turned this into a >60,000x cardinality
misestimate and a query that never completes. This task makes that
condition visible.

Read `CLAUDE.md`'s "Adaptive join-order re-optimization: investigated,
NOT pursued yet" section and `examples/adaptive_reopt_ndv_repro.rs` in
full before starting — this is the load-bearing investigation, don't
re-derive it.

## Outcome (2026-08-27)

### Where the fallback actually lives

Read `estimate_base_rows`, `column_ndv`, and `build_join_tree_dpsize`
in full. The silent fallback is a single closure,
`side_combined_ndv` inside `build_join_tree_dpsize`
(`src/optimizer/rules/join_reorder.rs`), which computed each edge
endpoint's combined NDV as:

```rust
let ndv = self.column_ndv(&relations[rel], e).unwrap_or(base_rows[rel].max(10.0));
```

`column_ndv` returns `None` (triggering the fallback) when: the
relation's underlying table has no `TableStatistics` entry at all, OR
(the actual repro path) the entry exists but its `column_stats` map has
no entry for this column — exactly `MemoryTable::statistics()`'s shape
(`ExecutionContext::register_table`, real row count, empty
`column_stats`, confirmed by reading `src/physical/operators/scan.rs`
and `src/execution/context.rs::collect_table_statistics`, which inserts
a `TableStatistics` entry for EVERY registered provider whose
`statistics()` returns `Some(..)` — `MemoryTable` included). This is the
sole call site the task's acceptance criteria target; filter-selectivity
NDV usage (`range_selectivity`) is a different, out-of-scope consumer
(filters, not join edges).

### The reusable signal mechanism (for task 002)

New, free-standing public API in `src/optimizer/cost.rs` (chosen over
`join_reorder.rs` itself specifically for reuse: `join_reorder`'s own
module is private, `cost`'s public items are glob-re-exported at
`crate::optimizer::*`, so this is reachable crate-wide — including from
`src/storage/native_manifest.rs`/`native_delete.rs`/`native_update.rs`
for task 002 — with zero further plumbing):

```rust
pub enum UntrustworthyStats { Missing, Degenerate }
impl UntrustworthyStats { pub fn as_str(&self) -> &'static str }

pub fn classify_join_key_ndv(
    ndv_est: Option<f64>,
    relation_row_count: f64,
) -> Result<f64, UntrustworthyStats>;

pub fn warn_untrustworthy_join_key_stats(
    relation: &str,
    column: &str,
    reason: UntrustworthyStats,
    fallback_ndv: f64,
);
```

`classify_join_key_ndv` is pure (no I/O): `Missing` for `None`;
`Degenerate` for a non-positive NDV (reachable today —
`ParquetTable`'s `ndv_est` derivation can produce `Some(0)` for an
all-null integer column) or a single-value NDV (`<= 1.0`) on a relation
whose own row count exceeds `DEGENERATE_SINGLETON_ROW_THRESHOLD = 1000`
— guarding against flagging a genuinely tiny dimension table (TPC-H
`region`/`nation`-scale) whose real NDV IS 1 or a handful. Anything else
is `Ok(ndv)`, unchanged. `warn_untrustworthy_join_key_stats` fires
`tracing::warn!` unconditionally (no env-var gate), with `relation`,
`column`, `reason`, `fallback_ndv` as structured fields, matching this
codebase's existing `tracing` convention (`src/distributed/server.rs`'s
`tracing::warn!(node_id = ..., "...")` shape).

`side_combined_ndv` now calls `classify_join_key_ndv`, and on `Err`
computes the SAME fallback value as before (`base_rows[rel].max(10.0)`
— unchanged, not a cost-model change) and calls
`warn_untrustworthy_join_key_stats` with it before returning it. A new
`JoinReorder::describe_join_key_expr` helper labels the join key: the
bare column name for a plain `Expr::Column`, or every referenced column
name joined with `+` for a composite/expression key (e.g. a
`PackedJoinKeys`-packed key).

**Reuse seam for task 002, stated precisely**: task 002 does not need
to call `classify_join_key_ndv`/`warn_untrustworthy_join_key_stats`
directly from storage code at all in the common case — if a
DELETE/UPDATE materially invalidates a native table's derived
`ndv_est` (`src/storage/native_table.rs::table_statistics_from`), task
002 can simply have that derivation emit `None` (or a `Some(1)`
collapsed value) for the invalidated column. The very next time that
column feeds a join edge, `JoinReorder`'s existing call site
automatically classifies it as `Missing`/`Degenerate` and fires the
identical warning — zero new code needed in `join_reorder.rs`. If task
002 instead wants to warn at MUTATION time (not query-planning time),
`crate::optimizer::classify_join_key_ndv`/
`crate::optimizer::warn_untrustworthy_join_key_stats` are directly
callable from anywhere in the crate for that too — one shared
mechanism, two possible call sites, by design.

### Validated against the real repro

`examples/adaptive_reopt_ndv_repro.rs` had no tracing subscriber
installed at all (a silent no-op for `tracing::warn!`); added the SAME
subscriber `src/main.rs` installs for `query_engine serve` (INFO
default level, no env var required) so the example demonstrates the
warning exactly as it appears in ordinary operation.
`scripts/claude-safe-build.sh ./target/debug/examples/
adaptive_reopt_ndv_repro --data data/tpch-10gb --mode plan-only`:

- **ACCURATE leg (all `ParquetTable`, real footer stats): ZERO
  warnings.** No false positives.
- **CORRUPTED leg (`customer`+`supplier` via `register_table`): 15
  warnings** across the ~3 DP invocations the optimizer's fixpoint loop
  runs on this plan (JoinReorder re-runs each iteration until the plan
  stabilizes — the DP is deterministic so later passes just repeat the
  first pass's warnings; not deduplicated, judged acceptable at this
  task's S-effort scope). Unique (relation, column) pairs warned, all
  correct and exactly the corrupted-stats relations' join keys:
  `supplier.s_nationkey`, `supplier.s_suppkey`, `customer.c_nationkey`,
  `customer.c_custkey` — every one `reason="no recorded NDV
  statistics"`, `fallback_ndv` matching each relation's own row count
  (100000.0 for supplier, 1500000.0 for customer), i.e. exactly
  `base_rows[rel].max(10.0)`, unchanged from before this task.
- **Join shapes before/after this task's diff are BYTE-IDENTICAL** to
  CLAUDE.md's own recorded repro output: accurate =
  `(((region JOIN nation) JOIN supplier) JOIN ((customer JOIN orders)
  JOIN lineitem))`, corrupted =
  `(((((region JOIN nation) JOIN supplier) JOIN customer) JOIN orders)
  JOIN lineitem)` — confirms this is a pure visibility addition, zero
  cost-model behavior change.

G1 (PRD) is met: the repro now shows a visible warning identifying the
missing-statistics relation and column, with no false positive on the
accurate leg.
