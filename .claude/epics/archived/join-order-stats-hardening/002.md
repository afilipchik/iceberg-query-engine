# Task: Native-table statistics staleness after mutation

## Description

Native table `ColumnStats` (`src/storage/native_manifest.rs`) has no
stored NDV — it's derived at query time from `min_i64`/`max_i64` and a
row count (per the module's own doc comment: "`ndv_est` DERIVED at that
point from `min_i64`/`max_i64`/`row_count` exactly the way
`ParquetTable`/`LanceTable` already derive it"). Per-segment `min_i64`/
`max_i64` are computed once at write time and never adjusted by
DELETE/UPDATE — only row counts (via deletion vectors) change. This
task investigates whether the derivation uses a row count that goes
stale after mutation, and if so, in which direction, and fixes it.

Read task 001's Outcome section first — reuse its visibility mechanism
rather than building a second one.

## Outcome (2026-08-27)

### Where NDV is actually derived, and the PHYSICAL vs LIVE finding

Read `src/storage/native_manifest.rs` in full (as instructed) and found
the actual derivation lives one layer up, in
`src/storage/native_table.rs::table_statistics_from` — task 001's Outcome
had already named this function precisely; confirmed by reading it
directly, not assumed. `native_manifest.rs` itself owns only the
STORAGE shape (`ColumnStats { min_i64, max_i64, null_count, min_f64,
max_f64 }`, no `ndv_est` field at all, per its own module doc) and
`Segment::live_row_count()` (`row_count - deleted_rows.len()`, added by
the native-tables-mutation epic's task 003) — `native_manifest.rs`
itself needed zero changes for this task.

**The row-count question, answered precisely, and NOT what the epic's
own investigation guessed**: `NativeTable::statistics()`
(`src/storage/native_table.rs`) was ALREADY passing `table_statistics_from`
the LIVE row count, not the physical one —
`let row_count: u64 = segs.iter().map(|s| s.live_row_count()).sum();`
(added by native-tables-mutation task 003, confirmed by reading the git
blame context: it long predates this task). So the naive "stale physical
row count inflates NDV" story the epic's own CLAUDE.md write-up
speculated about is **not the real bug** — that half was already fixed
two epics ago.

**What IS real, found by working through the actual formula
(`ndv_est = min(non_null_rows, max_i64 - min_i64 + 1)`) by hand rather
than re-stating the investigation's hypothesis**: `min_i64`/`max_i64`
themselves are computed ONCE at write time and are NEVER recomputed by
DELETE/UPDATE (confirmed directly — `native_delete.rs`/`native_update.rs`
never touch `Segment::column_stats`, only `Segment::deleted_rows`,
matching `native_manifest.rs`'s own doc: "Deliberately NOT recomputed on
DELETE — always safe... never chased to an exact post-delete bound").
The formula takes `min(row_count_term, range_term)`. The row_count term
already self-corrects (it uses live row count). The RANGE term
(`max - min + 1`) cannot self-correct — it is blind to WHICH values
inside that range survived a deletion. Whenever an estimate is
**range-bound** (the range term is the smaller of the two, i.e.
`non_null >= range`) — the classic shape of a **low/moderate-cardinality
column**, e.g. a status/category/enum-like integer column — a DELETE
that removes every row of ONE distinct value (`DELETE FROM t WHERE
status = 'CANCELLED'`) can NEVER be reflected: the stale range still
spans that now-nonexistent value, so `ndv_est` stays exactly as high as
before the value was fully deleted. This is precisely the epic's own
named dangerous direction — "overestimating post-deletion NDV understates
true join selectivity" — just triggered by stale MIN/MAX, not a stale row
count. A **row-count-bound** column (typically a high-cardinality/
near-unique key, where `non_null < range`) has no such problem: its
estimate already shrinks correctly and exactly with the live row count,
independent of which specific values were deleted.

### The fix: query-time-only, in `native_table.rs`, zero mutation-path changes

`table_statistics_from` (`src/storage/native_table.rs`) now takes both
the LOGICAL (live) row count it already had AND a new PHYSICAL row count
argument (`segs.iter().map(|s| s.row_count).sum()`, computed at the
existing `statistics()` call site for both the whole-table and
sharded-provider branches — the same cheap, already-in-memory per-segment
fold every other statistic there already does, not a new I/O or scan of
any kind). From these it computes `deletion_fraction = 1 - live/physical`.

For each column whose `ndv_est` candidate is **range-bound**
(`candidate == range && non_null >= range`) AND `deletion_fraction >
DELETION_STALENESS_THRESHOLD` (10%, a deliberately modest, defensible
line — see the constant's own doc comment for the full reasoning: large
enough that an ordinary trickle of incidental deletes doesn't
permanently blacklist a mutated table's low-cardinality columns, small
enough to catch the concentrated single-value DELETE this fix targets),
`ndv_est` is emitted as `None` instead of the possibly-stale `Some(v)`.
A row-count-bound column is NEVER touched by this check — per the
finding above, it has no staleness problem to fix, so degrading it would
be pure false-positive noise.

**Per the epic's own "one shared signal, not two" architecture
decision** and exactly the reuse seam task 001's own Outcome named:
emitting `None` needs ZERO new classification/warning logic. The very
next time this column feeds a join edge, `JoinReorder`'s existing call
site (`src/optimizer/rules/join_reorder.rs::side_combined_ndv`,
unchanged since task 001) calls `crate::optimizer::classify_join_key_ndv`,
which classifies `None` as `UntrustworthyStats::Missing` and fires
`warn_untrustworthy_join_key_stats` — the identical warning task 001
built and validated, now reachable from a genuinely new call path with
no new code in `cost.rs`/`join_reorder.rs` at all. Confirmed directly
(not just by design): a new test asserts
`classify_join_key_ndv(category_after.ndv_est.map(|v| v as f64), ...)`
returns `Err(UntrustworthyStats::Missing)` for a post-delete degraded
column, calling task 001's own function verbatim.

**No full rescan, verified by the diff itself, not just by argument**:
`git diff --stat` against this task's start shows exactly ONE file
touched, `src/storage/native_table.rs` (plus one new test file) — zero
changes anywhere in `native_write.rs`, `native_delete.rs`, or
`native_update.rs`. The fix is entirely inside `TableProvider::
statistics()`'s existing O(active-segment-count) fold; it adds one more
cheap sum (`physical_row_count`) to a function that was already summing
`live_row_count()`/`byte_size` over the same segment list, and one
`f64` division per `statistics()` call — no new I/O, no new pass over
row data, nothing on the mutation write path changes shape or cost at
all. This directly satisfies the epic's own "no full rescans"
Architecture Decision and this task's own "no regression to mutation
performance" acceptance criterion by construction, not merely by
benchmark: the write/mutation entrypoints
(`insert_into_native_table`/`delete_from_native_table`/
`update_native_table` and their underlying `native_write.rs`/
`native_delete.rs`/`native_update.rs` machinery) are byte-for-byte
unchanged by this diff.

### Real test: a genuine SQL DELETE through the real mutation path

`tests/native_ndv_staleness_tests.rs` (new) drives the REAL end-to-end
path a user hits — `CREATE TABLE ... AS SELECT` -> `DELETE FROM ...
WHERE ...` (through `ExecutionContext::delete_from_native_table` ->
`native_delete::delete_from_native_table`, unchanged) -> re-query
`NativeTable::statistics()` — not just editing `deleted_rows` directly
the way `native_table.rs`'s own unit tests do (deliberately, to isolate
the read side; see that file's own established convention).

Built `cat_native` (`o_orderkey` dense 1..=1500, plus `category =
o_orderkey % 3` — a real, deliberately low-cardinality column) from the
real `data/tpch-1mb` fixture, 1500 rows.

- **`concentrated_delete_of_a_whole_category_degrades_its_ndv_and_the_
  shared_signal_fires`** — `DELETE FROM cat_native WHERE category = 2`
  (a meaningful, concentrated fraction: exactly 500 of 1500 rows, 33.3%,
  chosen specifically because it eliminates a whole distinct value —
  the precise shape a stale min/max range can never reflect). Before:
  `category.ndv_est == Some(3)` (exact). After: `category.ndv_est ==
  None` (correctly degraded — a naive re-derivation would have kept
  reporting `Some(3)` when the true post-delete NDV is 2, an
  overestimate). Directly confirms `classify_join_key_ndv` classifies
  this as `Missing`. Contrast case in the same test: `o_orderkey`
  (dense/unique, row-count-bound) correctly keeps `ndv_est ==
  Some(after.row_count)` — proves the fix is targeted, not a blanket
  "degrade everything after any delete" hammer.
- **`a_small_delete_that_does_not_eliminate_a_value_does_not_degrade_
  ndv`** — a real DELETE removing under 10% of rows (some, not all, of
  category 2's rows): `category.ndv_est` stays `Some(3)`, confirming no
  false-positive degradation from an ordinary small mutation.
- **`a_no_op_delete_leaves_statistics_unchanged`** — a predicate matching
  zero rows leaves `statistics()` byte-for-byte identical, confirming
  the overwhelmingly common "queried a never-meaningfully-mutated table"
  path pays nothing extra.

Plus 2 new hermetic unit tests in `src/storage/native_table.rs` (same
scenario, built directly against the manifest API rather than through
SQL, for a faster/more isolated companion check):
`concentrated_deletion_of_a_low_cardinality_value_degrades_its_ndv_to_missing`,
`a_light_deletion_below_the_staleness_threshold_does_not_degrade_ndv`.

### Known residual limitation, named honestly rather than silently narrowed

The `deletion_fraction` denominator is the table's CURRENT physical row
count across all active segments, which includes segments an UPDATE (or
a later INSERT) has since ADDED — a fully-tombstoned segment is dropped
from the manifest entirely (task 001 of native-tables-mutation's own
Decision 3), but a segment that still has SOME live rows is not. Over a
very long history of many small, partial (not whole-segment) mutations
against the same table, this denominator can grow over time even while
the numerator (total tombstoned rows) grows too, which could in
principle dilute `deletion_fraction` below the threshold for a table
whose range-bound columns are nonetheless genuinely stale from a much
earlier, now-diluted deletion. This is the same class of accepted,
honestly-documented residual risk as the native-tables-mutation epic's
own "O(N²) manifest rewrite cost" and "deletion-vector JSON density at
very large segment counts" findings (`CLAUDE.md`'s "No compaction"
section) — real, bounded, not observed to matter at any scale this
program's own fixtures/benchmarks reach today, and not fixable within
this task's query-time-only, no-full-rescan scope (a tighter fix would
need per-value provenance this cheap zone-map format does not, and by
design should not, carry).
