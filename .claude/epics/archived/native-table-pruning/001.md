# Task: Implement segment-level scan pruning

## Description

`NativeTable::scan_with_filter` (`src/storage/native_table.rs`) is not
overridden today — it's the `TableProvider` trait's default, which just
calls `scan(projection)` and ignores any filter entirely, so every query
decodes every active segment in full. Implement real pruning: evaluate a
pushed-down predicate against each active segment's `ColumnStats`
(min/max/null-count, `src/storage/native_manifest.rs`) and skip segments
that provably cannot match, before calling `ipc_cache::read_row_group` on
them.

Read `.claude/prds/native-table-pruning.md` and this epic's `epic.md` in
full before starting.

## Acceptance Criteria

- [x] Read `src/storage/row_group_pruning.rs` in full — the existing
      Parquet pruning logic (AND/OR/NOT/BETWEEN/InList against per-row-
      group min/max) is the pattern to mirror or directly adapt, not
      reinvent. Also read `src/storage/parquet.rs`'s
      `read_file_with_filter` to understand exactly how/when a predicate
      reaches `scan_with_filter` for Parquet today — trace the actual
      caller-side decision (physical planner? scan operator?), don't
      assume it's already provider-agnostic.
- [x] `NativeTable::scan_with_filter` implemented: for each active
      segment, evaluate the predicate against that segment's
      `ColumnStats`; skip (never decode) any segment provably
      unsatisfiable. A segment with no relevant stats (e.g. a string
      predicate, `ColumnStats` has no string min/max today) or an
      unrecognized predicate shape is always scanned, never skipped.
- [x] Wire whatever caller-side eligibility mechanism is needed so native
      tables actually receive pushed predicates the same way Parquet
      tables do — if the current mechanism already generalizes, confirm
      and say so; if it's Parquet-specific, extend it correctly.
- [x] Deletion vectors remain fully respected: pruning decides whether to
      read a segment at all; any segment that IS read still goes through
      the existing `deleted_rows` filter inside `scan()` unchanged.
- [x] Observable pruning decisions: enough tracing (matching this
      codebase's existing env-gated diagnostic convention, e.g.
      `PLAN_DEBUG`/`HJ_TIMING`-style) to directly confirm, not infer from
      wall-clock time, that a segment was actually skipped.
- [x] Cell-exact validation for this task's own scope: at least one
      multi-segment native table, a range and an equality predicate on a
      column with stats, pruning-on results identical to pruning-off
      results and to an independent DuckDB oracle.
- [x] No regression to unfiltered/full-scan queries, the write path, or
      any other table type.
- [x] Full suite green (`scripts/claude-safe-build.sh cargo test`, all
      feature combinations); `cargo fmt --all -- --check` clean.

## Outcome (closed 2026-08-27)

**Caller-side wiring: already provider-agnostic, confirmed by reading it,
not assumed.** `PhysicalPlanner::create_physical_plan_inner`'s
`LogicalPlan::Scan` arm (`src/physical/planner.rs`) branches on
`provider.parquet_files()`: `Some` takes the streaming-Parquet-specific
fast path (`StreamingParquetScanExec`); `None` (every other provider,
`NativeTable` included — `parquet_files()` is never overridden there)
falls to the generic path, which unconditionally calls
`provider.scan_with_filter(node.projection.as_deref(),
node.filter.as_ref())` regardless of provider type. This call site needed
ZERO changes — it already passes the real predicate to whatever
`scan_with_filter` a provider implements; the only reason native tables
never received real pruning is that `NativeTable` itself only had the
trait's default (`scan_with_filter` = `scan`, filter ignored). No changes
were made to `src/physical/planner.rs`.

**Implementation, `src/storage/native_table.rs`.** `NativeTable::
scan_with_filter` is now a real override: for each active segment (in the
same canonical id-ascending order `scan()` already uses), a new
`segment_might_match(predicate, &seg.column_stats) -> bool` decides
whether the segment could possibly contain matching rows; `false` means
`ipc_cache::read_row_group` is never called for that segment at all — the
segment is never decoded, never even opened. Whatever segments pass the
check go through the exact same `filter_deleted_rows` deletion-vector
step `scan()` already uses, unchanged.

`segment_might_match` mirrors `row_group_pruning.rs::row_group_might_match`'s
exact recursive shape — `AND`/`OR`/`NOT` (conservative)/`BETWEEN`/`InList`
— because `ColumnStats` (`min_i64`/`max_i64`/`min_f64`/`max_f64`, no string
bounds) is a fundamentally different representation from parquet's
`RowGroupMetaData`/`Statistics`, so the top-level walk and the stats
lookup had to be rewritten; but the three low-level range-evaluation
helpers (`flip_op`, `eval_range` for i64, `eval_range_f64`) were made
`pub(crate)` in `row_group_pruning.rs` and reused VERBATIM rather than
reimplemented — a deliberate "adapt, don't reinvent" choice matching the
epic's own Architecture Decision. `check_comparison` extracts `(col op
literal)` (handling both `col op literal` and `literal op col`, flipping
the operator), looks the column up by the SAME (unqualified, lowercase)
key convention `compute_batch_stats`/`ColumnStats` already use (so
`t.o_orderkey` and `o_orderkey` resolve identically), and dispatches by
the literal's exact `ScalarValue` variant into `check_i64_stats`/
`check_f64_stats` — each of which returns `true` (always scan, never
skip) whenever the column has no stats of that exact numeric family, no
cross-type float/int coercion is attempted (a possible future refinement,
not needed for TPC-H-shaped predicates and safer to omit than to get
subtly wrong).

**Correctness posture, unchanged from the design**: skip only on PROVABLE
non-match; any ambiguity (string/binary column, unrecognized predicate
shape, `NOT`, a non-column-vs-literal comparison, a literal type with no
zone-map) returns `true` (scan). The physical planner's `FilterExec`
above the scan (`node.filter` wrapping) re-applies the FULL predicate to
whatever segments are read regardless — pruning is strictly a skip
decision, never a substitute for correctness.

**Tracing** (`QE_DEBUG_NATIVE_PRUNING=1`, matching the existing
`QE_DEBUG_SCAN_BUDGET`/`QE_DEBUG_ROLLUP`/`QE_GPU_DEBUG` env-gated,
zero-cost-when-unset convention): every segment's skip/scan decision plus
a per-call `scanned=N skipped=M total=N+M` summary line to stderr.

**Real, traced confirmation a segment was actually skipped** (not
inferred from wall-clock time): `examples/native_pruning_check.rs`
(new), run against real, already-committed, on-disk multi-segment native
tables (`data/tpch-1gb-native/orders`, 2 segments, disjoint
`o_orderkey` ranges `[1,1048576]`/`[1048577,1500000]`; `data/tpch-1gb-
native/lineitem`, 6 segments, disjoint `l_orderkey` ranges). With
`QE_DEBUG_NATIVE_PRUNING=1`:
  - `o_orderkey <= 1000` (range): `segment=0 scan`, `segment=1 SKIP`,
    `scanned=1 skipped=1 total=2`.
  - `o_orderkey = 1200000` (equality): `segment=0 SKIP`, `segment=1
    scan`, `scanned=1 skipped=1 total=2`.
  - `l_orderkey > 1100000 AND l_orderkey < 1200000` (AND, lineitem):
    `segment=0/1/2/3/5 SKIP`, `segment=4 scan`, `scanned=1 skipped=5
    total=6` — 5 of 6 segments skipped from one AND-of-two-comparisons
    predicate.
  - `l_orderkey BETWEEN 1100001 AND 1199999` (BETWEEN, same bounds):
    identical trace — confirms the `Expr::Between` recursion path (not
    just the `AND` path) actually prunes.

**Cell-exact validation, this task's own scope**:
  - `examples/native_pruning_check.rs`'s own in-process cross-check:
    the SQL/planner path's (pruned) result compared against an
    independent, pruning-INDEPENDENT baseline (`TableProvider::scan(&provider,

    Equality: 1 == 1. Lineitem AND: 400284 == 400284. Lineitem BETWEEN:
    400284 == 400284 (and equals the AND result exactly, as it must).
  - Independent DuckDB oracle (`.venv/bin/python`, `duckdb 1.4.4`, same

    `data/tpch-1gb/{orders,lineitem}.parquet`): `o_orderkey <= 1000` ->

    `l_orderkey > 1100000 AND l_orderkey < 1200000` -> 400284;
    `l_orderkey BETWEEN 1100001 AND 1199999` -> 400284. All five match
    the engine's pruned results exactly.
  - 12 new hermetic unit tests in `src/storage/native_table.rs` (`cargo

    against synthetic `ColumnStats` for simple comparisons, flipped
    literal/column order, `AND` (both sides possible / both impossible /
    one impossible), `OR` (requires BOTH sides impossible to skip),
    `BETWEEN` (including `NOT BETWEEN` staying conservative), `InList`
    (including `NOT IN` staying conservative), `NOT` (always
    conservative), a column with zero stats (always scans), an
    unrecognized predicate shape (`ScalarFunc`, always scans), a
    qualified column name resolving identically to unqualified; plus two
    end-to-end tests against a REAL two-segment on-disk table built via
    `write_test_table` (task 002's own fixture): `scan_with_filter`
    skips exactly the provably-unsatisfiable segment for both a `<=` and

**Design decisions and why**:
1. **Reuse `row_group_pruning.rs`'s range-evaluation helpers verbatim**
   (`flip_op`/`eval_range`/`eval_range_f64` made `pub(crate)`), rather
   than duplicating the same `Eq`/`NotEq`/`Lt`/`LtEq`/`Gt`/`GtEq`-vs-
   `[min,max]` logic a second time. The top-level predicate walk and the
   column-stats lookup could not be shared (different statistics
   representation entirely), but the pure comparison-vs-range logic
   has nothing parquet-specific about it.
2. **No cross-type numeric coercion** (an `Int64` literal is only
   checked against `min_i64`/`max_i64`, a `Float64` literal only against
   `min_f64`/`max_f64` — never converted to compare against the other).
   TPC-H-shaped predicates never need this (the binder types a literal
   to match its column), and adding it would mean either an f64
   round-trip (a real precision-loss risk for large i64 values, which
   `row_group_pruning.rs`'s own `definite_comparison` accepts ONLY for
   its much narrower "definitely matches, drop the RowFilter" use case,
   not for a "provably does NOT match, skip the segment entirely"
   decision where an incorrect skip would be a correctness bug, not
   just a missed optimization) or extra type-family bookkeeping for a
   case that doesn't arise in practice. Simplicity chosen over
   generality here, matching this task's own "correctness over
   cleverness" charter.
3. **No new caller-side wiring.** Confirmed (not assumed) that
   `PhysicalPlanner`'s Scan arm already calls `scan_with_filter`
   unconditionally for any non-streaming-Parquet provider — `src/
   physical/planner.rs` was read in full and is untouched by this task.
4. **Tracing at the segment level, not the predicate level.** Matches
   `row_group_pruning.rs`'s own scope (no equivalent tracing exists
   there either) and this codebase's established "enough to confirm the
   mechanism fired, gated behind an env var, zero cost unset" bar —
   deeper predicate-evaluation tracing was not needed to satisfy this
   task's own acceptance criterion.

**Real-world impact on the Q4/Q12/Q13 regression named in CLAUDE.md's
"Current limitations"**: NOT separately re-measured by this task — that
measurement is task 002's explicit job (`epic.md`'s own task breakdown:
"002: Validation — cell-exact across predicate shapes, the Q4/Q12/Q13
before/after measurement... depends on 001"). This task's own real
traced result (5 of 6 lineitem segments skipped for a selective
`l_orderkey` range at SF=1 scale) is direct evidence the mechanism is
real and effective for range-selective predicates on stat-bearing
columns, which is a necessary precondition for task 002's own
measurement to have a chance of showing improvement — but Q4/Q12/Q13's
own predicates (date ranges on `l_shipdate`/`l_commitdate`/`l_receiptdate`,
per CLAUDE.md's own root-cause writeup) were not tested here, and this
task deliberately does not claim a verdict on them.
