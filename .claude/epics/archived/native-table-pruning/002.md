## Outcome (closed 2026-08-27)

**Broader cell-exact sweep** (`examples/native_pruning_sweep.rs`, new,
against `data/tpch-10gb-native` — 58-segment `lineitem`/60M rows,
15-segment `orders`/15M rows — cross-checked by
`scripts/native_pruning_sweep_check.py` against a fresh DuckDB oracle over
`data/tpch-10gb`): 10 predicate/table combinations, EVERY one cell-exact
three independent ways at once — the real pruned `NativeTable` SQL path,
an UNPRUNED `MemoryTable` snapshot of the SAME data queried through the
IDENTICAL SQL/FilterExec path (structurally cannot prune: `MemoryTable`
never overrides `scan_with_filter`), and DuckDB. All 10 `PASS`:
`lineitem.range` (`l_orderkey <= 300000`, 55/58 segments skipped, engine
1208363 == duckdb 1208363), `lineitem.equality` (`l_orderkey = 14500000`,
56/58 skipped, 1==1), `lineitem.multi_column_and` (`l_orderkey BETWEEN
5000000 AND 5500000 AND l_discount > 0.095` — two DIFFERENT column
families, i64 + f64 — 55/58 skipped, 100516==100516),
`lineitem.no_stats_string` (`l_shipmode = 'AIR'`, 0/58 skipped as
required, 8571429==8571429), `lineitem.spans_multiple_segments`
(`l_orderkey BETWEEN 300000 AND 2000000`, 50/58 skipped — some segments
skipped, some scanned, in the SAME query, 6796692==6796692),
`lineitem.date_range_q4_shape` (`l_shipdate BETWEEN DATE '1996-03-01' AND
DATE '1996-03-31'`, 0/58 skipped — see Q4/Q12/Q13 finding below,
726445==726445), `orders.range`/`orders.equality` (14/15 skipped each,
500000==500000, 1==1), plus both tables' unfiltered `COUNT(*)` matching
their manifest row counts exactly (60000000, 15000000). Every skip/scan
decision independently confirmed via `QE_DEBUG_NATIVE_PRUNING=1` tracing,
not inferred.

**Real before/after measurement on Q4/Q12/Q13** (two release binaries:
`before` built from `e0e10cc`, the commit immediately preceding this
epic's own PRD/task creation; `after` this branch's HEAD — both reading
the IDENTICAL on-disk native table directories, so any timing difference
is attributable ONLY to the pruning mechanism):

*SF=10* (`data/tpch-10gb-native`, all 22 queries, best-of-5,
`scripts/native_pruning_before_after.py`):

| query | before (ms) | after (ms) | ratio |
|---|---|---|---|
| Q4  | 114.9 | 121.6 | 1.058 (6% slower) |
| Q12 | 3267.2 | 3235.0 | 0.990 (flat, within noise) |
| Q13 | 674.9 | 702.7 | 1.041 (4% slower) |
| TOTAL (22 queries) | 8525.6 | 8566.5 | 1.005 (+0.5%, flat/noise) |

A second, independent run (best-of-2) shows the same pattern (Q4 +14%,
Q12 -0.7%, Q13 +6%, total +1.1%) — consistent, not a one-off.

*SF=100* (`data/tpch-100gb-native`, Q4/Q12/Q13 only,
`scripts/native_pruning_before_after.py --skip-sf10-full`):
- **Q4**: FAILS identically before and after — `SEMI join build side
  exceeds the memory budget, but the join spill path currently supports
  only INNER joins`. Q4's `EXISTS` subquery compiles to a SEMI join; a
  DIFFERENT, previously-undocumented `SpillableHashJoinExec` gap, wholly
  unrelated to pruning (a safe refusal, not a crash or wrong answer).
- **Q12**: first (cold-cache) run showed before=59497ms, after=33743ms —
  a misleading 43% "speedup." Caught the confound (the `before` run reads
  ~65GB of native table data from cold disk/page-cache; `after` runs
  second, warm) and re-ran BOTH binaries with the cache already warm from
  that first pass: before=46041ms, after=46027ms — 0.03%, pure noise. NO
  measurable difference once cache-controlled.
- **Q13**: FAILS on both — `before` times out at 900s (never completes in
  a reasonable time); `after` fails fast with a pre-existing
  `SpillableHashJoinExec` temp-file-rename error, unrelated to pruning
  (neither this task's `MemoryTable` fix nor task 001's pruning logic
  touches the spill temp-file path at all).

**Root cause of "pruning doesn't help Q4/Q12/Q13," confirmed directly, not
inferred**: `l_orderkey`/`o_orderkey` ARE disjoint per segment (write path
preserves source-parquet order, which IS key order — ideal for min/max
pruning). But Q4/Q12/Q13's own selective predicates are DATE-range filters
(`o_orderdate`, `l_receiptdate`, `l_commitdate`/`l_shipdate`), and this
generator's dates are NOT correlated with write order — inspected
directly via each table's `_manifest.json`: EVERY lineitem segment
(58/58) reports `l_shipdate` min=8035/max=10591, the table's FULL date
range, and orders' `o_orderdate` is identical (every one of the first 6
and last 3 segments checked spans 8035-10591). A date-range predicate is
therefore provably unsatisfiable against ZERO segments — confirmed via
the sweep's own `date_range_q4_shape` trace: `scanned=58 skipped=0`. With
nothing prunable, `segment_might_match`'s own small per-segment
evaluation cost has nothing to offset, which is exactly the measured
small slowdown on Q4/Q13 (Q12's own cost is dominated by the join spill
itself, swamping the tiny pruning overhead into noise).

**No-regression check, targeted** (isolated from the mixed 22-query
sweep): genuinely unfiltered `SELECT COUNT(*) FROM lineitem` /
`FROM orders` (no `WHERE` at all, the `filter: None` early-return path),
best-of-5, both binaries: `lineitem` 33.5ms → 30.6ms, `orders` 9.8ms →
8.3ms — both slightly FASTER after (within measurement noise), certainly
not slower. Confirms `filter: None` degrades to byte-identical `scan()`
behavior with zero added cost, exactly as designed.

**A real bug found and fixed**: this task's "pruned vs. unpruned" sweep
methodology (registering a native table's own unfiltered `scan()` output
as a second `MemoryTable`) was the FIRST thing in this codebase's history
to push a projection down to `MemoryTable::scan` for data carrying a
dictionary-coerced column under a plain-`Utf8`-declared schema — exactly
what a native table's own `scan(None)` output looks like. It failed
outright: `MemoryTable::scan(Some(indices))` built the projected schema
from the DECLARED field types, not the batches' ACTUAL column types, so
`RecordBatch::try_new` errored ("expected Utf8 but found
Dictionary(Int32, Utf8)"). Root-caused via a minimal standalone repro
(`examples/repro_dict_filter{,2,3}.rs`, used to isolate the bug then
deleted — not part of the final diff), confirmed NOT reproducible on a
single native table alone (only when re-registered as `MemoryTable`), and
fixed in `src/physical/operators/scan.rs` by applying the SAME "field
types follow the actual columns" reconciliation `MemoryTableExec::
execute`'s own `rewrap` (a few lines below in the same file) already
uses — this codebase's established pattern for this exact
declared-vs-actual-type bug class (previously also fixed in
`ProjectExec::project_batch`, `hash_join.rs`'s `batch_with_actual_types`,
and 3 spill-path call sites by the mutation epic's own QA close-out). One
new regression test:
`memory_table_scan_projection_tolerates_declared_vs_actual_dictionary_mismatch`
(`src/physical/operators/scan.rs`), a hermetic unit test reproducing the
exact shape (declared Utf8, actual Dictionary(Int32, Utf8)) without
needing a real native table, asserting both the projected-column-type-
follows-actual behavior AND that a column whose type DOES match keeps its
original field metadata.
