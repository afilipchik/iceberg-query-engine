# Task: INSERT — Append write mode + SQL wiring

## Description

`INSERT INTO <native table> SELECT ...` — the simplest of this epic's
three mutations, and the only one that doesn't need the deletion-vector
mechanism at all: it just writes new, immutable segments (exactly like
phase 1's write path already does) and extends the existing manifest
rather than replacing it wholesale. Delivers standalone value even before
DELETE/UPDATE exist — a native table stops being "load once, done."

## Acceptance Criteria

- [x] `NativeWriteMode::Append` (new variant) in `src/storage/
      native_write.rs`: writes new segment(s) using the exact same
      streaming, bounded-memory discipline phase 1's `Create`/`Overwrite`
      modes already use (task 003's own Outcome measured ~406MB peak RSS
      converting 60M rows — this mode must hold the same bound, verified
      not assumed).
- [x] Manifest update uses task 001's decided atomic-publish mechanism:
      new segments' entries appended to `segments: Vec<Segment>`,
      `table_stats` re-rolled up to include the new segments (reuse
      phase 1's existing rollup/merge functions — find their exact names
      in `native_manifest.rs` rather than reimplementing), `snapshot.
      version` bumped, `table_id` preserved.
- [x] `Statement::Insert` handled in `Binder::bind()` — new match arm,
      following the `CreateTable` arm's established shape: bind the
      `INSERT`'s source query via the existing `bind_query()` (confirmed
      by task 001 to work the same way), refuse (by name) any `Insert`
      shape this epic doesn't support (e.g. `INSERT ... VALUES` with
      literal rows, if task 001 scoped this to `INSERT ... SELECT` only —
      check its decision) exactly as thoroughly as the `CreateTable` arm
      refuses its ~57 unsupported struct fields — mechanically verified
      against the real `sqlparser::ast::Insert` struct, not eyeballed.
- [x] A new `ExecutionContext` entrypoint (e.g. `insert_into_native_table`)
      following `create_table_as_select`'s shape — `&mut self`, streams
      the source query's `RecordBatchStream` directly into
      `NativeWriteMode::Append`, does not go through `sql()`'s
      materializing path.
- [x] Wired into the REPL (`src/main.rs`) alongside `CREATE TABLE`'s
      existing dispatch.
- [x] Cell-exact validation: insert into a native table, compare against
      an independently-computed reference (e.g. re-running the
      equivalent combined query directly against the original source).
      Cover: inserting into a table that already has data from CTAS;
      inserting an empty result set (zero new rows — must not corrupt
      the manifest or crash); a schema mismatch between the INSERT
      source and the target table (must be a named, clean error, never
      silent coercion or corruption).
- [x] `statistics()`/`distributed_splits()` correctly reflect the
      post-insert state (new segments show up, rollup stats update) —
      re-run phase 1's own relevant tests against a post-insert table,
      not just a freshly-created one.
- [x] No regression to `CREATE TABLE ... AS SELECT` or the CLI write path
      — both existing modes (`Create`/`Overwrite`) stay byte-for-byte
      unchanged in behavior.
- [x] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Populated by task 001's decisions — read `001.md`'s Outcome section in
full before starting. Summary of what directly shapes this task
(Decisions 4 and 6 are the most load-bearing here):

- **Atomic publish (Decision 4) — do NOT reuse `native_manifest::
  publish_table_dir` unchanged.** It does `remove_dir_all(final_dir)`
  then `rename(staging, final_dir)` — correct only when staging is a
  complete, self-sufficient replacement (Create/Overwrite), and would
  silently delete every pre-existing segment file if called on an
  Append's partial staging set. Instead: write new segment file(s)
  DIRECTLY into the LIVE table directory (not a fresh staging dir) under
  fresh, non-colliding segment ids —
  `existing_manifest.segments.iter().map(|s| s.id).max().unwrap_or(0) + 1..`,
  never restarting at 0 (a real bug `SegmentWriter::new`'s current
  `next_id: 0` would silently reintroduce if reused as-is for Append).
  Then build ONE new `Vec<Segment>` (existing segments unchanged + new
  segments' entries), call the EXISTING `NativeManifest::build(&schema,
  table_id, version + 1, new_segments, now_ms)` UNCHANGED (it already
  derives `row_count`/`table_stats` fresh via `Self::rollup` — no new
  merge function needed), write it to a temp file inside the same
  directory, then `std::fs::rename(tmp, native_manifest::manifest_path
  (dir))` — ONE atomic file-level rename (POSIX guarantees this the
  same as a directory rename, the primitive `publish_table_dir` already
  trusts). A crash before this rename leaves orphan segment files
  nothing references yet (harmless) and the OLD manifest fully intact.
- **Single-writer lock (Decision 5)**: acquire `std::fs::File::
  try_lock()` (stable std, zero new dependency — confirmed against
  `rustc 1.93.0`'s shipped std source) on a sibling lock path (e.g.
  `final_dir.with_file_name(format!("{name}.lock"))`, mirroring
  `staging_dir_for`'s own sibling-path convention) BEFORE reading the
  existing manifest, hold it for the whole read-modify-write-publish
  span via an RAII guard, release on every exit path (guard `Drop`, plus
  the kernel auto-releases on a crash — verified live via a
  SIGKILL test, see 001.md's Outcome Decision 5). On contention
  (`TryLockError::WouldBlock`), fail with `QueryError::Storage` naming
  the table directory — no new error variant needed.
- **Schema/dictionary inheritance, not rediscovery (Decision 6)** — the
  concrete trap to avoid: `SegmentWriter::accept` today validates ONLY
  column count, and `SegmentWriter::flush`'s dictionary-candidacy
  decision is made fresh from whatever data it's FIRST given. Neither
  is correct for Append: the new segments must conform to the TARGET
  table's ALREADY-DECLARED schema (`NativeManifest::arrow_schema()`),
  both in column name/type (validate before writing; a mismatch is a
  clean, named `Err`, never silent coercion — this task's own
  acceptance criterion) and in which columns are dictionary-encoded
  (read the decision from the existing manifest's `ManifestDataType::
  Dictionary` fields and apply it unconditionally to every new batch,
  never re-derive it from the new data's own cardinality).
- **`require_supported_insert_shape`**, mirroring
  `require_supported_create_table_shape`'s exact discipline (mechanical,
  checked against the real `sqlparser::ast::Insert` struct — ~26
  semantic fields, confirmed via `.scratch/mutation_sqlparser_spike/`).
  Accept: `table` (name only), `source: Some(Query)` (SELECT- or
  VALUES-bodied — both bind via the SAME existing `bind_query()`, `
  SetExpr::Values` already has a binder arm at `binder.rs:653`, so
  `INSERT ... VALUES` needs zero extra binder work), `selection`
  implicitly via the source query. Refuse by name: non-empty `columns`
  (explicit column list/reordering — not supported, matches CTAS's own
  `ct.columns` refusal), `overwrite: true` (Hive `INSERT OVERWRITE
  TABLE` — silently treating this as Append would be a real semantic
  bug), non-empty `assignments` (MySQL `INSERT ... SET`), `on.is_some()`
  (`ON CONFLICT`/`ON DUPLICATE KEY UPDATE` — upsert, out of scope),
  `returning`, `output`, `partitioned`, `table_alias`, `replace_into`,
  and the rest of the struct's fields.
- **The wildcard-qualification bug, known from phase 1, must not
  reappear**: `SELECT * FROM src` produces table-qualified field names
  (`"src.col"`) via `Binder::bind_select_items`'s `Wildcard` arm — phase
  1 tasks 003/004 each independently hit and fixed this for CTAS. INSERT
  must re-wrap the source stream's batches against the TARGET's existing
  schema by position (`RecordBatch::try_new(target_schema,
  batch.columns().to_vec())`, the same pattern `create_table_as_select`
  already uses), never trust the source query's own field names — this
  is even more direct for INSERT than it was for CTAS, since the target
  schema already exists.
- **Reusable building block for task 004 (UPDATE)**: per Decision 2,
  expose the segment-writing core as a function that writes segments and
  returns their `Segment` entries WITHOUT touching or publishing the
  manifest (the publish steps above factored into a separate, thin
  wrapper) — task 004 needs to compose this with task 003's own
  non-publishing DELETE core into ONE atomic publish, not call two
  separate self-publishing entrypoints sequentially.
- New CLI/`ExecutionContext` entrypoint naming, streaming discipline
  (never through `sql()`'s materializing path), and cell-exact
  validation expectations are unchanged from this file's own existing
  Acceptance Criteria above — nothing in task 001's findings changes
  those.

## Outcome (closed 2026-08-24)

`INSERT INTO <native table> SELECT ...` / `INSERT INTO <native table>
VALUES (...)` implemented end to end, on top of task 001's design spike
decisions. The write-path core is deliberately factored into clean,
independently-reusable, non-publishing building blocks — task 003
(DELETE) and task 004 (UPDATE) should call these directly rather than
re-deriving equivalent logic; exact signatures below are the load-bearing
contract, precise enough that neither task should need to read this
task's source to use them correctly.

### `src/storage/native_write.rs` — the write path

**New enum variant**:
```rust
pub enum NativeWriteMode { Create, Overwrite, Append }
```
`"append"` now parses via `NativeWriteMode::from_str`. `write_batches`/
`write_batches_with_options(stream, schema, out_dir, NativeWriteMode::
Append, options)` dispatch to `append_to_native_table` internally (the
`schema` parameter is IGNORED for this mode — the target's schema always
comes from its existing manifest) and adapt the richer
`NativeAppendResult` down to the pre-existing `NativeWriteResult` shape
(`rows`/`segments` there mean the table's TOTALS after the append, for
CLI/`write-native --mode append` parity with Create/Overwrite's own
"whole table" semantics) — zero changes to the Create/Overwrite code
paths themselves (the `Append` branch is a separate, early return before
any Create/Overwrite-specific logic runs).

**Result types**:
```rust
pub struct NativeAppendResult {
    pub table_id: String,       // unchanged by an Append
    pub version: u64,           // == pre-append version if rows_appended == 0 (no-op)
    pub rows_appended: u64,     // 0 for an empty source -- not an error
    pub segments_appended: usize,
    pub total_rows: u64,        // table's TOTAL row count after this append
    pub total_segments: usize,  // table's TOTAL segment count after this append
}
```
(`NativeWriteResult` — pre-existing, unchanged shape — is what
`write_batches_with_options` returns for ALL three modes; its
`rows`/`segments` mean "whole table" for Create/Overwrite and, for
Append, are populated from `NativeAppendResult`'s `total_rows`/
`total_segments`, NOT the delta.)

**Building block 1 — single-writer lock** (task 001 Decision 5):
```rust
pub fn lock_path_for(final_dir: &Path) -> PathBuf;          // final_dir's sibling `<name>.lock`
pub fn lock_table_for_write(final_dir: &Path) -> Result<TableWriteLock>;
```
`TableWriteLock` is an RAII guard (`std::fs::File::try_lock()`, Drop
calls `unlock()`). Non-blocking: `QueryError::Storage` naming
`final_dir` immediately on contention. **Must be acquired ONCE by
whichever function owns the whole mutation, BEFORE reading the existing
manifest, and held for the entire read-modify-write-publish span** — do
NOT have each building block acquire its own lock; task 004 (UPDATE)
needs to hold ONE lock across both its DELETE-identification and its
Append-write steps.

**Building block 2 — non-publishing write core**:
```rust
pub async fn write_append_segments(
    stream: RecordBatchStream,
    target: &NativeManifest,   // the EXISTING manifest -- schema/dict decision/next-id all read from this
    table_dir: &Path,          // the LIVE table directory -- segments written DIRECTLY here, no staging
    options: NativeWriteOptions,
) -> Result<Vec<Segment>>;     // ONLY the new segments -- does NOT read, build, or publish any manifest
```
Casts every batch BY POSITION to `target.arrow_schema()` (exact type
match, or plain-Utf8-source-into-target's-existing-Dictionary — the
one sanctioned coercion; anything else is `QueryError::Type`, checked
before any write). New segment ids continue from
`target.segments.iter().map(|s| s.id).max().unwrap_or(0) + 1..` — never
restart at 0. Zero-row source → `Ok(vec![])`, not an error. Callers
should pre-strip incidental Dictionary encoding from source batches
first (e.g. via `decode_dictionary_batch`, mirroring
`create_table_as_select`) — this function does not decode a
Dictionary-encoded source column back to plain.

**Building block 3 — non-locking publish core**:
```rust
pub fn publish_manifest_update(
    table_dir: &Path,
    schema: &Schema,
    table_id: impl Into<String>,
    version: u64,
    segments: Vec<Segment>,    // the CALLER-assembled COMPLETE segment list (old + new / tombstoned)
    created_at_ms: i64,
) -> Result<NativeManifest>;
```
Calls `NativeManifest::build` (existing, unchanged — re-derives
`row_count`/`table_stats` from `segments`) then
`native_manifest::write_manifest_atomic` (new, below). Does NOT lock —
caller must already hold `TableWriteLock`.

**The new atomic-publish primitive it calls** (`src/storage/
native_manifest.rs`, purely additive, sibling to `publish_table_dir`):
```rust
pub fn write_manifest_atomic(dir: &Path, manifest: &NativeManifest) -> Result<()>;
```
Validates `manifest`, writes it to `dir/_manifest.json.tmp-<pid>`, then
`std::fs::rename`s that onto `dir/_manifest.json` — ONE atomic
single-FILE rename. Touches NOTHING else in `dir` (unlike
`publish_table_dir`'s whole-directory `remove_dir_all`+`rename` — do
NOT use `publish_table_dir` for any incremental mutation).

**Self-publishing entrypoint** (composes all three blocks; what
`ExecutionContext::insert_into_native_table` and `write_batches_with_
options(..., Append, ...)` both call):
```rust
pub async fn append_to_native_table(
    stream: RecordBatchStream,
    table_dir: impl AsRef<Path>,
    options: NativeWriteOptions,
) -> Result<NativeAppendResult>;
```
Sequence: `lock_table_for_write` → `native_manifest::read_manifest` →
`write_append_segments` → (if empty, return the table's unchanged
current state, no publish) → assemble `existing.segments.clone()` +
new → `publish_manifest_update(table_dir, existing.arrow_schema().
as_ref(), existing.table_id.clone(), existing.snapshot.version + 1,
all_segments, now_ms())`. `table_dir` MUST already be a native table
(`native_manifest::read_manifest`'s own clean `QueryError::Storage`
otherwise — Append never creates a table).

**Task 004 (UPDATE)'s expected composition**, per task 001's Decision 2
(do NOT call two self-publishing entrypoints sequentially): acquire
`lock_table_for_write` ONCE → read the manifest ONCE → call task 003's
own non-publishing DELETE-identification block (tombstoned/edited
segments) → evaluate SET expressions into new-row batches → call
`write_append_segments` on those batches against the SAME already-read
manifest → fold DELETE's edited segments + Append's new segments into
ONE `Vec<Segment>` → call `publish_manifest_update` ONCE.

### `src/planner/binder.rs`

```rust
pub fn insert_target_name(stmt: &Statement) -> Option<String>;
```
Mirrors `create_table_target_name`: `Some(name)` for
`Statement::Insert` whose `table` is `TableObject::TableName`, `None`
for `TableObject::TableFunction`/`TableObject::TableQuery` (both refused
downstream) and every other statement kind. Extraction is deliberately
separate from validation (same split as `create_table_target_name`).

`Binder::bind()` gained a `Statement::Insert(insert)` arm: calls the
private `require_supported_insert_shape(insert)` (mechanically checked
against all 26 fields of sqlparser 0.62's real `ast::Insert` struct —
refuses explicit column lists, Hive `INSERT OVERWRITE`, `ON CONFLICT`/
`ON DUPLICATE KEY UPDATE`, MySQL `INSERT...SET`/alias/priority,
ClickHouse `SETTINGS`/`FORMAT`, Snowflake multi-table `INSERT ALL/
FIRST`, `RETURNING`/`OUTPUT`, a table alias, and a non-`TableName`
target — full list in the function itself), then binds `insert.source`
(required; `None` is refused with a named error) via the EXISTING
`bind_query()` — returns ONLY that source query's `LogicalPlan`, no new
DML node, identical shape to the `CreateTable` arm. `INSERT ... VALUES`
is SUPPORTED (not refused): confirmed to bind via the pre-existing
`SetExpr::Values` arm in `bind_set_expr` with zero extra binder work.

### `src/execution/context.rs`

```rust
pub struct InsertResult {
    pub table_name: String,
    pub table_id: String,
    pub version: u64,
    pub rows_inserted: u64,     // == NativeAppendResult::rows_appended
    pub segments_added: usize,  // == NativeAppendResult::segments_appended
    pub total_rows: u64,        // == NativeAppendResult::total_rows
    pub elapsed: Duration,
}

pub async fn ExecutionContext::insert_into_native_table(&mut self, sql: &str) -> Result<InsertResult>;
```
Shape mirrors `create_table_as_select`: parse → `insert_target_name`
(→ `InvalidArgument` if not an INSERT) → look up the target in
`self.tables` (→ `TableNotFound` if unregistered — INSERT never
auto-discovers a table under `native_table_root()`, matching every
other table access's "register before you reference it" contract) →
downcast to `NativeTable` via `TableProvider::as_any()` (→
`InvalidArgument` if the target isn't a native table) → `Binder::bind()`
(validates shape + binds source) → optimize → physical-plan → execute
every partition, `decode_dictionary_batch` each (strips INCIDENTAL
Dictionary encoding only — real target-schema conformance happens
inside `write_append_segments`) → merge via `futures::stream::
select_all` (same pattern `create_table_as_select` already uses) →
`native_write::append_to_native_table` → `register_native_table` again
(so the new rows are visible in the same session, mirroring
`create_table_as_select`'s own "make it immediately queryable" step).

`ExecutionContext::sql()` gained the same INSERT-refusal guard it
already had for CREATE TABLE (necessary, not optional, once `bind()`
accepts `Statement::Insert` — otherwise `sql()` would silently execute
only the source query and insert nothing): `InvalidArgument` naming
`insert_into_native_table` as the correct entrypoint.

### A real, pre-existing bug found and fixed (in scope)

`LogicalPlan::Values`'s physical planning (`src/physical/planner.rs`)
was an unimplemented stub — `MemoryTableExec::new("values", schema,
vec![], None)`, always zero rows regardless of the literal `VALUES`
rows, with the code's own comment saying so ("For now, return empty").
This silently made EVERY `VALUES (...)` clause anywhere in the engine a
permanent no-op; no existing test anywhere in the suite exercised
literal `VALUES` SQL text (confirmed via grep before fixing), so it was
genuinely dead, untested code, not a regression risk. It directly broke
`INSERT ... VALUES` (found via a genuinely failing integration test —
`rows_inserted` came back `0` instead of `1` — not by code inspection).
Fixed by evaluating each row's expressions with the existing
`evaluate_expr` (`physical::operators::evaluate_expr`) against a
1-row/0-column dummy batch — the SAME trick `LogicalPlan::EmptyRelation`
already uses one match arm above for a table-less `SELECT <literal>` —
then `arrow::compute::concat`-ing per column. Fixes `VALUES (...)`
everywhere in the engine (confirmed the ONLY construction site is
`bind_set_expr`'s `SetExpr::Values` arm; every other reference is a
read-only pattern match on the logical node, unaffected). Zero
regression risk confirmed both by the "no prior test exercised this"
grep and by the full suite staying green.

### Memory — measured, not assumed (two premises, reported separately)

`examples/native_append_memory_check.rs`, `QE_MEM_CHECK_MODE=direct|sql`,
appending SF=10 `lineitem` (60,000,000 rows, 2.8GB compressed) to an
existing native table, `/usr/bin/time -v`:

| mode | what it measures | peak RSS |
|---|---|---|
| `direct` | `append_to_native_table` called directly, fed by `StreamingParquetReader` — apples-to-apples with task 003's own `write_from_parquet` methodology | **328MB** — better than task 003's own 406MB CREATE-mode baseline for the same row count |
| `sql` | the full `INSERT INTO t SELECT * FROM lineitem_src` statement via `insert_into_native_table` | **~5.3GB** |

The `direct` number is the load-bearing confirmation of this task's own
acceptance criterion (Append's write core holds Create/Overwrite's
bound, verified not assumed). The `sql` number's gap is root-caused, not
just observed: `StreamingParquetScanExec::output_partitions()` returns
one partition per row-group work item, and `insert_into_native_table`
(IDENTICAL structure to `create_table_as_select`, confirmed by reading
both) drives every partition via `physical.execute(partition_id)` and
merges them all with `futures::stream::select_all` before the
single-threaded Append writer drains them — many partitions' worth of
decoded parquet data can be "in flight" concurrently, no backpressure.
Confirmed PRE-EXISTING and CTAS-shared (`create_table_as_select` has the
identical code shape), not introduced by this task's Append core —
named as a residual risk in CLAUDE.md for a future task, not fixed here
(would mean changing the engine's generic multi-partition scan/
stream-merge pattern well outside this task's own charter).
