- **Compaction is confirmed OUT OF SCOPE for this epic** (Decision 3,
  not merely "if task 001 deferred it" as this file's own acceptance
  criteria conditionally phrase it) — the CLAUDE.md update this task
  writes should state this explicitly, alongside the one in-scope
  exception task 003 implements (a 100%-tombstoned segment is dropped
  from the manifest, which is not full compaction). State the honest,
  named cost: segment count grows with every Append/INSERT, and disk
  space from partial deletes is never physically reclaimed.
- **Single-writer only, enforced via `std::fs::File::try_lock()`**
  (Decision 5) — document this in CLAUDE.md as this epic did for
  memory safety in phase 1: name the mechanism, and its explicit scope
  boundary (process-crash-safe via kernel-released `flock`, verified
  live; NOT `fsync`/power-loss-durable beyond the OS's own page-cache
  behavior — matching, not narrowing, phase 1's own established scope).
- **A never-mutated table must show zero regression** — the deletion-
  vector consultation inside `scan()` is designed as a fast no-op for a
  segment with an empty `deleted_rows` (the state of every segment
  phase 1 ever wrote, and of any segment untouched by a DELETE since).
  This task's benchmark should include this as an EXPLICIT case (not
  just "mutation doesn't regress a mutated table's later reads"): a
  freshly-CTAS'd table's read performance, post this epic's code
  landing, should match phase 1's own recorded SF=10 numbers (5.324s,
  1.23x DuckDB-parquet) within noise — confirming the new code path
  costs nothing when it has nothing to filter.
- **Atomic-publish mechanism to document**: single-file atomic
  `rename()` of a freshly-written manifest onto the live
  `_manifest.json`, generalizing phase 1's whole-directory
  `publish_table_dir` (used unchanged only by Create/Overwrite) — worth
  a CLAUDE.md line distinguishing the two, since a future reader might
  otherwise assume one mechanism covers all write modes.

## Outcome (closed 2026-08-24)

Full detail — every number, every code pointer, every command to
reproduce — lives in two places by design (this task's own job was
largely to populate them, not to duplicate them a third time here):
CLAUDE.md's "Mutation: QA close-out (task 006)" section (the technical
narrative: what was tested, what broke, what was fixed, what was found
and left unfixed, every benchmark table) and this epic's own `epic.md`
close-out section (the program-management view: per-task attribution
across all 6 tasks, G1-G5 verdicts, residues, deferred work, commits).
This section is the short version.

**QA found real problems and fixed most of them.** Real-scale (SF=10,
not the ~1500-row fixtures individual tasks used) validation is what
this task's whole charter demanded, and it delivered exactly what that
discipline is for: a plain `SELECT * FROM <native table> ORDER BY ...`
over 15,000,000 rows — the very first query in this task's own cell-
exact validation script — crashed outright. Root-caused to a real,
pre-existing (NOT mutation-specific; reproduces on phase 1's own
never-mutated fixtures) bug: `ExternalSortExec`'s and
`SpillableHashJoinExec`'s SPILL paths (the ALWAYS-used spillable
operators) never reconciled their declared output schema (which has no
Dictionary representation) against Dictionary-encoded actual data —
three OTHER operators in this codebase already carry the fix for this
exact class of bug; the spill-specific code just never got it. Fixed at
all 3 missing call sites, plus one genuinely separate k-way-merge
staleness bug in the same file (found while re-testing after the first
fix), with 4 new regression tests. Once fixed, the real-scale cell-exact
validation this task exists to perform ran clean: 14,507,798 rows, 0
cells different from an independent DuckDB DML reference.

**QA also found something it deliberately did NOT fix.** Re-running the
benchmark after the crash fix revealed TPC-H Q12's spilling join
completes but returns a WRONG (2x-inflated) answer after ~320 seconds —
a SEPARATE, deeper bug in the same operator's partition/spill algorithm,
investigated but not confidently root-caused within this task's own
time budget. This directly contradicts CLAUDE.md's own prior claim
(from phase 1) that this exact situation was "always... never wrong
data" — that claim was only true because the now-fixed crash always
fired first. Documented in full, including the explicit reasoning for
NOT reverting the 3 schema fixes to restore the crash as an accidental
safety net (the duplication bug is not Dictionary-specific, so it is
reachable by any large spilling INNER join regardless — reverting would
narrow, not close, the real exposure, while regressing the now-verified
15M-row sort case this task's own validation depends on). This is the
single most important residue of the whole epic and is named as such in
`epic.md`'s own close-out.

**Everything else this task's acceptance criteria asked for came back
clean**: full suite green in all 4 feature combinations (final state,
fixes included), never-mutated table performance matches phase 1's own
recorded numbers within noise, a mutated table's real read-performance
cost is measured and honestly explained (not hidden), dense-direct-
address and GPU offload both still fire correctly post-mutation (GPU's
speedup specifically shown to be masked by deletion-vector overhead,
with a clean CPU/GPU x pristine/mutated 2x2 comparison as evidence),
M1/M2 distributed gates PASS, and all 5 of this epic's own G1-G5 success
criteria are MET with evidence, not asserted.
