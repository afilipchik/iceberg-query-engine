# Task: Design spike — deletion mechanism, UPDATE semantics, compaction scope, atomic-publish model

## Description

This epic's Architecture Decisions section is explicit that five real
design questions gate everything else and must be resolved with evidence,
not assumption — mirroring phase 1's own task 001, whose SQL-DDL-scope
and manifest-format decisions unblocked its entire epic without rework.
This epic's stakes are higher: phase 1 substantially exposed an
already-proven mechanism (the IPC sidecar); this epic builds genuinely
new infrastructure (mutation) the engine has never had in any form.

### Decision 1 — Deletion mechanism: a per-segment sorted deletion
vector (`Vec<u32>` of local row positions), stored as a NEW field
inline on the EXISTING `Segment` struct in `_manifest.json` — not
roaring, not a sibling file, not copy-on-write

**Copy-on-write vs. merge-on-read, decided from this engine's actual
segment format, not generically.** Segments are immutable Arrow IPC
files, one per `Segment` manifest entry, read via
`ipc_cache::read_row_group` — mmap zero-copy
(`Buffer::from_custom_allocation`), no in-place mutation mechanism
exists or is being built (`native_manifest.rs`'s own module doc: "Read
mechanism, confirmed reusable UNCHANGED, zero refactor needed"). A
copy-on-write DELETE would have to re-read, re-filter and re-write
EVERY segment touched by the predicate on every single DELETE — for a
`WHERE` clause matching even 1 row of a 1,000,000-row segment (the
default `target_rows_per_segment`), that is a full 1M-row rewrite for a
1-row logical change: real write amplification, and it directly
violates the epic's own stated preference ("bounded read-time cost, no
write amplification on every delete"). A deletion vector instead costs
O(matched rows) to WRITE (append positions to a small list) and O(1)
extra work per SCANNED row to CONSULT (a sorted-list/set membership
check, or — see below — a bitmap bit-test), paid only by future reads,
and never touches segment bytes at all. **Recommendation: merge-on-read
deletion vector**, confirmed against this engine's actual shape, not
assumed from industry convention.

**Correcting the epic's own stated precedent.** `epic.md`'s Architecture
Decisions section claims deletion vectors are "one this codebase already
has read-side precedent for via `src/storage/iceberg.rs`." Read in full:
this is not accurate. `src/storage/iceberg.rs::data_files_of` (lines
258-268) REFUSES any Iceberg table containing delete files outright —
`content != 0` (position or equality deletes) is a hard
`QueryError::NotImplemented("... row-level deletes are not supported —
compact the table first")`, not consulted. There is no existing
deletion-vector *consultation* code anywhere in this codebase to reuse;
this task's own design is the first. `epic.md` is corrected accordingly
(see "Files touched").

**Representation: plain sorted `Vec<u32>`, NOT `roaring`.** Weighed
directly against this project's "no new dependency unless justified"
discipline (`Cargo.toml` has no bitmap crate today; `uuid`, `memmap2`
are the closest precedents for "a small, justified addition").
Segments are capped at ~1,000,000 rows by construction
(`NativeWriteOptions::target_rows_per_segment` default, confirmed in
`native_write.rs`) — an order of magnitude below the row counts where
`roaring`'s compression actually starts winning meaningfully over a
flat structure. Two representations were weighed on THIS format's own
numbers, not the general case:
- A fixed bitmap (`ceil(row_count/64)` `u64` words): a segment with
  even ONE deleted row costs the SAME fixed ~125KB (1,000,000 bits) as
  a segment 99% deleted — wasteful for the realistically-common case of
  a narrow, selective DELETE.
- A sorted `Vec<u32>` of deleted local positions: costs ~4 bytes per
  DELETED row, i.e. near-zero for narrow deletes (the common case) and
  human-readable/greppable as a plain JSON number array — matching this
  manifest format's own established design ethos (phase 1 task 001's
  Decision 2 chose JSON specifically for hand-inspectability). Its
  worst case (a segment deleted almost to 100%) is bounded by Decision
  3's "drop a wholly-tombstoned segment" rule below, so the pathological
  4MB-per-segment case this representation is weakest at never actually
  persists.
`roaring` would be strictly better at BOTH extremes simultaneously, but
given segment-capped scale and the empty-segment-drop mitigation, the
plain `Vec<u32>` is sufficient for this epic without a new dependency;
if task 005's adversarial testing (broad-but-shallow deletion across
many segments — see that file's updated Technical Details) finds real
memory pressure from this choice, the field's on-disk representation
can be swapped to compressed bytes later with zero change to any
consumer's logical view (the field stays opaque outside one decode
function) — deferring is forward-compatible, not a dead end.

**Storage location: inline in the existing single `_manifest.json`, not
a sibling file per segment, not one separate whole-table file.** Both
alternatives were considered and rejected on the SAME ground: they
reintroduce a multi-file atomicity problem this task's own atomic-publish
decision (Decision 4) exists to avoid — a mutation would need to
publish the main manifest AND N per-segment delete-sidecars (or a
second `_deletes.json`) as one atomic unit, which is strictly more
moving parts than one file for no benefit at this format's scale
(manifests are already established, by phase 1 task 001, as fine up to
"low MBs," read once at open time). Concretely: `Segment` gains
`#[serde(default)] deleted_rows: Vec<u32>` (sorted, deduplicated local
row positions within that segment's own row ordering) — an empty
`Vec` (the default, via `#[serde(default)]`) means "no deletions,"
so every manifest phase 1 already wrote round-trips unchanged, and
every segment that has never been touched by a DELETE costs zero extra
bytes.

**Read-path composition — the concrete code-level answer.**
`NativeTable::scan()` currently loops `active_segments()` and calls
`ipc_cache::read_row_group(&self.dir, seg.id as usize, projection, None)`
per segment, concatenating results (`src/storage/native_table.rs`,
`scan()`, confirmed by reading it). The deletion vector must be
consulted INSIDE this loop, as one new step per segment: after reading
a segment's batches back (which, confirmed by reading
`ipc_cache::read_row_group`'s body, preserves on-disk block order with
no reordering — multiple ~65,536-row batches are the NORMAL case per
segment, since `native_write.rs` already calls
`ipc_cache::reslice_large` before writing), track a running local-row
offset across those batches and apply `arrow::compute::filter` with a
boolean mask computed from `deleted_rows` before appending each batch
to the output. **This is a single choke point**: every existing and
future consumer of `scan()`/`scan_with_filter()` — the generic
aggregate/join/filter path, task 005 of phase 1's dense-direct-address
fast path (`try_execute_dense_direct`, `src/physical/operators/
morsel_agg.rs`), a future distributed shard — sees an already
deletion-filtered view with ZERO changes required at any call site.
For a segment with an empty `deleted_rows` (the default, and the ONLY
case for a table that has never been mutated), this must be a fast
no-op (skip the mask/filter work entirely) so phase 1's own G2
benchmarks (SF=10 1.23x, dense-direct-address firing) do not regress
for an unmutated table — a concrete, checkable requirement for task 003.

**Composition with phase 1's dense-direct-address fast path — verified
correct with ZERO changes needed to `morsel_agg.rs`, not assumed.** Read
`try_execute_dense_direct`'s native branch (`src/physical/operators/
morsel_agg.rs` lines ~777-800): it calls
`provider.scan_with_filter(eff_projection.as_deref(), None)` and hands
the returned batches to `accumulate_dense_batch`, which sets a bit in a
shared `presence` bitmap only for row values it actually accumulates
(line 591); the OUTPUT-emission pass (lines 880-888) iterates only SET
`presence` bits. Since scan-level deletion filtering happens BEFORE
these batches are ever produced (previous paragraph), deleted rows
simply never reach `accumulate_dense_batch` at all — the sparse-key
handling this fast path already needs for ordinary gapped key ranges is
exactly the same mechanism that makes it deletion-safe with no
awareness of deletion vectors whatsoever. task 003/005 of THIS epic do
not need the "fall back to the generic path when deletions are
pending" escape hatch its own acceptance criteria worried might be
necessary — this scan-level design makes it unnecessary. One real,
minor, named cost: `TableProvider::statistics()`'s `min_i64`/`max_i64`
(which size the dense accumulator array) are NOT recomputed on DELETE
(Decision on `table_stats`, below) so they may be wider than the live
data strictly needs post-delete — this is always SAFE (a wider bound
only wastes a few unused accumulator slots, `presence` still gates
emission correctly) and never a correctness risk; not worth chasing
exact post-delete bounds for the modest, bounded memory cost of a wider
array.

**`statistics()` row count — a NEW computation, not a change to
`manifest.snapshot.row_count`'s existing meaning.** Read
`NativeManifest::validate()`: it enforces `snapshot.row_count == sum of
segments[].row_count` as a hard internal-consistency invariant, and
`NativeManifest::build()` derives both fields fresh from a `Vec<Segment>`
every time it's called. Decision: leave `Segment.row_count`/
`Snapshot.row_count` meaning exactly what they mean today — the
PHYSICAL row count actually written to a segment's `.arrow` file,
unaffected by later deletes — so `validate()`'s existing invariant is
satisfied with ZERO code changes, and `NativeManifest::build()` remains
callable unchanged after every mutation (see Decision 4). The LOGICAL
(post-delete, visible) row count is instead a NEW, separate computation
inside `NativeTable::statistics()` itself: `segment.row_count -
segment.deleted_rows.len()`, summed over active segments. This is not
a new pattern — `NativeTable::statistics()` ALREADY computes its own
`row_count` independently from `active_segments()` rather than reading
`manifest.snapshot.row_count` directly (confirmed by reading
`native_table.rs`'s `statistics()` — `let row_count: u64 =
segs.iter().map(|s| s.row_count).sum();`), so this is a one-line
extension of an already-established pattern, not a new one — directly
satisfying task 003's own acceptance criterion that stale statistics
must not mislead the planner.

**Memory-budget composition (phase 1 task 006) — confirmed to need ZERO
changes, with a real named residual risk for task 005 to adversarially
test.** `NativeTable::check_scan_budget()` estimates
`self.statistics().total_byte_size` — the whole active segment set's
ON-DISK byte size. Deletion vectors do not shrink a segment's physical
file (DELETE never rewrites segment bytes), and `scan()` still must
mmap-decode a segment's full physical content BEFORE the new
per-batch deletion filter can drop rows — so `total_byte_size` remains
a valid, sufficient upper bound on `scan()`'s true memory need with
ZERO changes to task 006's existing formula
(`memory_limit * spill_threshold`). The deletion vector's OWN memory
footprint (the `Vec<u32>`s, held in the in-memory `NativeManifest` once
a table is opened) is bounded per segment (at most `row_count * 4`
bytes for a fully-tombstoned segment, which Decision on "drop empty
segments" below prevents from persisting) — for a NARROWLY-deleted-from
table this is negligible. **Named risk, not hidden**: a table with many
segments EACH lightly touched by broad, shallow deletes (e.g. 1000
segments x 1% deleted each) could add tens of MB to the manifest's
in-memory/on-disk footprint — real, worth task 005 adversarially
measuring specifically (propagated into `005.md`), not assumed safe by
analogy alone.

### Decision 2 — UPDATE semantics: DELETE + INSERT, confirmed — with one
load-bearing implementation refinement the epic text does not state

No concrete, evidenced reason was found for true in-place update to be
better on this engine's shape — segments are immutable Arrow IPC files
by design (unchanged from phase 1), so "in-place" would mean the same
copy-on-write rewrite Decision 1 already rejected for DELETE, just
applied to UPDATE too. **Confirms the epic's own leaning**: DELETE the
matched rows (Decision 1's mechanism) + INSERT their recomputed values
as new rows (Decision-4-shaped Append). The `sqlparser` evidence
supports this directly: `Assignment.value` (an UPDATE `SET` right-hand
side) is a plain `Expr` — confirmed via the `.scratch/` spike that even
`UPDATE t SET a = (SELECT MAX(x) FROM other WHERE other.id = t.id)
WHERE y > 10` (a correlated scalar subquery as a SET value) parses
cleanly to `Assignment { target: ColumnName(...), value:
Subquery(Query{...}) }` — the identical `Expr::ScalarSubquery` shape
this engine's existing WHERE/SELECT-list binding already handles. So
"compute a matched row's new values" is ordinary expression evaluation
against that row's current column values (`filter::evaluate_expr`, the
SAME function `FilterExec`/DELETE's own row-identification already
use), not new evaluation machinery.

**The refinement task 004 needs and the epic text does not spell out**:
UPDATE must NOT be implemented as two sequential calls to task 002's and
task 003's PUBLIC, self-publishing entrypoints (`insert_into_native_
table`, `delete_from_native_table`) — each would perform its own
independent atomic manifest publish, leaving a real window (a crash, or
even just a concurrent reader, between the two publishes) where a
reader could observe the OLD rows deleted but the NEW rows not yet
present, directly the failure mode task 004's own acceptance criteria
warn about ("not two separate operations a crash could leave half-done").
The fix is architectural, decided here so task 002/003 build the right
shape from the start: **both task 002 (Append) and task 003 (DELETE)
must expose a lower-level, NON-publishing building block** —
"write N new segments and return their `Segment` entries, without
touching the manifest" (Append's core, minus the final `build`+publish
step) and "identify matched (segment, position) pairs and return an
updated `Vec<Segment>` with `deleted_rows` extended, without touching
the manifest" (DELETE's core, minus the final `build`+publish step).
Task 004 then: (1) calls DELETE's identification building block to get
both the matched ROWS (for computing new values) and the tombstoned
segment list, (2) evaluates SET expressions against each matched row to
build the new-row batches, (3) calls Append's non-publishing write
building block on those new-row batches, (4) constructs ONE
`Vec<Segment>` (old segments with `deleted_rows` extended + newly
written segments appended), (5) calls `NativeManifest::build()` ONCE
and publishes ONCE (Decision 4's single-file rename). This gives UPDATE
true all-or-nothing atomicity for free from Decision 4's existing
primitive — a reader NEVER observes a mid-update manifest, because
there is only ever one manifest write for the whole statement, not two.

### Decision 3 — Compaction: explicitly deferred to a future epic, not
built here — with the concrete, evidenced answer for what it will need

**Recommendation: defer.** Weighed explicitly, not assumed either way,
per this task's own acceptance criterion:
- Correctness never depends on it: Decision 1's deletion vector is
  correctness-preserving indefinitely (confirmed: reads always apply
  the filter, regardless of how large `deleted_rows` grows) — deferring
  compaction ships nothing broken, only something that does not reclaim
  space or shrink segment count.
- This epic already carries five substantial dependent tasks
  (002-006); a general compact-N-segments-into-fewer mechanism is a
  materially separate feature with its OWN atomicity/locking surface
  (it would itself be a mutation needing Decision 4's lock and
  atomic-publish machinery) — bundling it risks exactly the
  scope-creep this program's own conventions warn against.
- Matches this program's own repeated "smallest safe slice first"
  discipline — phase 1 itself deferred ALL of mutation for the same
  reason; deferring compaction within mutation is the same discipline
  one level down.

**Honest downside, stated explicitly per this task's own instructions,
not hidden**: without compaction, (a) segment count grows by at least
one per `Append`/`INSERT` statement forever — a session issuing many
small `INSERT ... VALUES` (one row at a time) produces many small
segments well under the 1,000,000-row target (the classic
small-files problem every lakehouse compaction feature exists to
solve), and (b) disk space from deleted rows is never physically
reclaimed within this epic — a segment's `.arrow` file keeps its
original on-disk size forever even if every one of its rows is
tombstoned in `deleted_rows` (except the one case below). Both are
real, measurable, and explicitly the concern task 005's own "many
sequential mutations" acceptance criterion already anticipates
(propagated/sharpened there).

**One narrow, cheap, IN-SCOPE exception — not full compaction**: when a
DELETE makes `deleted_rows.len() == segment.row_count` (a segment is
now 100% tombstoned), task 003 should drop that `Segment` from the
manifest's `segments: Vec<Segment>` list entirely (its `.arrow` file
becomes an inert, unreferenced orphan — the same "harmless if never
referenced" property an abandoned staging directory already has today).
This costs nothing extra (it's a manifest-only edit, part of the SAME
`Vec<Segment>` reconstruction DELETE already does) and directly bounds
Decision 1's worst-case deletion-vector size (a fully-tombstoned
segment's maximal `deleted_rows` list never actually persists in the
manifest). This is NOT a substitute for real compaction (it does
nothing for a PARTIALLY-live small segment, or for merging many small
segments into fewer larger ones) but is the concrete, low-risk floor
this epic ships.

**What a future compaction task will need — the concrete answer this
epic's own acceptance criterion demands**: every building block it
needs already exists or is being built for other reasons in this epic,
confirmed by tracing the exact call sequence: (1) pick candidate
segments (e.g. `deleted_rows.len() / row_count` above some threshold,
or byte size below some target — a cost-model decision for that future
task, not this one); (2) read them via the SAME
`scan()`-with-deletion-filtering logic Decision 1 already builds — "the
surviving rows" is directly what a deletion-vector-aware scan already
produces, no separate mechanism needed; (3) write the survivors out as
fresh, larger segment(s) via the SAME segment-writer mechanism
Append/CTAS already use; (4) publish via the SAME single-file atomic
manifest rename (Decision 4), holding the SAME single-writer lock
(Decision 5) for the duration (a compaction is, mechanically, just
another mutation). Compaction is therefore compositional reuse of this
epic's own mechanisms, not a blocked-on-something-hard future task —
which is precisely why deferring it now is low-risk.

### Decision 4 — Atomic-publish mechanism: single-FILE atomic rename of
a freshly-written manifest, generalizing phase 1's single-DIRECTORY
rename — phase 1's mechanism is confirmed NOT safely reusable unchanged
for incremental mutations, with the concrete reason and the concrete fix

**Confirmed by reading the actual implementation, not assumed either
way (directly answering this task's own question)**:
`native_manifest::publish_table_dir(staging, final_dir)` does
`std::fs::remove_dir_all(final_dir)` THEN `std::fs::rename(staging,
final_dir)` — a WHOLE-DIRECTORY replace. This is correct and safe
EXACTLY for the case it was built for: `Create`/`Overwrite`, where the
staging directory is a complete, self-sufficient copy of the entire new
table state before the rename. It is a real, load-bearing FINDING —
not an assumption — that this is **not** safely reusable unchanged for
`Append`/`DELETE`/`UPDATE`: those need to preserve MOST of an existing
directory's segment files while only adding new ones or editing
metadata, and calling `publish_table_dir` naively would
`remove_dir_all` away every pre-existing segment file the new manifest
has not (and, for DELETE, never will) copied into a fresh staging
directory — corrupting the table, and for DELETE specifically, defeating
the entire point of choosing merge-on-read over copy-on-write (Decision
1) by forcing a full-directory copy on every delete anyway. This
directly confirms the task's own hinted answer: "phase 1's atomicity
only worked because full-replace writes have no partial-update window
to protect against" — true, evidenced by reading the code, not assumed.

**The concrete new mechanism, generalizing rather than replacing**:
1. Write new segment file(s), if any (`Append`'s new data;
   Decision-2-shaped UPDATE's new rows), DIRECTLY into the LIVE table
   directory (not a separate staging directory) — under FRESH,
   non-colliding segment ids (`existing_manifest.segments.iter().map(|s|
   s.id).max().unwrap_or(0) + 1..`, never restarting at 0 — a real,
   easy-to-miss bug this decision heads off explicitly, since
   `SegmentWriter::new` today always starts `next_id: 0`, correct only
   for Create/Overwrite). If the process crashes here, these are
   harmless orphan files: no manifest references them yet, so no reader
   ever sees them (mirrors exactly how an abandoned `.<pid>.building`
   staging directory is already inert today).
2. Construct the ONE new, complete `Vec<Segment>` in memory: existing
   segments (untouched, or with `deleted_rows` extended/segment
   dropped per Decision 1/3) plus any newly written segments' entries.
3. Call `NativeManifest::build(&schema, table_id, version + 1, new_segments,
   now_ms)` — CONFIRMED reusable completely unchanged: it already
   derives `row_count`/`table_stats` fresh from whatever `Vec<Segment>`
   it is given via `Self::rollup`, so this satisfies task 002's own
   acceptance criterion ("reuse phase 1's existing rollup/merge
   functions... rather than reimplementing") with ZERO new manifest-
   merge function — the existing `build()` IS the merge function,
   for every one of INSERT/DELETE/UPDATE, once callers assemble the
   right `Vec<Segment>` input.
4. Write that manifest to a TEMPORARY file inside the SAME table
   directory (e.g. `_manifest.json.tmp-<pid>`), then
   `std::fs::rename(tmp_path, native_manifest::manifest_path(dir))` —
   ONE file-level rename. POSIX guarantees `rename()` atomicity for a
   single file exactly as it does for a directory, on the same
   filesystem (both source and destination are), which is the SAME
   primitive `publish_table_dir` and `ipc_cache.rs::build_sidecar`
   already rely on for their own directory-level atomicity — this is a
   narrowing of an already-trusted guarantee, not a new risk. A reader
   opening `_manifest.json` at any instant sees EITHER the fully-old
   manifest (every segment it names still physically present, untouched)
   OR the fully-new one (every segment it names, old and new, now
   physically present) — never a torn/partial manifest, and never a
   manifest naming an unwritten segment, because step 1 always
   completes before step 4 is attempted.
5. Held for the WHOLE sequence (steps 1-4) under Decision 5's lock —
   the per-step atomicity above prevents a TORN read, but only the lock
   prevents a LOST UPDATE from two concurrent writers each reading the
   same starting manifest and independently computing conflicting
   "next" states (see Decision 5).

**Explicit scope boundary, stated honestly**: this provides read-atomicity
(never torn) and process-crash-safety (Decision 5's lock; a killed
writer leaves either the pre- or post-mutation state, never a corrupt
one) — it does **not** add `fsync`/power-loss durability beyond
whatever the OS/filesystem's own page-cache-flush behavior already
provides. This is not a new gap this epic introduces: phase 1's own
`publish_table_dir`/`build_sidecar` do not `fsync` either (confirmed by
reading both — no `sync_all`/`sync_data` calls anywhere in either), so
this matches the established, existing scope boundary rather than
narrowing it. Named for task 006's documentation, not silently assumed.

### Decision 5 — Single-writer enforcement: `std::fs::File::try_lock()`
— stable in this toolchain's std, zero new dependency, held for the
whole mutation, verified cross-process AND SIGKILL-safe with a live test

**Why a lock is still needed even though every individual publish step
is atomic (Decision 4)**: atomicity of one rename prevents a TORN read;
it does not prevent a LOST UPDATE across the READ-MODIFY-WRITE span of
an entire mutation. Two concurrent writers (e.g. two concurrent
DELETEs, or an Append racing a DELETE) each read the same starting
manifest at version N, each independently compute their own version
N+1 manifest reflecting only their own change, and each rename their
own tmp-manifest into place — whichever rename lands LAST silently
discards the other writer's fully-valid, individually-atomic change.
This is a correctness gap Decision 4 cannot close on its own; only
serializing writers can.

**Mechanism, with real evidence, not just documentation trust**:
`std::fs::File::{lock, try_lock, unlock}` are STABLE standard-library
methods (confirmed directly against this toolchain's shipped std source,
`~/.rustup/.../library/std/src/fs.rs`, lines 828/944/1045) — this repo's
pinned toolchain is `rustc 1.93.0` (`rustc --version`, confirmed), well
past the 1.89.0 stabilization. `try_lock(&self) -> Result<(),
TryLockError>` wraps `flock(2)` on Unix: NON-blocking, fails immediately
with `TryLockError::WouldBlock` if another process already holds an
exclusive lock on the same file — exactly "fail cleanly and namedly"
per this task's own acceptance criterion, with **zero new Cargo
dependency** (directly satisfies "no new dependency unless justified"
more strongly than any crate option would: nothing to justify, it is
already in std).

**Real, live, cross-process verification performed for this task** (not
assumed from documentation): built two tiny binaries in
`.scratch/mutation_sqlparser_spike/src/bin/` (`lock_holder`,
`lock_contender`), both built via `scripts/claude-safe-build.sh cargo
build`. Sequence actually run:
1. `lock_holder` acquires `try_lock()` on a fixed path, prints `LOCKED`,
   sleeps.
2. While it is alive, `lock_contender` tries the same file:
   **`CONTENDER: WOULD_BLOCK (as expected while holder alive)`** — confirmed
   the lock genuinely blocks a second process, not just a second thread.
3. `lock_holder` is `kill -9`'d (SIGKILL — an unrecoverable hard kill, the
   worst case a crash-mid-mutation scenario could produce, deliberately
   NOT a graceful shutdown).
4. `lock_contender` immediately retries the SAME file: **`CONTENDER:
   ACQUIRED (unexpected if holder still alive)`** — confirmed the kernel
   released the `flock` the instant the holding process died, for ANY
   reason including SIGKILL, with **zero manual cleanup**.

This directly answers the crash-safety half of the requirement that a
simpler mechanism cannot: a plain `OpenOptions::new().create_new(true)`
marker-file lock would NOT self-release on a SIGKILL'd writer (the file
would persist, permanently blocking every future writer until a human
manually deletes it) — `File::try_lock()`'s kernel-managed `flock`
solves exactly this with no extra code, which is why it is the
recommended mechanism over a marker file.

**Concrete design**: a sibling lock file per table directory (mirrors
`native_manifest::staging_dir_for`'s own sibling-path convention, e.g.
`final_dir.with_file_name(format!("{name}.lock"))`, computed once, not
pid-suffixed — the whole point is one stable identity per TABLE, not
per attempt). Held for the FULL span of a mutation (open destination ->
identify/write -> publish, i.e. wrapping Decision 4's steps 1-4), via a
small RAII guard whose `Drop` calls `unlock()`/closes the file so an
early `?`-propagated error or a panic still releases it deterministically
in the non-crash case (the kernel-level auto-release on process death
is the backstop for the crash case). Contention failure reuses the
existing `QueryError::Storage` variant (matching every other
native-table-directory error already in `native_manifest.rs`/
`native_write.rs` — no new error variant needed), naming the table
directory so the failure is diagnosable. **Readers never lock — this
is writer-vs-writer only**, matching every other design decision in
this program (no reader has ever blocked on anything in this codebase,
and this does not change that).

### Decision 6 — SQL lift sizing: grammar is a solved non-issue for all
three statements (confirmed by spike, not assumed from CTAS parity) —
effort is in refusal-boilerplate + execution mechanism, not parsing

**Method**: `.scratch/mutation_sqlparser_spike/` (its own `Cargo.toml`
pinning `sqlparser = "0.62"`, the exact version this repo pins,
confirmed via `Cargo.toml:19`), parsing through the identical
`sqlparser::dialect::GenericDialect` `src/parser/mod.rs::parse_sql`
uses — mirroring phase 1 task 001's own spike discipline exactly, but
run fresh for INSERT/DELETE/UPDATE specifically rather than assumed to
transfer from the CREATE TABLE finding (per this task's own explicit
instruction). Full transcript in `.scratch/mutation_sqlparser_spike/out.txt`
(gitignored, not committed) and cross-checked against the real
`sqlparser-0.62.0` struct definitions on disk
(`~/.cargo/registry/src/.../sqlparser-0.62.0/src/ast/{dml.rs,mod.rs}`).

**INSERT** — `Statement::Insert(Insert{ table: TableObject, columns:
Vec<ObjectName>, source: Option<Box<Query>>, assignments: Vec<Assignment>,
overwrite: bool, on: Option<OnInsert>, ... })`, ~26 semantic fields total.
Confirmed parsing:
- `INSERT INTO t SELECT a, b FROM src WHERE a > 10` → `source:
  Some(Query{..})`, `columns: []`. A JOIN+GROUP BY source (`INSERT INTO
  t SELECT a, COUNT(*) FROM src JOIN other ON src.id = other.id GROUP BY
  a`) parses identically cleanly — `source` is the SAME `Box<Query>`
  type `Binder::bind_query()` already fully handles (joins, aggregates,
  subqueries — the identical finding phase 1 task 001 made for CTAS,
  re-confirmed here for INSERT specifically, not assumed to transfer).
- `INSERT INTO t VALUES (1, 2), (3, 4)` also parses to `source:
  Some(Query{ body: Values(..), .. })` — and `Binder::bind_set_expr`
  ALREADY has a `SetExpr::Values` arm (`binder.rs:653`, pre-existing,
  confirmed by reading it) — meaning `INSERT ... VALUES` binds through
  the identical `bind_query()` call with ZERO extra binder work,
  a genuine "comes for free" finding worth task 002 keeping (not
  special-case-refusing `Values` bodies) rather than scoping INSERT to
  `... SELECT` sources only.
- `INSERT INTO t (a, b) SELECT/VALUES ...` (explicit column list) also
  parses — **recommend REFUSING this by name** (mirrors CTAS's own
  `ct.columns` refusal): supporting column reordering/partial lists
  with defaults is real new logic with no existing precedent in this
  write path, not needed for the "smallest safe slice."
- `INSERT OVERWRITE TABLE t SELECT a FROM src` (Hive form) parses with
  `overwrite: true` — **must be refused by name**: silently treating it
  as a plain Append would be a real semantic bug (the user asked for a
  full-table replace, not an accumulating append).
- `Insert.assignments` (MySQL `INSERT ... SET`), `Insert.on` (`ON
  CONFLICT`/`ON DUPLICATE KEY UPDATE` — upsert semantics), `returning`,
  `output`, `partitioned`, `table_alias`, `replace_into`, and the rest
  of the ~26 fields should be refused by name, mirroring
  `require_supported_create_table_shape`'s exact discipline (a new
  `require_supported_insert_shape`, mechanically checked against the
  real struct — task 002's job to write, not this task's).
- **A known bug class from phase 1, must not be reintroduced**: a bare
  `SELECT *`-sourced INSERT hits the SAME table-qualified-column-name
  binder property phase 1 tasks 003/004 already found and fixed for
  CTAS (`SELECT * FROM orders` produces field name `"orders.o_orderkey"`,
  not `"o_orderkey"`). Unlike CTAS (which defines a fresh schema from
  whatever the query produces), INSERT must conform to the TARGET
  table's ALREADY-DECLARED schema — so the fix is even more direct:
  re-wrap the source stream's batches against the target's existing
  `NativeManifest::arrow_schema()` by POSITION (`RecordBatch::try_new(target_schema,
  source_batch.columns().to_vec())`, the exact pattern
  `create_table_as_select` already uses for its own dictionary/schema
  normalization step), never trusting the source query's own field
  names.
- **A real, load-bearing gap in the existing write path, found while
  tracing Append's needs**: `SegmentWriter::accept` (`native_write.rs`)
  today validates ONLY column COUNT (`batch.num_columns() !=
  self.declared_schema.fields().len()`), never column name or type.
  This is fine for Create/Overwrite (the schema is being defined BY the
  data), but wrong for Append (rows must conform to the schema the
  table ALREADY has) — task 002 must validate the INSERT source's
  output schema against the target's existing manifest schema
  (name+type, not just count) before writing, turning a mismatch into
  the clean, named error task 002's own acceptance criteria already
  require, not silent corruption.
- **A second real trap for Append specifically**: dictionary encoding
  is decided ONCE from the FIRST segment ever written and locked in for
  the table's lifetime (phase 1 task 003's own design). Append must NOT
  re-run `SegmentWriter`'s "decide from this call's own first flush"
  logic (it would re-decide independently per Append call, potentially
  producing a segment whose column is plain `Utf8` while the table's
  declared schema already says `Dictionary(Int32, Utf8)` — a schema
  mismatch). Append's writer must instead be constructed with the
  dictionary decision ALREADY KNOWN, read from the target's EXISTING
  manifest schema, and cast every new batch to match it unconditionally
  — not discovered fresh from the new data.

**DELETE** — `Statement::Delete(Delete{ tables: Vec<ObjectName>, from:
FromTable, using: Option<Vec<TableWithJoins>>, selection: Option<Expr>,
returning, output, order_by, limit })`. Confirmed parsing: `DELETE FROM
t WHERE x = 1` (`selection: Some(..)`), `DELETE FROM t` with no WHERE
(`selection: None` — must be supported as "delete all rows," a real
case task 003's own acceptance criteria already name), `DELETE FROM t
WHERE x IN (SELECT id FROM other)` (subquery in WHERE — parses and
should bind via the IDENTICAL WHERE-predicate binding `bind_select`
already uses). MySQL's multi-table comma form (`DELETE t1 FROM t1 JOIN
t2 ON ... WHERE ...`) does **NOT** parse under `GenericDialect`
("Expected: end of statement, found: FROM") — confirmed a genuine
non-issue, not something to defensively refuse in the binder, though
`tables`/`using` should still be checked non-empty/`None` defensively
since another dialect path could in principle populate them. Refuse by
name: `!tables.is_empty()`, `using.is_some()` (Postgres/Snowflake/MySQL
`USING` — a join-shaped delete, materially different feature),
`FromTable::WithFromKeyword`/`WithoutKeyword` naming more than one
table or a `TableWithJoins` with non-empty `joins`, `returning`,
`output`, non-empty `order_by`/`limit` (MySQL `ORDER BY`/`LIMIT` on
DELETE — this epic's simple predicate-match model has no "which N rows"
ordering concept).

**UPDATE** — `Statement::Update(Update{ table: TableWithJoins,
assignments: Vec<Assignment>, from: Option<UpdateTableFromKind>,
selection: Option<Expr>, returning, output, or, order_by, limit })`.
Confirmed parsing: `UPDATE t SET a = a + 1, b = 'x' WHERE y > 10`
(ordinary case), `UPDATE t SET a = 1` with no WHERE (`selection: None`
— "update all rows," must be supported, matches task 004's own
acceptance criteria), and — the load-bearing check for Decision 2 —
`UPDATE t SET a = (SELECT MAX(x) FROM other WHERE other.id = t.id)
WHERE y > 10` (correlated scalar subquery as a SET value) parses
cleanly to `Assignment.value: Expr::Subquery(..)`. Also confirmed
parsing and **must be refused by name**: `UPDATE t SET a = 1 FROM other
WHERE t.id = other.id` (Postgres `UPDATE ... FROM` — `from:
Some(UpdateTableFromKind::..)`) is a materially different feature
(joining another table's columns into the SET computation) that this
epic's DELETE+INSERT-over-the-row's-own-current-values model does not
support — refuse `from.is_some()` explicitly, do not silently ignore
the clause. Also refuse: non-empty `table.joins`, `AssignmentTarget::
Tuple` (multi-column `SET (a,b) = (1,2)` — single-column assignments
only), `returning`, `output`, `or`, non-empty `order_by`/`limit`.

**Overall sizing conclusion**: mirrors phase 1's own finding exactly —
`sqlparser` does 100% of the grammar work for all three statements
already, including realistic complex shapes (joins/aggregates as INSERT
sources, subqueries in DELETE's WHERE, correlated scalar subqueries in
UPDATE's SET) — nothing new is needed at the parser layer. The real
effort in tasks 002-004 is (a) the refusal-by-name boilerplate per
statement (mechanical, time-consuming, low-risk — the exact same shape
as `require_supported_create_table_shape`'s ~57-field sweep) and (b)
each statement's EXECUTION-side mechanism (Append's schema/dictionary
inheritance traps above; DELETE's genuinely new row-identification +
deletion-vector consultation; UPDATE's atomic composition of both) —
consistent with why 003.md/004.md are already sized larger than a
pure-SQL-wiring task would be, and confirming task 002's own estimate
is not being driven by parsing risk.
