# Task: UPDATE

## Description

`UPDATE <native table> SET <assignments> WHERE <predicate>` — built on
top of INSERT (task 002) and DELETE (task 003)'s mechanisms. Per task
001's semantics decision (most likely DELETE the matched rows + INSERT
their updated values as new rows), this task is substantially composition
rather than new mechanism — but the composition itself, and the new-value
computation, are real new work.

## Acceptance Criteria

- [x] `Statement::Update` handled in `Binder::bind()` — new match arm.
      Binds the `WHERE` predicate (reuse DELETE's row-identification
      logic from task 003) and the `SET` assignment expressions (new —
      each assignment is an expression evaluated per matched row,
      against that row's OTHER current column values, e.g. `SET x = x +
      1` must read the row's existing `x` before computing the new one).
- [x] Implementation per task 001's semantics decision — if DELETE+INSERT:
      read matched rows' full current values, apply the SET expressions
      to compute new rows, delete the old rows (task 003's mechanism),
      insert the new rows (task 002's mechanism), all as one atomically-
      published operation (not two separate operations a crash could
      leave half-done — the old rows must not become deleted without the
      new rows also becoming visible, or vice versa).
- [x] Cell-exact validation: update a native table, compare against an
      independently-computed reference. Cover: an UPDATE whose SET
      expression references the row's own pre-update value (`SET total =
      total * 1.1`); an UPDATE whose WHERE matches zero rows (clean
      no-op); an UPDATE whose WHERE matches all rows; an UPDATE on a
      column that's part of a dictionary-encoded segment (per phase 1's
      task 004 Outcome, a Dictionary-typed logical schema is a real,
      previously-buggy area — confirm this still round-trips correctly
      after an update); a second UPDATE that overlaps a first (order of
      operations must be well-defined and correct, not racy).
- [x] No partial-state visibility: verify (not just design for) that a
      reader querying mid-update never sees a state where old rows are
      gone but new rows aren't yet visible, or vice versa — this is the
      single highest-value adversarial test in this task, given this
      program's repeated history of exactly this class of bug in
      partial/multi-step execution paths.
- [x] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Populated by task 001's decisions — read `001.md`'s Outcome section, and
task 002/003's own Outcome sections for their exact final APIs, before
starting. Summary of what directly shapes this task (Decision 2 is the
one load-bearing refinement beyond "DELETE + INSERT" the epic text
alone does not spell out):

- **DELETE + INSERT confirmed** (task 001's Outcome, Decision 2) — no
  evidenced reason found for true in-place update on this engine's
  immutable-segment shape.
- **Atomicity requires sharing task 002/003's LOWER-LEVEL building
  blocks, not calling their public entrypoints twice.** Calling
  `insert_into_native_table` then `delete_from_native_table` (or vice
  versa) as two independent, separately-publishing operations leaves a
  real window (a crash, or even just a concurrent reader, between the
  two publishes) where old rows are gone but new rows aren't visible
  yet, or vice versa — exactly what this file's own "no partial-state
  visibility" acceptance criterion forbids. Instead: (1) use task 003's
  non-publishing row-identification core to get BOTH the matched
  (segment, position) pairs (for tombstoning) AND the matched rows'
  full current column values (for computing new values); (2) evaluate
  each `Assignment.value` expression (bound via the SAME `Binder::
  bind_expr` DELETE uses — confirmed by the `.scratch/` spike that even
  a correlated scalar subquery as a SET value parses to a plain `Expr`,
  the identical shape `evaluate_expr` already handles) against each
  matched row's OTHER current column values to build the new-row
  batches; (3) use task 002's non-publishing segment-writer core to
  write those new rows as new segments (inheriting the target's
  existing schema/dictionary decision, per task 002's own Decision-6
  notes) WITHOUT publishing; (4) construct ONE new `Vec<Segment>` (old
  segments with `deleted_rows` extended/dropped, per task 003's logic,
  PLUS the newly written segments from step 3); (5) call
  `NativeManifest::build()` ONCE and publish ONCE via task 002/003's
  shared single-file-atomic-rename helper, under ONE acquisition of the
  single-writer lock (Decision 5) spanning the whole statement. This is
  the concrete mechanism that makes "all as one atomically-published
  operation" (this file's own acceptance criterion) actually true,
  rather than an aspiration two sequential calls would not deliver.
- **`SET x = x + 1`-style self-referential assignments need no special
  handling** beyond evaluating assignment expressions against each
  matched row's CURRENT batch (the same batch the row was read from
  during identification) before any column is overwritten — i.e.
  evaluate all `SET` expressions first (reading only pre-update values),
  then assemble the new row, exactly like an ordinary projection
  evaluates multiple output expressions against one input row.
- **Dictionary round-trip**: a matched row's new value for a
  dictionary-coerced column must be cast back into the SAME
  `Dictionary(Int32, Utf8)` type the target's existing manifest schema
  already declares (reuse task 002's schema/dictionary-inheritance
  logic for the new segments UPDATE writes — do not let the new rows
  regress to plain `Utf8`, which would corrupt the table's one-type-
  per-column-for-the-whole-table invariant `native_manifest.rs`
  documents).
- **`require_supported_update_shape`**, mirroring the same discipline,
  checked against the real `sqlparser::ast::Update` struct. Accept:
  `table` (name only, no `joins`), `assignments: Vec<Assignment>` with
  `target: AssignmentTarget::ColumnName` (single column) and an
  arbitrary `value: Expr`, `selection: Option<Expr>` (`None` = update
  all rows). Refuse by name: `from.is_some()` (confirmed parses —
  Postgres `UPDATE ... FROM`, a materially different feature: joining
  another table's columns into the SET computation, which this epic's
  update-the-row's-own-current-values model does not support — refuse
  explicitly, never silently ignore the clause), non-empty
  `table.joins`, `AssignmentTarget::Tuple` (multi-column `SET (a,b) =
  (1,2)`), `returning`, `output`, `or`, non-empty `order_by`/`limit`.

## Outcome (closed 2026-08-24)

`UPDATE <native table> SET <col> = <expr>, ... [WHERE ...]` implemented
end to end on top of task 001's design spike decisions and task 002/003's
reusable primitives — every one of them (`lock_table_for_write`,
`write_append_segments`, `publish_manifest_update`,
`identify_matching_rows`, `apply_deletions`, `now_ms`) reused COMPLETELY
UNCHANGED, exactly as instructed; no second manifest-building or publish
path was written. This task's own new work is the composition itself (one
atomic publish, not two sequential ones) and the SET-expression evaluation
— both are the load-bearing contracts below, precise enough that task 005
(adversarial verification) and task 006 (final QA) should not need to read
this task's source.

### `src/storage/native_update.rs` (new module) — the atomic composition

```rust
pub struct NativeUpdateResult {
    pub table_id: String,
    pub version: u64,           // == pre-update version on either no-op case below
    pub rows_updated: u64,      // NET count of LIVE matched rows recomputed (never gross matches)
    pub segments_dropped: usize,
    pub segments_added: usize,
    pub total_rows: u64,        // LOGICAL total -- always == pre-update total for a real UPDATE
    pub total_segments: usize,
}

pub async fn update_native_table(
    table_dir: impl AsRef<Path>,
    predicate: Option<&Expr>,          // None = every row
    assignments: &[(String, Expr)],    // (unqualified column name, bound value expr), SET-list order
) -> Result<NativeUpdateResult>;
```

**The exact atomic-composition sequence** (task 001's Decision 2 — the
load-bearing contract this whole task exists to make real, not
aspirational):

1. `native_write::lock_table_for_write(table_dir)` — acquired ONCE, held
   for the ENTIRE span below via the returned `TableWriteLock` guard
   (released on `Drop` at function return, including every error path).
2. `native_manifest::read_manifest(table_dir)` — read ONCE.
3. `native_delete::identify_matching_rows(table_dir, &existing, predicate,
   materialize_rows: true)` — called ONCE, with `materialize_rows: true`
   (task 003's own Outcome names this exact call shape as task 004's
   need) to get BOTH the tombstone-candidate `(segment, position)` pairs
   AND matched rows' CURRENT column values in the SAME pass. Empty match
   → return the unchanged current state, no further steps, no publish.
4. **`live_matched_rows`** (new, this task's own fix — see below) filters
   each segment's materialized matches down to only positions NOT already
   in that segment's OWN `deleted_rows`, BEFORE any SET expression is
   evaluated. All-dead-already → treated as a true no-op (case 2 below).
5. **`assemble_updated_batch`** evaluates EVERY assignment's bound value
   expression via `physical::operators::evaluate_expr` against the
   UNTOUCHED live-matched-rows batch (never against a batch any earlier
   assignment has already written into), THEN overwrites only the
   assigned column positions to build the new-row batch. This is what
   makes `SET x = x + 1` (and any multi-assignment SET list) correct by
   construction: every assignment reads only pre-update values, exactly
   like an ordinary projection evaluates several output expressions
   against one input row.
6. `native_delete::apply_deletions(&existing, &matches)` — called with the
   FULL, unfiltered match set (unioning an already-dead position is a
   harmless no-op) — the tombstoning half.
7. `native_write::write_append_segments(new_rows_stream, &existing,
   table_dir, options)` — called against the SAME already-read `existing`
   manifest (so schema/dictionary inheritance and next-segment-id
   continuation are exactly INSERT's own behavior) — the recomputed-rows
   half.
8. Fold both segment lists into ONE `Vec<Segment>` (tombstoned-old +
   new).
9. `native_write::publish_manifest_update(table_dir, target_schema, ...,
   version + 1, all_segments, now_ms())` — called EXACTLY ONCE.
10. Lock released (guard `Drop`).

A reader can therefore only ever observe the fully-pre-update manifest or
the fully-post-update one — never an intermediate state — because exactly
one `rename(2)` (inside `write_manifest_atomic`) publishes the whole
statement. Verified empirically, not just by this design argument (see
Tests below).

**Two distinct no-op cases**, both leave the manifest byte-for-byte
untouched and never bump the version (mirrors
`native_delete::delete_from_native_table`'s own precedent):
1. The predicate matches zero PHYSICAL rows.
2. The predicate matches rows, but EVERY one was already tombstoned by a
   prior DELETE/UPDATE (case 4 above) — nothing LIVE to recompute.

### A real correctness gap found and fixed (in scope, not anticipated by 001/003)

`identify_matching_rows` deliberately does not consult
`Segment::deleted_rows` (harmless for DELETE — re-matching an
already-deleted position is a no-op union, by that function's own design
doc). UPDATE is different in kind: a match means "read this row's CURRENT
value and write a BRAND-NEW live row from it," so a match that is ALREADY
tombstoned (a second UPDATE overlapping a first, or an UPDATE after a
DELETE, whose predicate still structurally covers an already-removed row)
must NOT be resurrected as a new row. Without a fix, this would silently
DUPLICATE rows: one copy correctly recomputed from the row's actual
current (live) location, one copy wrongly resurrected from its dead
original location with STALE pre-first-update values.

Fixed by `live_matched_rows(seg: &Segment, m: &SegmentMatch) ->
Result<Option<RecordBatch>>`: builds a boolean mask over `m.positions`
against `seg.deleted_rows` (a `BTreeSet` membership check) and filters
`m.rows` down to only the live subset before any SET expression evaluates
it (`Ok(None)` if every position in this segment was already dead). Found
and confirmed load-bearing by writing the required "a second UPDATE that
overlaps a first" adversarial test FIRST against the naive (unfiltered)
composition — it failed with duplicate ids and wrong values exactly as
predicted — then adding this fix, after which it passes. `rows_updated`
is therefore the NET count of live matched rows actually recomputed, not
the gross predicate-match count (mirrors `NativeDeleteResult::
rows_deleted`'s own NET-vs-gross discipline for the identical reason).

### Dictionary round-trip — reused, not reinvented

A matched row's NEW value for a dictionary-coerced column evaluates to a
plain `Utf8` array (`evaluate_expr`'s literal/arithmetic/string paths
never re-encode dictionaries); an UNTOUCHED dictionary column passes
through unchanged (`assemble_updated_batch` only overwrites assigned
column positions, so an unassigned column's original `Dictionary(Int32,
Utf8)` array — read straight from the on-disk segment — flows through
verbatim). Both land correctly because `write_append_segments`'s own
by-position `cast_batch_to_target` (task 002, reused completely
UNCHANGED) already handles exactly these two shapes: an exact type match
passes through as-is, and a plain-`Utf8`-into-declared-`Dictionary`
mismatch is the ONE sanctioned coercion it already implements. The
manifest's declared schema for the column is NEVER re-derived from the
new data — `publish_manifest_update` is always called with the SAME
`target_schema` read at the very start of the operation — so a regression
back to plain `Utf8` is structurally impossible, not merely tested
against. Verified end to end via a real dictionary-encoded TPC-H
`o_orderstatus` column, cell-exact (`tests/native_update_tests.rs`).

### `src/planner/binder.rs`

```rust
pub fn update_target_name(stmt: &Statement) -> Option<String>;   // extraction, mirrors delete_target_name
pub fn bind_update(&mut self, stmt: &ast::Update)
    -> Result<(String, Vec<(String, Expr)>, Option<Expr>)>;      // (table_name, assignments, predicate)
```

`require_supported_update_shape` is mechanically checked against
sqlparser 0.62's real 11-field `ast::Update` struct (`src/ast/dml.rs`)
plus `TableFactor::Table`'s 10 fields (identical check to
`require_supported_delete_shape`'s own). Accepts: `table` (a single,
unjoined plain table name), `assignments: Vec<Assignment>` with
`target: AssignmentTarget::ColumnName` (single column — `Tuple` refused)
and an arbitrary `value: Expr`, `selection: Option<Expr>` (`None` =
update all rows). Refuses by name: `from.is_some()` (Postgres/Snowflake/
MySQL `UPDATE ... FROM` — confirmed parses in BOTH `BeforeSet`/`AfterSet`
forms via task 001's spike; a materially different join-shaped feature
this epic's "recompute against the row's own current values only" model
does not support), non-empty `table.joins`, `AssignmentTarget::Tuple`,
`returning`, `output`, `or` (SQLite conflict resolution), non-empty
`order_by`/`limit`, and the same 8-field `TableFactor::Table` sweep
DELETE already established (table-valued function, MSSQL hints, version
qualifier, `WITH ORDINALITY`, `PARTITION`, JSON path, `TABLESAMPLE`,
MySQL index hints).

`assignment_target_column_name` extracts an assignment target's
UNQUALIFIED column name (the LAST identifier of its `ObjectName`, so both
`col` and `alias.col` resolve identically — mirrors `find_column_index`'s
own "qualification is optional" convention); its existence against the
table's schema is validated at BIND TIME (`bind_update`, a clean
`QueryError::ColumnNotFound`), not left to fail confusingly deep in the
storage layer.

`Binder::bind()` gained a `Statement::Update(update)` arm: validates shape
then ALWAYS returns `Err` naming `update_native_table` as the real
entrypoint — UPDATE has no `LogicalPlan` to give back (same reason
DELETE's arm doesn't), so unlike Insert/CreateTable this is not a
`bind_query()` wrapper. `bind_update` does the real work: validates shape,
binds every SET assignment's value expression AND the WHERE predicate (if
any) via the SAME `bind_expr` method `bind_delete` uses, against the
target's schema (aliased if the UPDATE names one, identical convention to
`bind_delete`). A subquery ANYWHERE — the WHERE clause OR any SET value
(task 001's spike confirmed even a correlated scalar subquery as a SET
value parses to a plain `Expr`) — BINDS successfully but is refused right
after, by name: this epic's subquery-free evaluator (`physical::
operators::evaluate_expr`, no `SubqueryExecutor`) cannot execute it,
mirroring `bind_delete`'s own "refuse cleanly and early" discipline
exactly (two separate refusal checks: one for the predicate, one scanning
all assignments).

### `src/execution/context.rs`

```rust
pub struct UpdateResult {
    pub table_name: String,
    pub table_id: String,
    pub version: u64,
    pub rows_updated: u64,       // == NativeUpdateResult::rows_updated (NET)
    pub segments_dropped: usize,
    pub segments_added: usize,
    pub total_rows: u64,         // == NativeUpdateResult::total_rows (LOGICAL)
    pub elapsed: Duration,
}

pub async fn ExecutionContext::update_native_table(&mut self, sql: &str) -> Result<UpdateResult>;
```

Shape mirrors `delete_from_native_table`: parse → `update_target_name`
(→ `InvalidArgument` if not an UPDATE) → look up the target in
`self.tables` (→ `TableNotFound` if unregistered — no auto-discovery,
matching every other mutation's "register before you reference it"
contract) → downcast to `NativeTable` (→ `InvalidArgument` if not a
native table) → `Binder::bind_update` directly (NOT `bind()` + a physical
plan — no `LogicalPlan`/`PhysicalOperator` pipeline involved at all) →
`native_update::update_native_table` → `register_native_table` again (the
update is immediately visible in the same session). `ExecutionContext::
sql()` gained the same UPDATE-refusal guard it already has for CREATE
TABLE/INSERT/DELETE.

### A live example (real result, captured 2026-08-24)

`repl --tpch data/tpch-1mb`, a 1500-row `orders_native` table (CTAS from
the TPC-H fixture):

```
UPDATE orders_native SET o_totalprice = o_totalprice * 1.1 WHERE o_orderkey <= 500;
-- Updated 500 row(s) in 'orders_native' (0 segment(s) dropped, 1 segment(s) added, now 1500 row(s) total, version 2) in 0.974ms
```
Before: `o_orderkey=1 -> o_totalprice=360828.2497833599`. After:
`o_orderkey=1 -> o_totalprice=396911.07476169587` (== `360828.2497833599 *
1.1`, self-referential SET correctly reading the pre-update value).
`SELECT COUNT(*) FROM orders_native` stays `1500` throughout — an UPDATE
never changes row count.

### No-partial-state-visibility — verified, not just designed for

`tests/native_update_tests.rs::no_partial_state_visibility_during_a_
concurrent_update`: a REAL concurrent reader (tight polling loop using the
production `TableProvider::scan` read path via `NativeTable` — task 003's
own deletion-aware scan, deliberately NOT the non-production
`native_write::read_back`) races 60 back-to-back UPDATEs (alternating a
marker column between two values, matching every one of a 1500-row
table's rows each time) run by a `tokio::spawn`ed writer task. Required a
genuine multi-threaded tokio runtime (`#[tokio::test(flavor =
"multi_thread", worker_threads = 2)]`): neither side's I/O is truly async
(both are blocking `std::fs` calls wrapped in async fns), so the default
single-threaded runtime let the reader's tight loop starve the writer task
completely — confirmed empirically, the test hung indefinitely before this
fix, not a hypothetical. Every single poll (hundreds of samples per run,
5 repeated runs, zero flakes) observed EITHER exactly 1500 rows of the
pre-update marker OR exactly 1500 of the post-update one — never a
row-count dip, never a mix of the two. A second, independent,
non-timing-dependent angle on the same property
(`each_update_bumps_the_version_by_exactly_one_never_two`): asserts each
UPDATE call bumps `snapshot.version` by EXACTLY 1 — a regression to two
sequential self-publishing calls (the exact anti-pattern task 001's design
spike forbids) would deterministically show as a jump of 2 for one
statement, with zero timing dependence at all.
