# Task: Memory safety + concurrency/crash-safety adversarial verification

## Description

Phase 1's task 006 (memory safety) found a real, previously-undiscovered
OOM in code that "should have been" safe by inspection — `NativeTable::
scan()` was not spill-aware and got SIGKILL'd under a tight memory cap.
That task's own lesson — inspection alone missed it, only adversarial
testing under real memory pressure caught it — applies with more force
here, since mutation introduces new unbounded-growth surfaces (deletion
vectors, sequences of small writes) that don't exist in phase 1 at all.
This task's job is to adversarially test, not just review, and fix what
it finds.

## Acceptance Criteria

- [x] **Deletion vector growth**: repeatedly delete rows (many small
      DELETEs, or one DELETE matching a large fraction of a large table)
      and confirm the deletion vector's memory footprint stays bounded
      and accounted for in the existing memory-budget mechanism (phase
      1's task 006) — not a new, uncounted allocation.
- [x] **Many sequential mutations**: a long sequence of INSERT/DELETE/
      UPDATE operations against the same table — confirm no unbounded
      growth in manifest size, segment count, or open file handles (each
      `Append` creates new segments; without compaction — if task 001
      deferred it — segment count grows with every insert; confirm this
      growth is at least BOUNDED-PER-OPERATION, even if not compacted
      away, and that a large segment count doesn't itself become a
      correctness or performance cliff for `scan()`/`statistics()`).
- [x] **Concurrent-write attempt**: verify task 001's single-writer
      enforcement mechanism actually works — two attempted concurrent
      writers to the same table, confirm the second fails cleanly and
      namedly rather than corrupting the first's work or silently
      succeeding with a lost update.
- [x] **Crash-safety simulation**: interrupt a mutation mid-write (e.g.
      kill the process between writing new segments and publishing the
      updated manifest) and confirm the table is left in either its
      pre-mutation state or its fully-post-mutation state — never a
      state a reader could observe as corrupt or partially-applied.
      Mirror the adversarial rigor of phase 1's own `gdb`-based
      investigation into the `HashJoinExec` bug — use real tooling to
      prove this, not just reason about it.
- [x] Test under `scripts/claude-safe-build.sh`'s memory-capped execution
      model — this repo's standard way of safely testing memory-pressure
      scenarios without risking the terminal/session.
- [x] Fix whatever real gaps are found (small, scoped fixes preferred; if
      a finding is large enough to need a redesign, stop and document it
      clearly rather than scope-creep this task into a rewrite).
- [x] **New finding from task 002 (INSERT), carried forward, must be
      examined here, not left to fade**: the full SQL round-trip path
      for `INSERT INTO ... SELECT` measured **~5.3GB peak RSS** on a
      60M-row source (`examples/native_append_memory_check.rs`'s `sql`
      mode), vs. 328MB for the same data through the direct, non-SQL
      append core. Root-caused by task 002 to `StreamingParquetScanExec`
      merging many parallel partitions via `select_all` with no
      backpressure — a characteristic SHARED with `CREATE TABLE ... AS
      SELECT` (not introduced by INSERT specifically), left unfixed as
      out of task 002's scope. This task must: (a) confirm whether this
      is bounded at all or truly unbounded as source size grows (test at
      a size where 5.3GB would become dangerous, not just re-confirm the
      60M-row number); (b) confirm it fails safely (clean refusal) rather
      than OOMing the process under `scripts/claude-safe-build.sh`'s
      memory cap, the same bar phase 1's task 006 held; (c) if it's a
      real, unbounded risk, decide whether a minimal, scoped mitigation
      belongs in THIS task (e.g. bounding `select_all`'s concurrency) or
      is large enough to name as a follow-up for a dedicated task/epic —
      don't silently let a 5.3GB measurement stand as "fine" without an
      explicit verdict either way.
- [x] A well-evidenced "tested X, found no issue" is a complete, valid
      finding for any of the above — this program has repeatedly valued
      a negative result as much as a positive one, provided it's real
      evidence and not just an assumption.
- [x] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Read phase 1's task 006 Outcome section in full (`.claude/epics/
archived/native-tables-foundation/006.md`) for the exact methodology
that found the real OOM there — register a real table, run under a real
memory cap, observe the actual failure mode (SIGKILL, not a graceful
error) — and apply the same standard here rather than a lighter one.
Also read `001.md`'s Outcome in full; the specific things it flagged for
THIS task to adversarially verify (not just design-review):

- **Compaction is confirmed deferred (Decision 3)** — segment count
  growing by at least one per Append/INSERT statement, and disk space
  from deletes never being physically reclaimed (except the one
  in-scope exception below), is EXPECTED, not a bug to fix here. This
  task's job is to confirm the growth stays BOUNDED-PER-OPERATION and
  that a large segment count doesn't itself become a correctness or
  performance cliff for `scan()`/`statistics()` — per this file's own
  acceptance criterion — not to add compaction.
- **The one in-scope exception task 003 should have implemented**: a
  segment tombstoned to 100% (`deleted_rows.len() == row_count`) is
  dropped from the manifest entirely. Adversarially confirm this
  actually fires (e.g. `DELETE FROM t` with no WHERE against a small
  table, or a sequence of DELETEs that collectively empty one segment)
  and that it measurably bounds segment/manifest growth versus a
  version of the same test with that exception disabled/not firing.
- **Deletion vector memory footprint — task 001 named a REAL, not just
  hypothetical, scaling risk**: a plain `Vec<u32>` per segment is
  bounded per segment (mitigated by the empty-segment-drop rule above),
  but a table with MANY segments EACH lightly touched by a broad,
  shallow delete (e.g. hundreds of segments, each ~1% deleted) was
  estimated at potentially tens of MB of aggregate `deleted_rows`
  content across the manifest — adversarially test EXACTLY this shape
  (not just "one huge DELETE against one large table," which task 003's
  own empty-segment-drop rule and per-segment bound already handle
  cheaply) alongside the large-single-DELETE case this file's own
  acceptance criteria already name. If this measures as a real problem,
  the documented forward-compatible fix is swapping the field's on-disk
  encoding (still `Segment`-local, still opaque outside one decode
  function) to something more compact — not a redesign.
- **Single-writer lock (Decision 5) — adversarially verify the SAME way
  task 001's own spike did, not just trust the design**: two concurrent
  writers to the same table, confirm the second gets a clean, named
  failure (`QueryError::Storage`, from `TryLockError::WouldBlock`) while
  the first holds `std::fs::File::try_lock()`'s lock; then `kill -9` the
  first writer MID-MUTATION (between writing new segment files and the
  final manifest rename — task 001's own live spike used
  `.scratch/mutation_sqlparser_spike/src/bin/{lock_holder,
  lock_contender}.rs` as a minimal pattern to mirror, though this task
  should test against the REAL mutation code path, not a synthetic
  lock-only harness) and confirm: (a) the lock is available again
  immediately (kernel auto-release, already confirmed for the mechanism
  in isolation — confirm it holds for the real code path too), and (b)
  the table is left in EXACTLY its pre-mutation state (orphaned segment
  files, if any were written before the kill, are harmless and
  unreferenced; `_manifest.json` is untouched) — never a state a reader
  could observe as corrupt.
- **Memory-budget composition (phase 1 task 006's mechanism) — verified
  by task 001 to need no formula change**, since deletion doesn't
  shrink on-disk segment bytes and `scan()` still must decode a
  segment's full physical content before filtering — this task should
  still confirm this holds under real adversarial load (e.g. a
  heavily-deleted-from large table still refuses cleanly, rather than
  OOMing, under a tight `--memory-limit`), since task 001's reasoning is
  evidence-based but this program's own history (phase 1 task 006's
  real find) is exactly why a dedicated adversarial task exists rather
  than trusting design analysis alone.

## Outcome (closed 2026-08-24)

Six adversarial scenarios, each given a real, evidence-based verdict —
four new diagnostic binaries under `examples/` (this repo's established
pattern for this kind of measurement, mirroring `native_append_memory_
check.rs`'s own precedent from task 002), one real code fix, three new
unit tests, zero regressions. Every number below is a measured result
from a real run on this machine, not an estimate — reproduction commands
are given per finding so task 006 (final QA) can re-run any of them
without re-deriving methodology.

### Finding 1 — Deletion vector growth: bounded per-entry, "many segments
lightly touched" measured larger than task 001's own guess but still not
urgent at realistic scale

`examples/native_mutation_growth_check.rs` built a REAL table (via the
actual `native_write`/`native_delete`/`native_update` code paths, never a
synthetic model) up to 2573 segments / 4.67M rows through 3000 separate
Append/Delete/Update calls, then ran one broad, shallow DELETE (~1% of
every segment — task 001's own named "hundreds of segments, each ~1%
deleted" shape, not just the large-single-DELETE case the acceptance
criteria already name).

- **Single large DELETE**: cheap by construction — confirmed, not just
  assumed; a segment tombstoned to 100% is dropped entirely (Finding 3
  below), and a segment only PARTIALLY deleted costs `~4 bytes x deleted
  rows` in the deletion vector itself.
- **Many-segments-lightly-touched**: measured **~13.1-13.7 bytes per
  `deleted_rows` JSON array entry**, stable across a 313-segment run and
  a 2573-segment run (two independent measurements agreeing within 5% —
  confirms this is a real, scale-invariant per-entry cost, not noise).
  Extrapolated (clearly labeled as extrapolation, not re-measured at
  literal scale — building 1000 segments x 1,000,000 rows each was judged
  disproportionate effort for this one number) to task 001's own literal
  worry ("1000 segments x 1,000,000 rows x 1% deleted" = 10,000,000
  entries): **~131MB** — LARGER than task 001's "tens of MB" guess, a
  real correction task 006 should carry forward.
- **Verdict**: tested, found a real but not urgent problem. At CURRENT
  realistic scales (hundreds to low thousands of segments, the scale this
  epic's own benchmarks/fixtures actually reach — see CLAUDE.md's native-
  table benchmark tables), manifest sizes stay in the sub-2MB range, not
  131MB. Task 001's own named forward-compatible escape hatch (swap
  `deleted_rows`'s on-disk encoding to something more compact) is real
  but requires a backward-compatible migration story (`#[serde(default)]`
  currently lets every pre-existing manifest round-trip unchanged; a new
  encoding needs the same guarantee, doubling the implementation and
  testing surface) — judged large enough to name as a follow-up rather
  than attempt inside this already six-scenario task, per this task's own
  "document clearly rather than scope-creep" instruction.
- Reproduce: `scripts/claude-safe-build.sh cargo build --release --example
  native_mutation_growth_check && scripts/claude-safe-build.sh
  ./target/release/examples/native_mutation_growth_check` (env:
  `QE_GROWTH_N_APPENDS`, `QE_GROWTH_ROWS_PER_SEG`).

### Finding 2 — Sequential-mutation growth: bounded-per-operation and no
scan()/statistics() cliff, CONFIRMED — but a new, real O(N²) cumulative-
cost finding beyond the letter of the acceptance criteria, named not fixed

Same run as Finding 1, checkpointed every ~250 operations:

| ops | segments | manifest bytes | statistics() | scan() |
|---|---|---|---|---|
| 250 | 216 | 89,365 | 103µs | 982µs |
| 1000 | 859 | 354,090 | 400µs | 4.97ms |
| 2000 | 1716 | 707,628 | 815µs | 9.78ms |
| 3000 | 2573 | 1,061,307 | 1.24ms | 14.14ms |

- **Manifest size**: perfectly linear, **~413 bytes/segment** at every
  checkpoint (89365/216 = 413.7; 1061307/2573 = 412.5) — bounded per
  operation, confirmed, no super-linear blowup.
- **`scan()`/`statistics()`**: both stay roughly linear in segment/row
  count (statistics() ~12x cost for ~12x segments; scan() ~14.4x cost for
  ~11.9x rows — mildly super-linear from per-segment fixed overhead, but
  NOT a cliff). Correctness held throughout: `scan()` and `statistics()`
  agreed EXACTLY at every single checkpoint across the whole 3000-op
  mixed sequence.
- **New finding, beyond the acceptance criteria's literal `scan()`/
  `statistics()` wording, but squarely in its spirit** ("a large segment
  count doesn't itself become a... performance cliff"): the CUMULATIVE
  cost of a long mutation SEQUENCE is O(N²) — per-mutation latency grew
  from **~0.44ms/op near-empty to ~8.8ms/op at 2500+ segments** (a ~20x
  increase for a ~12x segment-count increase, i.e., roughly linear
  per-op growth), because every single Append/Delete/Update re-reads AND
  re-writes the WHOLE `_manifest.json` (`lock_table_for_write` ->
  `read_manifest` -> ... -> `publish_manifest_update`, unconditionally,
  for every mutation regardless of size). This is the direct, expected
  mechanical consequence of task 001's own already-justified design
  (single JSON manifest, no compaction — Decision 3) — not a new bug,
  and NOT fixed here: a real fix means either compaction (explicitly
  epic-out-of-scope) or incremental manifest updates (a materially larger
  redesign of the format's own publish model). Named as a quantified
  residual risk with concrete numbers for a future compaction task to
  size against, per this task's own "document clearly" instruction.
- **Open file descriptors**: flat at **10** for the entire 3000-op run —
  confirmed no handle leak (each mutation opens/closes its files
  transiently; nothing holds a segment or manifest file open across
  calls).
- Reproduce: same binary/command as Finding 1 (both scenarios share one
  constructed table for efficiency).

### Finding 3 — Empty-segment-drop exception: measured effective, not
just designed for

Same run, final phase: 5 whole, previously-untouched append-created
segments fully tombstoned via exact-range DELETEs.

- **5/5 targeted segments actually dropped** from the manifest (confirmed
  by segment-count delta, not assumed from the code's own claim).
- **Real "bytes saved" counterfactual**, computed by literally
  constructing the actual pre-delete `Segment` value WITH `deleted_rows`
  filled solid (`0..row_count`) and serializing it with the SAME
  `serde_json` the manifest itself uses (not a hand-estimate): **~9,112-
  9,115 bytes per segment that would have persisted without the
  exception, vs. 0 bytes actual** — **~45.6KB saved across the 5 segments
  tested**.
- Verdict: tested, confirmed effective, exactly as designed. No fix
  needed.

### Finding 4 — Single-writer lock under a REAL `kill -9`: PASS, 6/6 runs,
zero flakes

`examples/native_crash_kill_check.rs` — a genuine two-process test
against the REAL `native_write::write_append_segments`/
`publish_manifest_update` building blocks (task 002), not a lock-only
synthetic harness (mirroring task 001's own spike shape, but now driving
production mutation code, per this task's own explicit instruction). A
child process acquires the real lock, writes a new segment file, signals
readiness via a marker file, then sleeps; the orchestrator polls for the
marker and sends a REAL external `kill -9 <pid>` subprocess (not
`Child::kill()`'s in-process wrapper — chosen deliberately to remove any
doubt this is a real, unrecoverable hard kill) the instant it appears,
guaranteeing the kill lands inside the write-then-publish window every
run (not a timing gamble).

Verified, every run (6/6, zero flakes):
1. Child reaped with `signal=Some(9)` (confirmed SIGKILL, not a graceful
   exit).
2. `_manifest.json` byte-for-byte unchanged (1014 bytes before, 1014
   after, every run).
3. The new segment file exists on disk as an unreferenced orphan (the
   manifest still lists exactly the pre-crash segment count).
4. **The lock is immediately re-acquirable** in the SAME process right
   after reaping the killed child — kernel auto-release confirmed for the
   REAL mutation code path, not just the bare-lock mechanism task 001
   verified in isolation.
5. The table reads back as EXACTLY its pre-crash state via the REAL
   `TableProvider::scan()`/`statistics()` read path (1000/1000 rows every
   run).
6. The table is still normally writable afterward (a genuine follow-up
   Append succeeds) — the orphan segment does not brick the table.

A second mode (`QE_CRASH_MODE=concurrent`) spawns two REAL child
processes racing a real Append against the same table: **3/3 runs**,
exactly one succeeds and the other fails with a clean, named
`QueryError::Storage` ("another writer already holds the lock on native
table ...: lock acquisition failed because the operation would block") —
never silent data loss, never corruption; the final table state exactly
matches the successful writer's own contribution (seed + its rows, no
more, no less).

Reproduce: `scripts/claude-safe-build.sh cargo build --release --example
native_crash_kill_check && scripts/claude-safe-build.sh
./target/release/examples/native_crash_kill_check` (crash-kill);
`QE_CRASH_MODE=concurrent` prefix for the two-writer scenario.

### Finding 6 — Carried-forward 5.3GB SQL-path finding (from task 002):
given a full, real verdict — confirmed bounded, confirmed unsafe before
this task's fix, FIXED with a small, scoped, root-cause change

**(a) Bounded or unbounded as source size grows?** CONFIRMED BOUNDED, not
unbounded in source row count — the carried-forward finding's own biggest
open question. Measured (not re-estimated) at a size where an
unbounded relationship would become genuinely dangerous, per this task's
own explicit instruction: SF=10 `lineitem` (60,000,000 rows) measured
**5.38GB** peak RSS through the SQL `INSERT INTO ... SELECT` path;
SF=100 (600,000,000 rows, 10x the data) measured **5.86GB** — only **+9%
for 10x the data**. Root cause confirmed by reading
`StreamingParquetScanExec::try_new`: `num_partitions = min(rayon::
current_num_threads(), row_group_count)` — CAPPED BY CPU THREAD COUNT
(32 on this box), not by source row count — and row-group size is
~constant (~1,048,576 rows) regardless of scale (confirmed via
`pyarrow.parquet.ParquetFile` metadata on both SF=10 and SF=100
`lineitem`: 58 vs. 573 row groups, but the SAME ~1,048,576 rows/group
either way). The partition COUNT, not the DATA size, drives the
overhead — this refines task 002's own "many partitions in flight, no
backpressure" root-cause into a precise, falsifiable, now-CONFIRMED
mechanism.

**(b) Does it fail safely?** CONFIRMED IT DID NOT, before this task's
fix — the same bar phase 1 task 006 held. Two independent proofs:
- Setting `ExecutionConfig::memory_limit` (`--memory-limit`) to a tiny
  1GB had **ZERO effect** on actual memory use — the query still peaked
  at 5.43GB, proving this path consults NO admission-control mechanism
  at all (unlike `NativeTable::scan()`'s `check_scan_budget`).
- Under a real `SAFE_BUILD_MEM=2G` cgroup cap, the process was
  OOM-killed by the KERNEL — confirmed via `journalctl -k` directly, not
  inferred from an exit code: `"Memory cgroup out of memory: Killed
  process ... (native_append_m) total-vm:10586308kB, anon-
  rss:2085404kB..."`, `systemd[...]: safe-build-....scope: Failed with
  result 'oom-kill'`. The identical failure class phase 1 task 006 found
  for `NativeTable::scan()`.

**(c) Mitigation decided and implemented**: a small, scoped, root-cause
fix, not a redesign. `ExecutionContext::create_table_as_select`/
`insert_into_native_table` (`src/execution/context.rs`) now merge their
per-partition streams via a new `bounded_partition_merge` helper
(`futures::stream::iter(streams).flatten_unordered(Some(limit))`, `limit`
from `QE_INSERT_MERGE_CONCURRENCY`, default 8) instead of unconditionally
concurrent `futures::stream::select_all` — directly bounding how many
partition readers' decoded-row-group working sets can be resident at
once (the confirmed root cause from (a)). **Measured effect — a clean
win, not a slow-but-safe tradeoff**:

| | before | after | delta |
|---|---|---|---|
| SF=10 peak RSS | 5.38GB | **1.63GB** | **-70%** |
| SF=100 peak RSS | 5.86GB | **1.67GB** | **-71%**, and now even MORE scale-invariant |
| SF=10 wall time | 6.54s | 6.29s | neutral (slightly faster) |
| SF=100 wall time | 100.3s | 77.8s | **-22%, genuinely faster** |
| 2GB cgroup cap | OOM-killed | **succeeds** | fixed |
| 1GB cgroup cap | (untested before fix; would have failed — need ~5.4GB) | **succeeds** | fixed |
| 512MB cgroup cap | OOM-killed | still OOM-killed (`signal 9`) | residual gap, now MUCH narrower |

Correctness verified, not assumed: all 21 pre-existing INSERT/CTAS
integration tests (`tests/native_insert_tests.rs`,
`tests/native_table_validation.rs`) pass unchanged, plus 3 new unit tests
directly exercising `bounded_partition_merge` (every row preserved at
concurrency limits 1/2/8/100; the empty-stream-list edge case). The
60M-row and 600M-row SQL INSERTs themselves are an additional real-scale
correctness check: `rows_inserted`/`total_rows` matched the exact
expected counts (60,000,000 / 600,000,000 + the 6000-row seed) both
before and after the fix.

**Residual risk, named not silently accepted**: this path still has NO
formal pre-flight admission check consulting `--memory-limit` (unlike
`NativeTable::scan()`'s `check_scan_budget`) — an extreme sub-1GB
`--memory-limit`/cgroup configuration can still OOM. Not fixed in this
task: a reliable memory-need estimate for THIS path (dominated by
partition-count x per-partition decode working set, not simply "total
source bytes" the way the read-path's clean proxy works) is harder to
derive correctly, and a wrong heuristic risks a NEW class of bug (false
refusals of legitimately-small operations) — judged worse than the now-
much-narrower residual gap it would close. Named as follow-up work.

Reproduce: `scripts/claude-safe-build.sh cargo build --release --example
native_append_memory_check && QE_MEM_CHECK_MODE=sql
scripts/claude-safe-build.sh /usr/bin/time -v ./target/release/examples/
native_append_memory_check` (SF=10); add `QE_MEM_CHECK_SOURCE=sf100
QE_MEM_CHECK_LIMIT_GB=60` for SF=100; prefix `SAFE_BUILD_MEM=2G` (or
`1G`/`512M`) for the tight-cap legs; `QE_MEM_CHECK_LIMIT_GB=1` isolates
the "engine's own memory_limit is not consulted" proof.

### Finding 7 (named in Technical Details, not the top-level acceptance
list) — memory-budget composition still holds for a heavily-deleted-from
table under real adversarial load

Task 001/003 argued analytically that phase 1 task 006's `check_scan_
budget` formula needs zero changes post-DELETE (deletion never shrinks a
segment's physical bytes). Verified for real, not trusted, against the
IDENTICAL real 60,000,000-row `lineitem` native table fixture
(`data/tpch-10gb-native/lineitem`, 5,641,105,508 bytes on disk) phase 1
task 006 itself used for its own OOM reproduction —
`examples/native_delete_then_scan_budget_check.rs` hard-links the
fixture's segment files (DELETE never touches segment bytes, so sharing
them is safe and avoids a slow multi-GB copy) into a scratch table, then:

- Deletes a real, substantial chunk (`l_linenumber > 6`; this generator's
  `l_linenumber` ranges 1-60, not the TPC-H-spec 1-7, and is skewed
  toward small values since it is an item's position within an order —
  confirmed by reading the manifest's own stats, not assumed uniform):
  **10,675,193 rows net-deleted**, table now 49,324,807 LOGICAL rows.
- **On-disk bytes: unchanged, exactly** (5,641,105,508 before AND after,
  delta=0) — the invariant the whole formula depends on, confirmed
  empirically for a REAL heavily-mutated table, not just argued.
- **A 200MB budget refuses CLEANLY** ("needs an estimated 5641105508
  bytes to scan... exceeds the configured memory safety budget of
  200000000 bytes") — proving the check correctly uses the UNCHANGED
  physical size, not the much-smaller post-delete logical row count
  (which would have wrongly let it through).
- **A generous budget (physical size + 1GB) succeeds**, returning exactly
  the 49,324,807 expected logical rows — proving the check isn't merely
  refusing everything.
- Both assertions hold under a real `SAFE_BUILD_MEM=8G` cgroup cap with
  no crash (exit 0) — confirmed via `/usr/bin/time -v` alongside the
  in-process assertions, matching this task's own "test under
  `scripts/claude-safe-build.sh`'s memory-capped execution model"
  requirement.

Verdict: tested, confirmed correct, no code change needed — task 001/003's
analytical argument holds under real adversarial load, not just on paper.
