## Outcome (closed 2026-09-02)

**Does NOT reproduce on current main — and the acceptance bar's gold
standard was met: a live run at the pruning epic's exact failing commit
reproduced the exact error on demand, with the mechanism caught in the
act.**

**Reproduction attempt at current HEAD** (serve `--tables
data/tpch-100gb-native --memory-limit 100G` — the pruning epic's exact
SF=100 settings from `native_pruning_before_after.py` — `QE_MEM_CAP=110G`,
`QE_SPILL_DEBUG=1`, systemd-run `MemoryMax=110G`, 1800s timeout): Q13
completes **HTTP 200 in 13.5s**, ZERO spill traces, and is **cell-exact
vs a freshly computed DuckDB oracle** over the same `data/tpch-100gb`
parquet (2 rows, order-sensitive and value-exact: `(15, 10000000)`,
`(0, 5000000)` — verified programmatically, not by row count).

**Root cause, confirmed live, not inferred.** The failing operator was
never `SpillableHashJoinExec` (the pruning record's attribution was
loose — the error string names no operator): it was the spillable
AGGREGATE above Q13's join. At the pruning epic's HEAD (`2534739`), the
ONLY `fs::rename` in spillable.rs was `merge_parquet_files` ("Failed to
rename merged file: {}"), called solely from
`SpillableHashAggregateExec::aggregate_with_spilling` on REPEAT
evictions: write `merged_{idx}.parquet` (plus `temp_{idx}_{n}.parquet`
staging), then rename it over the partition's existing spill file. The
`merged_*` name is deletable by any other process for the ENTIRE
read+merge+write window (deleting an open file is harmless on Linux; the
rename then fails ENOENT) — and the default spill root was PID-less
(`$TMPDIR/query_engine_spill`) until `cd8a33b`, which was committed 38
minutes AFTER `2534739`; 2026-08-27's machine demonstrably had concurrent
engine processes sharing that root (sjc-2 001's own Outcome records
cross-process spill-dir bleed that same day). Contributing factor: the
Dictionary `estimate_batch_size` bug (~4,000x, fixed 2026-08-29) is what
pushed Q13's post-join aggregate into the spill path at all at a 100G
limit (it priced 155M collected rows at 356GB).

**Live reproduction at `2534739`** (binary built into a separate
CARGO_TARGET_DIR from a worktree; same query, same settings, wrapped):
the run entered `[spill-agg]` exactly as predicted (155,000,000 rows,
356,340,216,310 "bytes"), spilled to PID-less
`/tmp/query_engine_spill/agg_0_0`, and mid-run the dir contained
`merged_12.parquet` next to `part_12_191.parquet` (191 spill appends to
one partition — the O(n²) merge grind that also explains the 'before'
binary's historical 900s timeout). Acting as the colliding process (a
loop deleting `merged_*.parquet` from the shared dir): **first deletion**
→ `drain task p=0 returned Err: ... Failed to rename merged file: No
such file or directory (os error 2)` (swallowed by the fused-streaming
fallback, which re-executed everything from scratch); **second deletion**
(during the retry's non-fused pass, `agg_0_1`) → **HTTP 400 in 744.3s:
"Execution error: Partition 0 execution failed: Execution error: Failed
to rename merged file: No such file or directory (os error 2)"** — the
exact historical failure, client-visible, 2 deletions → 2 hits.

**Which merged changes removed it (three, independently sufficient):**
1. `cd8a33b` (spill-join-correctness-2 001): PID-embedded default spill
   root — no cross-process sharing, so no foreign deleter.
2. `a0b760d` (oom-safety-hardening 002): open-writer agg spill rewrite —
   `merge_parquet_files` deleted outright; NO `fs::rename` exists
   anywhere in spillable.rs today, so there is no rename window even
   against a hostile deleter.
3. `2912456`+ (spill-size-estimate-fix): content-aware Dictionary
   estimate — Q13@100G no longer enters the spill path at all (zero
   spill traces at HEAD).

**Fix**: none needed in the operator — the mechanism is already doubly
removed; per the task's own charter ("no changes outside the confirmed
mechanism") the code change is the regression pin only.

**Regression test** (deterministic, unit-level, no SF=100):
`agg_spill_has_no_rename_window_under_adversarial_intermediate_deletion`
(spillable.rs) — forced-spill aggregate (fused-ineligible via
COUNT(DISTINCT), 256KB limit) runs while an adversary thread continuously
deletes any `merged_*`/`temp_*` file under the spill root (simulating the
colliding process's cleanup); asserts the spill engaged, the adversary
observed ZERO rename-window intermediates (they must never exist), and
the result is byte-identical to an unlimited-memory run. Doc comment
names the full mechanism and both removing fixes.
