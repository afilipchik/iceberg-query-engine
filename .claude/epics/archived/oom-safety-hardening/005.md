# Task: Formal admission check for INSERT/CTAS write path

## Description

`create_table_as_select`/`insert_into_native_table`
(`src/execution/context.rs`) rely on `bounded_partition_merge`'s
concurrency cap (70% RSS reduction, but a 512MB cgroup cap still
SIGKILLs — the documented residual from native-tables-mutation task
005). Add a formal, named pre-flight admission check mirroring
`check_scan_budget`'s formula (`memory_limit * spill_threshold`) and
error style: refuse cleanly, by name, with exact byte counts, BEFORE
expensive work, when the estimated working set cannot fit (PRD G3).

Estimate = bounded by merge concurrency × per-partition working set
(row-group size × decode expansion), not source total size —
deliberately conservative but must not false-refuse the workloads that
already pass (SF=10/SF=100 appends at 1-2GB caps, measured 1.63-1.67GB
peaks).

## Outcome (2026-08-29, stream E — full evidence in updates/005/stream-E.md)

**Shipped**: `ExecutionContext::check_insert_write_admission`
(`src/execution/context.rs`), the formal, named
"insert/CTAS write-path admission check", wired into BOTH
`create_table_as_select` and `insert_into_native_table` immediately after
`create_physical_plan` (partition count known) and before any
`physical.execute()` call or target write-lock — a refusal leaves the
target byte-for-byte untouched (tested via manifest comparison).

**Estimate formula** (pure, unit-tested `evaluate_insert_admission`):

    estimate = min(QE_INSERT_MERGE_CONCURRENCY, num_partitions)
               x max_source_parquet_row_group_total_byte_size x 3

refused when `estimate > memory_limit * spill_threshold` —
`check_scan_budget`'s exact budget formula and error style. The 3x decode
expansion is calibrated, not guessed: SF=10 lineitem's 59.1MB
(`total_byte_size`) row groups decode to ~132MB of Arrow (2.24x, measured
via pyarrow), plus per-stream pipeline slack. The estimate is the
BOUNDED-MERGE working set, never source total size — the write path
streams row group by row group and `bounded_partition_merge` polls at most
`concurrency` partition streams at once. No parquet-backed source in the
plan (VALUES, memory tables, native-table sources already guarded by
`check_scan_budget`) => no estimate basis => admit, never refuse on a
guess. `QE_DEBUG_INSERT_ADMISSION=1` traces every decision.

**Calibration held on both sides, measured live**:
- SF=10 estimate = 8 x 59,120,848 x 3 = 1,418,900,352 B. At 512MiB limit
  (budget 429,496,729 B): harness insert scenario flipped from task 001's
  journal-confirmed memcg SIGKILL (exit 137) to a clean named refusal,
  exit 2, 28-30MB peak RSS, BOTH levers — message cites check name, exact
  estimate/budget bytes, and both knobs (`--memory-limit`,
  `QE_INSERT_MERGE_CONCURRENCY`).
- At 2GiB limit (budget 1,717,986,918 B): ADMITTED, and the real run under
  a real 2GB cgroup cap (`MemoryMax=2G`, swap off) completed 60M rows in
  9.0s, peak RSS 1,682,372 KB. Uncapped-ish re-measure: 1,673,240 KB
  (~1.6GB band) — the bounded-merge 70% RSS reduction is unregressed.

**Tests** (default features, via claude-safe-build.sh): 5 new unit tests
(SF=10 calibration both sides, partition-capped concurrency, knob-advice
truthfulness, no-source admit) + new `tests/insert_admission_tests.rs`
(4 e2e tests incl. refusal-leaves-target-untouched). Existing suites
unchanged and green: native_insert 9, native_delete 10, native_update 12,
native_table_validation 12, rollup suites 11+8+7+16, lib context 14.
`cargo fmt` clean.

**Also**: `examples/oom_cap_harness.rs` `scenario_insert` now takes
`QE_HARNESS_INSERT_LIMIT` (default 512MB = the driver's cap) instead of
the pre-fix deliberate 8GB — post-fix the engine limit is exactly what
drives the refusal; the history and rationale are documented inline.
