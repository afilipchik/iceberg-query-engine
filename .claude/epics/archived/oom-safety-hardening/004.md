# Task: Streaming native-table scan into spilling consumers

## Description

`NativeTable::scan()` materializes every active segment; oversized
tables can only REFUSE (`check_scan_budget`). Add a streaming scan path
— mirroring the `ParquetTable::scan()` vs `StreamingParquetScanExec`
split — that reads segment-at-a-time via the existing
`ipc_cache::read_row_group` mmap reader and feeds spill-capable
consumers (aggregate, join), so a native-table query over budget
COMPLETES by spilling instead of refusing (PRD G2).

`check_scan_budget` stays as the guard for shapes that genuinely must
materialize (raw `SELECT *` dump into a `QueryResult`) — document that
boundary explicitly in CLAUDE.md's native-table Limitations section, do
not silently narrow it.

### Design as shipped (epic Architecture Decision 4, exactly)

- **`NativeStreamingScanExec`** (`src/physical/operators/native_scan.rs`,
  new): segment-at-a-time lazy streaming through the UNCHANGED
  `ipc_cache::read_row_group` mmap reader; ≤8 partitions, round-robin
  segment assignment, one segment resident per partition at a time
  (mmap-backed = reclaimable page cache under memcg, invisible to
  `RLIMIT_DATA`); `MemoryTableExec`-style rewrap for dictionary
  transparency and alias-qualified names; `spawn_blocking` for the
  decode.
- **`NativeTable` helpers** (`src/storage/native_table.rs`):
  `scan_budget_exceeded()` (check_scan_budget's exact condition,
  exposed), `streaming_segment_ids(filter)` (the SAME
  `segment_might_match` pruning `scan_with_filter` uses, +
  `QE_DEBUG_NATIVE_PRUNING` trace tagged `streaming`),
  `read_segment_batches(id, projection)` (read + `filter_deleted_rows`,
  identical to `scan()`'s per-segment body).
- **Planner gate** (`src/physical/planner.rs`): a Scan streams IFF the
  provider is a `NativeTable` AND `scan_budget_exceeded()` AND the Scan
  node has an **Aggregate ancestor** (`collect_agg_covered_scans`
  pre-pass, keyed by ScanNode address, run in `create_physical_plan`).
  Aggregate-only (not join-only) because a bare `SELECT * FROM a JOIN b`
  materializes at the `QueryResult` root — streaming it would trade a
  clean refusal for an OOM at collection; the criterion's join shape
  (aggregate over join) passes through both nodes and streams.
  `try_extract_native_dense_source` declines over-budget tables so the
  dense-direct route (whose execution-time scan would refuse) falls to
  the generic spillable aggregate over the streaming scan. The full
  Scan-level predicate is always re-applied by `FilterExec` above the
  operator (pruning only skips provably-unsatisfiable segments).

### Acceptance criteria, one by one

1. **Harness scenario 3 flips refusal → completion (both levers), agg AND
   join.** Pre-fix (task 001, recorded): clean-refusal exit 2, 27MB peak.
   Post-fix aggregate (default scenario query, 5.64GB lineitem at 512MB
   memory_limit, 2G caps): **cgroup exit 0 / 170MB peak, rlimit exit 0 /
   165MB peak**, 3 group rows, 0.10s wall — independently re-confirmed by
   task 007's sweep (0/143MB + 0/152MB). Post-fix join consumer (new
   additive `QE_HARNESS_SCAN_SQL` knob; 60M×60M self-join on
   (l_orderkey, l_linenumber), GROUP BY l_returnflag, QE_SPILL_DEBUG=1):
   **both levers exit 0** (peaks 2097/2048MB, i.e. pinned at the 2G cap
   by reclaimable page cache, never killed), with REAL observed spill —
   `execute_spill_path START ... in_memory_partitions=1
   spilled_partitions=63`, 60M probe rows, per-partition build/probe
   hash-checks all ok, on BOTH levers.
2. **Deletion vectors + pruning on the streaming path, cell-exact on a
   mutated table.** Operator tests: real `delete_from_native_table`
   tombstones (id%10) never streamed; `id >= 450` prunes 4/5 segments
   (pinned via `segment_count()`). E2E
   (`tests/native_streaming_scan_tests.rs`): id%7 DELETE spread across
   every segment of an over-budget table, then GROUP BY/COUNT/SUM —
   cell-exact against an INDEPENDENT in-test recomputation AND an
   unconstrained context; filtered aggregate cell-exact with pruning en
   route.
3. **Dense-direct + GPU eligibility unaffected in-budget.** The gate
   short-circuits on `scan_budget_exceeded()` — an in-budget table's
   planning is byte-identical (no code path touched); pinned by
   `in_budget_tables_are_unaffected` and by the bench parity run below.
4. **Raw-materialization refusal documented + pinned.**
   `oversized_select_star_still_refuses_by_name` (asserts the "memory
   safety budget" named error) + `other_materializing_shapes_still_refuse`
   (filter-only, ORDER BY-only). Boundary documented in CLAUDE.md's
   native-tables Memory-safety section and `native_table.rs`'s module doc
   (not silently narrowed: the shapes that still refuse are listed).
5. **No regression to the never-mutated native band.**
   `native_bench_compare.py --no-duckdb` over pristine
   `data/tpch-10gb-native` (serve-driven, 40G limit, iterations 2, idle
   machine): 22/22 OK, **TOTAL 5513.76ms** — inside the recorded
   5324ms/5667ms band.

### Residuals (documented, deliberate — not defects)

- ORDER BY-only / filter-only / raw `SELECT *` over an over-budget table
  still refuse by name (the documented boundary; extending the gate to
  Sort ancestors is possible follow-up now that task 003's sort streams,
  but output still materializes at the root, so it needs the same
  root-shape reasoning, not just a one-line gate change).
- Subquery-planned scans (SubqueryExecutor's own planners) run their own
  pre-pass; a shared Arc'd subtree referenced from both an aggregate and
  a dump position is marked streaming if EITHER parent qualifies —
  noted in `collect_agg_covered_scans`'s doc, considered acceptable.
