# Task: Reliable reproduction + instrumented root-cause investigation

## Description

The entry point and hardest part of this epic. TPC-H Q12's spilling
INNER join, against a native table that went through a full `CREATE→
INSERT→DELETE→UPDATE` sequence at SF=10, was found to return an answer
exactly 2x too high (`high_line_count` 707644 vs DuckDB's 353822) and
take ~320 seconds. The orchestrating session independently re-verified
afterward: the extreme slowness reproduced identically on a fresh table
AND on the same table after one plain `DELETE` (both ~150s), but the
wrong answer did NOT reproduce in either of those two simpler attempts —
only the full original mutation sequence triggered it. A prior
investigation (native-tables-mutation task 006) already read
`execute_spill_path`/`build_with_partitioning`/`probe_with_spilling`/
`process_spilled_partition` end to end looking for a duplicate-counting
mechanism and did NOT find one by inspection — the partition/spill
bookkeeping "reads as mutually-exclusive-by-construction." This task's
job is to catch the bug in the act with real instrumentation, not read
the same code a third time hoping to spot it.

This task's Description (above) says the bug was found "against a
native table that went through a full `CREATE→INSERT→DELETE→UPDATE`
sequence." Re-reading the ORIGINAL raw investigation log
(`native-tables-mutation/updates/006/stream-A.md`, not just CLAUDE.md's

finding came from running the standard 22-query `native_bench_compare.py`

warehouse. The mutation sequence is a completely separate diagnostic

### Reliable reproduction (exact steps, numbers, determinism explicitly tested)

1. Fixture: `data/tpch-10gb-native` (already on disk from the
   native-tables-foundation/mutation epics; built via `write-native
   --from-parquet` from `data/tpch-10gb`; unchanged by this task).
2. `target/release/query_engine serve --bind 127.0.0.1:<port> --tables
   data/tpch-10gb-native --flight-bind none --memory-limit 40G`
   (`setsid nohup ... & disown` — plain `nohup`/`disown` without `setsid`
   was observed to intermittently fail to survive this sandbox's
   per-tool-call teardown, exit code 144, no log file, no process; adding
   `setsid` was 100% reliable across ~20 launches).
3. `POST /sql?format=csv&distributed=0` with Q12's exact spec SQL (from
   `src/tpch/queries.rs`).
4. DuckDB oracle, independently computed: `MAIL,353822,529784` /
   `SHIP,352224,530051` (matches CLAUDE.md's cited 353822 exactly).

**21 total runs. 1 wrong (4.8%). 21/21 uniformly slow (140-291s vs
150-350ms for every other TPC-H query).** The one wrong run:
`MAIL,705002,1055639` / `SHIP,701718,1056148` — BOTH aggregates, BOTH
groups, inflated by the SAME ~1.9925-1.9927x ratio (not exactly 2x — the
original report's own "exactly 2x" was 707644/353822 = 2.0000x exactly;
this task's own catch was close but not identical, confirming the ratio
itself varies run to run, not a fixed constant). Wall time 291s vs ~141s
for correct runs (~2.06x). Non-determinism was tested explicitly, not
assumed either way, per this task's own instruction: repeated the exact
same server+query on both warm (same process, repeated queries) and cold
(fresh process restart) conditions; an initial apparent "outcome fixed
per warm process" pattern did not hold up (see stream-A.md — it's
explained by chance at a ~5-10% true per-query rate, and a specific,
already-fixed historical bug in this exact codebase rules out the
per-process-hash-seed mechanism that pattern would have implied).
Varying `--memory-limit` (40G → 10G; 1G refuses via `NativeTable`'s
admission-control check) had no effect on the signature — all 64 hash
partitions were already spilling at 40G, so the trigger isn't gated by
how tight the memory budget is.

**Smaller/faster repro: not found.** Only `--memory-limit` was varied
(no effect). A deliberately downsized synthetic dataset was not
attempted — named as the single highest-leverage next step for anyone
continuing this investigation, since 140-291s per trial made this task's
own ~21-trial budget expensive in wall-clock time.

### Instrumentation (shipped, in `spillable.rs`, gated behind `QE_SPILL_DEBUG`)

- `execute_spill_path`: START/DONE trace — build rows, build-partition
  in-memory-vs-spilled breakdown, probe rows, in-memory-matched vs
  spilled-matched vs total-matched row counts, elapsed time, keyed by the
  pre-existing `SPILL_COUNTER`-derived `spill_id`.
- `execute_fused_streaming`: START/OK/ABORTED trace — a new monotonic
  `call_id` (`SJ_TRACE_SEQ`/`next_sj_trace_id()`), and on abort, the
  captured error text from whichever site set it (drain-task `Err`,
  drain-task panic, worker-thread panic, or `process_batch`'s own error
  via a new `abort_reason: Arc<Mutex<Option<String>>>` slot).
- `SpillableHashAggregateExec::execute`: one line at the exact call site
  that re-executes a non-idempotent child after a fused-streaming abort.

Verified behavior-neutral: full suite green, **1188 passed / 0 failed /
1 ignored** — identical to the pre-existing recorded baseline in
CLAUDE.md. `cargo fmt --all -- --check` clean.

### Root-cause verdict: NOT confirmed — but with a real, direct, decisive negative result

The single most obvious candidate mechanism, directly documented by the
code's own comments (`BuildDecision::Spill`'s doc comment: "an operator
above may legitimately execute its child more than once (the fused
streaming aggregate drains, aborts, and re-executes)"), was tested with
a controlled chaos/fault-injection experiment — a temporary env var
(`QE_SPILL_CHAOS_FORCE_ABORT`, removed before finishing) that forced
`execute_fused_streaming` to discard its own fully-completed, correct
result and fall through to the "re-execute the input from scratch"
path. Result: wall time **283s** (closely matching the original wrong
run's 291s — CONFIRMS this mechanism fully explains the SLOWNESS
pattern), but the final answer came back **CORRECT**
(`MAIL,353822,529784` / `SHIP,352224,530051`) — DISPROVING this
mechanism as sufficient to explain the WRONGNESS.

Also ruled out by direct reading, each with a specific supporting fact
(full detail in stream-A.md):
- The `ORDER BY l_shipmode` Sort operator re-executing the aggregate:
  ruled out — `SpillableHashAggregateExec` doesn't override
  `output_partitions()` (inherits the trait's hardcoded `1`), so
  `ExternalSortExec`'s `collect_input_partitions_concurrently` takes the
  single-call fast path for it.
- Per-process hash-seed randomization: ruled out — partition routing
  uses an explicit fixed seed, specifically because of a past real bug
  of exactly that shape (documented in the code's own comment).
- Build-side or probe-side double-collection: ruled out by the chaos
  test itself (both attempts reported identical, correct row counts).
- Duplication within a single clean `execute_spill_path` call
  (`build_with_partitioning`/`probe_with_spilling`/
  `process_spilled_partition`/`probe_partition`/`build_hash_table`/
  `JoinKey`): read in full, structurally airtight, and empirically never
  wrong across 20 correct, fully-traced runs.
- Aggregation-state merge dictionary-index misattribution: reasoned out
  (not chaos-tested) — `merge()` reconciles by real key VALUE not raw
  per-batch dictionary index, and a misattribution bug would redistribute
  counts between groups (grand total unchanged), not inflate the grand
  total uniformly the way the actual symptom does.

**Slowness/duplication shared-cause verdict: partial.** Slowness is
fully, mechanically explained by "the whole computation ran ~2x"
(confirmed). Wrongness is NOT explained by the same mechanism in its
simplest, clean form — the chaos test proves a clean two-attempt retry
is insufficient. Whether a MESSIER version of the same "ran twice"
family (a genuine mid-computation failure rather than a clean
post-completion discard, potentially interacting with the extremely
I/O-heavy spill path — see below) is still responsible for the
wrongness remains an open, not a closed, question.

**Best remaining hypotheses for whoever continues:**
1. A genuine mid-computation failure (not the chaos test's clean
   post-completion discard) inside the extremely I/O-heavy
   `append_to_parquet`-based spill path, possibly leaving some shared
   state (memory-pool accounting, an orphaned spill directory, something
   not yet identified) inconsistent in a way a clean retry can't
   exercise. Next step: instrument `append_to_parquet`/
   `write_batches_to_parquet`/`read_parquet` directly (call counts, error
   capture) and keep hunting for a NATURAL abort — none was caught
   naturally with tracing on in this task's 21-run budget (the one wrong
   run predates the instrumentation).
2. A mechanism entirely outside the retry/re-execution family this
   task's instrumentation targeted (expression evaluation, batch
   concatenation, Arrow buffer aliasing under a rare partition-boundary
   condition). Not investigated — lower prior, budget ran out first.
3. Build a deliberately downsized synthetic repro to cut the ~140-291s
   per-trial cost to seconds, enabling hundreds of trials instead of
   ~20 — the single highest-leverage next step, not attempted here.

### A separate, real finding along the way (not the wrong-answer bug — independently valuable)

`append_to_parquet` (spillable.rs) does a full read-entire-file +
rewrite-to-temp + atomic-rename on EVERY call. With all 64 hash
partitions spilling almost immediately (only ~4% of the eventual
1,765,881 build rows were ever in memory at spill time, per the trace)
and 916 build batches (plus the full 15,000,000-row probe side) getting
progressively appended, this is an O(n²)-ish disk I/O pattern and a
strong, independent candidate for why even a CORRECT run takes 140+
seconds. Not fixed (out of this task's scope — instrumentation and
root-cause only) but flagged for whoever picks up a fix, per this task's
own "report what you'd fix and why, don't implement it" instruction.
