# Task: Fix confirmed O(n²) append_to_parquet spill slowness

## Re-scope note (2026-08-24)

This task was originally "fix the wrong-answer bug." Task 001 closed
without confirming that bug's root cause, so per the epic's own
"no guess-fixes" gate, that fix does NOT proceed — do not attempt it
here. Instead, this task fixes a SEPARATE, independently-confirmed
problem task 001 found along the way: `append_to_parquet` in
`spillable.rs` does a full read-entire-file + rewrite-to-temp +
atomic-rename on every spill append. With all 64 hash partitions
spilling almost immediately and hundreds of build batches (plus the

let this task's changes accidentally mask or alter it — the regression
test added here validates correctness is unchanged, not that the
wrong-answer bug is gone (it isn't, and this task doesn't touch its
mechanism).

## Description

Replace the O(n²) read-rewrite-rename-per-append pattern in
`append_to_parquet` (`src/physical/operators/spillable.rs`) with an
append-friendly approach — the standard fix for this shape is switching
from "rewrite the whole file every call" to either (a) writing each
spilled batch to its own small file within a partition's spill
directory and merging once at read time, or (b) using a true streaming
Parquet writer that appends row groups without re-reading prior
content. Pick whichever fits this codebase's existing spill-read path
with the least disruption — read `process_spilled_partition` and
whatever reads these files back before choosing, since the fix must
stay compatible with however spilled partitions are currently
consumed.

## Outcome (closed 2026-08-25)

Full chronological detail (context gathered, exact reasoning for the
design choice) lives in
`.claude/epics/spill-join-correctness/updates/002/stream-A.md`; this is
the load-bearing summary.

### Root cause (re-confirmed by reading the code directly, matching task 001's finding exactly)

`append_to_parquet(path, batch)` — called once per hash-partitioned
chunk of every incoming build/probe batch, for any partition that had
already spilled — did, on EVERY call: open the existing spill file, read
its schema, stream the ENTIRE existing file's row groups into a brand
new temp file, write the ONE new batch, close, then atomically rename
the temp file over the original. Cost per call was O(bytes already
spilled for that partition), so the whole build/probe phase cost
O(n^2) in bytes read+written for a partition accumulating n batches.
With `NUM_PARTITIONS` = 64 and, per task 001's own trace, all 64 build
partitions spilling almost immediately plus the full probe side (100%
of matches came via the spilled path), this was the dominant cost of
task 001's 140-291s Q12 repro.

### Fix

Replaced the read-rewrite-rename-per-append pattern with a single
`ArrowWriter<File>` kept OPEN per partition for the whole build (or
probe) phase, appending each new batch as one more row group
(`append_batch_streaming`, new), closed exactly once when that phase's
loop ends (`close_spill_writers`, new). Cost per append is now
O(batch), not O(prior file size) — the direct fix for the acceptance
criterion's own language. The on-disk SHAPE is UNCHANGED: still exactly
one Parquet file per partition, still one row group per appended batch
— so `process_spilled_partition`/`read_parquet` (the read-back path)
needed ZERO changes. This is deliberately the "(b) true streaming
Parquet writer" option named in this task's own Technical Details,
chosen over "(a) many small files merged at read time" specifically
because it required no changes to the read-back path at all, and avoids
creating potentially tens of thousands of tiny per-batch files (916
build batches x up to 64 partitions, plus a much larger number of probe
batches, in task 001's own repro).

The old `append_to_parquet` function was deleted entirely — confirmed
via a repo-wide grep it had exactly two call sites, both replaced, and
no other caller anywhere. `write_batches_to_parquet`, `read_parquet`,
and `merge_parquet_files` (the sibling function the AGGREGATE spill path
uses — a different, deliberately untouched mechanism, out of this
task's scope) are unchanged.

Sole file touched: `src/physical/operators/spillable.rs`, exactly as
the task specified.

### Tests added

Two new unit tests in `spillable.rs`'s own `#[cfg(test)]` module:
- `append_batch_streaming_preserves_all_rows_across_many_appends`:
  correctness — 50 batches (37 rows each, deliberately not a round
  number) appended through one shared writer slot, read back, every
  row asserted present in write order.
- `append_batch_streaming_cost_does_not_grow_with_prior_data`: direct
  evidence for the acceptance criterion's exact language ("cost per
  append does not grow with the total data already spilled"). Times
  append #2 vs append #301 through the same writer/file (the identical
  call pattern `build_with_partitioning` uses) and asserts the late
  append is not dramatically more expensive (generous 20x + 25ms fudge
  factor against scheduler jitter, while still failing clearly if the
  old O(n)-per-append cost ever regressed back in — that would make
  append #301 roughly 150x append #2's cost, since the file being fully
  re-read+rewritten on every call would have grown ~150x between the two
  measurements).

Both pass, both fast (part of the 8-test `spillable::tests` module
finishing in 0.17s total).

### Wall-clock validation (task 001's exact repro, `.scratch/spill_join_repro/repro.sh`, reused unchanged)

**Before** (task 001's own recorded, well-evidenced 21-run baseline —
re-cited here, not re-measured; see 001's Outcome/stream-A.md for the
full record): **140-291s per run, 21/21 uniformly slow.**

**After** (this task, built `target/release/query_engine` with the fix
via `scripts/claude-safe-build.sh cargo build --release`, then reran the
saved repro script): **30 fresh-process trials (ports 18701-18730, run
sequentially): 30/30 correct. HTTP query wall time: min 3s, max 4s, avg
3.30s. Full script wall time (incl. ~1-2s server startup/readiness):
3-5s per trial.** The improvement is consistent, not run-to-run
variable — every one of the 30 trials landed in the same narrow 3-5s
band, no outliers. That is a **~40-90x speedup** (141s/3.3s ~= 43x
against task 001's own "normal correct run" baseline; 291s/3.3s ~= 88x
against its one recorded slow/wrong run).

Also ran 10 additional WARM trials (one persistent server process,
repeated queries — task 001's own methodology included both fresh and
warm trials): **10/10 correct, 4-6s each** (the lance/gpu/pulsar test
suites were compiling concurrently in the background during this
specific batch, plausibly explaining the slightly wider 4-6s vs the
isolated 3-4s fresh-process band — still nowhere near the old 140-291s
regime).

**Total: 40/40 trials correct across this task's own validation.**

### Correctness / wrong-answer-bug status (explicit, as required)

Per this epic's own scope boundary, the wrong-answer bug (~4.8%, 1/21,
per task 001) was NOT investigated or touched by this task. 0/40 of
this task's own trials reproduced a wrong answer. **This is reported
honestly, not as a claim of a fix**: at an unchanged true 4.8% rate, the
probability of observing zero wrong answers across 40 independent
trials is 0.952^40 ~= 13.9% — a real, non-negligible chance, so 0/40 is
fully CONSISTENT with an unaffected rate, not evidence the rate changed
in either direction. `append_batch_streaming`/`close_spill_writers`
change how and when bytes are written to a spill file's underlying
`ArrowWriter`, not what rows are computed, matched, partitioned, or
counted — there is no mechanism by which this change could plausibly
touch the wrong-answer bug either way, but "plausibly shouldn't" is not
the same claim as "confirmed doesn't," so this is stated as an
observation (0/40) with its honest statistical caveat, not a verdict.
