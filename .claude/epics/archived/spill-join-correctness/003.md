# Task: Blast-radius characterization of the wrong-answer bug

## Re-scope note (2026-08-24)

## Description

Determine the actual scope of exposure to task 001's wrong-answer bug:
is it native-table-specific, or reachable via plain Parquet sources
too? Which other TPC-H queries that spill (beyond Q12) are exposed?
Does key cardinality/skew change the observed rate? This is
intelligence-gathering to inform prioritization and future
investigation — not a fix, and not expected to reduce the ~4.8% rate.

### 1. Which queries engage the JOIN spill path at SF=10 — confirmed via trace, not slowness

At the SAME realistic setting task 001 used (`serve --memory-limit 40G`):

- **Native tables: ONLY Q12** (`execute_spill_path START` fires exactly
  once; all other 21 queries complete in <1.4s with zero spill events).
  Re-confirmed at `--memory-limit 10G` (task 001's own admission-control
  floor) — identical. Q4 correctly, loudly refuses
  (`SEMI join build side exceeds the memory budget ... supports only
  INNER joins`) — the pre-existing, intentional, already-documented
  safety behavior, not a new bug.
- **Plain parquet: NONE spill — not even Q12** (0.16-0.27s, zero spill
  events). Pushed `--memory-limit` down through
  8G/4G/2G/1G/512M/256M/128M/64M with **zero effect**; Q12 only starts
  spilling on parquet between 64M and 32M.
- **Root cause of the source difference, confirmed by diffing
  `PLAN_DEBUG=1` output side by side**: the optimized LOGICAL PLAN IS
  IDENTICAL between sources (same projection, same filter). The
  difference is scan-level: parquet applies its projection + predicate
  physically (row-group stats + `RowFilter`) before the join ever sees
  the data; native has no scan-level pushdown. **Refinement to CLAUDE.md's
  own existing explanation**: this is NOT a row-count difference into the
  join — `sj-trace` shows **`build_batches=916 build_rows=1765881`,
  IDENTICAL between native (natural) and parquet (forced) once both
  spill**. The trigger difference lives in the per-batch/per-row
  BYTE-SIZE ESTIMATE feeding `execute_spill_path`'s `memory_threshold`
  check, not row count fed into the join. Not root-caused further (a
  threshold/estimate question, not the wrong-answer mechanism — out of
  this task's charter) but reported as a finding for whoever next touches
  that estimate.
- Settled on **`--memory-limit 1M`** as the standard "force parquet Q12 to
  spill" setting for all trials below: `in_memory_partitions=1
  spilled_partitions=63` (98.5% spilled), closely matching native's
  natural `in_memory_partitions=0 spilled_partitions=64` (100% spilled).
- **SF=100** (native `data/tpch-100gb-native`, 65GB; parquet
  `data/tpch-100gb`, 97GB — both already on disk): same pattern. Native
  @ `--memory-limit 100G`: only Q12 spills (35.5s, correct this pass); Q4
  refuses loudly as before; **Q13 timed out at 300s** with the
  AGGREGATE's own, separate spill mechanism engaged (`agg_spill=1`,
  `join_spill_events=0` — NOT the join operator this task characterizes)
  — consistent with, and independently corroborating, task 002's own
  explicitly-named follow-up risk (`merge_parquet_files`'s possible
  analogous O(n²) pattern, never examined). Not investigated further here
  (different operator). Parquet @ 100G: Q12 does not spill, matching
  SF=10.

### 3. Parquet vs. native — the single most important result

**No evidence found that the bug is native-table-specific.** The
identical `execute_spill_path`/`build_with_partitioning`/
`probe_with_spilling`/`process_spilled_partition` code, executing over
parquet-sourced data forced into the same spill shape, produced 0/80
wrong — statistically indistinguishable from native's own 0/80 this task
(equal trial counts, equal outcome, 95% CI [0%, 4.51%] both). This is
**consistent with** (not proof of) the epic's own working hypothesis #2
("general to any large spilling INNER join, not just native tables") —
the mechanism is source-agnostic at the code level (confirmed both by
reading it and by tracing it), and no source-specific behavioral
difference emerged at matched trial counts. Given the bug's low absolute
occurrence rate, this task's own sample size cannot rule out a real but
smaller difference between sources — stated honestly as a bound, not a
proof of parity.

### 4. Cardinality/skew (light, time-boxed)

One variant tried: `l_shipmode IN (...)` widened from 2 values to all 7
TPC-H shipmodes (`.scratch/spill_blast_radius/q12_allmodes.sql`) — ~3.5x
larger build side (elapsed 6.2s vs 3.2s, consistent with the size
increase), 7 output groups instead of 2. 20 cold trials, native @ 40G:
**0/20 wrong**, all 20 confirm spill engagement. This is a weak signal on
its own (95% CI [0%, 16.84%]) — reported honestly as such, not rounded up
to "cardinality doesn't matter." Parquet skew variant and any other
skew/cardinality shape: **NOT attempted** (explicit time-budget cut).

### 5. Distributed (M1/M2) — confirmed exposed, plus a real surprise

**Spilling joins DO occur in distributed execution** — but via the
**SCATTER "sharded-fact/replicated-dims" `two_phase` model**
(`x-qe-distribution` header: `"shape":"two_phase","shard_count":3`), NOT
the GATHER path a first read of CLAUDE.md's own summary text for "joins"
suggests. Q12's shape (one large table referenced once, joined to a
smaller table, exactly-mergeable SUM aggregates) qualifies for scatter's
ClickHouse-style election — each of the 3 nodes independently runs
`execute_spill_path` over ITS OWN ~1/3 shard of `lineitem` joined to a
full local copy of `orders`; results merge via generated SQL. Confirmed
directly, not inferred: per-node `build_rows` summed EXACTLY to the
single-process total (586783+586268+592830=1,765,881).

**A genuinely new, distinct bug found and root-caused (not fixed, per the
gate)**: the first un-isolated 3-node cluster attempt FAILED —
`Parquet error: Required field schema is missing`, HTTP 400. Root cause:
`spill_path`'s default (`$TMPDIR/query_engine_spill`) has NO per-process
disambiguation beyond a **per-process-local** `SPILL_COUNTER` starting at
0 in every process, so three CONCURRENT `serve` processes sharing one
host's `$TMPDIR` all computed `spill_id=0` and wrote to the SAME
`/tmp/query_engine_spill/join_0_0/` directory simultaneously — confirmed
by finding those exact colliding directories still on disk after the
failure. A fix-shape test (giving each node its own `TMPDIR`) made the
identical query succeed, cell-exact — confirming the collision was the
sole cause, not a distributed-specific instance of the target bug. This
is a REAL, PRACTICAL risk for any deployment where nodes share a temp
filesystem (this repo's own local multi-process test harness included)
but is DISTINCT from the ~4.8% wrong-answer bug: it fails LOUDLY with a
clear I/O error, never silently returns a wrong answer.

**40 repeated distributed trials** (fresh 3-node cluster per trial,
per-node `TMPDIR` isolation, native @ 40G, `distributed=1` forced):
**0/40 wrong**, 95% CI [0%, 8.81%], every trial's `x-qe-distributed: true`
and at least one (usually 2-3 of 3) node per trial independently
confirming `execute_spill_path START` via its own log.

**Parquet-distributed: NOT independently tested.** Reasoned, not
confirmed: the SAME `--memory-limit` gates BOTH the scatter/gather
admission check (needs the TOTAL compressed bytes across
gathered/sharded tables — GB-scale at SF=10 — to fit under half the
budget) AND the join's own spill threshold (needs ~tens of MB for
parquet's small post-filter build side) — a ~50-100x gap that cannot be
satisfied by one uniform flag. Extrapolated from the single-process
parquet≈native equivalence (§3), not independently confirmed for the
distributed case.

### 6. Bonus finding: broader "under extreme memory pressure" sweep — two MORE distinct bugs found, neither the target one

At a deliberately adversarial `--memory-limit 1M` (parquet, all 22
queries, single pass — **NOT a trial-count characterization**), 13
queries' joins engage the spill path (2,3,5,7,8,9,10,12,14,15,16,19,21).
Two showed cell-exact mismatches, investigated immediately:

- **Q2, Q3 (both have `ORDER BY ... LIMIT N`)**: row-count BLOWUPS (2085
  vs 100; 755880 vs 10), not value inflation. Directly compared the
  engine's first-N rows against DuckDB's LIMIT-ed oracle: **byte-for-byte
  identical** for every row compared. This is a "correct top-K prefix,
  LIMIT never applied to truncate it" bug — a completely different
  symptom shape than the join's value-inflation target bug (which keeps
  row/group count correct and inflates VALUES). Likely
  `ExternalSortExec`'s spill path or the top-k fusion rule losing the
  LIMIT under a spilled input. **Reported, not fixed, not investigated
  further** (out of charter).
- **Q10**: crashed — `Failed to open run file
  ".../sort_0_27/merged_pass0_48.parquet": No such file or directory` — a
  SORT-spill run-file-management bug, again clearly distinct. **Reported,
  not fixed, not investigated further.**
- Q4/13/18/20/21/22 all correctly, loudly refuse (non-INNER join spill
  attempts) — confirmed this is the pre-existing, intentional, documented
  safety behavior, not a new bug, even under this adversarial setting.
- Repeat-trial characterization of the other 1M-only-spilling queries
  (5,7,8,9,14,15,16,19) was explicitly **NOT attempted** — Q9 alone took
  207s for a SINGLE pass at this setting, and the time was better spent
  accurately characterizing the two newly-found, unrelated bugs above
  than multiplying an already-adversarial, unrealistic condition.

### Final verdict

**Confirmed exposed** (spill path reliably engages, confirmed via trace):
Q12, both sources (native naturally at realistic settings; parquet only
via an aggressive, unrealistic memory-limit at SF=10/SF=100 — never
observed spilling parquet at any realistic setting tried), single-process
AND distributed (scatter).

**Confirmed clean** (0 wrong / N trials, N stated, not rounded up to
"safe"): Q12 native this task 0/80 (epic-wide cumulative 1/141≈0.71%, CI
up to 3.89%); Q12 parquet-forced 0/80 (CI up to 4.51%); Q12
distributed-native 0/40 (CI up to 8.81%); Q12 widened-cardinality native
0/20 (CI up to 16.84%, weak signal); Q12 SF=100 native 0/8 (CI up to
33.63%, very weak signal). **None of these is proof of a fix** — the
duplicate-counting mechanism remains unconfirmed and completely untouched
by this task.

**Remains unknown** (explicitly, not silently skipped): the individual
wrong-answer rate of the ~12 other queries whose joins only spill under
an artificial 1M memory-limit (structural reachability confirmed by a
single pass each; repeat-trial characterization not attempted — cost,
especially Q9's 207s/trial); SF=100 under a forced-spill parquet
condition (not attempted); SF=100 distributed (not attempted); parquet
under distributed execution at all (not attempted, reasoned equivalence
only); any skew/cardinality dimension besides the one native variant
tried; whether the bug's true rate differs meaningfully between native
and parquet (this task's sample size bounds but cannot rule out a smaller
difference).

**New findings, reported not fixed** (all confirmed DISTINCT from the
~4.8% target bug by direct symptom comparison, not assumption): (a) a
spill-directory collision across concurrent same-host `serve` processes
(distributed correctness/availability risk); (b) LIMIT not enforced when
an `ORDER BY...LIMIT` query's plan spills under extreme memory pressure
(Q2/Q3-shaped); (c) a sort-spill run-file-not-found crash (Q10-shaped)
under the same extreme pressure; (d) the native-vs-parquet spill-trigger
gap is a byte-size-ESTIMATE effect, not a row-count effect (refines, does
not fix, an existing CLAUDE.md claim).
