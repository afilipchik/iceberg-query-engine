# Task: Q16 — anti-join parallel-probe investigation + fix

## Description

Q16 (`SELECT p_brand,p_type,p_size,COUNT(DISTINCT ps_suppkey) FROM
partsupp,part WHERE ... AND ps_suppkey NOT IN (SELECT s_suppkey FROM
supplier WHERE s_comment LIKE '%Customer%Complaints%') GROUP BY ...`) has
two joins: an anti-join (the `NOT IN` subquery) and an inner join
(`p_partkey = ps_partkey`). Measured this session (clean run,
`HJ_PROF=1`): the anti-join probes all **8,000,000 partsupp rows as a
single `partition 0` unit (49.2ms)**, plus its build phase (42.1ms) —
**91.3ms combined, ~52% of Q16's ~175.5ms total** — while the second join
in the *same query* probes in parallel across 32 partitions in 6.2ms.
`JoinType::Anti` does not match whatever gate restricts batch-parallel
probing to `Inner`/`Left` (`src/physical/operators/hash_join.rs`, near
lines 2540-2545), so it and its build run effectively single-threaded on
a 32-logical-CPU box.

This is a parallelism gap, not an algorithmic one — the existing
sequential per-partition probe logic doesn't need to change, only whether
it runs on 1 partition or N.

## Outcome (2026-08-23)

**Oversight, not a correctness choice** — confirmed, not assumed. Three
independent findings: (1) `output_partitions()`'s hard-coded `1` for
Semi/Anti governs a different axis (async scheduling) than this gate
(how an already-fully-collected `probe_batches` slice is scanned inside
one call); (2) the existing `build_matched_atomic` state was already
atomic/relaxed/monotonic and explicitly commented "to enable parallel
probe"; (3) the sibling function `probe_semi_anti_parallel` has been
batch-parallel this exact way, for the harder (filtered) case, since it
was written — direct shipped precedent that this pattern is safe. The
"minimal safe fix" fallback the task scoped for an unsafe-as-is finding
was not needed.

Implemented exactly as the "if safe" branch describes:
`MIN_BATCHES_FOR_PARALLEL`'s gate widened to include `Semi | Anti`, reusing the
existing per-batch probe logic (extracted into one shared closure,
`probe_one_semi_anti_batch`, used by both the new parallel branch and
the pre-existing sequential fallback — not two implementations that can
drift). Added `QE_SEMI_ANTI_PARALLEL=0` as a same-binary A/B toggle,
matching this codebase's existing `QE_JOIN_PRUNE`/`QE_MORSEL` convention.

**Measured, not promised — and this one is a real win**, unlike task
003's negligible result on the same branch. Controlled, same-binary,
order-swapped A/B, 12 iterations per arm: Q16's anti-join probe
(8,000,000 rows) **41.5ms -> 6.2ms (6.7x)**; **Q16 total wall time
151.7ms -> 120.0ms, ~21% faster** (~31.7ms/query recovered). One
correction to this task's own original phase table: the recorded
"partsupp build 42.1ms" belongs to Q16's OTHER (Inner) join, not the
anti-join, whose own build side (filtered `supplier`) measures in
microseconds — so the original ~55.5%-of-Q16 framing bundled a cost this
fix was never going to touch; ~21% total-query recovery is the real,
verified number.

Also checked (and measured, not just noted) the task's "other queries"
ask: **Q22** (`NOT EXISTS`, unfiltered, same VHT-served shape as Q16) is
a confirmed secondary beneficiary — anti-probe 33.1ms -> 6.3ms (5.3x),
query total 198.2ms -> 162.4ms (~18% faster). **Q21**'s two EXISTS/NOT
EXISTS joins carry an extra ON-clause filter each, which was already
routing them to the always-parallel `probe_semi_anti_parallel` fallback
before this task existed — confirmed via per-row timing, not affected
either way.

NOT IN NULL-handling: investigated and confirmed unaffected. This engine
does not implement SQL's full three-valued `NOT IN` semantics (a NULL
build key is simply never inserted into the hash table, rather than
poisoning the whole result) — a pre-existing characteristic, upstream of
and untouched by this change, confirmed via code reading and two new
regression tests that run the same NULL-bearing scenario through both
the old sequential path and the new parallel path and assert identical
output. Fixing that gap is out of scope (needs new build-side tracking,
not a scheduling change); TPC-H's own `s_suppkey` is non-null so it never
manifests in the benchmark suite, confirmed by 22/22 CELL-EXACT at SF=10.

Full suite: 995 passed, 0 failed, 1 ignored (default build);
`tests/duckdb_validated.rs` 177/177; `cargo fmt --all -- --check` clean.
One real mistake made and caught during this task's own development is
recorded honestly in `updates/004/stream-A.md`: an early version of one
new regression test had its `left`/`right` roles backward relative to
`probe`/`build` for the `!swapped` case, which both silently failed to
exercise the new code path as intended AND carried a wrong hand-derived
expected value — caught by the very test suite this task added, fixed,
and turned into a doc comment on the shared test helper so the mistake
is harder to repeat. Full detail in `.claude/epics/duckdb-parity-2/
updates/004/stream-A.md`.
