# Task: Dense group-id remapping, Stage 0 + Stage 1

## Description

Since 2026-08-20 the performance program has repeatedly named "dense
group-id remapping" as its one unexecuted future item — the last
HashMap-fallback aggregation residue (`perf-marathon` epic close-out).
This epic's investigation produced a full staged design (Stages 0-4,
reconciled against a 67-finding competitive research sweep,
`.claude/plans/research/wave2-olap-engines.json`) and — critically —
found the codebase has **four** aggregation code paths, not the one or
two the prior research assumed: a shared core
(`morsel_agg.rs::AggregationState`, three tiers: perfect-hash, raw
single-column, true HashMap fallback) plus a **separate, more-boxed**
implementation in `hash_agg.rs` that anything with `DISTINCT` or a
handful of other functions routes to entirely, bypassing the shared
core's optimizations. This task is Stages 0 and 1 only — the kill-switch
microbenchmark and the single-int/date-column general-function flat
accumulator. Stages 2-4 are explicitly out of scope for this epic (see
the PRD's Out of Scope section and the design's own Stage 4
recommendation to spin it out as a follow-up epic).

**Scope depends on task 002's outcome.** Task 002 measures whether
extending the disjoint-aggregation threshold closes most of Q13's
aggregation-side cost. If it does, Q13 should NOT be this task's target
(redundant investment) — Stage 1 should instead target Q20 (already named
via `perf-marathon` IDEAS.md idea #6 as a "44.6M-group SPARSE aggregate,"
though its exact cost split is INCONCLUSIVE per this epic's own
floor-cluster re-check: ~55-60% of Q20's wall time evaded the available
profiling instrumentation, most likely the aggregation phase itself not
routing through an `AGG_TIMING`-instrumented path for Q20's specific
Semi/Left-join-dominated plan). Q10 is a candidate only if `PLAN_DEBUG=1`
confirms its 7-column GROUP BY still reaches the aggregate operator
un-collapsed — plausible it already reduces to a single `c_custkey`
column via the existing `GroupKeyReduction` optimizer rule before this
task would even apply, in which case Q10 needs no new work either.

## Outcome (2026-08-23)

**Stage 0 kill-switch: CLEARS** (24.5%-44.5% wall-time win, 10/10 points
across the 1M-50M-group x dense/sparse sweep, 1-aggregate shape).
**Neither Q10 nor Q20 has a confirmed target for Stage 1** — both already
bypass the `raw_groups` boxed tier Stage 1 would replace, via the
pre-existing, even-leaner `raw_sums` bare-`(u64,f64)` tier (Q10:
`SUM(l_extendedprice*(1-l_discount))` over `GroupKeyReduction`-collapsed
`c_custkey`; Q20: `SUM(l_quantity)` over an `EagerAggregation`-style
packed `__pk` key). **Stage 1 does not proceed** — a complete, evidenced
"no work needed" outcome, exactly as this task's own rules anticipated as
a valid possibility ("don't force Stage 1 implementation against a query
that doesn't need it").

Separately, task 002's SF=100 out-of-scope finding (`finalize_disjoint_
states` paying real shard/rehash cost to "merge" a single, already-
disjoint, oversized worker state with nothing) was judged in-scope here
(file `morsel_agg.rs`, well-evidenced, low-risk, directly informed by
this task's own investigation) and fixed: a `states.len() == 1` fast path
in `merge_states_to_batches_filtered` that goes straight to
`demote_raw_sums()` + `build_output`, skipping the shard-then-rehash
machinery built for combining *multiple* overlapping states. Measured
SF=100 (Q13, `data/tpch-100gb`, 3 iterations): merge step ~205ms/iter
(task 002's baseline) -> **~168ms/iter avg** (153.5-175.3ms), with the
`[raw-merge]` diagnostic print that marks the old wasteful path now
absent entirely (the same signal task 002 used to confirm its own fix).
Cell-exact at SF=100 (`scripts/sf100_engine_validate.py --query=13`):
MATCH. Full-suite and cell-exact test results below.

**Expected-vs-actual payoff, reconciled against wave2**: wave2's B3
(HashMap-fallback aggregation) findings estimated "1.5-2x on Q10/Q13/
Q16/Q22 aggregation phases" against a baseline where Q10 was 894ms and
"agg is the dominant non-scan cost." Actual, current-codebase numbers:
Q10 now runs ~200ms total with aggregation at ~0.3-0.7% of that (not
dominant at all) — the gap between wave2's baseline and today is almost
entirely explained by intervening, independently-shipped optimizations
(`GroupKeyReduction`, the `raw_sums` fast tier, `EagerAggregation`'s
packed keys, morsel parallelism), none of which is the generalized
FlatAgg/dense-group-id mechanism wave2 was estimating against. Q20 was
never actually a wave2 B3 finding at all (it appears only under B2,
join/gather, in all ~13 of its mentions) — the "Q20 needs dense-group-id"
hypothesis traces to `perf-marathon` IDEAS.md idea #6 alone, itself
hedged ("No single lever"). **Payoff on any currently-confirmed query:
~0%** — not because the lever is bad (Stage 0 proves a real 25-44% win
exists in isolation for 1-aggregate shapes, the exact shape both
candidates have) but because cheaper, already-shipped, more targeted
fixes already captured the value for every query this program tracks.
This is a complete, honest close-out of the "dense group-id remapping"
epic item this program has repeatedly flagged as unexecuted since
2026-08-20: it is now *investigated and staged* (this task's design +
Stage 0 evidence), and *correctly deferred* rather than spent on a query
that does not need it. A future epic should re-open Stage 1 only against
a freshly-confirmed query, and should note the aggregate-count nuance
found here (win concentrates at 1 aggregate, reverses by 3) when scoping
it.
