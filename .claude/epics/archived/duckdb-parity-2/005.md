# Task: Q16 — distinct_set hasher swap

## Description

`AccumulatorState::distinct_set: Option<std::collections::HashSet
<GroupValue>>` (`src/physical/operators/hash_agg.rs:315`) is the **only**
hash-based collection in either aggregation file
(`hash_agg.rs`/`morsel_agg.rs`) using `std::collections::HashSet`
(SipHash, deliberately DoS-resistant and slow) instead of `hashbrown`.
Every `HashMap` in both files already gets `hashbrown`'s faster default
hasher for free (`use hashbrown::HashMap;` at the top of each file) — this
is a pre-existing inconsistency, confirmed via code reading during this
epic's investigation, not a symptom of any larger architectural issue.

Measured this session (temporary instrumentation, reverted): the
`CountDistinct` insert path executes ~1.3M times on Q16's SF=10 data
(matching the real join-output cardinality: 330K surviving part rows × 4
partsupp-per-part). The mechanism is real, but **it is not Q16's
dominant cost** — the anti-join parallelism gap (task 004, 55.5% of wall
time) exceeds the entire aggregation bucket (44.5%), and within that
bucket the true wall-clock share of the hasher itself is likely a
minority of the 78ms aggregation phase (the raw insert/merge counters are
inflated by `Instant::now()` measurement overhead comparable to
SipHash-on-i64's native cost). Land this fix on its own merits (it's
free, zero-risk, zero-new-dependency) — don't expect it to move Q16's
ratio dramatically on its own.
