# Task: Extend leaf-resolution/linking for multi-join chaining

## Description

`src/physical/planner.rs`'s runtime-filter wiring (~lines 1517-1590)
resolves a probe-side leaf by unwrapping only `Project` nodes, keyed by
raw leaf pointer in `streaming_scans`. Once a leaf is consumed into one
`HashJoinExec`, a later, independently eligible Inner join touching the
same logical table gets `probe_leaf=SpillableHashJoin`/`Filter` and no
link at all — confirmed live on Q7 (SF=100) and Q9 (SF=10/100) via
`RT_DEBUG=1`. Fix this.

Read `.claude/prds/runtime-filter-chaining.md` and this epic's
`epic.md` in full before starting — the research trail (exact file:line
references, the live `RT_DEBUG` traces) is summarized there; re-read the
actual current code yourself rather than trusting the summary for
anything you're about to change.

### Design decision: BOTH transitive resolution and multi-slot storage
— neither alone was sufficient, and this is documented as a finding,
not assumed going in

Reading `src/physical/planner.rs`'s `LogicalPlan::Join` arm
(`~1538-1749` after this change) plus `src/physical/operators/
streaming_parquet_scan.rs`'s `RuntimeFilterConfig`/`SharedRuntimeFilter`
showed the two options named in the epic are not actually independent
alternatives for this codebase:

- **Multi-slot alone doesn't help**, because the SECOND join's own
  `right` child, after the existing Project-unwrap loop, resolves to a
  `SpillableHashJoin`/`Filter` operator — never the raw
  `StreamingParquetScanExec` — so there is nothing to attach a second
  slot TO without first finding a path down to the original scan.
- **Transitive resolution by walking DOWN into an ancestor join's own
  `children()` is unsafe**, because `HashJoinExec`/`SpillableHashJoinExec`
  expose no public `join_type`/`build_right` getters, so a generic walk
  into `children()[1]` cannot verify "physical right == probe side" for
  an arbitrary already-built join before descending into it — a Left/
  Right/Full join walked the wrong way would resolve to a BUILD-side
  scan and publish a filter keyed on the wrong table's column values
  (a silent correctness bug, not just a missed optimization).
- **A leaf touched by two-plus joins on genuinely DIFFERENT probe
  columns** (confirmed live: Q7's lineitem leaf is touched via both
  `l_suppkey` and `l_orderkey`; Q9 SF=100's via `l_partkey`, `l_suppkey`
  AND `l_orderkey`) needs somewhere to hold more than one populated
  `(idx, SharedRuntimeFilter)` pair regardless of how the leaf is found.

**Implemented shape**: `RuntimeFilterConfig`'s inner type changed from
`Option<(usize, SharedRuntimeFilter)>` to `Vec<(usize, SharedRuntimeFilter)>`
(multi-slot), and `PhysicalPlanner`'s existing `streaming_scans` registry
(previously populated only at raw-scan-construction time) is now ALSO
populated by the `Join` arm itself: whenever a join successfully links to
a probe-side scan (directly, or by finding a PRIOR join's own
registration), it re-inserts the SAME `(RuntimeFilterConfig, SchemaRef)`
pair keyed by ITS OWN resulting physical operator's pointer, right before
returning. A later join up the tree resolves through the pre-existing
Project-unwrap-only lookup — no new unwrap logic, no `children()`
traversal, no downcasting — because by the time it looks, the operator it
sees IS already a registered key. This only ever forwards a registration
a join ITSELF already proved safe (by successfully linking, which only
happens through the pre-existing `rt_eligible`/`build_prefers_left`
gates), so it can never walk into an unverified build side. Zero changes
needed to `hash_join.rs`/`spillable.rs`: each join still owns exactly one
`SharedRuntimeFilter` cell and publishes into it exactly as before; only
the SCAN-side config and the planner's registration/lookup changed.

Sole files touched: `src/physical/planner.rs` (leaf-resolution/
registration) and `src/physical/operators/streaming_parquet_scan.rs`
(multi-slot `RuntimeFilterConfig`, both consumption sites — the parquet
decoder `RowFilter` and the IPC-sidecar post-load path — now apply every
populated slot: `RowFilter`'s own multi-predicate semantics AND them
together automatically; the IPC path folds them as sequential passes).
`src/physical/operators/hash_join.rs` was read in full per the task's
own requirement but needed NO changes.

The `o_orderkey` join (previously blocked) now links onto the SAME
lineitem scan's config that `l_suppkey` already occupied
(`slots_now=1 -> 2`) — the exact grounding example from the PRD.

Q9, SF=100, before: only `l_partkey` links (`s_suppkey`, `l_suppkey`,
`o_orderkey` all blocked as `probe_leaf=SpillableHashJoin`). After:
```
[rt] linked col 3 (s_nationkey) slots_now=1
[rt] linked col 1 (l_partkey) slots_now=1
[rt] linked col 2 (l_suppkey) slots_now=2
[rt] linked col 0 (l_orderkey) slots_now=3
```
Three chained links on the lineitem leaf, up from one.

Q9, SF=10: **identical before and after** — `l_partkey` links, `l_suppkey`
and `l_orderkey` still show `no link: probe_leaf=SpillableHashJoin`. Root
cause, confirmed via `PLAN_DEBUG=1` (not assumed): at SF=10 the optimizer
places the partsupp `EagerAggregation` join — whose ON key is a COMPUTED
packed expression (`(CAST(l_suppkey) * N) + CAST(l_partkey)`), not a
plain `Expr::Column` — in the MIDDLE of the join chain, between the
`l_partkey` link and the `l_suppkey`/`l_orderkey` joins above it. A
packed-key join is (correctly, unchanged) never itself linkable, so it
breaks the chain at that point regardless of this task's fix — this is
the PRD's own explicitly out-of-scope "composite/packed key eligibility"
gate, not a leaf-resolution gap. At SF=100 the optimizer instead places
that SAME packed-key join at the very TOP of the tree (confirmed via the
same `PLAN_DEBUG=1` comparison), so all three plain-column joins sit
below it and chain successfully. This is a genuine, honestly-reported
finding: the task's own premise ("confirmed live on Q9 SF=10/100") was
only half-right on closer inspection — SF=100 was blocked by the
leaf-resolution gap this task fixes, SF=10 is blocked by a DIFFERENT,
already out-of-scope gate that no leaf-resolution change can address.

Q19 (SF=10) and Q21 (SF=10) traces are **byte-for-byte identical**
before/after (verified via the same stashed-binary A/B, not assumed from
