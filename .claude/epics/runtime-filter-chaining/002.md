## Outcome (closed 2026-08-28)

### Headline: the fix is correct (task 001's RT_DEBUG evidence holds),
but the honest wall-clock verdict is "no measurable net win on Q7
SF=100" — flat to a small, consistent regression on the direct
before/after, and a small-but-noisy net positive on the RT_DISABLE
isolation. This is smaller than the PRD's own ~150-200ms/11-13%
grounding estimate (which was for the ORIGINAL single filter, pre-this-
epic) by a wide margin, and is reported exactly as found, per this
task's own explicit instruction to do so even when the result
disappoints the premise. Cell-exact correctness and full-suite health
are unambiguously clean — nothing here is a correctness problem.

### Methodology

Two binaries built via `scripts/claude-safe-build.sh cargo build
--release`: `qe_before` = commit `dec6227` (pre-task-001, in a separate
`git worktree`), `qe_after` = current HEAD `a9e01d9` (post-task-001,
this epic's own chaining fix). Both binaries' `RT_DEBUG=1` traces on Q7
SF=100 were re-confirmed identical to task 001's own recorded evidence
before any timing was taken (before: `o_orderkey` blocked
`probe_leaf=SpillableHashJoin`; after: `o_orderkey` links,
`slots_now=2`) — the fix itself is not in question, only its wall-clock
value.

**This machine was under heavy, variable concurrent load for this
entire measurement session** (`uptime` showed load average 16-17 on a
32-core box partway through, `ps aux` showed multiple concurrent
`kube-apiserver`/`trino`/other-agent Claude sessions/builds running
throughout — this is a shared, multi-tenant development box, and per
this session's own system reminder, many other agents were concurrently
active). Per-pair timing noise (±50-100ms on a ~1500ms query) was
comparable in magnitude to the effect being measured, so — matching
this codebase's own established discipline for noisy machines
(`CLAUDE.md`'s GPU section: "interleaved A/B, 5 alternating pairs,
medians") — every comparison below uses INTERLEAVED single-shot A/B
(alternating binaries every ~1.5s, not sequential multi-iteration
blocks) as the primary read, with block-run comparisons reported too,
specifically because they showed a CONFLICTING sign — that conflict is
itself the most important honest finding of this task.

### Q7 SF=100 before/after (the direct chaining-fix A/B), 10 interleaved pairs

`scripts/claude-safe-build.sh <binary> benchmark-parquet --path
data/tpch-100gb --query 7 --iterations 1`, before/after alternated:

| | before (ms) | after (ms) |
|---|---|---|
| avg (n=10) | 1517.68 | 1545.05 |
| min | 1437.43 | 1503.11 |

**After is slower in all 10/10 pairs**, avg +27.4ms (+1.8%), a small
but directionally consistent regression — not the improvement the
grounding example anticipated. Plausible (not proven) explanation: the
second linked filter (`o_orderkey`) adds its own bitmap-probe cost to
every scanned `lineitem` row, and for this query/data shape that cost is
not clearly recovered by additional pruning once the first filter
(`l_suppkey`, nation-restricted) has already eliminated most
non-matching rows — i.e. the second filter's own marginal selectivity on
top of the first may be small. This was not root-caused further
(instrumenting per-filter selectivity was judged out of this task's own
S-size scope); named as a candidate follow-up, not asserted as fact.

### `RT_DISABLE=1` A/B on Q7 SF=100 (isolates the WHOLE mechanism, both filters, vs. none)

**Interleaved single-shot, n=20 pairs** (primary read, matching this
program's own noise discipline):

| | RT on (both filters, ms) | RT off (`RT_DISABLE=1`, ms) |
|---|---|---|
| avg | 1534.69 | 1569.71 |
| median diff (off−on) | — | **+40.9ms (+2.7%) favoring RT on** |
| mean diff (off−on) | — | +35.0ms (+2.3%) favoring RT on |
| pairs favoring RT on | 15/20 (75%) | — |

**Two separate 8-iteration same-process block runs (order swapped
between them) showed the OPPOSITE sign and larger magnitude**: RT off
averaged ~75-85ms (~5%) FASTER than RT on in both blocks. This directly
contradicts the interleaved-pairs verdict above. Both measurement
methods were re-verified mechanically sound — `RT_DEBUG=1 RT_DISABLE=1`
was independently confirmed to actually propagate through
`claude-safe-build.sh`'s `systemd-run --scope` wrapper (all links show
`no link` with `RT_DISABLE=1`, all five link with it unset) — so this is
not an instrumentation bug, it is genuine measurement noise on a loaded
shared machine exceeding the true effect size. **Honest verdict: the
combined runtime-filter mechanism's net wall-clock contribution to Q7
SF=100 today is SMALL (low single-digit percent at most) and its SIGN
could not be pinned down with confidence at the noise level available
this session** — a materially different, more modest picture than the
PRD's ~150-200ms/11-13% figure, which was for the original ONE filter,
measured on a presumably quieter machine at a different time. This is
reported as-is per this task's own explicit instruction, not
smoothed over.
