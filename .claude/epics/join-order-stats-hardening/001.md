# Task: Missing/degenerate join-key statistics visibility

## Description

`JoinReorder`'s DPsize cost model (`src/optimizer/rules/
join_reorder.rs`) computes join selectivity from per-column NDV
estimates. When a relation's join-key column has no recorded
statistics (confirmed real, shipped path: `ExecutionContext::
register_table`/`MemoryTable` carries a real row count but an empty
`column_stats` map), the cost model falls back to a near-arbitrary
default (`base_rows[rel].max(10.0)`-style, per the go/no-go
investigation's own finding) with zero signal to anyone. The
investigation's repro turned this into a >60,000x cardinality
misestimate and a query that never completes. This task makes that
condition visible.

Read `CLAUDE.md`'s "Adaptive join-order re-optimization: investigated,
NOT pursued yet" section and `examples/adaptive_reopt_ndv_repro.rs` in
full before starting — this is the load-bearing investigation, don't
re-derive it.

## Acceptance Criteria

- [ ] Read `src/optimizer/rules/join_reorder.rs`'s `estimate_base_rows`,
      `column_ndv`, and the DP cost computation in full. Identify
      exactly where/how a missing or degenerate NDV currently falls
      back silently.
- [ ] Add tracing (this codebase's `tracing` crate usage elsewhere is
      the convention to match) that fires when a relation feeding a
      join edge has no usable column statistics for its join key — name
      the relation and column explicitly. This must fire in NORMAL
      operation, not gated behind a debug-only env var like
      `DP_DEBUG` — the whole point is diagnosing a hang someone didn't
      know to look for, so a `tracing::warn!` (or equivalent) that
      shows up in ordinary logs is the right level, not print-only
      debug output.
- [ ] Decide and document what counts as "degenerate" beyond "entirely
      missing" (e.g. a zero or negative NDV, a range that collapses to
      a single value for a column that clearly has more distinct
      values than that) — your own investigation of the actual fallback
      logic should inform this, not a guess.
- [ ] No regression to the DP cost model's behavior on real, valid
      statistics — this is a visibility addition, not a cost-model
      change. Confirm via existing join-order/cost tests staying green.
- [ ] The mechanism you build here (however you implement "this
      relation's stats are missing/degenerate, signal it") should be
      reusable by task 002 — design it as something task 002 can call
      or extend, not something scoped narrowly to just this one call
      site if a shared version is easy to provide.
- [ ] Full suite green (`scripts/claude-safe-build.sh cargo test`, all
      feature combinations); `cargo fmt --all -- --check` clean.
