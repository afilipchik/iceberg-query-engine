# Task: Native-table statistics staleness after mutation

## Description

Native table `ColumnStats` (`src/storage/native_manifest.rs`) has no
stored NDV — it's derived at query time from `min_i64`/`max_i64` and a
row count (per the module's own doc comment: "`ndv_est` DERIVED at that
point from `min_i64`/`max_i64`/`row_count` exactly the way
`ParquetTable`/`LanceTable` already derive it"). Per-segment `min_i64`/
`max_i64` are computed once at write time and never adjusted by
DELETE/UPDATE — only row counts (via deletion vectors) change. This
task investigates whether the derivation uses a row count that goes
stale after mutation, and if so, in which direction, and fixes it.

Read task 001's Outcome section first — reuse its visibility mechanism
rather than building a second one.

## Acceptance Criteria

- [ ] Read `src/storage/native_manifest.rs` in full, specifically
      wherever NDV is actually derived at query time (find the exact
      function — likely in `TableProvider::statistics()` or wherever
      `ColumnStats` gets turned into the optimizer-facing
      `TableStatistics`/NDV shape). Confirm precisely: does the
      derivation use the segment's PHYSICAL row count (write-time,
      unaffected by deletion) or LIVE row count (`live_row_count()`,
      post-deletion)? This determines whether staleness is even real —
      verify, don't assume the investigation's own hypothesis is
      correct without checking.
- [ ] If staleness is confirmed real: design a fix. Two acceptable
      shapes, your call which fits best once you've seen the actual
      code — (a) make the NDV derivation use live, not physical, row
      count (cheap, already-available data, no rescan) if that alone
      meaningfully improves accuracy; (b) if min_i64/max_i64 themselves
      could be stale in a way live-row-count-adjustment doesn't fix
      (e.g. the true min/max value was among the deleted rows), route
      the derived estimate through task 001's degraded-statistics
      signal once a table's deletion fraction crosses a reasoned
      threshold, rather than pretending the number is still accurate.
- [ ] No full rescan on any mutation — this must stay a cheap,
      incremental, or honestly-degraded fix, not a correctness-by-
      recomputation approach that reintroduces mutation cost.
- [ ] Real test: mutate a native table (DELETE a meaningful fraction of
      rows concentrated in a way that would shift true NDV) and confirm
      the fix behaves correctly — either the derived NDV now reflects
      reality, or the degraded-statistics signal fires and the query
      planner treats it accordingly (falls back safely, per task 001's
      own mechanism).
- [ ] No regression to native-table mutation's own measured performance
      characteristics (check the mutation epic's own recorded numbers —
      `CLAUDE.md`'s Native Tables mutation sections — and confirm this
      fix doesn't reintroduce cost there).
- [ ] Full suite green; `cargo fmt --all -- --check` clean.

## Technical Details

Primary files: `src/storage/native_manifest.rs`. May also touch
`native_delete.rs`/`native_update.rs` if the fix needs to compute
anything at mutation time rather than purely at query time — prefer
query-time-only if it achieves the same result, since that's cheaper
and touches less mutation-path code.
