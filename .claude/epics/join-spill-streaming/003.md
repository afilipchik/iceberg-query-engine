# Task: Parallel spilled-partition processing under the shared budget

## Description

Process up to K spilled partitions concurrently (blocking work on
`spawn_blocking`/rayon; K = min(available_parallelism, a cap, number
of spilled partitions), chunk table budget = threshold / K so the total
transient table memory is unchanged) and yield each partition's batches
as it finishes. Within a partition, probe the chunk's table over probe
batches in parallel (rayon `par_iter` over probe batches, results
concatenated) for INNER; SEMI/ANTI bitmaps merge with OR / per-batch
ownership. Trace: K, per-partition elapsed. Target: Q9 SF=100 parquet
@1G ≤ 300s cell-exact (from ~1,400s).

### What shipped (`src/physical/operators/spillable.rs`)
- **Phase B, K-way** (`plan_phase_b`, `process_spilled_partitions`):
  K = min(available_parallelism, 8, spilled) further clamped by
  threshold / predicted table of the LARGEST spilled partition (a
  partition that out-sizes the budget is read back in K× more chunks at
  budget/K and every chunk re-probes the whole probe partition — K jobs
  do K× the lookups in the same wall time, so the budget is not split
  there); `SpillableHashJoinExec::with_spill_join_parallelism(Some(k))`
  then `QE_SPILL_JOIN_PARALLELISM` override (clamped to the spilled
  count). Chunk table budget = threshold / K — the K jobs share ONE
  threshold. Jobs on a `JoinSet` of `spawn_blocking`s, ≤ K in flight,
  every job's batches sent as produced; first error surfaces after the
  in-flight jobs drain.
- **Streaming read-back** (`process_spilled_partition`,
  `open_spill_reader`): build file streamed chunk by chunk (whole
  8,192-row batches while predicted table + batch bytes ≤ chunk
  budget), probe file re-opened per chunk and probed in 16-batch groups
  rayon-parallel — INNER per-batch `probe_partition`; probe-side
  SEMI/ANTI per-batch bitmaps (by file position, identical across
  re-reads) OR'd across chunks with a final emission pass; build-side
  SEMI/ANTI per-chunk `AtomicBool` bitmap (`mark_build_matches_atomic`),
  per-chunk emission. A job's footprint is one chunk + one probe group
  + bitmaps + the batch in flight — never a partition file (this is what
  closed the harness's build_right=0 1G legs that 002 alone missed).
  Hash-check lines unchanged; per-partition trace `done: build_rows=..
  chunks=.. probe_rows=.. elapsed=..`; phase-B trace with K/hw/budget.
- **Phase A, parallel and budget-sized** (`probe_with_spilling`,
  `phase_a_process_group`, `PhaseAState`): probe batches gathered into
  ~262k-row groups, each on the blocking pool: concat, per-row partition
  ids over 8,192-row ranges (new `partition_row_ids`, the single routing
  definition `partition_batch_by_hash` now wraps), then one ~4k-row
  gather per partition, probed / spilled / ANTI-emitted on the same
  thread — on a rayon pool of `memory_threshold / 64MB` threads clamped
  to [1, 8] (Q9 @1G: 8; 256MB budget: 3; 64M: 1), created per call and
  dropped before phase B. Outputs sent per group. Trace: `probe
  collected ... phase_a_threads=N`.
- `SpilledPartition::build_rows` exact across appends (was frozen at the
  eviction-time count; diagnostic-only before, `plan_phase_b` sizes K
  from it now).
- Test `spilled_partitions_processed_in_parallel_are_cell_exact`: K
  forced to 3 and 8 over INNER (both orientations + sparse), SEMI/ANTI
  both orientations × dense/sparse — rows identical to the in-memory
  delegate and equal to the naive ground truth (22 fixture runs).

### Things learned the hard way (recorded so 004 does not re-learn them)
- After 002, the second Q9 join's read-back ran at ~1.7 of 32 cores: its
  consumer — the first join's phase A — hashed 333M probe rows on one
  thread. Parallel phase B alone (003) gave 607s; parallel phase A is
  what reached ~225s.
- Rayon parallelism on the global pool costs ~12MB of RSS per thread
  that touches a group's short-lived allocations (mimalloc retention),
  which is why phase A's pool is sized by the operator's budget.
- Two harness legs (003b anti build_right=0) were memcg-killed at 1G and
  one (003d) passed by 30MB before the pool was sized by budget; the
  numbers in the table are from the final binary only.
