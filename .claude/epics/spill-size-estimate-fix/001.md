# Task: Fix estimate_batch_size + validate against Q12 and a real stress case

## Description

`estimate_batch_size` (`src/physical/operators/spillable.rs`) reports
Dictionary-typed columns' size via Arrow's `get_array_memory_size()`,
which returns the size of the ENTIRE underlying mmap buffer a column's
`Buffer` points into — not the column's actual logical content. Native
table segments are read as one large mmap'd Buffer per segment file
(`ipc_cache.rs`'s `Buffer::from_custom_allocation`), so a Dictionary
column drags the whole segment's on-disk size along as its "size,"
roughly 3x over. Measured on Q12: real build side ~42MB, estimator
reports ~167.7GB. Fix it.

Read the diagnostic investigation already performed this session
(`examples/spill_size_estimate_check.rs`, and this conversation's own
record of the finding) before starting — don't re-derive the root
cause, it's already precisely located.

## Outcome (2026-08-29, partial — see below)

**`estimate_batch_size`'s own fix (Dictionary-column + generalized
fallback via `ArrayData::get_slice_memory_size()`) is DONE and
validated**: regression test `dictionary_column_estimate_is_content_aware_
not_mmap_capacity` passes; all 15 `spillable::` unit tests and all 7
`spill_tests.rs` integration tests pass; no regression.

**The stress-case acceptance criterion is NOT met, and this task should
NOT be closed yet.** Constructing the required "real oversized-build-side
stress case" (`examples/spill_dictionary_oversized_build_repro.rs` +
`examples/_control_int32_repro.rs`, both modeled on `spill_join_oom_repro.
rs`) surfaced a real, SEPARATE, more severe bug — not a spill-suppression
failure (the estimate fix does NOT under-count; both repros correctly
enter the spill path), but a genuine memory-accounting hole in
`build_with_partitioning`/`append_batch_streaming` confirmed via real
`systemd-run -p MemoryMax=...` caps:

- `examples/_control_int32_repro.rs` (PLAIN Int32 build side, no
  Dictionary column — rules out any connection to this task's own fix):
  500MB configured `memory_limit`, genuinely OOM-killed by the kernel at
  ~3.1GB RSS under a 3G cap (`journalctl -k`:
  "Memory cgroup out of memory: Killed process ... (_control_int32_)").
- `examples/spill_dictionary_oversized_build_repro.rs`: 30MB limit,
  survived under a 900M cap but peaked at ~738MB RSS — ~24x its budget.

Root-caused ONE real, confirmed, fixed contributor: `append_batch_
streaming`'s spill writers relied on `parquet`'s default row-COUNT-based
row-group flush (1,048,576 rows) — for 64 hash partitions, most spilled
partitions never individually reach that count before the phase ends, so
their data stays fully memory-resident in the writer's own internal
buffer, invisible to `total_memory`'s accounting. **Fixed** (see
`append_batch_streaming`'s own doc comment in `spillable.rs` for the full
story, including a REJECTED first attempt): added both
`set_max_row_group_bytes` (1MB, a secondary net for wide rows) AND
`set_max_row_group_row_count` (8,192, matching this file's own `CHUNK_
ROWS` precedent — the BINDING limit, since the byte-based cap alone
measured as a no-op: `parquet`'s own doc says it flushes against
ESTIMATED ENCODED size, and both repros use deliberately low-cardinality/
repetitive keys whose compressed footprint stays tiny regardless of raw
rows buffered — the identical "estimate vs. real content" failure class
this whole epic exists to fix, just inside the Parquet writer instead of
Arrow's own `get_array_memory_size()`).

**Honest result: this fix did NOT measurably change either repro's peak
RSS** (dictionary case: 723→740→737MB across three runs, within noise;
control case: still genuinely OOM-killed at the same ~3G cap, unchanged).
Confirmed via `MIMALLOC_SHOW_STATS=1` that the ~738MB peak is a REAL,
touched/committed peak (1.8GB cumulative purged over the run — mimalloc
IS actively returning memory, ruling out "stale allocator retention,
not a real leak" as an explanation). No regression from the fix (all
existing tests still pass) — but the row-group-flush theory, while a
real and worth-keeping fix in its own right, is **NOT the dominant
driver** of this test's overshoot. The true dominant driver is still
UNKNOWN. Ruled out so far: `evict_build_partition_to_disk` (reads
cleanly, no obvious extra retention); `partition_batch_by_hash` (a
standard `compute::take`-per-partition pattern, nothing pathological on
inspection); mimalloc allocator retention (stats show active purging).

**Recommendation, not attempted further this session**: real memory
profiling (`heaptrack`/`valgrind --tool=massif`) against
`spill_dictionary_oversized_build_repro`, rather than continued
hypothesis-and-rebuild cycles — this matches the "no-guess-fixes"
discipline already established for this exact code area (the still-open
`spill-join-correctness` duplicate-counting bug). This should become the
`oom-safety-hardening` epic's own first, highest-priority task, not a
same-session patch: the two adversarial repros above are ready-made,
committed reproductions for whoever picks it up.

**Practical framing, so this isn't read as more alarming than warranted**:
both repros use a DELIBERATELY extreme ratio (30-500MB budget vs. a
~670MB build side — the process is asked to hold working memory at
5-75% of one dataset's own uncompressed size). Real production
`--memory-limit` values are GB-to-tens-of-GB against real build sides
in the tens of MB (Q12's real build side is ~42MB) — a ~700MB absolute
overshoot at this test's extreme ratio would be a rounding error at
realistic scale. This does NOT mean the underlying issue is safe to
ignore (a genuinely large production build side at a genuinely tight
production memory-limit could hit the same mechanism), but it does mean
the 2026-08-28 incident's real 107GB peak is not fully explained by this
specific mechanism alone and most likely also involved simply running a
real, large, UNWRAPPED workload directly (see `scripts/claude_hooks/
enforce_safe_build.sh`, already shipped, which now prevents that specific
bypass regardless of this bug's own resolution).
