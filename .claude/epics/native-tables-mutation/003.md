# Task: Deletion vector mechanism + DELETE

## Description

`DELETE FROM <native table> WHERE <predicate>` — the first mutation that
needs genuinely new read-path infrastructure: phase 1's `NativeTable::
scan()` reads every row of every (assigned) segment unconditionally.
This task adds task 001's chosen deletion mechanism (most likely a
deletion vector consulted at read time) and the SQL surface that writes
to it. Shipped together — the mechanism has no independent value without
the SQL surface that exercises it, and testing the mechanism in isolation
from real DELETE statements risks missing exactly the kind of subtle bug
this program has repeatedly found in exactly this kind of area.

## Acceptance Criteria

- [x] Deletion mechanism implemented per task 001's decision — read its
      Outcome section for the exact representation, storage location,
      and atomic-publish approach before starting.
- [x] `NativeTable::scan()`/`scan_with_filter()` consult the deletion
      mechanism and filter matched rows out — correctness-critical, must
      compose correctly with: phase 1's dense-direct-address fast path
      (task 005 of the foundation epic — a deleted row must not be
      double-counted or mis-counted by that path; if the fast path
      cannot cheaply account for pending deletes, it must fall back to
      the generic path for a table with any pending deletions, not
      silently produce a wrong answer for speed), distributed splits
      (`shard_by_splits` — deletions must apply per-shard correctly, not
      just at the whole-table level), and the memory-budget check from
      phase 1's task 006 (a deletion vector itself must be bounded and
      accounted for in that budget, not a new unbounded-growth path).
- [x] `Statement::Delete` handled in `Binder::bind()` — new match arm.
      The `WHERE` predicate must be evaluated against the table's actual
      current data (a filtered scan) to identify matching row positions
      — this is real new binding/execution work, not a small wrapper
      around existing machinery the way CTAS's `AS SELECT` was.
- [x] A new `ExecutionContext` entrypoint (e.g. `delete_from_native_
      table`) following the established `&mut self`, non-`sql()` shape.
- [x] Cell-exact validation: delete from a native table, compare against
      an independently-computed reference. Cover: deleting all rows
      (table becomes logically empty but still exists — subsequent
      queries must return zero rows correctly, not error); deleting zero
      rows (predicate matches nothing — must be a clean no-op, not an
      error); deleting from a table with multiple segments (deletions
      must apply to the correct segment, not silently apply to the wrong
      one or all of them); repeated deletes on overlapping predicates
      (idempotency — deleting an already-deleted row via a second,
      overlapping DELETE must not corrupt the deletion vector or
      double-count).
- [x] `statistics()` reflects post-delete row counts correctly (not the
      pre-delete rollup) — this is a real correctness surface, since
      stale statistics could mislead the query planner (e.g. into a
      wrong join-order decision), not just report a cosmetic wrong
      number.
- [x] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Populated by task 001's decisions — read `001.md`'s Outcome section in
full before starting. Summary of what directly shapes this task:

- **Deletion vector representation and location (Decision 1)**: a new
  `#[serde(default)] deleted_rows: Vec<u32>` field on the EXISTING
  `Segment` struct in `_manifest.json` — sorted, deduplicated LOCAL row
  positions within that segment's own on-disk row ordering. Not
  `roaring`, not a sibling file per segment, not a separate whole-table
  file — inline in the one manifest, matching this format's established
  atomicity/inspectability discipline (full tradeoff analysis in
  001.md's Outcome). `#[serde(default)]` means every manifest phase 1
  already wrote round-trips unchanged (empty `Vec` = no deletions).
- **Row identification — a BESPOKE loop, not the generic query
  pipeline.** The standard `LogicalPlan`/`PhysicalOperator` pipeline
  (what CTAS/INSERT reuse for their source query) has no way to carry a
  matched row's (segment id, local position) back out — `TableProvider::
  scan()` returns only `Vec<RecordBatch>`, no positional metadata. Bind
  the `WHERE` predicate via `Binder::bind_expr` (the SAME method
  `bind_select`'s own WHERE-clause binding already calls — expose a new
  `pub fn bind_delete(&mut self, stmt: &ast::Delete) -> Result<(String,
  Option<Expr>)>` on `Binder` returning the target table name + bound
  predicate), then EVALUATE it directly via `filter::evaluate_expr
  (batch, &predicate)` — the SAME function `FilterExec` uses — inside a
  loop that: opens the target `NativeTable`'s CURRENT manifest, iterates
  `active_segments()` in id order, calls `ipc_cache::read_row_group(dir,
  seg.id, None, None)` per segment (confirmed by reading it: batches
  come back in stable on-disk block order, multiple ~65,536-row batches
  per segment is the NORMAL case since `native_write.rs` already
  reslices before writing — track a running local-row offset across
  batches, reset per segment), and collects positions where the
  predicate's boolean mask is true. `selection: None` (no WHERE) means
  "match every row" — must be supported cleanly (this file's own
  acceptance criteria already name "deleting all rows" as a case to
  cover).
- **Idempotency is structural, not a special case**: union new matched
  positions into the segment's existing `deleted_rows` via a
  `BTreeSet<u32>` (insert + re-serialize as sorted `Vec`) — re-matching
  an already-deleted row is then naturally a no-op, satisfying this
  file's own "repeated deletes on overlapping predicates" acceptance
  criterion with no extra logic.
- **The narrow in-scope compaction exception (Decision 3)**: when a
  segment's `deleted_rows.len() == segment.row_count` after this
  DELETE, drop that `Segment` entirely from the manifest's `segments:
  Vec<Segment>` (its `.arrow` file becomes an inert, unreferenced
  orphan). This bounds the deletion vector's own worst-case size and is
  the concrete, cheap thing task 001 identified as in-scope despite
  deferring full compaction — implement it here, not as a follow-up.
- **`statistics()` row count — read `NativeTable::statistics()`'s
  EXISTING implementation before changing it**: it already computes
  `row_count` itself from `active_segments()` rather than reading
  `manifest.snapshot.row_count` directly. Extend that existing
  computation to `segment.row_count - segment.deleted_rows.len()`,
  summed over active segments — a NEW, separate computation. Do **not**
  touch `Segment.row_count`/`Snapshot.row_count` themselves: they must
  keep meaning the PHYSICAL (write-time) count, unaffected by deletion,
  so `NativeManifest::validate()`'s existing invariant
  (`snapshot.row_count == sum(segments[].row_count)`) is satisfied with
  ZERO changes and `NativeManifest::build()` stays callable unchanged
  after a DELETE (see next bullet).
- **Atomic publish (Decision 4) — same single-file-rename mechanism as
  task 002, and the SAME `NativeManifest::build()` call, unchanged.**
  DELETE never writes new segment DATA at all (no new `.arrow` files) —
  it only edits `Vec<Segment>` in memory (mutating `deleted_rows` on
  affected entries, dropping wholly-tombstoned ones per above), then
  calls `NativeManifest::build(&schema, table_id, version + 1,
  edited_segments, now_ms)` and publishes via ONE temp-file-then-rename
  onto `_manifest.json` — reuse task 002's publish helper, do not write
  a second one.
- **Single-writer lock (Decision 5)**: acquire the SAME `std::fs::File::
  try_lock()` sibling-lock-file mechanism task 002 uses (same lock path
  convention, same RAII-guard pattern) — DELETE and Append/INSERT
  against the same table must serialize through the identical lock.
- **Dense-direct-address composition (Decision 1) — verified needs ZERO
  changes to `morsel_agg.rs`**: `try_execute_dense_direct`'s native
  branch calls `provider.scan_with_filter(..)` and only emits groups
  whose `presence` bit was actually set during accumulation (confirmed
  by reading `morsel_agg.rs` lines ~591, ~880-888) — since scan-level
  deletion filtering (this task's own read-path change) happens BEFORE
  those batches are produced, deleted rows never reach the accumulator
  at all. No "fall back to the generic path when deletions are pending"
  escape hatch is needed; do not build one unless a NEW correctness gap
  is actually found.
- **Memory-budget composition (phase 1 task 006) — verified needs ZERO
  changes to `check_scan_budget`'s formula**: it estimates
  `total_byte_size`, which deletion vectors don't shrink (segment bytes
  are never rewritten, and `scan()` must still mmap-decode a segment's
  full physical content before the new per-batch filter can drop rows)
  — the existing bound remains valid and sufficient. The deletion
  vector's OWN memory footprint is a separate, new, real concern —
  propagated to task 005 for adversarial testing (broad-shallow
  deletion across many segments), not something to solve speculatively
  here.
- **`require_supported_delete_shape`**, mirroring
  `require_supported_create_table_shape`'s discipline, checked against
  the real `sqlparser::ast::Delete` struct. Accept: exactly one target
  table (`FromTable::WithFromKeyword`/`WithoutKeyword` naming one
  `TableWithJoins` with empty `joins`), `selection: Option<Expr>`
  (`None` = delete all rows). Refuse by name: non-empty `tables`
  (multi-table delete — confirmed the MySQL comma form doesn't even
  parse under this engine's `GenericDialect`, but check defensively),
  `using.is_some()` (Postgres/Snowflake/MySQL `USING` — a join-shaped
  delete, materially different), more than one table or non-empty
  `joins` inside `FromTable`, `returning`, `output`, non-empty
  `order_by`/`limit`.

### `src/storage/native_manifest.rs` — the format extension

```rust
pub struct Segment {
    pub id: u32,
    pub path: String,
    pub row_count: u64,        // PHYSICAL count -- UNCHANGED by deletion
    pub byte_size: u64,
    pub column_stats: BTreeMap<String, ColumnStats>,  // UNCHANGED by deletion
    #[serde(default)]
    pub deleted_rows: Vec<u32>,   // NEW -- sorted, deduplicated LOCAL positions
}
impl Segment {
    pub fn live_row_count(&self) -> u64;  // NEW -- row_count - deleted_rows.len()
}
```
`NativeManifest::validate()` gained bounds checking on `deleted_rows`:
every entry `< row_count`, and entries strictly increasing (sorted +
deduplicated) — a hand-edited or corrupted manifest is refused at load
time with a named error, never silently misread. `Segment.row_count`/
`Snapshot.row_count`/`column_stats` are **guaranteed unchanged** by any
DELETE — `NativeManifest::validate()`'s pre-existing `row_count ==
sum(segments[].row_count)` invariant and `NativeManifest::build()` both
needed zero code changes, confirmed by tests, not just by design intent.

### `src/storage/native_delete.rs` — the row-identification + deletion-vector core (NEW module)

**Building block 1 — row identification, THE function task 004 reuses**:
```rust
pub struct SegmentMatch {
    pub segment_id: u32,
    pub positions: Vec<u32>,        // sorted, ascending LOCAL positions
    pub rows: Option<RecordBatch>,  // Some iff materialize_rows was true
}
pub struct MatchedRows {
    pub schema: SchemaRef,          // == target.arrow_schema()
    pub per_segment: Vec<SegmentMatch>,  // only segments with >=1 match, sorted by id
    pub total_matched: u64,
}
impl MatchedRows {
    pub fn is_empty(&self) -> bool;  // true iff total_matched == 0
}

pub fn identify_matching_rows(
    dir: &Path,
    target: &NativeManifest,   // the CURRENT manifest -- caller already holds it
    predicate: Option<&Expr>,  // None = match every row
    materialize_rows: bool,    // task 004: pass true to get SegmentMatch::rows
) -> Result<MatchedRows>;
```
Bespoke loop, NOT the generic `LogicalPlan`/`PhysicalOperator` pipeline
(that pipeline has no way to carry a matched row's segment/position back
out). Opens `target`'s segments directly (sorted by id), reads each via
`ipc_cache::read_row_group(dir, seg.id as usize, None, None)` (same
mmap-backed reader `NativeTable::scan` uses — batches come back in
stable on-disk block order), evaluates `predicate` batch-by-batch via
`physical::operators::evaluate_expr(batch, pred)` (the SAME function
`FilterExec` itself uses — three-valued NULL-is-not-matched semantics),
tracking a running local-row offset across a segment's (possibly many)
batches to convert matches into segment-relative positions.
`predicate: None` appends the whole contiguous range per batch directly
(no all-true mask ever built) — the "delete/update all rows" shape.

**`materialize_rows` is the load-bearing design decision for task 004's
reuse**: when `false` (what DELETE always passes — it only needs WHICH
rows, never their VALUES), `SegmentMatch::rows` stays `None` and no
`compute::filter`/concat work happens at all, so a broad `DELETE FROM t`
(matching most/all of a table) never pays to materialize row data it
will never use. When `true`, each matched batch's rows are filtered
(`arrow::compute::filter` per column) and concatenated per segment into
`SegmentMatch::rows: Some(RecordBatch)`, in `positions` order, same
schema as `MatchedRows::schema` — **task 004 should call this with
`materialize_rows: true`** to get matched rows' CURRENT column values
for evaluating its SET expressions against, reusing this exact function
rather than re-deriving an equivalent scan.

`identify_matching_rows` does NOT consult or edit `Segment::deleted_rows`
itself — an already-deleted row is still "matched" again by an
overlapping predicate. This is deliberate: it is what makes building
block 2's union idempotent, rather than this function needing to
special-case already-deleted positions.

**Building block 2 — deletion-vector editing**:
```rust
pub fn apply_deletions(target: &NativeManifest, matches: &MatchedRows) -> Vec<Segment>;
```
Folds `matches` into `target.segments`, returning the new COMPLETE
`Vec<Segment>` (does NOT touch or publish any manifest). For each
segment with a match: unions `matches`' positions into the segment's
EXISTING `deleted_rows` via a `BTreeSet<u32>` (insert + re-serialize
sorted) — idempotent by construction, so a second overlapping DELETE
naturally does not duplicate or corrupt anything. If the union now
covers every row (`set.len() as u64 >= seg.row_count`), the segment is
DROPPED from the returned `Vec` entirely (task 001's Decision 3's narrow
compaction exception — its `.arrow` file becomes an inert orphan).
Segments with no match are returned as cheap, identical clones.

**Self-publishing entrypoint** (what `ExecutionContext::
delete_from_native_table` calls; task 004 should NOT call this — see its
own composition note below):
```rust
pub struct NativeDeleteResult {
    pub table_id: String,
    pub version: u64,           // == pre-delete version on either no-op case below
    pub rows_deleted: u64,      // NET newly-tombstoned count, NOT the gross match count
    pub segments_dropped: usize,
    pub total_rows: u64,        // LOGICAL (post-delete) total -- NOT snapshot.row_count
    pub total_segments: usize,
}

pub async fn delete_from_native_table(
    table_dir: impl AsRef<Path>,
    predicate: Option<&Expr>,
) -> Result<NativeDeleteResult>;
```
Sequence: `native_write::lock_table_for_write` (held for the whole span)
→ `native_manifest::read_manifest` → `identify_matching_rows(..,
materialize_rows: false)` → (if empty, return unchanged state, no
publish) → `apply_deletions` → compute the LOGICAL row-count delta →
(if delta is `0` — every matched row was ALREADY deleted — return
unchanged state, no publish; this is a REAL refinement found during
implementation, not in the original design: `rows_deleted` is the NET
count, not gross matches, so a fully-redundant repeat DELETE is a TRUE
no-op, not just "doesn't double-count") → `native_write::
publish_manifest_update(table_dir, schema, table_id, version + 1,
new_segments, now_ms)`.

**Task 004 (UPDATE)'s expected composition** (per task 001's Decision 2 —
do NOT call two self-publishing entrypoints sequentially): acquire
`native_write::lock_table_for_write` ONCE → `native_manifest::
read_manifest` ONCE → `native_delete::identify_matching_rows(dir,
&manifest, predicate, materialize_rows: true)` to get BOTH the
tombstone-candidate positions AND matched rows' current values →
evaluate SET expressions against `SegmentMatch::rows` to build new-row
batches → `native_write::write_append_segments` on those batches against
the SAME already-read manifest → `native_delete::apply_deletions` for
the tombstoning half → fold both edited-and-new segment lists into ONE
`Vec<Segment>` → `native_write::publish_manifest_update` exactly ONCE.

### `src/storage/native_table.rs` — read-path consultation

`NativeTable::scan()` gained a deletion-filtering step: for each segment
with non-empty `deleted_rows`, a new private free function
`filter_deleted_rows(batches: Vec<RecordBatch>, deleted_rows: &[u32]) ->
Result<Vec<RecordBatch>>` tracks a running local-row offset across the
segment's batches and applies `arrow::compute::filter`, with a per-batch
fast path (a monotonic cursor into the sorted `deleted_rows`) that skips
the mask/filter call entirely when no deleted position falls in that
batch's range. A segment with EMPTY `deleted_rows` skips the whole step
(`scan()`'s own caller-side check) — zero allocation, zero behavior
change from before this task.

**Confirmed composition (verified against the ACTUAL implementation, not
just carried forward from task 001's design-time analysis)**:
- `TableProvider::scan_with_filter`'s DEFAULT implementation is exactly
  `self.scan(projection)`, and `NativeTable` does not override it — so
  EVERY read path that goes through `scan_with_filter` (not just `scan`
  directly) gets deletion filtering for free. Confirmed by grepping
  every call site in the crate: `morsel_agg.rs`'s dense-direct-address
  fast path (`try_execute_dense_direct` calls `provider.
  scan_with_filter(eff_projection.as_deref(), None)`), `physical/
  planner.rs`'s generic `MemoryTableExec` scan path (line ~1380) and its
  prescan cache (line ~597), and `scan.rs`'s own `MemoryTableExec::
  execute` — all four funnel through the identical `NativeTable::scan`.
  Dense-direct-address needed LITERALLY ZERO code changes: it only sets
  a `presence` bit for keys it actually accumulates and only emits set
  bits, so a deleted row (filtered out before `try_execute_dense_direct`
  ever sees the batch) simply never reaches the accumulator — the exact
  same sparse-key mechanism that already handles ordinary gapped key
  ranges. No "fall back to generic path when deletions are pending"
  escape hatch was needed or built.
- `check_scan_budget`'s `memory_limit * spill_threshold` formula
  (phase 1 task 006) needed zero changes: it estimates `self.
  statistics().total_byte_size`, which this task's `statistics()` change
  deliberately does NOT touch (see below) — the formula's existing bound
  stays valid and sufficient.
- `shard_by_splits` (distributed splits): unmodified by this task, but
  composes correctly by construction — a shard clones the WHOLE
  `NativeManifest` (including every segment's `deleted_rows`) and
  narrows only `only_segments`; `scan()`'s per-segment deletion
  filtering runs identically regardless of `only_segments`, so a shard's
  own segment's deletions are applied correctly. Verified with a
  dedicated test (`shard_by_splits_scan_and_statistics_respect_the_
  shards_own_segment_deletions`), not just inferred.

`NativeTable::statistics()`: `row_count` now sums `segment.
live_row_count()` (the NEW logical count) instead of raw `segment.
row_count`, for BOTH the whole-table and sharded-provider branches.
`total_byte_size` and the column-stats rollup (min/max/NDV) are
DELIBERATELY left untouched (task 001's Decision 1: deletion vectors
never shrink a segment's physical bytes, and a wider stats bound is
always safe, never a correctness risk).

### `src/planner/binder.rs` — SQL surface

```rust
pub fn delete_target_name(stmt: &Statement) -> Option<String>;
```
Mirrors `insert_target_name`: extracts the FIRST FROM-table's name
regardless of whether the statement is otherwise a supported shape
(extraction is deliberately separate from validation).

```rust
pub fn bind_delete(&mut self, stmt: &ast::Delete) -> Result<(String, Option<Expr>)>;
```
Validates shape (`require_supported_delete_shape`, mechanically checked
against sqlparser 0.62's real 10-field `ast::Delete` struct plus
`TableFactor::Table`'s 10 fields — refuses by name: non-empty `tables`
[MySQL multi-table form, confirmed structurally UNREACHABLE under this
engine's `GenericDialect` by reading `Parser::parse_delete`'s source
directly, kept as defensive code], a multi-table `FromTable` list, a
JOIN in the target, `USING`, table-valued-function/hint/version/
ordinality/partition/json-path/sample/index-hint variants of the target,
`RETURNING`, `OUTPUT`, `ORDER BY`, `LIMIT`), then binds `stmt.selection`
(if present) via the SAME `bind_expr` method `bind_select`'s own WHERE
binding uses, against the target table's schema (aliased via the
DELETE's own alias if present, mirroring `bind_table_factor`'s
convention — `WHERE alias.col = ...` binds identically to `WHERE col =
...` since `evaluate_expr`'s `find_column_index` falls back to
unqualified matching regardless). `selection: None` binds to predicate
`None` (match every row) — not a trivial `TRUE` literal, not an error.

**A refusal found and added beyond the original Technical Details**: a
WHERE subquery (`DELETE FROM t WHERE id IN (SELECT ...)`) BINDS
successfully (confirmed — the identical `bind_expr` path `bind_select`
uses) but is refused right after, by name (`predicate.contains_
subquery()`), because evaluating it needs a `SubqueryExecutor`, which
the bespoke `identify_matching_rows` loop does not have and wiring one
up was out of this task's scope. Refusing at bind time (not letting it
fail deep inside `evaluate_expr` with a generic "no executor available"
message) matches this codebase's "refuse cleanly and early" discipline.

`Binder::bind()` gained a `Statement::Delete(delete)` arm: validates
shape then ALWAYS returns `Err` naming `delete_from_native_table` as the
real entrypoint — DELETE has no `LogicalPlan` to give back (unlike the
Insert/CreateTable arms, this is genuinely not a small `bind_query()`
wrapper). Reachable only via direct `bind()` callers (e.g.
`logical_plan()`); `ExecutionContext::sql()` refuses a DELETE by name
BEFORE ever calling `bind()`, mirroring its pre-existing CREATE
TABLE/INSERT guards.

### `src/execution/context.rs`

```rust
pub struct DeleteResult {
    pub table_name: String,
    pub table_id: String,
    pub version: u64,
    pub rows_deleted: u64,       // == NativeDeleteResult::rows_deleted (NET)
    pub segments_dropped: usize,
    pub total_rows: u64,         // == NativeDeleteResult::total_rows (LOGICAL)
    pub elapsed: Duration,
}

pub async fn ExecutionContext::delete_from_native_table(&mut self, sql: &str) -> Result<DeleteResult>;
```
Shape mirrors `insert_into_native_table`: parse → `delete_target_name`
(→ `InvalidArgument` if not a DELETE) → look up the target in
`self.tables` (→ `TableNotFound` if unregistered — no auto-discovery) →
downcast to `NativeTable` (→ `InvalidArgument` otherwise) →
`Binder::bind_delete` (validates + binds — NOT `bind()` + a physical
plan; there is no `LogicalPlan`/`PhysicalOperator` pipeline involved at
all) → `native_delete::delete_from_native_table` directly →
`register_native_table` again (so the deletion is immediately visible in
the same session).

`ExecutionContext::sql()` gained the same DELETE-refusal guard it
already had for CREATE TABLE/INSERT.
