# Task: Deletion vector mechanism + DELETE

## Description

`DELETE FROM <native table> WHERE <predicate>` — the first mutation that
needs genuinely new read-path infrastructure: phase 1's `NativeTable::
scan()` reads every row of every (assigned) segment unconditionally.
This task adds task 001's chosen deletion mechanism (most likely a
deletion vector consulted at read time) and the SQL surface that writes
to it. Shipped together — the mechanism has no independent value without
the SQL surface that exercises it, and testing the mechanism in isolation
from real DELETE statements risks missing exactly the kind of subtle bug
this program has repeatedly found in exactly this kind of area.

## Acceptance Criteria

- [ ] Deletion mechanism implemented per task 001's decision — read its
      Outcome section for the exact representation, storage location,
      and atomic-publish approach before starting.
- [ ] `NativeTable::scan()`/`scan_with_filter()` consult the deletion
      mechanism and filter matched rows out — correctness-critical, must
      compose correctly with: phase 1's dense-direct-address fast path
      (task 005 of the foundation epic — a deleted row must not be
      double-counted or mis-counted by that path; if the fast path
      cannot cheaply account for pending deletes, it must fall back to
      the generic path for a table with any pending deletions, not
      silently produce a wrong answer for speed), distributed splits
      (`shard_by_splits` — deletions must apply per-shard correctly, not
      just at the whole-table level), and the memory-budget check from
      phase 1's task 006 (a deletion vector itself must be bounded and
      accounted for in that budget, not a new unbounded-growth path).
- [ ] `Statement::Delete` handled in `Binder::bind()` — new match arm.
      The `WHERE` predicate must be evaluated against the table's actual
      current data (a filtered scan) to identify matching row positions
      — this is real new binding/execution work, not a small wrapper
      around existing machinery the way CTAS's `AS SELECT` was.
- [ ] A new `ExecutionContext` entrypoint (e.g. `delete_from_native_
      table`) following the established `&mut self`, non-`sql()` shape.
- [ ] Cell-exact validation: delete from a native table, compare against
      an independently-computed reference. Cover: deleting all rows
      (table becomes logically empty but still exists — subsequent
      queries must return zero rows correctly, not error); deleting zero
      rows (predicate matches nothing — must be a clean no-op, not an
      error); deleting from a table with multiple segments (deletions
      must apply to the correct segment, not silently apply to the wrong
      one or all of them); repeated deletes on overlapping predicates
      (idempotency — deleting an already-deleted row via a second,
      overlapping DELETE must not corrupt the deletion vector or
      double-count).
- [ ] `statistics()` reflects post-delete row counts correctly (not the
      pre-delete rollup) — this is a real correctness surface, since
      stale statistics could mislead the query planner (e.g. into a
      wrong join-order decision), not just report a cosmetic wrong
      number.
- [ ] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Populated by task 001's decisions — read `001.md`'s Outcome section in
full before starting. Summary of what directly shapes this task:

- **Deletion vector representation and location (Decision 1)**: a new
  `#[serde(default)] deleted_rows: Vec<u32>` field on the EXISTING
  `Segment` struct in `_manifest.json` — sorted, deduplicated LOCAL row
  positions within that segment's own on-disk row ordering. Not
  `roaring`, not a sibling file per segment, not a separate whole-table
  file — inline in the one manifest, matching this format's established
  atomicity/inspectability discipline (full tradeoff analysis in
  001.md's Outcome). `#[serde(default)]` means every manifest phase 1
  already wrote round-trips unchanged (empty `Vec` = no deletions).
- **Row identification — a BESPOKE loop, not the generic query
  pipeline.** The standard `LogicalPlan`/`PhysicalOperator` pipeline
  (what CTAS/INSERT reuse for their source query) has no way to carry a
  matched row's (segment id, local position) back out — `TableProvider::
  scan()` returns only `Vec<RecordBatch>`, no positional metadata. Bind
  the `WHERE` predicate via `Binder::bind_expr` (the SAME method
  `bind_select`'s own WHERE-clause binding already calls — expose a new
  `pub fn bind_delete(&mut self, stmt: &ast::Delete) -> Result<(String,
  Option<Expr>)>` on `Binder` returning the target table name + bound
  predicate), then EVALUATE it directly via `filter::evaluate_expr
  (batch, &predicate)` — the SAME function `FilterExec` uses — inside a
  loop that: opens the target `NativeTable`'s CURRENT manifest, iterates
  `active_segments()` in id order, calls `ipc_cache::read_row_group(dir,
  seg.id, None, None)` per segment (confirmed by reading it: batches
  come back in stable on-disk block order, multiple ~65,536-row batches
  per segment is the NORMAL case since `native_write.rs` already
  reslices before writing — track a running local-row offset across
  batches, reset per segment), and collects positions where the
  predicate's boolean mask is true. `selection: None` (no WHERE) means
  "match every row" — must be supported cleanly (this file's own
  acceptance criteria already name "deleting all rows" as a case to
  cover).
- **Idempotency is structural, not a special case**: union new matched
  positions into the segment's existing `deleted_rows` via a
  `BTreeSet<u32>` (insert + re-serialize as sorted `Vec`) — re-matching
  an already-deleted row is then naturally a no-op, satisfying this
  file's own "repeated deletes on overlapping predicates" acceptance
  criterion with no extra logic.
- **The narrow in-scope compaction exception (Decision 3)**: when a
  segment's `deleted_rows.len() == segment.row_count` after this
  DELETE, drop that `Segment` entirely from the manifest's `segments:
  Vec<Segment>` (its `.arrow` file becomes an inert, unreferenced
  orphan). This bounds the deletion vector's own worst-case size and is
  the concrete, cheap thing task 001 identified as in-scope despite
  deferring full compaction — implement it here, not as a follow-up.
- **`statistics()` row count — read `NativeTable::statistics()`'s
  EXISTING implementation before changing it**: it already computes
  `row_count` itself from `active_segments()` rather than reading
  `manifest.snapshot.row_count` directly. Extend that existing
  computation to `segment.row_count - segment.deleted_rows.len()`,
  summed over active segments — a NEW, separate computation. Do **not**
  touch `Segment.row_count`/`Snapshot.row_count` themselves: they must
  keep meaning the PHYSICAL (write-time) count, unaffected by deletion,
  so `NativeManifest::validate()`'s existing invariant
  (`snapshot.row_count == sum(segments[].row_count)`) is satisfied with
  ZERO changes and `NativeManifest::build()` stays callable unchanged
  after a DELETE (see next bullet).
- **Atomic publish (Decision 4) — same single-file-rename mechanism as
  task 002, and the SAME `NativeManifest::build()` call, unchanged.**
  DELETE never writes new segment DATA at all (no new `.arrow` files) —
  it only edits `Vec<Segment>` in memory (mutating `deleted_rows` on
  affected entries, dropping wholly-tombstoned ones per above), then
  calls `NativeManifest::build(&schema, table_id, version + 1,
  edited_segments, now_ms)` and publishes via ONE temp-file-then-rename
  onto `_manifest.json` — reuse task 002's publish helper, do not write
  a second one.
- **Single-writer lock (Decision 5)**: acquire the SAME `std::fs::File::
  try_lock()` sibling-lock-file mechanism task 002 uses (same lock path
  convention, same RAII-guard pattern) — DELETE and Append/INSERT
  against the same table must serialize through the identical lock.
- **Dense-direct-address composition (Decision 1) — verified needs ZERO
  changes to `morsel_agg.rs`**: `try_execute_dense_direct`'s native
  branch calls `provider.scan_with_filter(..)` and only emits groups
  whose `presence` bit was actually set during accumulation (confirmed
  by reading `morsel_agg.rs` lines ~591, ~880-888) — since scan-level
  deletion filtering (this task's own read-path change) happens BEFORE
  those batches are produced, deleted rows never reach the accumulator
  at all. No "fall back to the generic path when deletions are pending"
  escape hatch is needed; do not build one unless a NEW correctness gap
  is actually found.
- **Memory-budget composition (phase 1 task 006) — verified needs ZERO
  changes to `check_scan_budget`'s formula**: it estimates
  `total_byte_size`, which deletion vectors don't shrink (segment bytes
  are never rewritten, and `scan()` must still mmap-decode a segment's
  full physical content before the new per-batch filter can drop rows)
  — the existing bound remains valid and sufficient. The deletion
  vector's OWN memory footprint is a separate, new, real concern —
  propagated to task 005 for adversarial testing (broad-shallow
  deletion across many segments), not something to solve speculatively
  here.
- **`require_supported_delete_shape`**, mirroring
  `require_supported_create_table_shape`'s discipline, checked against
  the real `sqlparser::ast::Delete` struct. Accept: exactly one target
  table (`FromTable::WithFromKeyword`/`WithoutKeyword` naming one
  `TableWithJoins` with empty `joins`), `selection: Option<Expr>`
  (`None` = delete all rows). Refuse by name: non-empty `tables`
  (multi-table delete — confirmed the MySQL comma form doesn't even
  parse under this engine's `GenericDialect`, but check defensively),
  `using.is_some()` (Postgres/Snowflake/MySQL `USING` — a join-shaped
  delete, materially different), more than one table or non-empty
  `joins` inside `FromTable`, `returning`, `output`, non-empty
  `order_by`/`limit`.
