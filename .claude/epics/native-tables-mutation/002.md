# Task: INSERT — Append write mode + SQL wiring

## Description

`INSERT INTO <native table> SELECT ...` — the simplest of this epic's
three mutations, and the only one that doesn't need the deletion-vector
mechanism at all: it just writes new, immutable segments (exactly like
phase 1's write path already does) and extends the existing manifest
rather than replacing it wholesale. Delivers standalone value even before
DELETE/UPDATE exist — a native table stops being "load once, done."

## Acceptance Criteria

- [ ] `NativeWriteMode::Append` (new variant) in `src/storage/
      native_write.rs`: writes new segment(s) using the exact same
      streaming, bounded-memory discipline phase 1's `Create`/`Overwrite`
      modes already use (task 003's own Outcome measured ~406MB peak RSS
      converting 60M rows — this mode must hold the same bound, verified
      not assumed).
- [ ] Manifest update uses task 001's decided atomic-publish mechanism:
      new segments' entries appended to `segments: Vec<Segment>`,
      `table_stats` re-rolled up to include the new segments (reuse
      phase 1's existing rollup/merge functions — find their exact names
      in `native_manifest.rs` rather than reimplementing), `snapshot.
      version` bumped, `table_id` preserved.
- [ ] `Statement::Insert` handled in `Binder::bind()` — new match arm,
      following the `CreateTable` arm's established shape: bind the
      `INSERT`'s source query via the existing `bind_query()` (confirmed
      by task 001 to work the same way), refuse (by name) any `Insert`
      shape this epic doesn't support (e.g. `INSERT ... VALUES` with
      literal rows, if task 001 scoped this to `INSERT ... SELECT` only —
      check its decision) exactly as thoroughly as the `CreateTable` arm
      refuses its ~57 unsupported struct fields — mechanically verified
      against the real `sqlparser::ast::Insert` struct, not eyeballed.
- [ ] A new `ExecutionContext` entrypoint (e.g. `insert_into_native_table`)
      following `create_table_as_select`'s shape — `&mut self`, streams
      the source query's `RecordBatchStream` directly into
      `NativeWriteMode::Append`, does not go through `sql()`'s
      materializing path.
- [ ] Wired into the REPL (`src/main.rs`) alongside `CREATE TABLE`'s
      existing dispatch.
- [ ] Cell-exact validation: insert into a native table, compare against
      an independently-computed reference (e.g. re-running the
      equivalent combined query directly against the original source).
      Cover: inserting into a table that already has data from CTAS;
      inserting an empty result set (zero new rows — must not corrupt
      the manifest or crash); a schema mismatch between the INSERT
      source and the target table (must be a named, clean error, never
      silent coercion or corruption).
- [ ] `statistics()`/`distributed_splits()` correctly reflect the
      post-insert state (new segments show up, rollup stats update) —
      re-run phase 1's own relevant tests against a post-insert table,
      not just a freshly-created one.
- [ ] No regression to `CREATE TABLE ... AS SELECT` or the CLI write path
      — both existing modes (`Create`/`Overwrite`) stay byte-for-byte
      unchanged in behavior.
- [ ] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Populated by task 001's decisions — read `001.md`'s Outcome section in
full before starting. Summary of what directly shapes this task
(Decisions 4 and 6 are the most load-bearing here):

- **Atomic publish (Decision 4) — do NOT reuse `native_manifest::
  publish_table_dir` unchanged.** It does `remove_dir_all(final_dir)`
  then `rename(staging, final_dir)` — correct only when staging is a
  complete, self-sufficient replacement (Create/Overwrite), and would
  silently delete every pre-existing segment file if called on an
  Append's partial staging set. Instead: write new segment file(s)
  DIRECTLY into the LIVE table directory (not a fresh staging dir) under
  fresh, non-colliding segment ids —
  `existing_manifest.segments.iter().map(|s| s.id).max().unwrap_or(0) + 1..`,
  never restarting at 0 (a real bug `SegmentWriter::new`'s current
  `next_id: 0` would silently reintroduce if reused as-is for Append).
  Then build ONE new `Vec<Segment>` (existing segments unchanged + new
  segments' entries), call the EXISTING `NativeManifest::build(&schema,
  table_id, version + 1, new_segments, now_ms)` UNCHANGED (it already
  derives `row_count`/`table_stats` fresh via `Self::rollup` — no new
  merge function needed), write it to a temp file inside the same
  directory, then `std::fs::rename(tmp, native_manifest::manifest_path
  (dir))` — ONE atomic file-level rename (POSIX guarantees this the
  same as a directory rename, the primitive `publish_table_dir` already
  trusts). A crash before this rename leaves orphan segment files
  nothing references yet (harmless) and the OLD manifest fully intact.
- **Single-writer lock (Decision 5)**: acquire `std::fs::File::
  try_lock()` (stable std, zero new dependency — confirmed against
  `rustc 1.93.0`'s shipped std source) on a sibling lock path (e.g.
  `final_dir.with_file_name(format!("{name}.lock"))`, mirroring
  `staging_dir_for`'s own sibling-path convention) BEFORE reading the
  existing manifest, hold it for the whole read-modify-write-publish
  span via an RAII guard, release on every exit path (guard `Drop`, plus
  the kernel auto-releases on a crash — verified live via a
  SIGKILL test, see 001.md's Outcome Decision 5). On contention
  (`TryLockError::WouldBlock`), fail with `QueryError::Storage` naming
  the table directory — no new error variant needed.
- **Schema/dictionary inheritance, not rediscovery (Decision 6)** — the
  concrete trap to avoid: `SegmentWriter::accept` today validates ONLY
  column count, and `SegmentWriter::flush`'s dictionary-candidacy
  decision is made fresh from whatever data it's FIRST given. Neither
  is correct for Append: the new segments must conform to the TARGET
  table's ALREADY-DECLARED schema (`NativeManifest::arrow_schema()`),
  both in column name/type (validate before writing; a mismatch is a
  clean, named `Err`, never silent coercion — this task's own
  acceptance criterion) and in which columns are dictionary-encoded
  (read the decision from the existing manifest's `ManifestDataType::
  Dictionary` fields and apply it unconditionally to every new batch,
  never re-derive it from the new data's own cardinality).
- **`require_supported_insert_shape`**, mirroring
  `require_supported_create_table_shape`'s exact discipline (mechanical,
  checked against the real `sqlparser::ast::Insert` struct — ~26
  semantic fields, confirmed via `.scratch/mutation_sqlparser_spike/`).
  Accept: `table` (name only), `source: Some(Query)` (SELECT- or
  VALUES-bodied — both bind via the SAME existing `bind_query()`, `
  SetExpr::Values` already has a binder arm at `binder.rs:653`, so
  `INSERT ... VALUES` needs zero extra binder work), `selection`
  implicitly via the source query. Refuse by name: non-empty `columns`
  (explicit column list/reordering — not supported, matches CTAS's own
  `ct.columns` refusal), `overwrite: true` (Hive `INSERT OVERWRITE
  TABLE` — silently treating this as Append would be a real semantic
  bug), non-empty `assignments` (MySQL `INSERT ... SET`), `on.is_some()`
  (`ON CONFLICT`/`ON DUPLICATE KEY UPDATE` — upsert, out of scope),
  `returning`, `output`, `partitioned`, `table_alias`, `replace_into`,
  and the rest of the struct's fields.
- **The wildcard-qualification bug, known from phase 1, must not
  reappear**: `SELECT * FROM src` produces table-qualified field names
  (`"src.col"`) via `Binder::bind_select_items`'s `Wildcard` arm — phase
  1 tasks 003/004 each independently hit and fixed this for CTAS. INSERT
  must re-wrap the source stream's batches against the TARGET's existing
  schema by position (`RecordBatch::try_new(target_schema,
  batch.columns().to_vec())`, the same pattern `create_table_as_select`
  already uses), never trust the source query's own field names — this
  is even more direct for INSERT than it was for CTAS, since the target
  schema already exists.
- **Reusable building block for task 004 (UPDATE)**: per Decision 2,
  expose the segment-writing core as a function that writes segments and
  returns their `Segment` entries WITHOUT touching or publishing the
  manifest (the publish steps above factored into a separate, thin
  wrapper) — task 004 needs to compose this with task 003's own
  non-publishing DELETE core into ONE atomic publish, not call two
  separate self-publishing entrypoints sequentially.
- New CLI/`ExecutionContext` entrypoint naming, streaming discipline
  (never through `sql()`'s materializing path), and cell-exact
  validation expectations are unchanged from this file's own existing
  Acceptance Criteria above — nothing in task 001's findings changes
  those.
