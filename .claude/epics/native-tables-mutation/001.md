# Task: Design spike — deletion mechanism, UPDATE semantics, compaction scope, atomic-publish model

## Description

This epic's Architecture Decisions section is explicit that five real
design questions gate everything else and must be resolved with evidence,
not assumption — mirroring phase 1's own task 001, whose SQL-DDL-scope
and manifest-format decisions unblocked its entire epic without rework.
This epic's stakes are higher: phase 1 substantially exposed an
already-proven mechanism (the IPC sidecar); this epic builds genuinely
new infrastructure (mutation) the engine has never had in any form.

## Acceptance Criteria

- [ ] **Read phase 1 in full first**: `.claude/epics/archived/
      native-tables-foundation/epic.md` and every one of its 8 tasks'
      Outcome sections (`001.md` through `008.md`) — especially 002
      (exact `NativeManifest`/`Segment`/`ColumnStats` schema and the
      staging/atomic-publish pattern its write path already uses), 003
      (the exact `NativeWriteMode`/`write_batches_with_options` API), 004
      (`NativeTable`, `create_table_as_select`, the binder's
      `CreateTable` arm as your template for new DML arms), 005 (the
      `as_any()` mechanism and dense-direct-address integration your
      deletion vector must not silently break), 006 (the memory-budget
      mechanism and the exact OOM it found — your deletion vector design
      must not reintroduce an equivalent unbounded-growth risk), 008
      (the `HashJoinExec` multi-round bug — a reminder of the class of
      bug re-execution paths can hide).
- [ ] **Deletion mechanism decision**: deletion vector (bitmap or sorted
      row-id list, consulted at read time — merge-on-read) vs. rewrite
      affected segments on every delete (copy-on-write). Give a concrete
      recommendation with reasoning grounded in THIS engine's actual
      segment format (immutable Arrow IPC files, `rg_{id:05}.arrow`,
      mmap-read via `ipc_cache::read_row_group`) and read patterns, not
      generic lakehouse-format lore. If deletion vectors: decide the
      concrete representation (a crate like `roaring`, or a simple
      sorted `Vec<u32>`/bitmap per segment — weigh against this
      project's own "no new dependency unless justified" discipline) and
      exactly where it's stored (a manifest field, a sibling file per
      segment, one file for the whole table).
- [ ] **UPDATE semantics decision**: DELETE + INSERT (reusing both
      mechanisms) vs. true in-place update. Recommend DELETE+INSERT
      unless there's a concrete, evidenced reason this engine's shape
      makes in-place meaningfully better — state the reason if you
      diverge from the epic's own leaning.
- [ ] **Compaction scope decision**: in this epic, or explicitly deferred
      to a later one. A deletion vector alone is correctness-preserving
      indefinitely (only a performance concern as deletes accumulate) —
      weigh the "smallest safe slice first" argument for deferring
      against the risk of shipping a mechanism nothing ever reclaims
      space from. State your recommendation and, if deferring, exactly
      what a future compaction task would need (this epic's deletion
      vector format must not make future compaction harder than
      necessary).
- [ ] **Atomic-publish mechanism**: the concrete answer for how an
      `Append` (new segments + updated manifest) and a delete (updated
      manifest/deletion vector) become visible to readers atomically —
      a reader must never observe a manifest referencing an unwritten
      segment, or a half-updated deletion vector. State the exact
      mechanism (e.g., write to a staging path, then atomic rename over
      the published manifest — confirm whether phase 1's write path
      already has this pattern to extend, per its own Outcome notes, or
      whether phase 1's atomicity only worked because full-replace
      writes have no partial-update window to protect against).
- [ ] **Single-writer enforcement decision**: name the concrete mechanism
      (even a simple advisory lock file, checked and held for the
      duration of a mutation) that prevents two concurrent writers to the
      same native table from corrupting each other's work — this engine
      has no lock manager, WAL, or MVCC, and this epic is not building
      any of those; the enforcement must be lightweight and explicit.
- [ ] **SQL lift sizing**: confirm (via a `.scratch/` spike, mirroring
      phase 1's own sqlparser-CREATE-TABLE spike) that `sqlparser` 0.62
      already parses `INSERT INTO ... SELECT`, `DELETE FROM ... WHERE`,
      and `UPDATE ... SET ... WHERE` into ASTs this binder's existing
      expression/predicate binding can mostly reuse — don't assume
      parity with the CREATE TABLE spike's finding without checking.
- [ ] Propagate every decision into tasks 002-006's own files' Technical
      Details sections (edit them directly) so none of those tasks needs
      to re-derive this work — continuing the exact discipline phase 1's
      task 001 established.
- [ ] No source code changes required unless a tiny throwaway spike is
      the fastest way to get evidence — keep it in `.scratch/`, never in
      `src/`.
