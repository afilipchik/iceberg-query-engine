## Technical Details

Reference format: `.claude/epics/archived/native-tables-foundation/
epic.md`'s close-out section. Also read `001.md`'s Outcome section —
the following of its decisions bear directly on this task's own
acceptance criteria:

- **Compaction is confirmed OUT OF SCOPE for this epic** (Decision 3,
  not merely "if task 001 deferred it" as this file's own acceptance
  criteria conditionally phrase it) — the CLAUDE.md update this task
  writes should state this explicitly, alongside the one in-scope
  exception task 003 implements (a 100%-tombstoned segment is dropped
  from the manifest, which is not full compaction). State the honest,
  named cost: segment count grows with every Append/INSERT, and disk
  space from partial deletes is never physically reclaimed.
- **Single-writer only, enforced via `std::fs::File::try_lock()`**
  (Decision 5) — document this in CLAUDE.md as this epic did for
  memory safety in phase 1: name the mechanism, and its explicit scope
  boundary (process-crash-safe via kernel-released `flock`, verified
  live; NOT `fsync`/power-loss-durable beyond the OS's own page-cache
  behavior — matching, not narrowing, phase 1's own established scope).
- **A never-mutated table must show zero regression** — the deletion-
  vector consultation inside `scan()` is designed as a fast no-op for a
  segment with an empty `deleted_rows` (the state of every segment
  phase 1 ever wrote, and of any segment untouched by a DELETE since).
  This task's benchmark should include this as an EXPLICIT case (not
  just "mutation doesn't regress a mutated table's later reads"): a
  freshly-CTAS'd table's read performance, post this epic's code
  landing, should match phase 1's own recorded SF=10 numbers (5.324s,
  1.23x DuckDB-parquet) within noise — confirming the new code path
  costs nothing when it has nothing to filter.
- **Atomic-publish mechanism to document**: single-file atomic
  `rename()` of a freshly-written manifest onto the live
  `_manifest.json`, generalizing phase 1's whole-directory
  `publish_table_dir` (used unchanged only by Create/Overwrite) — worth
  a CLAUDE.md line distinguishing the two, since a future reader might
  otherwise assume one mechanism covers all write modes.
