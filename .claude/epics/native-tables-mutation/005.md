# Task: Memory safety + concurrency/crash-safety adversarial verification

## Description

Phase 1's task 006 (memory safety) found a real, previously-undiscovered
OOM in code that "should have been" safe by inspection — `NativeTable::
scan()` was not spill-aware and got SIGKILL'd under a tight memory cap.
That task's own lesson — inspection alone missed it, only adversarial
testing under real memory pressure caught it — applies with more force
here, since mutation introduces new unbounded-growth surfaces (deletion
vectors, sequences of small writes) that don't exist in phase 1 at all.
This task's job is to adversarially test, not just review, and fix what
it finds.

## Acceptance Criteria

- [ ] **Deletion vector growth**: repeatedly delete rows (many small
      DELETEs, or one DELETE matching a large fraction of a large table)
      and confirm the deletion vector's memory footprint stays bounded
      and accounted for in the existing memory-budget mechanism (phase
      1's task 006) — not a new, uncounted allocation.
- [ ] **Many sequential mutations**: a long sequence of INSERT/DELETE/
      UPDATE operations against the same table — confirm no unbounded
      growth in manifest size, segment count, or open file handles (each
      `Append` creates new segments; without compaction — if task 001
      deferred it — segment count grows with every insert; confirm this
      growth is at least BOUNDED-PER-OPERATION, even if not compacted
      away, and that a large segment count doesn't itself become a
      correctness or performance cliff for `scan()`/`statistics()`).
- [ ] **Concurrent-write attempt**: verify task 001's single-writer
      enforcement mechanism actually works — two attempted concurrent
      writers to the same table, confirm the second fails cleanly and
      namedly rather than corrupting the first's work or silently
      succeeding with a lost update.
- [ ] **Crash-safety simulation**: interrupt a mutation mid-write (e.g.
      kill the process between writing new segments and publishing the
      updated manifest) and confirm the table is left in either its
      pre-mutation state or its fully-post-mutation state — never a
      state a reader could observe as corrupt or partially-applied.
      Mirror the adversarial rigor of phase 1's own `gdb`-based
      investigation into the `HashJoinExec` bug — use real tooling to
      prove this, not just reason about it.
- [ ] Test under `scripts/claude-safe-build.sh`'s memory-capped execution
      model — this repo's standard way of safely testing memory-pressure
      scenarios without risking the terminal/session.
- [ ] Fix whatever real gaps are found (small, scoped fixes preferred; if
      a finding is large enough to need a redesign, stop and document it
      clearly rather than scope-creep this task into a rewrite).
- [ ] A well-evidenced "tested X, found no issue" is a complete, valid
      finding for any of the above — this program has repeatedly valued
      a negative result as much as a positive one, provided it's real
      evidence and not just an assumption.
- [ ] Full suite green; `cargo fmt --all -- --check` clean; every build
      through `scripts/claude-safe-build.sh`.

## Technical Details

Read phase 1's task 006 Outcome section in full (`.claude/epics/
archived/native-tables-foundation/006.md`) for the exact methodology
that found the real OOM there — register a real table, run under a real
memory cap, observe the actual failure mode (SIGKILL, not a graceful
error) — and apply the same standard here rather than a lighter one.
Also read `001.md`'s Outcome in full; the specific things it flagged for
THIS task to adversarially verify (not just design-review):

- **Compaction is confirmed deferred (Decision 3)** — segment count
  growing by at least one per Append/INSERT statement, and disk space
  from deletes never being physically reclaimed (except the one
  in-scope exception below), is EXPECTED, not a bug to fix here. This
  task's job is to confirm the growth stays BOUNDED-PER-OPERATION and
  that a large segment count doesn't itself become a correctness or
  performance cliff for `scan()`/`statistics()` — per this file's own
  acceptance criterion — not to add compaction.
- **The one in-scope exception task 003 should have implemented**: a
  segment tombstoned to 100% (`deleted_rows.len() == row_count`) is
  dropped from the manifest entirely. Adversarially confirm this
  actually fires (e.g. `DELETE FROM t` with no WHERE against a small
  table, or a sequence of DELETEs that collectively empty one segment)
  and that it measurably bounds segment/manifest growth versus a
  version of the same test with that exception disabled/not firing.
- **Deletion vector memory footprint — task 001 named a REAL, not just
  hypothetical, scaling risk**: a plain `Vec<u32>` per segment is
  bounded per segment (mitigated by the empty-segment-drop rule above),
  but a table with MANY segments EACH lightly touched by a broad,
  shallow delete (e.g. hundreds of segments, each ~1% deleted) was
  estimated at potentially tens of MB of aggregate `deleted_rows`
  content across the manifest — adversarially test EXACTLY this shape
  (not just "one huge DELETE against one large table," which task 003's
  own empty-segment-drop rule and per-segment bound already handle
  cheaply) alongside the large-single-DELETE case this file's own
  acceptance criteria already name. If this measures as a real problem,
  the documented forward-compatible fix is swapping the field's on-disk
  encoding (still `Segment`-local, still opaque outside one decode
  function) to something more compact — not a redesign.
- **Single-writer lock (Decision 5) — adversarially verify the SAME way
  task 001's own spike did, not just trust the design**: two concurrent
  writers to the same table, confirm the second gets a clean, named
  failure (`QueryError::Storage`, from `TryLockError::WouldBlock`) while
  the first holds `std::fs::File::try_lock()`'s lock; then `kill -9` the
  first writer MID-MUTATION (between writing new segment files and the
  final manifest rename — task 001's own live spike used
  `.scratch/mutation_sqlparser_spike/src/bin/{lock_holder,
  lock_contender}.rs` as a minimal pattern to mirror, though this task
  should test against the REAL mutation code path, not a synthetic
  lock-only harness) and confirm: (a) the lock is available again
  immediately (kernel auto-release, already confirmed for the mechanism
  in isolation — confirm it holds for the real code path too), and (b)
  the table is left in EXACTLY its pre-mutation state (orphaned segment
  files, if any were written before the kill, are harmless and
  unreferenced; `_manifest.json` is untouched) — never a state a reader
  could observe as corrupt.
- **Memory-budget composition (phase 1 task 006's mechanism) — verified
  by task 001 to need no formula change**, since deletion doesn't
  shrink on-disk segment bytes and `scan()` still must decode a
  segment's full physical content before filtering — this task should
  still confirm this holds under real adversarial load (e.g. a
  heavily-deleted-from large table still refuses cleanly, rather than
  OOMing, under a tight `--memory-limit`), since task 001's reasoning is
  evidence-based but this program's own history (phase 1 task 006's
  real find) is exactly why a dedicated adversarial task exists rather
  than trusting design analysis alone.
