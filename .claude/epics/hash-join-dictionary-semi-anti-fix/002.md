# Task: Dictionary keys on the vectorized hash-table path

## Description

`VectorizedHashTable::build` returns "Cannot vectorize key types" for
Dictionary keys, which is why the buggy generic path was reachable at all.
Decode Dictionary key arrays to their value type ONCE per batch at build
time and at every probe entry point (`probe_batch`, `probe_batch_semi`,
and whatever `probe_vectorized`/`probe_one_semi_anti_batch` evaluate),
using the same `compute::cast` the aggregate and the spill path use, so
`can_vectorize_arrays` accepts them. Assert with a test that a
Dictionary-keyed build produces a VHT (not the fallback). Time a
Dictionary-keyed Semi join at SF=10 native before/after (same machine,
back to back) — it must not be slower than the generic path it replaces.

## Acceptance Criteria

- [ ] VHT builds for Dictionary(Int32,Utf8) keys (test asserts the
      table exists / the fallback is not taken)
- [ ] Inner, Semi, Anti, Left over Dictionary keys cell-exact vs naive
      truth through `HashJoinExec` in both orientations
- [ ] Measured: Dictionary-keyed Semi join at SF=10 native, before vs
      after, recorded; not slower
- [ ] Existing hash_join tests + M1/M2 gates green; fmt clean

## Outcome

- Dictionary keys on the vectorized path: `decode_dictionary_key` /
  `evaluate_join_keys` decode Dictionary key arrays to their value type
  once per batch at `VectorizedHashTable::build` and at every probe-side
  key evaluation feeding the VHT (probe_vectorized x4,
  probe_semi_anti_parallel, sequential probe_hash_table); build and probe
  always see one physical type. Asserted by
  `dictionary_keys_build_a_vectorized_hash_table` via a `#[cfg(test)]`
  `build_used_vectorized_table()` accessor; cell-exact
  `inner_semi_anti_left_over_dictionary_keys_are_cell_exact` (dict/dict,
  dict/utf8, utf8/dict; Inner/Semi/Anti/Left; both orientations; row-level
  vs naive truth).
- Measurement exposed a quadratic walk the pre-fix `break` had hidden:
  the 001-only binary did not finish the SF=10 build-left Dictionary Semi
  in 10 minutes (7 keys, 30.6M-row build: ~4.4M equal-key entries per
  probe row). Fixed with `VectorizedHashTable::mark_build_matches`
  (stop at the first already-marked equal entry; O(probe + build)),
  first-match `probe_batch_semi` for the swapped orientation, and
  already-matched skips in the generic loops; guard test
  `build_side_semi_anti_over_heavily_duplicated_keys_is_linear`.
- SF=10 native, same machine back to back, 3 runs, MemoryMax=48G /
  QE_MEM_CAP=44G: pre-fix 7fdc9a1 best **2.60s** (wrong: n=1 per mode) vs
  002 best **2.18s** (correct; vht=true; oracle = plain filtered
  aggregate, byte-identical). Not slower.
- Green: hash_join 17/17, spillable::tests 31/31, native_dictionary_semi_anti
  4/4, spill_tests 12/12; fmt clean. Commit **0c04da9**.
