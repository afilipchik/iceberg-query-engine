# Task: Rollup data model + matching/substitution mechanism

## Description

The epic's real risk and entry point. Prove that a query can be matched
against a registered rollup definition and transparently, correctly
answered from it — a mechanism with zero precedent anywhere in this
codebase (confirmed by dedicated research: every `OptimizerRule`
operates on one plan tree in isolation with no catalog/registry access;
`VectorSearchPushdown`, the closest analog, matches a hard-coded shape
within the SAME plan, not against an externally stored definition).
Deliberately built against a **programmatic** registration API, not SQL
DDL — that's task 002's job — so this task's effort goes entirely into
proving the mechanism, not into DDL polish.

Read `.claude/prds/native-tables.md` (functional requirement 6, success
criterion G5, the rollup paragraph under Out of Scope) and this epic's
own `epic.md` (Architecture Decisions, Technical Approach) in full
before starting — do not re-derive what's already decided there.

- [x] A programmatic registration API on `ExecutionContext` (e.g.
      `register_rollup(name, base_table, defining_sql)` or equivalent —
      your call, document the exact signature chosen) that: binds and
      plans the defining query, executes it once, writes the result as
      native-table segment storage (reusing `native_write.rs` unchanged
      — a rollup's row data IS a native table), and records the rollup
      manifest extension above.
- [x] The matching mechanism itself: given an incoming query's bound
      `LogicalPlan`, determine whether it exactly matches a registered
      rollup's defining plan shape (same base table, same GROUP BY
      expression SET, same requested aggregate SET) closely enough to
      answer from the rollup. Explicitly decide and document: is
      `GROUP BY a, b` treated as matching `GROUP BY b, a` (order-
      independence)? Column aliasing? This must be a deliberate,
      written decision — the research flagged this as an easy-to-get-
      wrong gotcha, not incidental.
- [x] Decide and document WHERE this mechanism plugs into the execution
      path, per the epic's own architecture decision that it does NOT
      belong inside `OptimizerRule` (no catalog access there by
      design). Most likely a pass with real registry access positioned
      around `Optimizer::optimize()` in `ExecutionContext`'s own
      execution flow — but this is your decision to make and justify,
      not assumed here.
- [x] On match: substitute a scan against the rollup's own native-table
      storage in place of the base-table plan (plus whatever reshaping
      — column order — the original query needs). On no match (or a
      stale rollup — staleness bookkeeping only needs to EXIST this
      task, the refresh model itself is task 003's job): fall back to
      the normal, unmodified base-table plan. Never silently wrong.
- [x] Provenance: when a rollup answers a query, this must be
      observably true (a debug/trace flag, a response header/metadata
      field, or equivalent — your call, document it) — per the epic's
      G3/the PRD's G5, never silently indistinguishable from the normal
      path.
- [x] Cell-exact validation: for every shape this task proves (at least

      rollup-answered result is cell-exact identical to the same query
      computed directly against the base table AND to an independently
      computed DuckDB oracle.
- [x] At least one explicit non-matching-shape test (different GROUP BY
      set, an added filter, a different aggregate) proving fallback to
      the base-table plan stays correct, not just "doesn't crash."
- [x] Full suite green (`scripts/claude-safe-build.sh cargo test`, all
      feature combinations this repo's CLAUDE.md directs); `cargo fmt
      --all -- --check` clean.
- [x] **Confidence gate, explicit**: if this task cannot reach a real,

### Design decisions, with exact code pointers

1. **Data model** (`src/storage/native_manifest.rs`): `NativeManifest`
   gained `#[serde(default)] pub rollup: Option<RollupMeta>` — additive,
   every pre-existing manifest still deserializes with `None`, verified
   by the full pre-existing `native_*` test suite (128 tests) staying
   green unmodified. `RollupMeta { base_table, defining_sql,
   base_table_id, base_table_version, columns: Vec<RollupColumn> }`;
   `RollupColumn { canonical_key, physical_name, is_group_by }` maps
   each GROUP BY/aggregate's canonical shape key to the rollup's own
   physical column name. `RollupMeta::group_by_key_set()`/
   `aggregate_key_set()` derive the sorted comparison sets on demand
   (no redundant stored duplication). `NativeManifest::validate()`
   gained matching checks (non-empty columns, no duplicate keys, every
   `physical_name` resolves against the table's own schema) —
   corruption is refused at load time, matching this file's existing
   discipline for every other field.

2. **Matching mechanism** (new sibling module `src/storage/
   native_rollup.rs`, ~650 lines incl. 19 unit tests): `canonical_expr_key`
   recursively renders an `Expr` to a string key, stripping every
   `Expr::Alias` wrapper and every `Column.relation` qualifier before
   falling back to a Debug-based rendering of each node's own
   deterministic tag (func/op/data_type — all already `derive(Debug)`).
   This is a DELIBERATE combination of the codebase's two existing
   plan-comparison precedents (`optimizer/mod.rs`'s fixpoint Debug-string
   hash, `subquery.rs`'s `plan_hash`, both EXACT-identity tools) with a
   semantic NORMALIZATION pass those precedents don't have — reusing one
   wholesale would have wrongly treated `SUM(x) AS a` and `SUM(x) AS b`,
   or `l_returnflag` and `lineitem.l_returnflag`, as different keys.
   `recognize(plan)` matches `Project(Aggregate(Scan))` — exactly what
   `Binder::bind_select` produces unmodified for a plain single-table
   GROUP BY query, confirmed by reading `bind_select`'s own construction,
   not guessed — and is the SAME function used both for registration-time
   validation (`require_rollup_defining_shape`, which turns a non-match
   into a descriptive `Err`) and match-time recognition (inside
   `substitute`), so the shape a rollup is defined from and the shape an
   incoming query is judged against can never silently diverge.

3. **Matching against the RAW BOUND plan, before `Optimizer::optimize()`
   runs — not after.** This was a live design choice, not the only
   option considered: several optimizer rules (`GroupKeyReduction`,
   `PackedGroupKeys`, `EagerAggregation`, `ProjectionPushdown`) rewrite an
   `AggregateNode`'s own `group_by`/`aggregates` fields or push work into
   the `Scan`, any of which could make two EQUIVALENT queries' optimized
   shapes diverge (or two DIFFERENT queries' optimized shapes coincide)
   for reasons unrelated to whether a rollup answers them correctly.
   Matching pre-optimizer sidesteps that coupling entirely.

4. **Order-independence and aliasing — decided explicitly, not left
   implicit** (the acceptance criterion's own named risk): GROUP BY and
   aggregate SETs are compared via SORTED-MULTISET equality (`GROUP BY
   a, b` matches `GROUP BY b, a`; element COUNT still matters, so
   nothing is silently collapsed the way a true `HashSet` would).
   Aliases never affect matching (canonicalization strips them before
   comparison) but the SUBSTITUTED plan's output always uses the
   INCOMING query's own alias names, verified directly by
   `aliasing_does_not_affect_matching` asserting the OUTPUT schema field
   names. Table qualification is stripped too (`l_returnflag` /
   `lineitem.l_returnflag` / an alias like `l.l_returnflag` all
   canonicalize identically) — safe ONLY because `recognize` structurally
   guarantees exactly one `Scan` is ever in play (no JOIN support this
   task). The requested aggregate SET must match EXACTLY, not be a
   subset in either direction (a query wanting only `SUM(x)` does not
   match a rollup storing `SUM(x), COUNT(*)`, and vice versa) — a
   genuinely different design choice from allowing the OUTER PROJECTION
   to expose only some of the `Aggregate`'s own GROUP BY/aggregate
   columns, which IS supported (`a_query_projecting_only_some_of_the_
   rollups_columns_still_matches`): the SET-equality check is against
   the `Aggregate` node's OWN fields, independent of what the `Project`
   on top happens to expose.

5. **Where this plugs in — confirmed NOT an `OptimizerRule`, exactly per
   the epic's own architecture decision, with the reasoning re-derived
   and confirmed against the actual trait definition** (`src/optimizer/
   mod.rs`: `fn optimize(&self, plan: &LogicalPlan) -> Result<LogicalPlan>`,
   no registry parameter, confirmed by reading it, not assumed).
   `ExecutionContext` (`src/execution/context.rs`) owns two new private
   methods: `rollup_candidates(&self) -> Vec<native_rollup::RollupCandidate>`
   (builds a snapshot from `self.tables`, the ONLY place real registry
   access exists, EXCLUDING any rollup whose recorded
   `(base_table_id, base_table_version)` no longer matches the base
   table's CURRENT manifest — this IS the staleness enforcement) and
   `substitute_rollups(&self, plan) -> Result<(LogicalPlan, Vec<String>)>`
   (calls `native_rollup::substitute`, structurally a no-op — no plan
   tree walk at all — when `rollup_candidates()` is empty). Wired into
   `sql()` and `optimized_plan()` immediately after `Binder::bind()`,
   BEFORE `Optimizer::optimize()`.

6. **Substitution mechanics** (`native_rollup::substitute`): a
   `VectorSearchPushdown`-style recursive walk (`src/optimizer/rules/
   vector_search.rs` read in full as the closest precedent, per the task
   spec — its mechanics reused, not its "hard-coded shape within the
   same plan" limitation, since this task's shape is compared against an
   EXTERNALLY REGISTERED definition instead) — try a match at the
   current node; on a hit, replace the WHOLE matched subtree with
   `Project(Scan(rollup_table))` (reshaped so the output schema is
   BIT-FOR-BIT identical to what the unsubstituted plan would have
   produced — verified directly by
   `substitute_matches_and_reshapes_to_a_rollup_scan`); on a miss,
   recurse into every child unchanged. This means `ORDER BY`/`LIMIT`/
   `DISTINCT`/`UNION` wrapping a matchable aggregate all keep working for
   free (`substitute_recurses_through_a_wrapping_sort` proves this
   directly), with one honest, explicitly documented limitation: a
   subquery embedded inside an `Expr` (e.g. correlated `EXISTS` in a
   WHERE clause) is never visited, since `LogicalPlan::children()` does
   not expose plans `Expr::ScalarSubquery`/`Exists`/`InSubquery` carry
   internally — named in both the module doc and CLAUDE.md, not silently
   dropped.

7. **Registration** (`ExecutionContext::register_rollup(name: impl
   Into<String>, base_table: impl Into<String>, defining_sql: &str) ->
   Result<RegisterRollupResult>`, `&mut self`, async — the exact
   signature chosen, matching the task spec's own suggested shape). The
   base table MUST already be a registered NATIVE table (a plain
   parquet/Iceberg/Lance base table is refused with a clear error) —
   this is a real, deliberate scope decision: staleness bookkeeping needs
   a real `(table_id, version)` pair to compare against, which only a
   native table's manifest provides. Reuses `create_table_as_select`'s
   own bind/optimize/physical-plan/stream/write pipeline (deliberately
   NOT refactored into a shared helper under this task's time budget —
   matches this codebase's own existing precedent of CTAS/INSERT/DELETE/
   UPDATE each being independently self-contained rather than sharing a
   framework) to write the rollup as an ordinary native table via
   `native_write::write_batches`, completely UNCHANGED (a rollup's row
   data IS a native table, confirmed not just asserted — the write path
   received zero code changes). `RollupMeta` is then attached via a
   SECOND, small, manifest-only atomic patch
   (`native_manifest::write_manifest_atomic`, the mutation epic's own
   single-file atomic-rename primitive, reused unchanged) rather than
   inventing a new write mechanism.

8. **Provenance** (G3 / PRD G5): `QueryMetrics::rollup_answered:
   Vec<String>` — the structured, programmatically-checkable record
   (every integration test asserts on it directly, never infers it from
   timing or side effects). `QE_DEBUG_ROLLUP=1` additionally traces every
   match/no-match/staleness decision to stderr, matching this codebase's
   established diagnostic-switch convention (`QE_DEBUG_SCAN_BUDGET`,
   `PLAN_DEBUG`, etc.).

### Cell-exact validation, exact results

**Rust-level integration** (`tests/native_rollup_tests.rs`, 15 tests,
`data/tpch-1mb`'s `lineitem`, real end-to-end SQL path — `ExecutionContext
::sql`/`register_rollup`, not internal functions):
- Core proof: the PRD's own worked example (`lineitem` grouped by
  `l_returnflag`/`l_linestatus`, `SUM(l_quantity)`, `SUM(l_extendedprice)`,
  `COUNT(*)`) answered by the rollup (provenance confirmed), cell-exact
  (byte-identical rendered output) vs. an independent context that never
  registered any rollup.
- Order-independence (`GROUP BY l_linestatus, l_returnflag` matches a
  rollup defined `GROUP BY l_returnflag, l_linestatus`); alias-blindness
  (different aliases still match; output names reflect the query's own
  aliases); subset-projection (grouping by both columns, full aggregate
  set, but projecting only one column still matches).
- THREE explicit non-matching-shape tests, each asserting the FALLBACK
  ANSWER is cell-exact vs. direct computation (not just "doesn't
  crash," per the acceptance criterion's own explicit wording): a
  different GROUP BY set (`GROUP BY l_returnflag` alone), an added
  `WHERE l_quantity > 25` filter, and a different aggregate (`AVG`
  instead of `SUM`/`COUNT`). Plus a different-base-table case.
- Staleness: a real `DELETE FROM lineitem_native WHERE l_orderkey = 1`
  against the base table (which actually removes rows and bumps its
  `snapshot.version`) makes the SAME previously-matching query stop
  matching (`rollup_answered` empty) and produces a fallback answer
  verified cell-exact against an INDEPENDENTLY mutated reference context
  (same source, same delete, no rollup involved at all) — and is
  confirmed to actually DIFFER from the pre-mutation answer, so the test
  is provably exercising a real data change, not a no-op.
- 5 `register_rollup` validation/error-path tests (unregistered base
  table, non-native base table, a WHERE clause in the defining query, a
  computed projection in the defining query, a base-table mismatch).

**Independent DuckDB oracle, real scale**
(`examples/native_rollup_cell_exact_check.rs` +
`scripts/native_rollup_cell_exact_check.py`): `data/tpch-1gb`'s
`lineitem`, 6,000,000 rows (real SF=1 scale, not the small `tpch-1mb`
fixture). The QUERY run against the engine deliberately differs from the
rollup's own DEFINING query in THREE independent ways at once (reversed
GROUP BY order, different aliases, reordered SELECT list) specifically
to exercise order-independence and alias-blindness at real scale, not
just in the smaller unit-level fixture. Provenance
(`rollup_answered == ["lineitem_rollup"]`) is asserted BY THE EXAMPLE
ITSELF before the result is trusted — a hard `assert!`, not a comment.
DuckDB independently recomputes the identical query directly against
`data/tpch-1gb/lineitem.parquet` and compares every group cell-by-cell.
**Result: PASS, 6/6 groups, 6 columns**, using this repo's own
PRE-EXISTING float-SUM comparison tolerance
(`scripts/native_bench_compare.py`'s `cell_compare`:
`tol = max(0.02, |v| * 1e-9)`). Worth stating plainly: a first pass at
the comparator used a flat `ROUND(x, 6)` and reported spurious
mismatches (e.g. `50454135251.76243` vs `50454135251.76236` — an
absolute difference of `7e-5` on a `~5e10` magnitude, i.e. ~`1.4e-15`
relative) — this is float64-summation-order noise from `SUM` over
~1,000,000 rows (this engine's own morsel/parallel accumulation order
differs from DuckDB's internal reduction order), the EXACT class of
noise this repo's own `cell_compare` tolerance already exists to absorb,
NOT a rollup-specific bug or a masked correctness issue — the observed
differences (`~1e-4` absolute) are four-plus orders of magnitude below
the applied tolerance floor (`~50` at this magnitude), so the tolerance
is not masking anything real.
