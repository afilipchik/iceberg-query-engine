# Task: SQL DDL surface — CREATE MATERIALIZED VIEW

## Description

Only starts if task 001 reached a real, working substitution mechanism
(its own explicit confidence gate). Wire `CREATE MATERIALIZED VIEW
<name> AS SELECT ...` to task 001's programmatic registration API.
Per the research, this needs **zero sqlparser grammar work** — at the
pinned sqlparser 0.62, `Statement::CreateView { materialized: true,
query: Box<Query>, .. }` already parses this natively, and
`Statement::CreateView` is currently completely unhandled in
`binder.rs` (falls to the generic `NotImplemented` catch-all). This is
purely a binder + execution-entrypoint task, mirroring a pattern this
codebase has already proven twice (`Statement::CreateTable`,
`Statement::Insert`).

## Acceptance Criteria

- [x] `Statement::CreateView` arm added to `Binder::bind()`
      (`src/planner/binder.rs`), mirroring `Statement::CreateTable`'s
      existing shape: a `require_supported_create_view_shape(cv)`-style
      check that refuses unsupported `CreateView` fields BY NAME
      (`or_replace`, `secure`, `cluster_by`, `to`, etc. — enumerate
      what sqlparser 0.62's `CreateView` struct actually carries and
      refuse each non-trivial one explicitly, don't silently ignore),
      requires `materialized == true` (a non-materialized `CREATE VIEW`
      is out of scope — refuse it by name, don't silently treat it as
      one), requires `query`, then binds it like `CreateTable` does.
- [x] `sql()`'s existing DDL/DML refusal-and-redirect pattern
      (`src/execution/context.rs`, the checks before `Binder`
      construction that redirect CREATE TABLE/INSERT/DELETE/UPDATE to
      their own `&mut self` entrypoints) gets a fifth case for
      `CREATE MATERIALIZED VIEW`, redirecting to a new dedicated
      entrypoint (`create_materialized_view` or equivalent) that calls
      task 001's registration API.
- [x] `IF NOT EXISTS` handled sensibly (sqlparser's `CreateView` carries
      `if_not_exists` — decide and document the behavior: error,
      no-op, or replace; don't leave it silently unhandled).
- [x] End-to-end: `CREATE MATERIALIZED VIEW r AS SELECT ...` through the
      normal SQL entrypoint (HTTP `/sql`, REPL, and CLI if applicable)
      populates the rollup and makes subsequent matching queries
      transparently answered from it — cell-exact, reusing task 001's
      own validated matching mechanism unchanged.
- [x] Reasonable error messages on malformed/unsupported shapes (mirror
      `CreateTable`'s existing error style — name the exact unsupported
      clause, don't just say "not supported").
- [x] Full suite green; `cargo fmt --all -- --check` clean.

### What works, concretely

```sql
CREATE MATERIALIZED VIEW lineitem_rollup AS
  SELECT l_returnflag, l_linestatus,
         SUM(l_quantity) AS sum_qty,
         SUM(l_extendedprice) AS sum_base_price,
         COUNT(*) AS count_order
  FROM lineitem_native
  GROUP BY l_returnflag, l_linestatus;
```
via `ExecutionContext::create_materialized_view(sql)` populates the
rollup; a subsequent, differently-shaped query (different GROUP BY
order, different aliases) through the ORDINARY `ExecutionContext::sql()`
path — the exact method the distributed HTTP `/sql` endpoint and the
REPL's own catch-all both call — is transparently answered from it,
provenance-confirmed (`metrics.rollup_answered == ["lineitem_rollup"]`)
and cell-exact vs. an independent context that never ran the DDL.

### Design decisions, with exact code pointers

1. **`Binder::bind()` gains a `Statement::CreateView` arm**
   (`src/planner/binder.rs`), placed immediately after `CreateTable`'s
   own arm and built to the identical shape: validate, then
   `self.bind_query(&cv.query)`. `require_supported_create_view_shape`
   mechanically enumerates and refuses, BY NAME, every one of sqlparser
   0.62's real 17 `CreateView` fields this epic does not implement
   (re-read directly from the vendored
   `sqlparser-0.62.0/src/ast/ddl.rs`, not a paraphrase) — `or_alter`,
   `or_replace`, `secure`, `columns` (explicit view column list),
   `options`, `cluster_by`, `comment`, `with_no_schema_binding`,
   `if_not_exists`, `temporary`, `copy_grants`, `to`, `params`. Only
   `name` and `query` are consumed. `materialized` is checked
   separately, directly in the `bind()` arm rather than inside the
   shape validator, because its required value is the OPPOSITE sense of
   every other field (all must be OFF; `materialized` must be ON) — a
   plain `CREATE VIEW` gets its own, differently-worded refusal ("out of
   scope entirely," not "a clause not yet supported"). Confirmed by
   reading the vendored struct directly: `CreateView.query` is a plain,
   always-present `Box<Query>` (unlike `CreateTable.query`'s
   `Option<Box<Query>>`), so "requires query" from the acceptance
   criteria is met structurally — there is no missing-query case to
   check, documented as such rather than adding a dead/unreachable
   check. `name_before_not_exists` (a pure SQLite syntax/span marker
   for which side of the name `IF NOT EXISTS` appeared on) is
   deliberately not checked, mirroring `require_supported_insert_shape`'s
   own established treatment of pure syntax markers — moot regardless,
   since `if_not_exists` itself is refused.

2. **`IF NOT EXISTS` — decided explicitly: ERROR**, matching `CREATE
   TABLE`'s own `ct.if_not_exists` precedent exactly, for the identical
   reason: honoring the real semantics (skip silently if a rollup of
   this name already exists) would require detecting an existing rollup
   and NOT replacing it, but `register_rollup` always
   recomputes/replaces wholesale — accepting the flag and ignoring it
   would silently change what the statement means rather than doing
   what it says. Not left unhandled, not silently no-op'd.

3. **`sql()`'s fifth DDL/DML redirect case** (`src/execution/context.rs`):
   mirrors the CREATE TABLE/INSERT/DELETE/UPDATE guards' exact shape,
   redirecting to `create_materialized_view`. One deliberate asymmetry
   from the other four guards, decided and documented: a PLAIN
   (non-materialized) `CREATE VIEW` is NOT caught by this guard — there
   is no dedicated entrypoint to redirect it to, since it is genuinely
   out of scope rather than "supported but needs `&mut self`" — so it
   falls through to the ordinary bind/plan/execute path and is refused
   there, directly, by `Binder::bind()`'s own arm. This mirrors
   `Statement::Delete`/`Statement::Update`'s own established precedent
   of letting `bind()`'s unconditional refusal fire for shapes with no
   alternate entrypoint, rather than adding a second, indirect hop
   through a guard that would just point at an entrypoint that itself
   immediately re-refuses.

4. **`ExecutionContext::create_materialized_view(&mut self, sql: &str)
   -> Result<RegisterRollupResult>`** (new, placed immediately after
   `register_rollup` in `context.rs`): parses the SQL, extracts the
   rollup's target name via a new `create_materialized_view_target_name`
   binder-level extractor (mirrors `create_table_target_name`'s
   "extraction is separate from validation" split exactly — and
   deliberately returns `None` for a non-materialized `CREATE VIEW`,
   mirroring `insert_target_name`'s own treatment of
   `TableObject::TableFunction`, a shape with no dedicated entrypoint),
   then calls `Binder::bind(&stmt)` (validates the CreateView shape AND
   binds the inner query in one call, exactly like `create_table_as_
   select` does for `CreateTable`). The resulting bound `LogicalPlan` is
   used for exactly one further thing: recovering the defining query's
   base table name via `native_rollup::recognize` — task 001's OWN
   recognition function, reused completely unchanged, called from a NEW
   call site. This was a deliberate design choice over a hand-rolled
   AST-level "find the FROM table" walk: `register_rollup`'s signature
   requires a `base_table: impl Into<String>` argument supplied
   up-front (it looks the table up BEFORE parsing `defining_sql` itself),
   so this layer needs a name from somewhere — using the SAME
   recognition function `register_rollup` will independently re-derive
   from `defining_sql` guarantees the two can never disagree about which
   table a rollup is defined against, and means an ill-shaped defining
   query (a JOIN, a WHERE clause, an aliased FROM) is caught HERE, with
   a clear message describing the required shape, before ever reaching
   `register_rollup`'s own re-parse. `defining_sql` is `cv.query.to_
   string()` (sqlparser's own `Display` impl on the parsed inner query,
   confirmed correct end to end by the passing test suite, including
   for `COUNT(*)` and multi-aggregate SELECT lists). This method never
   itself touches the plan/execute/write pipeline — `register_rollup`
   does all of that, unchanged, exactly per this task's "purely a DDL
   front end" scope.

5. **REPL wiring** (`src/main.rs`): a new dispatch arm in `run_repl`'s
   statement-routing match, placed before the catch-all `sql()` arm,
   mirroring CREATE TABLE/INSERT/DELETE/UPDATE's identical existing
   pattern exactly (parse once, route on
   `create_materialized_view_target_name(&stmt).is_some()`, call the
   dedicated entrypoint, print a result summary). A plain `CREATE VIEW`
   does not match this arm and falls through to the REPL's own
   catch-all `ctx.sql(line)` call, which reports `Binder::bind()`'s
   refusal — same behavior as the direct `ExecutionContext::sql()` path,
   confirmed by inspection (both routes end at the identical `bind()`
   arm).

6. **"HTTP `/sql`, REPL/CLI — check whether they share the `sql()`
   path" (the task's own explicit instruction) — checked, with a
   concrete finding**: `src/distributed/server.rs`'s `execute_statement`
   (the function both the HTTP `/sql` handler and the Arrow Flight
   `DoGet`/`GetFlightInfo` paths call) invokes `ctx.sql(&statement)`
   directly — confirmed by reading it, not assumed. This means CREATE
   MATERIALIZED VIEW's REGISTRATION step is **NOT reachable through HTTP
   `/sql` or Flight**, exactly mirroring CTAS/INSERT/DELETE/UPDATE's own
   pre-existing, already-documented boundary (CLAUDE.md's Native Tables
   section states this plainly for CTAS already) — only the SUBSEQUENT
   MATCHING/answering step runs through the real, shared `sql()` path.
   The REPL has its OWN dedicated dispatch for registration (item 5
   above), matching the other four DDL/DML statements' identical,
   already-shipped pattern; there is no other CLI subcommand that runs
   arbitrary DDL text (confirmed by grepping every `create_table_as_
   select`/`insert_into_native_table`/etc. call site in `main.rs` — all
   four, and now this fifth, are used ONLY in the REPL loop). This
   finding is reported here explicitly, not silently discovered and
   left unstated, per the task's own instruction to check and report.
