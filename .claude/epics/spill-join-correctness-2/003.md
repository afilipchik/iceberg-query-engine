# Task: Fault-injection/differential testing harness

## Description

The prior `spill-join-correctness` epic's own manual repro loop cost
140-291s/trial (pre-fix) or 3-6s/trial (post-fix) and its own "best
remaining hypotheses" list named a downsized synthetic repro as the
single highest-leverage unattempted next step. This task builds that
capability for real, as a reusable, permanent tool: force a spill at
chosen points during build/probe, and differentially compare the result
against a non-spilling reference execution of the identical query
(row-count and/or checksum invariants) — cheap enough to run hundreds of
trials, not tens.

Independent of task 001's outcome — build this regardless, and use it in
task 001 if task 001 hasn't already reached a verdict by the time this
lands (check task 001's status/coordinate rather than assuming strict
ordering).

### Mechanism

Two new, orthogonal, env-gated hooks in
`src/physical/operators/spillable.rs`, matching this file's own
`QE_SPILL_DEBUG` convention and informed by (but not copying) the
archived epic's `QE_SPILL_CHAOS_FORCE_ABORT` precedent — that mechanism
forced a specific abort/re-execution path; these target the spill/unspill
boundary generally, at two independently choosable points:

1. **`QE_SPILL_CHAOS_FORCE_SPILL` (WHEN)** — forces
   `compute_build_decision`'s build/no-build decision to cross into
   `BuildDecision::Spill` after a CHOSEN number of build batches
   (0 = the very first batch), regardless of `memory_limit`/
   `spill_threshold` or how much data is actually present. A genuine gap
   surfaced and fixed while wiring this up: for a build side small enough
   to arrive as a single Arrow batch (the common case for this harness's
   own small fixtures), a requested crossing point beyond that one batch
   could never be reached mid-stream, silently falling through to
   "fits in memory" — fixed with an end-of-stream fallback (new
   `finish_via_spill`, factored out of the crossing-branch logic so both
   sites share one copy of the INNER-only/no-filter guard and
   spill-directory setup) that forces the crossing at the end of the
   stream instead of silently no-op'ing.
2. **`QE_SPILL_CHAOS_FORCE_SPILL_PARTITIONS` (WHICH)** — forces specific
   hash partitions (`"all"`, or a comma-separated list of indices) to
   write their resident batches to disk in `build_with_partitioning` the
   moment they receive their first one, regardless of memory pressure —
   the lever that guarantees a REAL write+read-back round trip for chosen
   rows, even for a handful of rows that would otherwise trivially fit in
   memory end to end. Refactored the pre-existing inline
   largest-partition eviction into a shared `evict_build_partition_to_disk`
   so the organic (memory-pressure) and forced (chaos) code paths write
   spill files through byte-identical logic. Because probe-side spill
   routing (`probe_with_spilling`) already decides purely from whether a
   batch's build partition spilled, forcing build-side partitions here
   also forces the PROBE-side disk round trip (through
   `process_spilled_partition`) for the same partitions — one lever
   covers both build AND probe, per the acceptance criterion's own
   wording.

Both are pure env-var reads (`parse_chaos_force_spill_after_batches`/
`ChaosPartitionSpec::parse` factored out as pure functions, unit-tested
directly rather than via `std::env::set_var` — see "Process note"),
checked fresh per call, zero cost and zero behavior change unless a
caller explicitly sets them — never a default-on change, per the task's
own explicit constraint.

### Reusable harness: `examples/spill_chaos_harness.rs`

Permanent (not `.scratch/`), matching `examples/spill_join_oom_repro.rs`'s
own precedent. Each trial: registers `data/tpch-10mb` (or
`QE_CHAOS_DATA_DIR`) once in one shared `ExecutionContext`, then runs ONE
of 3 unaggregated INNER-join queries (raw join output, so a row-level
corruption is directly visible, not masked by aggregation) twice — once
with no chaos vars (baseline) and once with a randomly chosen `WHEN`
(0-2 batches) and `WHICH` (10% decision-only / 40% all-partitions / 50%
random subset) injection. `QE_CHAOS_TRIALS`/`QE_CHAOS_SEED`/
`QE_CHAOS_DATA_DIR` control scale, determinism, and fixture.

**Differential invariant**: an order-independent XOR checksum (rows,
u64 hash) over every output row's every column — modeled directly on
task 001's own `KeyChecksum`/`batch_key_checksum` (same order- and
batch-split-independence reasoning, applied to whole output rows instead
of just join keys) — rather than the stronger but O(rows log rows)
sort-and-compare `tests/spill_tests.rs` itself uses. Chosen specifically
for per-trial cheapness at "hundreds, not tens" of trials; documented in
the harness's own module doc comment. A before/after delta on
`ExecutionContext::memory_pool().spilled()` (not
`QueryResult::metrics.spill_metrics`, which is cumulative over the
context's whole lifetime and would misreport once ANY earlier trial had
spilled — a real bug caught and fixed while building this, see below)
confirms every `all`/`subset` trial genuinely touched disk, not just
that the decision code path was taken.

### Process note: a real concurrency bug in this task's own work, caught and fixed

An earlier version of this task's own work-in-progress added a
`#[tokio::test]` to `spillable.rs`'s existing test module that called
`std::env::set_var("QE_SPILL_CHAOS_FORCE_SPILL"/"_PARTITIONS", ...)`
directly, guarded by a local `Mutex` around its own set/unset section.
Running the FULL default-feature test suite (not just this module in
isolation) surfaced a genuine failure: `cargo test`'s default concurrent-
test-thread execution ran a pre-existing, otherwise-untouched LEFT JOIN
test
(`spillable_hash_join_retained_mask_matches_delegate_schema`) WHILE this
new test held `QE_SPILL_CHAOS_FORCE_SPILL` set, forcing that unrelated
LEFT JOIN's `execute()` into the disk-spill branch's INNER-only guard and
panicking it. A local mutex only serializes against OTHER tests that also
acquire IT — it does nothing for the hundreds of unrelated tests in the
same shared binary that don't know it exists. This is a real, observed
instance of exactly the hazard this codebase's own pre-existing comments
already document (`gpu.rs`'s `parse_cache_budget_mb`,
`execution::context::parse_merge_concurrency`: "a test that called
`std::env::set_var` here would race every other test reading the same
key"). Fixed by removing that test entirely and relying on (a) pure
parsing unit tests for the env-var-reading logic (no environment
mutation, matching the established convention exactly) and (b) the
standalone `spill_chaos_harness.rs` binary — a SEPARATE PROCESS, so no
shared-binary race is possible — for the actual end-to-end "forced spill
matches unforced" verification, at far greater trial volume than any
single unit test would exercise anyway. Confirmed fixed: the full default
suite (and this module's own tests in isolation) ran clean 4 times in a
row after the fix, including the run whose numbers are in the table
above.
