# Task: Fix the collect-fully-then-decide OOM hole

## Description

`SpillableHashJoinExec::execute` (`src/physical/operators/spillable.rs`)
collects the ENTIRE build side into memory via
`collect_input_partitions_concurrently`, THEN compares against
`memory_limit * spill_threshold` to decide whether to spill — a
documented hole where an oversized build side can OOM before the spill
decision ever runs. This is independent of task 001's investigation and
does not need to wait on its outcome.

## Acceptance Criteria

- [ ] Replace collect-fully-then-decide with streaming/incremental size
      tracking that can trigger the spill decision before the whole
      build side is memory-resident. Photon's documented two-phase
      reservation pattern (reserve/possibly-spill, then a
      guaranteed-spill-free allocation phase — see the research synthesis
      §2.6) is the reference design; adapt it to fit this engine's actual
      structure rather than porting it literally.
- [ ] Real, verified fix: construct a build side that would have OOM'd
      under the old behavior (oversized relative to a real memory limit)
      and confirm it now spills cleanly instead, under a real cgroup
      memory cap (matching this program's own "verified with a real
      `kill`/cgroup test" discipline elsewhere).
- [ ] No new unbounded-memory path introduced by the fix itself (the
      streaming size-tracking mechanism must itself be bounded).
- [ ] Cell-exact correctness unchanged — this is a memory-accounting
      change, not a computation change; validate against the existing
      spill-path correctness tests plus a fresh cell-exact run.
- [ ] No regression to the O(n²) slowness fix already shipped or to any
      other spill-path test.
- [ ] Full suite green; `cargo fmt --all -- --check` clean.

## Technical Details

Sole file: `src/physical/operators/spillable.rs`. Read
`collect_input_partitions_concurrently` and the spill-threshold check
that currently runs after it, in full, before designing the fix.
