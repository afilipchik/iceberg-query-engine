# Task: Fix the collect-fully-then-decide OOM hole

## Description

`SpillableHashJoinExec::execute` (`src/physical/operators/spillable.rs`)
collects the ENTIRE build side into memory via
`collect_input_partitions_concurrently`, THEN compares against
`memory_limit * spill_threshold` to decide whether to spill — a
documented hole where an oversized build side can OOM before the spill
decision ever runs. This is independent of task 001's investigation and
does not need to wait on its outcome.

## Acceptance Criteria

- [x] Replace collect-fully-then-decide with streaming/incremental size
      tracking that can trigger the spill decision before the whole
      build side is memory-resident. Photon's documented two-phase
      reservation pattern (reserve/possibly-spill, then a
      guaranteed-spill-free allocation phase — see the research synthesis
      §2.6) is the reference design; adapt it to fit this engine's actual

## Outcome (closed 2026-08-27)

### Root cause (confirmed by reading `SpillableHashJoinExec::execute` directly)

The build-decision `OnceCell` closure called
`collect_input_partitions_concurrently(build_side)` unconditionally as its
first step — draining every build-side input partition (via one spawned
task each, for cross-core parallelism) fully into one flat
`Vec<RecordBatch>` — and only THEN computed
`build_size > memory_limit * spill_threshold` to decide whether to spill.
This is independent of the eventual decision: an oversized non-INNER join
(which the spill path cannot handle and would error on anyway) paid the
exact same full-collection cost before ever reaching that check. Any build
side larger than the process's REAL available memory could exhaust it
during this initial collection, regardless of how the `memory_limit`
config was set — the configured budget was never consulted until
collection had already finished.

### Fix

Photon's (Databricks, SIGMOD'22) two-phase reservation pattern, adapted
rather than ported literally:

1. **New `stream_merge_input_partitions`** (module-level function): the
   streaming analog of `collect_input_partitions_concurrently` — same
   one-task-per-input-partition producer parallelism (preserves the
   original function's own documented cross-core benefit for a pipeline-
   breaking operator's collect side), but instead of collecting into a
   `Vec`, batches flow through a small, FIXED-capacity
   `tokio::sync::mpsc` channel (`PER_PARTITION_CAPACITY * input_partitions`,
   a constant per producer partition) wrapped as a `RecordBatchStream` via
   `tokio_stream::wrappers::ReceiverStream`. This is the mechanism that
   keeps the fix itself bounded, per the task's own "no new subtler
   unbounded-memory path" constraint.
2. **New `SpillableHashJoinExec::compute_build_decision`** (replaces the
   inline `OnceCell` closure): phase 1 ("reserve, possibly spill") reads
   from that merged stream batch by batch, tracking a running flat size
   total and checking it against `memory_threshold` on EVERY batch — not
   once, after a full collection. If the whole build side is consumed
   without ever crossing the threshold, this is the ordinary "fits in
   memory" case, reached at identical cost to before (same total bytes
   ever touched, just checked incrementally instead of after the fact) —
   still builds the same in-memory `HashJoinExec` delegate. The MOMENT the
   running total would cross the threshold (phase 2, "guaranteed-spill-
   free allocation" becomes "hand off to the bounded, spill-capable
   structure"): everything collected in phase 1, plus the crossing batch,
   plus the rest of the stream (via `stream::iter(..).chain(build_stream)`)
   feeds into the EXISTING `build_with_partitioning` — the same hash-
   partition-and-spill-as-needed bookkeeping the rest of the spill path
   already used, just entered mid-stream instead of only after a full
   prior collection. Peak flat/unpartitioned memory is now bounded to
   ~`memory_threshold`, never the whole build side. The INNER-join-only /
   no-filter checks (previously at the top of `execute_spill_path`, so an
   oversized non-INNER join paid the full collection cost before erroring)
   moved to this exact crossing point — an oversized non-INNER join now
   fails just as loudly, but this much earlier, without needing the rest
   of the build side pulled in first.
3. **`BuildDecision::Spill`** now stores the ALREADY hash-partitioned
   `(partitions: Vec<Option<BuildPartition>>, spilled: Vec<Option<SpilledPartition>>,
   spill_dir: PathBuf)` — computed exactly once by the `OnceCell`, same
   memoization discipline as before — instead of a flat `build_batches:
   Vec<RecordBatch>` that `execute_spill_path` had to re-partition from
   scratch (writing fresh spill files) on every call. This is strictly
   better for steady-state memory too: only the partitions that never
   spilled stay resident; the rest live on disk, for as long as the
   operator itself is alive, rather than the OLD code's flat `Vec` (kept
   in the `OnceCell` for the operator's whole lifetime specifically to
   support a legitimate repeat execution — e.g. a fused-streaming
   aggregate aborting and re-executing its join child) retaining the
   WHOLE build side regardless of the spill decision.
4. **`execute_spill_path`** now takes borrowed
   `&[Option<BuildPartition>]`/`&[Option<SpilledPartition>]`/`&PathBuf`
   from the memoized decision instead of an owned, re-partitioned copy.
   Because build-side spill files are now REUSED (not recreated) across a
   possible repeat call, they are no longer deleted at the end of every
   call (`std::fs::remove_dir_all` used to run there) — a repeat call must
   still be able to read them back. Cleanup happens exactly once instead,
   via a new `impl Drop for SpillableHashJoinExec` that removes `spill_dir`
   when the operator itself is finally dropped. Probe-side spill info
   (`probe_file`/`probe_key_checksum`), which IS call-specific (each call
   re-probes and writes fresh probe spill files), is threaded through
   `execute_spill_path`/`process_spilled_partition` as separate per-call
   parameters instead of being stored on the now build-only
   `SpilledPartition` struct.

### Real, cgroup-verified OOM fix (not simulated)

New `examples/spill_join_oom_repro.rs`: builds a `SpillableHashJoinExec`
whose build (left) side is a LAZY, streaming synthetic generator
(`LazyGeneratorExec`) — nothing beyond the current batch is ever
materialized ahead of time, so the test genuinely measures
`SpillableHashJoinExec`'s own collection behavior, not a pre-built `Vec`
this example itself constructed — totaling ~3.1GB (3,200,000 rows x
~1024B padding), several times both `MEMORY_LIMIT` (500MB, so the join
MUST decide to spill) and the cgroup cap it's run under. Probe (right)
side: 4 tiny in-memory rows, 3 of which match real build-side keys (a
concrete, checkable `matched_rows == 3` assertion, not just "didn't
crash").

Run under a REAL `systemd-run --user --scope -p MemoryMax=900M
-p MemoryHigh=900M -p MemorySwapMax=0 -p ManagedOOMMemoryPressure=kill`
cap — the identical mechanism `scripts/claude-safe-build.sh` itself uses,
per this task's own "matching this program's own... discipline"
requirement:

- **Pre-fix** (`git stash push -- src/physical/operators/spillable.rs`,
  rebuilt, run twice): **2/2 trials genuinely OOM-killed by the kernel.**
  Exit code 137 (128+SIGKILL) both times; `journalctl --user` independently
  confirms the mechanism, not just the exit code: `"A process of this unit
  has been killed by the OOM killer"` / `"Failed with result 'oom-kill'"`.
  Both trials printed only the startup banner and nothing else — killed
  mid-collection, never reaching the spill decision, exactly the bug this
  task fixes.
- **Post-fix** (`git stash pop`, rebuilt, run twice): **2/2 trials complete
  cleanly.** `matched_rows=3 expected=3`, `RESULT: PASS`, peak RSS
  ~650-680MB (`VmHWM` from `/proc/self/status`) — comfortably under the
  900MB cap and far under the 3.1GB build side, exit 0,
  `journalctl` shows normal `Consumed N.NNNs CPU time` with no OOM
  message.
