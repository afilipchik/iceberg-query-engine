# Task: Streaming native-table scan into spilling consumers

## Description

`NativeTable::scan()` materializes every active segment; oversized
tables can only REFUSE (`check_scan_budget`). Add a streaming scan path
— mirroring the `ParquetTable::scan()` vs `StreamingParquetScanExec`
split — that reads segment-at-a-time via the existing
`ipc_cache::read_row_group` mmap reader and feeds spill-capable
consumers (aggregate, join), so a native-table query over budget
COMPLETES by spilling instead of refusing (PRD G2).

`check_scan_budget` stays as the guard for shapes that genuinely must
materialize (raw `SELECT *` dump into a `QueryResult`) — document that
boundary explicitly in CLAUDE.md's native-table Limitations section, do
not silently narrow it.

## Acceptance Criteria

- [ ] Harness scenario 3 (task 001) flips from clean refusal to clean

- [ ] Deletion-vector filtering (`filter_deleted_rows`) and segment

- [ ] Dense-direct-address fast path and GPU-offload eligibility
      unaffected for in-budget tables (their entry conditions unchanged)
- [ ] Raw-materialization refusal boundary documented, with a test
      pinning that `SELECT *` over an oversized table still refuses by
      name
- [ ] No regression to the recorded never-mutated native benchmark band

## Technical Details

- New physical operator (e.g. `NativeStreamingScanExec`) or a streaming
  `scan_stream()` on `NativeTable` wired in `src/physical/planner.rs`
  where spill-capable consumers are planned; per-segment work items give
  natural partitioning (58 segments for SF=10 lineitem).
- Per-batch deletion filtering must track the same running local-row
  offset `filter_deleted_rows` uses today.
- Touches `src/storage/native_table.rs` + `src/physical/planner.rs` —
  no overlap with spillable.rs tasks; safe to run parallel with 002/003.
