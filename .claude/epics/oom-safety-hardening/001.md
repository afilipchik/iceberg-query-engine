# Task: Adversarial cap harness + pre-fix evidence + 2026-08-28 root-cause

## Description

Build ONE reusable adversarial memory-cap harness (PRD G6) and run it
against CURRENT code to record failing pre-fix evidence for every gap
this epic fixes; separately, root-cause what actually drove the
2026-08-28 107.2G spike (PRD G4) rather than assuming it was one of the
named gaps.

The harness mirrors `examples/spill_join_oom_repro.rs`'s established
pattern (real `systemd-run --user --scope -p MemoryMax=<N>` cap, exit
code + `journalctl -k` verification) and ADDS the second lever that now
exists: `QE_MEM_CAP=<N>` (in-binary `RLIMIT_DATA`, engine abort exit
134). A scenario passes only if the engine completes or refuses cleanly
under BOTH levers.

Battery (one scenario per gap):
1. Large `GROUP BY` aggregate over parquet (SpillableHashAggregateExec
   collect-then-decide) — expect pre-fix kernel kill / abort.
2. Large `ORDER BY` (ExternalSortExec collect-then-decide) — same.
3. Native-table scan over `check_scan_budget` feeding an aggregate —
   expect pre-fix clean refusal (documents today's boundary; post-fix
   this must COMPLETE by spilling).
4. Large `INSERT`/CTAS at a 512MB-class cap — expect pre-fix SIGKILL
   (the documented residual from native-tables-mutation task 005).

Root-cause side: reconstruct the 2026-08-28 incident (journalctl scope
kill record, what command was running, which operator path). Reproduce
if possible under a cap; name the responsible path. If it is a fourth,
undocumented gap, add a task to this epic rather than absorbing it
silently.

**PRIORITY LEAD (handed off from `spill-size-estimate-fix` task 001,
2026-08-29 — read its Outcome section in full first):** a confirmed,
unexplained memory-accounting hole in `build_with_partitioning`/
`append_batch_streaming` (`spillable.rs`). Ready-made committed repros:
`examples/_control_int32_repro.rs` (plain Int32 build side, 500MB
configured limit, genuinely kernel-OOM-killed at ~3.1GB RSS under a 3G
cap — NOT Dictionary-related) and
`examples/spill_dictionary_oversized_build_repro.rs` (30MB limit, ~738MB
real committed peak, ~24x budget). Already ruled out: the estimate bug
(fixed), parquet writer row-group buffering (fixed, didn't move the
peak), `evict_build_partition_to_disk`, `partition_batch_by_hash`,
mimalloc retention (MIMALLOC_SHOW_STATS shows active purging). The
recommended next step is REAL memory profiling, not more
hypothesis-and-rebuild: use the in-tree diagnostic allocator
(`QE_ALLOC_PROFILE=1`, `src/execution/alloc_profile.rs` — built for
exactly this since heaptrack/valgrind aren't installable here) under
`QE_MEM_CAP` containment to get top call sites by live bytes at peak.
Finding this dominant driver IS the heart of this task — the harness
scenarios wrap around it.
