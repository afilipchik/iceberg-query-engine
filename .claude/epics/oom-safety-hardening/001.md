### 1. The accounting hole is ROOT-CAUSED and named (the PRIORITY LEAD)

**`SpillableHashJoinExec::execute_spill_path` builds per-partition
`HashMap<JoinKey, Vec<HashEntry>>` hash tables with ZERO memory
accounting, and their real footprint is ~10-20x the batch bytes the
spill decision budgeted.** Two unbudgeted call sites
(`src/physical/operators/spillable.rs`): the in-memory-partition table
loop at the top of `execute_spill_path` (~line 871) and
`process_spilled_partition`'s per-read-back-partition table (~line
1240, which also fully materializes each spilled partition via
`read_parquet` first). Per unique Int64 key the table costs ~120-200
bytes across THREE allocations (~56B amortized hashbrown entry holding
two 24B Vec headers, one ~32B heap alloc for the key's 1-element
`Vec<JoinValue>`, one ~16-32B heap alloc for the 1-element
`Vec<HashEntry>`), vs the ~12B/row of raw batch data that
`estimate_batch_size`/`total_memory` accounts. The budget bounds
BATCHES; the in-memory partitions are deliberately kept AT the budget,
so the table amplification lands entirely on top, unchecked.

Profiler evidence (the in-tree `QE_ALLOC_PROFILE=1` diagnostic
allocator, under `systemd-run` caps): the ONLY call site holding live
>=256KB allocations at every recorded peak of both repros is
`hashbrown reserve_rehash <- build_hash_table <- execute_spill_path`.
Dict repro (30MB budget): allocator peak 640.4MB / 737MB RSS — climbs
163->452MB during the in-memory table loop (2 partitions, 1.87M rows =
22.5MB of correctly-budgeted batches -> ~280MB+ of unbudgeted tables),
peaks during spilled-partition idx=0 processing, then plateaus.
Control repro (500MB budget, plain Int32 — Dictionary-free by
construction): killed at a 3G memcg cap with 1347.5MB tracked across
15 live hashbrown tables at that same site, mid-table-loop; under a
generous 24G scope it reached 7.3G before a pressure kill —
i.e. the mechanism needs ~15-24x the configured budget, plateauing at
(roughly) budget x table-amplification, not growing forever.

Already ruled out by the prior epic (not re-derived): estimate bug,
parquet-writer row-group buffering, `evict_build_partition_to_disk`,
`partition_batch_by_hash`, mimalloc retention. No fix attempted here —
the fix is real operator work (account the tables against the budget /
process partitions with bounded table memory) belonging to the epic's
fix tasks; this task's charter was to name the mechanism precisely.

**Prerequisite finding: the diagnostic profiler had NEVER actually run
enabled — it self-deadlocked at startup** (any binary with
`QE_ALLOC_PROFILE=1` hung pre-`main`: `enabled()`'s
`OnceLock::get_or_init` closure calls `env::var`, which heap-allocates
the returned value only when the var is PRESENT, recursing into the
still-initializing `OnceLock`). Fixed (tri-state `AtomicU8` that reads
"disabled" during its own env read), plus a second latent deadlock
(`record_dealloc` locking `live()` with no reentrancy guard — the live
map's own resize-free re-enters it). Both in
`src/execution/alloc_profile.rs`, validated by the profiled runs above.

Also corrected: `append_batch_streaming`'s doc comment falsely claimed
the row-count-flush fix made the control repro "complete cleanly" —
contradicted by `spill-size-estimate-fix` 001's own Outcome and by
re-runs; comment now records the correction and points at the real
root cause.

### 2. Harness built and run — pre-fix evidence recorded (PRD G6)

`examples/oom_cap_harness.rs` (4 scenarios; exit 0=completed, 2=clean
named refusal, 134=rlimit abort, 137=memcg kill; calls
`enforce_process_memory_cap()` first so `QE_MEM_CAP` works in an
example) + `scripts/oom_cap_harness.sh` (both levers, machine-readable
`RESULT scenario= lever= cap= exit= peak_rss_mb= verdict= reason=`
lines, journal kill evidence appended per log). Final battery
(`.scratch/oom001/harness_final*`):

| scenario | lever | cap | exit | peak RSS | verdict |
|---|---|---|---|---|---|
| agg (COUNT DISTINCT GROUP BY, 250M rows, 256MB limit) | cgroup | 1G | 137 | 1025MB | FAIL oom-sigkill |
| agg | rlimit | 1G+1G | 134 | 1974MB | FAIL abort-at-rlimit |
| sort (ORDER BY, 250M rows, 256MB limit) | cgroup | 1G | 137 | 1026MB | FAIL oom-sigkill |
| sort | rlimit | 1G+1G | 134 | 1975MB | FAIL abort-at-rlimit |
| native-scan (5.64GB table, 512MB limit) | cgroup | 2G | 2 | 27MB | PASS clean-refusal (exact bytes named) |
| native-scan | rlimit | 2G+1G | 2 | 27MB | PASS clean-refusal |
| insert (CTAS 60M-row lineitem) | cgroup | 512M | killed | <1s | FAIL oom-sigkill (journal-confirmed) |
| insert | rlimit | 512M+1G | 0 | 1683MB | completed (lever coarseness, see below) |

Scenario verdicts pre-fix: **agg FAIL, sort FAIL, insert FAIL,
native-scan clean-refusal** — exactly the PRD's predicted pre-fix
pattern; the agg/sort kills happen inside
`collect_input_partitions_concurrently` (the G1 hole), the insert kill
is the documented task-005 residual, and native-scan's refusal is
`check_scan_budget`'s boundary that G2 must convert into a spilling
completion. Bonus validation: with input sized UNDER the lever, all
scenarios complete CORRECTLY through their spill paths (agg 1,000,003
exact groups; sort 100M rows verified globally ordered; CTAS 60M rows,
1.68GB peak ≈ the documented 1.63GB bounded-merge figure).

**rlimit-lever caveat (measured, documented):** `RLIMIT_DATA` counts
virtual private-anon mappings at mmap time; mimalloc reserves its first
~1GiB arena pre-`main` (before the cap is applied) and in-arena
allocations add no mappings — so the lever needs +1024M startup
headroom and can under-enforce by up to ~an arena for workloads that
fit prior reservations (the CTAS run completed at 1683MB RSS under a
1536M cap). It reliably catches multi-GB fresh-mmap overshoots (both
agg/sort aborted 134). The cgroup lever remains authoritative; the
rlimit lever's value is the clean in-process abort failure mode.
