# Task: Budget the join spill path's hash-table memory

## Description

Task 001's investigation root-caused the handed-off accounting hole (and,
transitively, the 2026-08-28 incident's growth mechanism):
`SpillableHashJoinExec::execute_spill_path` builds per-partition
`HashMap<JoinKey, Vec<HashEntry>>` hash tables with ZERO memory
accounting, at ~10-20x the batch bytes the spill decision budgeted.
Two unbudgeted sites in `src/physical/operators/spillable.rs`:

1. the in-memory-partition table loop (~line 871), and
2. `process_spilled_partition`'s per-read-back table (~line 1240, built
   after a full `read_parquet` materialization).

Per unique Int64 key: ~56B amortized hashbrown entry + ~32B heap Vec for
the key's values + ~16-32B Vec for entries ≈ 120-200B/row vs the ~12B/row
`total_memory` accounts. Because the budget keeps in-memory partitions AT
the threshold, the amplification lands entirely on top: measured 640MB
allocator peak at a 30MB budget (dict repro) and ≥7.3GB at a 500MB budget
(control repro) — a plateau of ~15-24x budget.

Fix = make the spill decision and partition eviction account for the
REAL cost of the hash tables they imply (batch bytes × a measured/
derived table-amplification factor, or direct accounting of table bytes
as tables are built, evicting partitions when the running total —
including table overhead — crosses the budget). Prefer direct accounting
over a fudge factor; document whichever is chosen. Consider also whether
a denser build-side representation (the non-spill join's RowStore
pattern) is a small, safe borrow — but do NOT rewrite the join; this
task is accounting, not architecture.

**Hard boundary**: do NOT touch the partition-routing/probe correctness
logic (the open ~0.34% duplicate-counting bug is out of scope; any
insight gets documented and handed to its own tracking).

### Mechanism chosen: direct accounting of table bytes + partition eviction

All inside the SPILL path; the phase-1 InMemory/Spill crossing check and
all probe-routing/probe logic are untouched (hard boundary respected).

1. **Streaming build loop** (`build_with_partitioning`): each resident
   partition is charged `BuildPartition::charged_bytes` = batch bytes +
   `predicted_hash_table_bytes(rows, key_cols)` (documented constants:
   ~56B amortized hashbrown bucket + key-values Vec + entries Vec + 16B
   per-alloc overhead ≈ 136B/row for a 1-column key — the worst,
   all-unique-keys case, so duplicate-heavy inputs only ever spill MORE
   readily). Residency now settles where batches AND tables genuinely
   fit under `memory_limit * spill_threshold`, instead of batch bytes
   alone sitting AT the threshold with 10-20x amplification unbudgeted
   on top.
2. **Hash-table budgeting pass** (`budget_partition_hash_tables`, run
   before spill writers close): builds each surviving partition's table
   largest-first, measures its REAL footprint directly
   (`hash_table_memory_bytes`: real capacity, real per-key Vec buffers,
   real String bytes), and evicts via the existing
   `evict_build_partition_to_disk` whenever resident batches + measured
   tables would cross the same threshold. Tables are memoized in
   `BuildDecision::Spill { tables, .. }` — the bound holds for the
   operator's lifetime and `execute_spill_path`'s old zero-accounting
   rebuild loop (task 001's root-caused hole) is deleted.
3. **Chunked read-back** (`process_spilled_partition`): the per-spilled-
   partition table (001's second unbudgeted site) is now built in chunks
   of whole batches sized so the predicted table cost stays under the
   threshold, probing the full probe set per chunk and dropping each
   chunk's table before the next. INNER-only spill path ⇒ chunk union is
   exactly equivalent (build rows disjoint across chunks; each
   (build,probe) pair emitted once).

Documented residual constants on top of the threshold: one chunk table
(≤ threshold), one read-back partition's batches (~build_bytes/64), the
probe-side full collection in `execute_spill_path` (pre-existing; tasks
002/003's streaming-reservation scope), accumulated results, runtime
baseline (~30MB).
