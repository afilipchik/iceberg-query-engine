# Task: Partitioned VHT build+probe behind QE_RADIX

## Description

VectorizedHashTable gains a partitioned mode for large Inner-join builds
with single-i64/packed keys: build rows scattered by hash top-bits into
P sub-tables (each L2/LLC-share-resident), probe batches scattered the
same way, matches emitted through the existing (bb, br, probe_row)
contract so `create_joined_batch` and all consumers are untouched.
Opt-in via QE_RADIX=1 until 003 decides the default.

## Acceptance Criteria

- [ ] Partitioned build parallel across sub-tables; bounded scatter
      buffers (no second copy of build data beyond entry arrays)
- [ ] Probe: one hash pass per batch reused for both partition selection
      and in-table bucket; per-batch row-id scatter (u32), no key copies
- [ ] Gate: builds ≥ 4M rows, Inner, no join filter, single-i64 key;
      everything else takes the existing monolithic path
- [ ] Match-order invariants verified: joined batches remain correct if
      match order changes (probe-side identity fast path in
      create_joined_batch requires probe_indices in order — either emit
      in probe-row order or prove the consumers tolerate reorder)
- [ ] Cell-exact SF=10 (validate22) + full test suite green
- [ ] Q9 SF=100 A/B with QE_RADIX=0/1 recorded (HJ_TIMING)

## Technical Details

hash_join.rs + vectorized_hash.rs. The probe currently par_iters over
probe batches; partitioned probing can keep that shape (each batch:
compute hashes, bucket row-ids by partition, walk partitions). The
identity fast path concern: Q9's FK joins produce in-order probe
indices today — preserve by emitting matches grouped by probe row
(iterate rows, look up their partition's sub-table directly — i.e.
partition selection per row WITHOUT physical scatter may already get the
cache win if consecutive rows cluster; measure both variants in 001).
