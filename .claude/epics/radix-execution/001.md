# Task: Probe-cost microbenchmark + G1 verdict

## Description

Before touching any operator: measure, on this exact box, whether
radix-partitioned probing beats the monolithic chained-bucket VHT on
Q9's shape — 80M-entry build (packed i64 keys, ~2^45 range), 600M probe
keys, FK-ish match rate. The scatter pass costs ~2 extra streaming
passes over probe keys; the verdict must price that in.

## Verdict (2026-08-18) — G1 kill-switch FIRED for join probes

Numbers (80M build / 300M FK probes, examples/radix_bench.rs, this box):

| layout | 1-thread | 32-thread wall |
|---|---|---|
| monolithic (VHT mirror) | 27.0 ns/probe | **3.81 ns/probe** |
| radix P=64 | 30.6 (0.88x) | 4.04 (0.94x) |
| radix P=256 | 30.7 (0.88x) | 4.03 (0.95x) |
| radix P=1024 | 30.8 (0.88x) | 4.09 (0.93x) |

**Radix REFUTED on this box**: independent probes have no serial
dependency, so the OoO core sustains ~10 outstanding misses per core
(memory-level parallelism) and the monolithic table already probes at
~DRAM-random-bandwidth. The scatter can only add work. This also
explains why software prefetch measured neutral in the prior epic.

**The finding that matters**: the isolated probe costs 3.8 ns/row wall
while Q9's REAL probe partitions run 900-1500 ns/row. ~240x of the
in-engine cost is NOT the hash lookup — it is the surrounding pipeline
(probe-key expression eval, match Vec growth, filter, row-store/take
gather, joined-batch construction, allocator). Epic re-scoped: tasks
002/003 become fine-grained probe-phase attribution and the fix for
whatever it names. Task 004 (radix aggregation) is ALSO likely refuted
by the same MLP argument (scan+process already at ~3.5 ns/row) — it
will only proceed if 002's attribution says otherwise.
