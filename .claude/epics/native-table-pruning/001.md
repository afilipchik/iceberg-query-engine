# Task: Implement segment-level scan pruning

## Description

`NativeTable::scan_with_filter` (`src/storage/native_table.rs`) is not
overridden today — it's the `TableProvider` trait's default, which just
calls `scan(projection)` and ignores any filter entirely, so every query
decodes every active segment in full. Implement real pruning: evaluate a
pushed-down predicate against each active segment's `ColumnStats`
(min/max/null-count, `src/storage/native_manifest.rs`) and skip segments
that provably cannot match, before calling `ipc_cache::read_row_group` on
them.

Read `.claude/prds/native-table-pruning.md` and this epic's `epic.md` in
full before starting.

## Acceptance Criteria

- [ ] Read `src/storage/row_group_pruning.rs` in full — the existing
      Parquet pruning logic (AND/OR/NOT/BETWEEN/InList against per-row-
      group min/max) is the pattern to mirror or directly adapt, not
      reinvent. Also read `src/storage/parquet.rs`'s
      `read_file_with_filter` to understand exactly how/when a predicate
      reaches `scan_with_filter` for Parquet today — trace the actual
      caller-side decision (physical planner? scan operator?), don't
      assume it's already provider-agnostic.
- [ ] `NativeTable::scan_with_filter` implemented: for each active
      segment, evaluate the predicate against that segment's
      `ColumnStats`; skip (never decode) any segment provably
      unsatisfiable. A segment with no relevant stats (e.g. a string
      predicate, `ColumnStats` has no string min/max today) or an
      unrecognized predicate shape is always scanned, never skipped.
- [ ] Wire whatever caller-side eligibility mechanism is needed so native
      tables actually receive pushed predicates the same way Parquet
      tables do — if the current mechanism already generalizes, confirm
      and say so; if it's Parquet-specific, extend it correctly.
- [ ] Deletion vectors remain fully respected: pruning decides whether to
      read a segment at all; any segment that IS read still goes through
      the existing `deleted_rows` filter inside `scan()` unchanged.
- [ ] Observable pruning decisions: enough tracing (matching this
      codebase's existing env-gated diagnostic convention, e.g.
      `PLAN_DEBUG`/`HJ_TIMING`-style) to directly confirm, not infer from
      wall-clock time, that a segment was actually skipped.
- [ ] Cell-exact validation for this task's own scope: at least one
      multi-segment native table, a range and an equality predicate on a
      column with stats, pruning-on results identical to pruning-off
      results and to an independent DuckDB oracle.
- [ ] No regression to unfiltered/full-scan queries, the write path, or
      any other table type.
- [ ] Full suite green (`scripts/claude-safe-build.sh cargo test`, all
      feature combinations); `cargo fmt --all -- --check` clean.

## Technical Details

Sole files: `src/storage/native_table.rs` (the implementation),
`src/storage/parquet.rs` (the caller-side pattern to trace/mirror),
possibly `src/physical/planner.rs` or wherever predicate pushdown
